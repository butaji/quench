# 22 — OSR as a natural transformation between tier functors

Status: planned

Resolution vs. [[45-no-tier-first-execution]]: 45 is the default architectural bet — guard/IC machinery lands in the *first* compilation so most code never needs a second tier at all, preserving the structural no-tiering advantage over V8/JSC. This task (22) is a **fallback only**, scoped narrowly to the case 45 cannot cover: a pathologically long-running loop that began executing under a guard configuration later proven suboptimal (e.g. a bounded-polymorphic cache from [[31-bounded-polymorphic-guards]] that should widen, or a closed-world proof from [[46-closed-world-mode]] that only becomes available after the loop started). Do not build 22 speculatively; build it only if measurement against the V8v7 suite shows single-tier-first execution has a real ceiling for long-running loops that [[48-submorphism-repatch-on-guard-miss]]'s sub-morphism patching cannot reach cheaply enough. If sub-morphism repatch (48) proves sufficient for re-specializing a running loop's guards without a full second tier, this task should be dropped rather than built.

Introduce a second, more aggressive stencil tier alongside the existing baseline stencil compilation. Both tiers compile the same AST region into `Stencil<Connector, Connector>` (or loop-typed connector) images — they are two different functors from the same source into machine code. On-stack replacement is the mechanism that swaps a *running* frame from the baseline image to the optimized image at a shared connector state (loop-top), not merely on the next call. Model it as an explicit natural transformation: a mapping at loop-top boundaries that reconstructs live bindings from the baseline frame layout into the optimized frame layout and transfers control, valid precisely because both tiers expose the same typed connector contract proven in [[01-stencil-category-core]].

This is a prerequisite for [[19-guard-typed-connectors]], [[23-egraph-rewriting]], [[24-escape-analysis-scalar-replacement]], and [[26-pgo-morphism-selection]] paying off in long-running loops: without OSR, a hot loop that started executing before a better tier existed never benefits from it.

Constraint: baseline tier compiles on first use per [[03-stencil-only-execution]]; there is still no interpreter fallback and no hotness-threshold gating of *baseline* compilation — only the transition into the optimized tier is triggered by a loop-iteration counter.

Acceptance: a long-running loop demonstrably executes optimized-tier code before it terminates (verified by an execution counter distinguishing baseline vs. optimized entries, not just final output); frame reconstruction at the transition point is correctness-tested against bindings captured from pure baseline execution of the same program; a loop that never reaches the transition threshold still produces identical results.
