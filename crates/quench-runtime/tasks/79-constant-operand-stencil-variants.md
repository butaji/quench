# 79 — Constant-operand stencil variants for macro-generated arithmetic

Status: planned

The macro-generated handler families in `stencil-aot/handlers.rs` (the binary-op family
at line 325 and the loop-add family at line 426) currently take two runtime `Value`
operands per handler. `deegen_dyn_loop_add_local_literal` (line 373) already establishes
the pattern of a literal-patched variant alongside the local/local one, but the other
arithmetic and comparison ops generated by the macros at 325 and 426 do not have a
literal-operand counterpart.

Copy-and-patch's core technique (per the original Xu/Kjolstad paper, and its Python 3.13
and R adoptions) is generating multiple stencil variants per operation and selecting
among them at cook time based on known operand shape — this gets constant folding and a
form of register allocation for free without a real optimizing pass.

Extend the macros at lines 325 and 426 to emit both a `_local_local` and a
`_local_literal` variant for each arithmetic/comparison op they currently generate.
Wire `build.rs`'s cook-time template selection to choose the literal variant whenever
one operand is a compile-time constant at the call site.

Acceptance: same semantic tests pass; measurable reduction in dynamic instruction count
or `KernelExit` count on the v8v7 suites for code with constant arithmetic operands;
`DEEGEN_JIT_STATS` reports which variant was selected (see task 82).

## Round-seventeen constant-class refinement

A patched literal is still opaque while rustc/LLVM cooks the template, so it cannot
trigger constant-specific instruction selection. Generate a bounded family by semantic
constant class, not by literal identity: zero, one, minus one, power of two, signed I32
constant divisor, mask, and generic immediate. In a Task 264 Word32 island, power-of-two
division/remainder lower to shifts/masks; other fixed divisors use LLVM's multiply/add/
shift magic-number lowering. Floating and generic-JS division retain their required
zero, NaN, infinity, fraction, and minus-zero obligations from Task 214.

Every class is a named enum variant emitted by the same arithmetic semantic macro.
`MAX_CONSTANT_CLASSES_PER_OPERATION` bounds catalog growth; no benchmark literal becomes
a template name. Disassembly must prove that the selected class actually changed the
instruction sequence before its code-size cost is accepted.

Sources: LLVM's division-by-constant algorithm
<https://github.com/llvm/llvm-project/blob/main/llvm/include/llvm/Support/DivisionByConstantInfo.h>
and V8's machine-operator constant reductions
<https://chromium.googlesource.com/v8/v8/+/refs/heads/main/src/compiler/machine-operator-reducer.cc>.

52 (maximize AOT codegen power).
