# 215 — Primary-source algorithm research, round seven

Status: complete

Research additional VM/compiler mechanisms that are not already represented in Tasks
00–214 and map them to current source and profiles. Preserve the standing constraints:
all execution is stencil/kernel based from first use; rustc/LLVM cooks a finite catalog
AOT; runtime generation is copy-and-patch; neither benchmark identity nor execution
frequency selects a path.

## Result

The research produced three non-duplicative additions:

1. **Guarded dense-array built-in kernels (Task 212).** SpiderMonkey treats guarded
   `obj.push(value)` as CacheIR-level inlining, while V8's append and concat paths guard
   array representation/prototype facts and perform direct storage operations. This
   project already has canonical built-in identities, but `push`, `pop`, `slice`, and
   `concat` still enter generic Rust built-in functions, borrow an `Rc<RefCell>` object,
   and often copy a `Vec`. Task 212 turns Task 183's recipes into shared immutable
   kernels plus patched guard instances.
2. **Canonical effective addresses and load/unbox fusion (Task 213).** SpiderMonkey has
   explicit Effective Address Analysis and `FoldLoadsWithUnbox`; JavaScriptCore's B3/Air
   selector fuses address, load/store, immediate, compare, branch, and arithmetic forms.
   The stencil adaptation is not a runtime instruction selector. It is one quoted
   `MemoryRef` data form whose finite legal target interpretations are generated by Rust
   macros and cooked by LLVM.
3. **Range facts plus late semantic-edge legalization (Task 214).** Production engines
   use numeric ranges to eliminate overflow/bounds checks and decide negative-zero
   obligations after other transformations. This fills a gap between Task 174's
   constants/type facts and Task 175's loop-specific scalar evolution.

## Priority against measured costs

These additions do not displace the current critical path. Post-Task191 samples still
put the generic block executor at 18.9–34.1% and call/frame lifecycle at 12.9–37.6% in
Splay, Richards, DeltaBlue, and RayTrace. Property-containing blocks account for
60.8–98.9% of residual entries. Therefore:

`146/181 direct continuation -> 148/162 VM heap -> 212 dense built-ins -> 149/158/171 -> 213 -> 174/214 -> 175`

Task 212 can begin with non-allocating `push`/`pop` recipes while the heap is built, but
its allocation-heavy `slice`/`concat` forms should target the Task 148 heap rather than
deepen the temporary `Rc` representation. Tasks 213 and 214 need the quoted region and
semantic-derivative infrastructure; adding exact hand-written bytecode sequences before
that would duplicate knowledge and recreate the selector sprawl already rejected.

## Refinements and negative findings

- Task 158 should treat constants, tag values, and immutable shape/kernel pointers as
  rematerializable and treat canonical side-exit uses as cold. B3 reports optimal
  constant materialization and special treatment for OSR-exit register allocation.
- Task 175 should consume Task 214's one canonical range fact rather than run a second
  independent interval analysis.
- Task 183 remains the single built-in semantic/identity catalog; Task 212 is a derived
  lowering, not a second catalog.
- ARM64 Top-Byte-Ignore (Task 208) is not a near-term optimization on this macOS target
  until an authoritative platform guarantee and an instruction-removal opportunity are
  demonstrated. Linux's tagged-address ABI is explicit about kernel-interface hazards;
  architecture capability alone is insufficient.
- Static branch weights (Task 209) are a small code-layout experiment. They may help
  only if disassembly first proves that rustc/LLVM currently lays out the relevant arm
  incorrectly; they cannot close a helper/call/ownership boundary.
- More tiny superinstructions remain low leverage. V8's Maglev account is direct: a
  baseline compiler has a low performance ceiling, while raw representations, SSA,
  register allocation, and deoptimization enable the larger gap closure.
