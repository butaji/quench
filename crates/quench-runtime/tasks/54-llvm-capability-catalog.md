# 54 — LLVM capability catalog for stencil cooking

Status: planned

This is the concrete back-side capability catalog [[53-bidirectional-stencil-cooking]] requires before any new handler is authored. Every entry is grounded in the actual mechanism visible in `stencil-aot/handlers.rs` and `build.rs` today, not generic JIT folklore — each states what's already exploited, what isn't yet, and exactly how to wrap it into the fixed handler ABI (`RawDynFrame`/`InlineSite` for the dyn-bytecode path; `thread/frame/code/site/accumulator/tag_mask/first_tag/scratch` for the number-stencil path) without breaking `build.rs`'s per-symbol extraction and tail-branch-relocation contract.

## A. Control-transfer / dispatch primitives

1. **`explicit_tail_calls` (`become`) — already in use.** Every stencil-to-stencil transfer in `handlers.rs` (`become __deegen_hole_next(...)`, `become __deegen_dyn_hole_next(...)`) uses Rust's nightly guaranteed-tail-call feature, which forces LLVM to lower the call as a genuine tail jump with no stack growth — this is the single most load-bearing LLVM capability in the whole design, since it's what makes an unbounded chain of stencils behave like one flat instruction stream rather than a deepening call stack. **Wrap:** every new handler family must use `become` for its terminal transfer, never a plain `return` plus caller-side dispatch; this is a hard rule, not a style preference.
2. **Tail-call eligibility preservation.** LLVM only lowers `become` as a true tail call when the callee's calling convention and argument shapes permit it (`extern "C"`, scalar/pointer args passed in registers, no destructors needing to run after the call). **Wrap:** keep every stencil signature to `Copy` scalars and raw pointers only (as today) — never introduce a struct-by-value, `Drop` type, or reference with a lifetime bound as a stencil argument, since any of those can silently downgrade `become` to a real call+return, breaking the flat-chain property with no compile error.
3. **Fixed `extern "C"` ABI + `#[unsafe(no_mangle)]` — already in use.** This guarantees `build.rs`'s `extract_catalog` sees a stable, externally-visible symbol per handler rather than an internal `fastcc`/`ghccc` symbol LLVM might rename, inline away, or reorder registers for. **Wrap:** every new handler keeps this pair of attributes; never switch to Rust's default (unspecified, unstable) calling convention for a function meant to be extracted.
4. **Register-pinned threaded state.** The number-stencil family (`deegen_number_add`, etc.) always passes `thread, frame, code, site, accumulator, tag_mask, first_tag, scratch` in that exact order — on AArch64's C ABI the first 8 integer/pointer args live in `x0`-`x7`. Keeping every stencil's leading arguments identical in count, order, and type means LLVM assigns the same physical register to the same logical piece of interpreter state across every stencil, so a chain of `become` calls never needs to spill/reload/shuffle registers between stencils — the interpreter state stays "hot" in fixed registers for the whole chain. **Wrap:** treat this argument list as a closed ABI contract; any new number-stencil-family handler must reuse the identical leading signature even for arguments it personally ignores, and any deviation must be justified and re-verified via objdump that register assignment didn't shift.

## B. Instruction selection

5. **Branchless compare-and-select (`csel`/`csinc`/`csetm`).** The `continue_or_slow!` macro's `if $guard { ... } else { become slow }` shape and `is_number`/`needs_drop`'s boolean tag checks are exactly the pattern LLVM's AArch64 backend turns into a compare followed by a conditional select or conditional branch with no extra instructions, when both arms are cheap. **Wrap:** keep guard conditions as single-expression scalar computations (as today) and keep the guarded fast-path body free of nested branches; this is what lets a "guarded" opcode compile to compare + do-the-op + one tail branch, with the "which stencil next" decision folded into the tail-call target rather than an internal jump.
6. **Bit-mask/tag fusion (`and`+`cmp`/`tst`).** `is_number` (`value.0 & TAG_MASK < FIRST_TAG`) and `needs_drop` (`value.0 & TAG_MASK >= FIRST_HEAP_TAG`) are single mask-and-compare expressions — exactly the shape LLVM's DAG combiner fuses into one or two instructions on AArch64. **Wrap:** any new tag/type check added for task 19/25/31's guard families must stay a single mask-and-compare expression over one register-width integer; splitting a tag check across multiple intermediate booleans defeats the fusion and costs an extra instruction per guard, multiplied by every guarded call site in the program.
7. **Multiply-accumulate / FMA (`madd`, `fmadd`).** Not yet exploited: `f64::from_bits(accumulator.0) $operator f64::from_bits(right_bits)` in `define_number_binary_stencil!` never uses `mul_add`, so a JS expression like `a * b + c` currently compiles as two separate stencils (multiply, then add) rather than one fused stencil. **Wrap:** add a fused multiply-add stencil variant (`deegen_number_fma`) using `f64::mul_add`, selected when the front-side demand catalog ([[53-bidirectional-stencil-cooking]]) confirms `a*b+c`/`a*b-c` patterns are frequent enough (check via [[37-aot-template-coverage-by-frequency]]) — note JS's IEEE-754 semantics tolerate the extra FMA precision only where the source doesn't rely on exact double-rounding, so this must be gated by correctness testing, not applied blindly.

## C. Whole-handler optimization

8. **Runtime-argument vs. patched-immediate tradeoff.** `tag_mask`/`first_tag`/`accumulator` currently arrive as register-passed runtime arguments on every `become` call — LLVM cannot constant-fold them at AOT-compile time since they're not compile-time constants, and every stencil in the chain re-receives them as live register state. But `tag_mask`/`first_tag` are actually *link-time* constants (fixed per build, not per call) — they don't need to be threaded through registers at all if the copy-patch step instead patches them as immediate operands into each stencil instance at link time, the same way `CopyPatch::Word`/`Pointer` already patches literal values today. **Wrap:** move `tag_mask`/`first_tag` from register arguments to patched immediates (a new `Hole`/`CopyPatch` kind targeting an immediate field inside the stencil body, verified via `build.rs`'s existing relocation machinery), freeing two argument-register slots per stencil in the chain — fewer live registers threaded through every `become` call, and one less pair of runtime loads per stencil.
9. **Aliasing clarity for LICM inside `deegen_dyn_run`'s dispatch loop.** LLVM applies loop-invariant code motion within a single compiled function, but only where it can prove pointers don't alias. `RawDynFrame`'s `registers`/`locals` are separate raw pointers with no `noalias`/`restrict` annotation; if LLVM can't prove they're disjoint, it may reload `frame_ref.local_count`/`run_end` more often than necessary across loop iterations. **Wrap:** verify (via extracted-object inspection) whether these reloads actually happen; if so, restructure `RawDynFrame` construction so `registers` and `locals` are provably non-overlapping slices at the call site (e.g. via Rust's `&mut [RawValue]` slice-splitting, which does carry noalias metadata, instead of two independent raw pointers) so LLVM can hoist the bounds/count checks out of the loop.
10. **Jump-table dispatch for `match item.opcode`.** `deegen_dyn_run`'s `match item.opcode { INLINE_LOAD_LITERAL => ..., ... }` should lower to a dense jump table (`adr`+indexed `br`) rather than a chain of compares, since the opcode constants are small and dense (1-13). **Wrap:** verify this via objdump before assuming it; if LLVM instead emits a compare chain (possible if the match arms' bodies are large enough that LLVM's jump-table cost model opts out), either shrink the match arms or force the table via `#[repr(u8)]` enum dispatch instead of raw `usize` constants — ties directly into [[34-coproduct-tag-dispatch]]'s coproduct framing, which is exactly what a `#[repr(u8)]` closed enum plus a `match` gives you for free.

## D. Data layout / memory instructions

11. **Load/store pair fusion (`ldp`/`stp`).** Binary-op handlers load `left` and `right` from `frame_ref.registers.add(item.left)`/`.add(item.right)` as two independent loads; when those two register-file slots happen to be adjacent, LLVM can fuse them into one `ldp`. **Wrap:** where the register allocator assigning `left`/`right`/`dst` slots has freedom to do so, prefer adjacent slot assignment for the two operands of a binary op — a small, mechanical layout decision in the register-allocation logic (feeds [[30-stencil-register-allocation-quality]]) that makes this fusion possible more often.
12. **NEON/SIMD batch stencils.** Not yet present: every numeric stencil operates on one scalar `RawValue`/`f64` per invocation, so there is no loop body inside a single compiled handler for LLVM's autovectorizer to act on — the loop lives in the *interpreter's* dispatch across stencils, invisible to any one handler's own codegen. **Wrap:** for [[39-vectorized-numeric-stencils]], define fixed-batch-size handler variants (e.g. `deegen_number_add_x4` operating on `[f64; 4]` via `core::simd` or `core::arch::aarch64` NEON intrinsics) selected by the linker only when [[32-element-kind-guarded-arrays]] has proven a packed-numeric array segment of at least that length — this is a distinct code path from the scalar stencils, not an automatic optimization of them.
13. **Fixed-array layout for small monomorphic objects.** Once [[07-hidden-classes]] proves an object shape is a small fixed set of numeric fields (e.g. a 3-vector), backing it with a `[f64; 3]` array instead of individually named/offset slots lets LLVM's SLP vectorizer pack sibling field operations (raytrace's `Vector.add`/`multiplyScalar`) into single vector instructions. **Wrap:** this requires [[09-object-memory-model]] to expose a "fixed small numeric array" backing option alongside the general slot array, selected by shape metadata, not a universal replacement.

## E. Whole-program / link-time capabilities

14. **Fat LTO for the handler crate (task 52).** Internal cross-handler optimization within `stencil-aot/handlers.rs`'s single compilation unit; must be re-verified against `extract_catalog`'s one-symbol-per-template assumption, since LTO's function-merging pass could in principle collapse two now-identical handler bodies (e.g. `deegen_dyn_load_literal` and a hypothetical byte-identical future handler) into one symbol.
15. **PGO for handler-internal branch layout (task 52).** Optimizes the fast/slow-path order *inside* one handler's own `continue_or_slow!` branch — a different granularity from [[28-profile-driven-block-layout]], which reorders composition at the `Stencil`/`Seq` level between whole templates, not within one template's own compiled body.

## F. Target/ISA configuration

16. **Explicit, pinned `target-feature` set (task 52).** No `-C target-cpu`/`target-feature` flags are passed today; AArch64 codegen uses the generic baseline. Pin a specific feature set (not `native`, for build reproducibility) once a deployment target is chosen, unlocking wider load/store pairing and better addressing modes the generic baseline conservatively avoids.
17. **Relocatability constraint on every capability above.** `-Crelocation-model=pic` (already set) is required because extracted bytes are copied to an arbitrary executable-memory address at runtime. Any new capability adopted from this catalog — especially jump tables (idea 10) and SIMD constant-pool loads (idea 12) — must be re-validated against this constraint, since some LLVM lowering choices assume a fixed load address and would silently break copy-and-patch relocation if adopted without checking.

Acceptance: each catalog entry above is either marked "in use" with its evidence (file/line in `handlers.rs`) or "not yet adopted" with a linked task that will adopt it; no entry is added to this file without either objdump/`llvm-mca` evidence (already-in-use entries) or a concrete wrapping plan referencing the exact ABI change required (not-yet-adopted entries) per [[53-bidirectional-stencil-cooking]]'s rule against aspirational capability claims.

Architecture scope note: every instruction-level entry above (items 5-13, 16-17) is stated in AArch64 terms, since that is the only backend that exists today. [[55-architecture-target-matrix]] defines the abstraction boundary that keeps this catalog's *principles* (branchless select, tag-mask fusion, FMA, register-pinned threading, relocatability) architecture-neutral while their concrete instruction/encoding form is re-derived per architecture — [[56-x86-64-sysv-backend]] is where the x86-64 equivalents of items 5-13 get filled in, not a copy of this file's AArch64 opcodes.
