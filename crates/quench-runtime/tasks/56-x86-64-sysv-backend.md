# 56 — x86-64 System V stencil backend (Linux)

Status: planned

Add the second architecture in the target matrix ([[55-architecture-target-matrix]]): Linux/x86-64 under the System V AMD64 calling convention. Do not target macOS/x86-64 — Apple Silicon is the forward Mac target, not Intel Macs.

## Concrete ABI mapping (vs. AArch64's `a64_abi`)

- **Integer/pointer argument registers**: SysV64 passes the first six integer/pointer arguments in `rdi, rsi, rdx, rcx, r8, r9` (vs. AArch64's `x0`-`x7`, eight registers) — the number-stencil family's 8-argument signature (`thread, frame, code, site, accumulator, tag_mask, first_tag, scratch`) does not fit in registers on x86-64; the 7th/8th arguments spill to the stack per the calling convention. This changes register-pinning economics from [[54-llvm-capability-catalog]]'s item 4: on x86-64, keep only the six hottest, most-frequently-touched pieces of interpreter state as register arguments, and either drop `scratch`/reduce the argument count, or accept two stack-passed arguments for this specific stencil family — verify via objdump which is faster in practice rather than assuming parity with the AArch64 design.
- **Floating-point argument/return registers**: SysV64 uses `xmm0`-`xmm7` for `f64` arguments/returns (vs. AArch64's `d0`-`d7`); `a64_abi`'s `FP_ACC = 0`/`FP_RIGHT = 1` register-index convention maps directly (`xmm0`/`xmm1`) but the instruction encodings (`FADD_D0_D0_D1`, `FMUL_D0_D0_D1`, etc.) are entirely different byte sequences (SSE2 `addsd`/`mulsd`/`divsd`/`subsd` opcodes, or AVX `vaddsd` etc. if targeting a modern baseline) — this is a full second constant table, not a reinterpretation of the AArch64 one.
- **Callee-saved registers**: `rbx, rbp, r12-r15` are callee-saved on SysV64 (vs. AArch64's `x19`-`x28`); `a64_abi`'s `ACC = 19`/`FRAME = 20` (both callee-saved AArch64 registers used to persist interpreter state across calls) map conceptually to picking two of `rbx`/`r12`-`r15` for the same persistent role.
- **Tail-call / branch instruction encoding**: AArch64's unconditional branch (`AARCH64_TAIL_BRANCH_OPCODE = 0x1400_0000`, top 6 bits `000101`, low 26 bits a word-granularity signed immediate) has no byte-aligned displacement — patching it requires the same bit-packing arithmetic used throughout `a64_abi`. x86-64's near jump (`E9 <rel32>`) is **structurally simpler for copy-and-patch**: the opcode byte (`0xE9`) is fixed and the 4-byte little-endian displacement immediately follows at a flat byte offset, requiring no bit-field packing/unpacking at all — patch it exactly like `CopyPatch::Word` already patches a plain `u32`. This is a genuine simplification opportunity worth exploiting directly rather than porting AArch64's bit-packing logic unnecessarily.
- **Red zone**: SysV64 defines a 128-byte red zone below `rsp` that leaf functions may use as scratch space without adjusting the stack pointer — AArch64 has no equivalent. A stencil relying on this must not be treated as "leaf" if reached via a signal handler or if the red zone assumption is violated by an intervening call; do not use red-zone scratch space for any stencil that itself performs a `become` tail call to unknown/patched code, since the callee's own stack usage is not visible to the compiler's leaf-function analysis at that call site.
- **`explicit_tail_calls`/`become` on x86-64**: LLVM's guaranteed-tail-call lowering is architecture-independent in principle, but sibling-call eligibility on x86-64 additionally requires the caller and callee to agree on stack-passed argument cleanup convention; given SysV64 only has 6 register argument slots (vs. AArch64's 8), any stencil signature with more than 6 integer/pointer arguments needs its tail-call eligibility re-verified on x86-64 specifically — this is not guaranteed to port cleanly from the AArch64 design and must be checked via objdump before assuming `become` still lowers to a bare `jmp` rather than a real `call`+cleanup+`ret`.
- **Page size**: Linux/x86-64 is essentially always 4 KB pages (unlike AArch64 Linux, see [[57-jit-memory-portability]]), so the existing hardcoded `PAGE_BYTES` assumption is actually safe on this specific target combination — but should still route through the same runtime `sysconf` query introduced in [[57-jit-memory-portability]] for consistency rather than carrying a second hardcoded constant.
- **Memory mapping**: `mmap`/`mprotect`/`munmap` signatures are identical to the AArch64/Linux path already implemented; only the icache-invalidation call differs — x86-64 has coherent instruction/data caches by hardware guarantee, so **no cache-flush call is needed at all** after writing executable memory (unlike both AArch64 targets, which require `sys_icache_invalidate`/`__clear_cache`). Omitting this call on x86-64 is correct, not an oversight — document it explicitly so a future contributor doesn't add a spurious flush.

## New work required

1. A sibling `x64_abi` module (per [[55-architecture-target-matrix]]'s abstraction boundary) with SysV64's register assignment and the SSE2 floating-point instruction encoding table.
2. A parallel `stencil-aot/handlers.rs` compilation target (or `#[cfg(target_arch = "x86_64")]` variants of the same handler source) — verify the existing `become`-based handler source compiles to correct tail calls under the x86-64 backend without modification, since the Rust source itself is architecture-neutral; only `build.rs`'s extraction logic and the constant tables change.
3. `build.rs`'s tail-branch recognition extended with an x86-64 variant (`0xE9` opcode byte check) alongside the existing AArch64 bit-pattern check.

Acceptance: the full correctness suite ([[05-performance-harness]]) passes on Linux/x86-64 with stencil mode enabled (not falling through to the AST interpreter); an extracted x86-64 template's tail transfer is verified via objdump to be a genuine `jmp rel32`/`jmp r/m64` with no intervening `call`+`ret`; A/B comparison against the AArch64 target on equivalent hardware class is recorded, not assumed equivalent.

Development environment: [[59-colima-docker-linux-environment]] provides the Colima/Docker-based Linux/x86-64 (QEMU-emulated) and Linux/AArch64 (native under Apple Silicon Colima) containers this task is built and correctness-tested in from the macOS dev machine — build this task's correctness suite against that environment; do not treat emulated x86-64 timing from it as perf-authoritative, only the correctness/objdump verification.
