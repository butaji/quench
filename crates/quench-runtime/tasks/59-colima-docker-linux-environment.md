# 59 — Colima/Docker-based Linux dev and CI environment

Status: planned

Sequencing: build this **after** the macOS side of [[55-architecture-target-matrix]] and [[57-jit-memory-portability]] is done (macOS/AArch64 stays the primary dev target). This task exists so [[56-x86-64-sysv-backend]] and the Linux/AArch64 half of [[57-jit-memory-portability]] can be built and correctness-tested from the macOS dev machine without separate physical Linux hardware, using Colima (already installed and running locally: `colima status` reports `arch: aarch64`, `runtime: docker`, macOS Virtualization.Framework) rather than requiring a remote Linux box for every iteration.

## What was verified feasible (spike, not yet wired into scripts)

- `docker run --platform linux/arm64 debian:bookworm-slim` runs **natively** under Colima's default aarch64 VM (Apple Silicon, Virtualization.Framework) — `uname -m` reports `aarch64`, no emulation, representative of real Linux/AArch64 performance.
- `docker run --platform linux/amd64 debian:bookworm-slim` runs under **QEMU user-mode emulation** — `uname -m` reports `x86_64`, correct for build/correctness testing, but **not representative of real performance**; do not use emulated x86-64 timing for any A/B acceptance measurement gated by [[05-performance-harness]], only for correctness and for verifying [[56-x86-64-sysv-backend]]'s extracted object code (objdump/tail-call shape) is structurally correct.
- Both containers report `getconf PAGE_SIZE` = 4096. **This means the container approach does not reproduce the 16 KB/64 KB Linux/AArch64 page-size configurations [[57-jit-memory-portability]] is concerned about** — generic cloud/desktop Linux kernels default to 4 KB pages regardless of host. Do not claim this environment validates the non-4-KB page-size fix; it only validates the standard 4 KB case (already the common case, useful for regression coverage, not a substitute for the harder case).
- `apt-get install gcc libc6-dev` succeeds inside the arm64 container, confirming a real Linux toolchain (needed for `mmap`/`mprotect` smoke testing and eventually the pinned nightly rustc) is obtainable inside the VM without extra host configuration.

## Design

1. **Two container images**, not one multi-arch image with runtime detection: `docker/linux-aarch64.Dockerfile` and `docker/linux-x86_64.Dockerfile`, both based on a Debian/Ubuntu base matching whatever glibc baseline the project targets, each installing `rustup` and pinning the **exact** nightly matching `PINNED_RUSTC_RELEASE` in `build.rs` (`rustc 1.98.0-nightly (e7815e522 2026-06-04)`) for that image's own target triple (`aarch64-unknown-linux-gnu` / `x86_64-unknown-linux-gnu`) — `verify_toolchain()`'s exact-string assertion must pass inside the container unmodified, not be special-cased for containerized runs.
2. **A driver script** (`scripts/linux-dev.sh <arch> <cargo-subcommand...>`) that: builds the matching image if stale, runs it via `docker run --platform linux/<arch> -v $(pwd):/repo -w /repo <image> cargo <subcommand...>`, and passes through `DEEGEN_*` env vars already used by the harness. Mount the repo read-write so `cargo build`'s `OUT_DIR` artifacts stay in a container-local target directory (`--target-dir /tmp/target-linux-<arch>` or a Docker volume) rather than colliding with the host's native macOS build artifacts in `target/`.
3. **Correctness-only vs. performance-eligible split**: `scripts/linux-dev.sh x86_64 test` (QEMU-emulated) is for [[56-x86-64-sysv-backend]]'s correctness suite and objdump/instruction-shape verification only. `scripts/linux-dev.sh aarch64 test` (native under Colima) is fast enough to also run [[05-performance-harness]]'s A/B comparisons and treat the results as representative of real Linux/AArch64 deployment, distinct from the macOS/AArch64 numbers already tracked.
4. **Seccomp/JIT-permission check**: verify Docker's default seccomp profile does not block the `mmap`+`mprotect` W^X-toggle sequence `map_executable` performs (expected to work unmodified — Docker's default profile permits `mmap`/`mprotect`; no `--security-opt seccomp=unconfined` should be necessary, but this must be confirmed with an actual JIT-allocation smoke test inside the container before relying on it, not assumed from the generic-container spike above).
5. **CI wiring**: once the local scripts are validated, the same `docker/*.Dockerfile` images are reusable by any CI runner with Docker/Colima-equivalent support, giving Linux/x86-64 coverage in CI without requiring a dedicated x86-64 runner — though CI's own emulation performance characteristics must be re-verified independently of this local spike.

Acceptance: `scripts/linux-dev.sh aarch64 test` and `scripts/linux-dev.sh x86_64 test` both run the full correctness suite inside their respective containers with stencil mode enabled (once [[56-x86-64-sysv-backend]] exists) and report pass/fail distinctly per architecture; the pinned-nightly `verify_toolchain()` check passes unmodified inside both images; the README documents that emulated x86-64 timing is not perf-authoritative and that this environment does not cover non-4-KB-page Linux/AArch64 configurations, so [[57-jit-memory-portability]]'s exotic-page-size case still needs a real non-4-KB-page host or an explicit unit-level page-size-injection test instead.
