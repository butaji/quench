# 53 — Bidirectional stencil cooking: AST demand meets LLVM capability

Status: planned

Stencil templates should not be authored as ad hoc Rust source that happens to compile well at `-O3` and hoped to extract cleanly. Cook each template from both directions at once: from the **front**, the actual shapes of code JS/V8v7 demand ([[04-bytecode-coverage-map]]'s coverage map and [[37-aot-template-coverage-by-frequency]]'s frequency ranking say *what* needs a template and *how often*); from the **back**, a deliberate catalog of what LLVM is known to lower exceptionally well on the target (branchless `cmp`+`csel` for guarded comparisons, multiply-accumulate fusion, autovectorizable loop idioms, addressing-mode-friendly array indexing) says *what shape of Rust source* to write to get that lowering reliably, rather than hoping the optimizer finds it. A template is "cooked" when a demand pattern from the front is deliberately written in the idiom the back is known to lower best — not when either side is treated in isolation.

This reframes [[02-rustc-aot-templates]] and [[36-direct-opcode-stencils]] from "extract whatever `stencil-aot/handlers.rs` currently contains" into a standing methodology: no new handler is added without first checking both catalogs.

Concrete steps:
1. **Build the front-side demand catalog.** Extend [[04-bytecode-coverage-map]]/[[37-aot-template-coverage-by-frequency]]'s frequency ranking into a structured list of demand *shapes*, not just opcode names — e.g. "guarded int32 add-then-compare," "packed-numeric elementwise loop," "monomorphic property load" — grouping opcodes that share a codegen shape even if they differ in AST surface form, since LLVM cares about the shape, not the JS syntax that produced it.
2. **Build the back-side capability catalog.** [[54-llvm-capability-catalog]] is this catalog: it documents, with `llvm-mca`/objdump evidence (shared with [[43-aot-codegen-quality-audit]] and [[52-maximize-aot-codegen-power]]), which Rust source idioms reliably produce which optimal AArch64 lowering on the pinned target-cpu — branchless comparison-and-select, fused multiply-add, autovectorized loops, bit-test-and-branch fusion, and the ABI-level tricks (`become`/tail-call preservation, register-pinned threaded state) already load-bearing in `handlers.rs`. This is empirical, not aspirational — an idiom only enters the catalog once verified in extracted object code, matching [[04-bytecode-coverage-map]]'s rule against aspirational coverage labels.
3. **Match front to back deliberately for each new template.** When promoting an opcode per [[37-aot-template-coverage-by-frequency]], look up its demand shape in step 1's catalog, find the matching lowering idiom in step 2's catalog, and write the handler source specifically in that idiom — rather than writing the most natural Rust expression of the semantics and accepting whatever LLVM happens to do with it.
4. **Feed gaps back in both directions.** A demand shape with no matching capability-catalog entry is a candidate for [[52-maximize-aot-codegen-power]]'s codegen-flag work or a hand-written fallback (as [[39-vectorized-numeric-stencils]] already anticipates for vectorization specifically); a capability with no current demand is not built speculatively, keeping this general-purpose rather than benchmark-shaped per [[04-bytecode-coverage-map]]'s constraint.

Acceptance: every handler added to `stencil-aot/handlers.rs` from this point on cites both a demand-catalog entry (why it's needed, at what frequency) and a capability-catalog entry (what lowering idiom it targets and the object-code evidence it achieves it); a template written without consulting both catalogs is treated as a process violation, not merely a missed optimization; the two catalogs are living documents updated as [[37-aot-template-coverage-by-frequency]] finds new high-frequency demand shapes or [[52-maximize-aot-codegen-power]]/[[43-aot-codegen-quality-audit]] find new verified lowering idioms.
