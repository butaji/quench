FIVE NAMESONE ENGINE

blog / 11 June 2026 · 3 min read · history

Quench started as a TypeScript-to-Rust transpiler

The first commit was a compiler driver, not a JavaScript engine. Four names, one embedded engine and one deleted interpreter later, the project admitted what it was becoming.

Quench did not start as a JavaScript engine. The first real commit, on 16 May 2026, is titled "Implement core cargo-rune compiler driver". It parsed a restricted TypeScript dialect in *.r.ts files with SWC, checked that the code stayed inside the subset, and generated Rust source from the TypeScript AST.

The idea was simple: write terminal UIs in TSX, ship them as native Rust binaries. For three weeks the project chased that idea under four different names.

The interpreter we deleted for being an interpreter

A transpiler has a slow edit loop: change TSX, generate Rust, compile Rust, run. To get hot reload we added a small interpreter over our own intermediate representation on 26 May. It ran the same program without the Rust compile step.

Eleven days later we deleted it. The roadmap note from that day says why in one line: it "was becoming a custom JS engine". Every feature a real program needed (closures, exceptions, getters, iteration) pulled the little interpreter closer to full JavaScript semantics, and we did not want to maintain an engine.

So we embedded one. We measured two Rust-friendly options on 6 June:

QuickJS won, and for most of June the architecture was "about 78% Rust, 22% JavaScript": a Rust core for layout and rendering, with user code running in QuickJS.

The same question, three more times

The layout engine went through the same loop. We adopted Taffy, replaced it with a 300-line flexbox of our own on 4 June, tried Yoga, reverted Yoga the same day, then made Yoga the only backend two days later. The parser went SWC, then OXC, then SWC again, then OXC again by 12 July, where it has stayed.

Each of those reversals has the same shape. A dependency does 95% of what you need, the last 5% is the part your product is about, and you end up either forking it or replacing it.

28 June: the plan to drop QuickJS

On 28 June a commit landed titled "add plan to drop quickjs for custom swc-based js runtime", followed by a new crate, quench-runtime. Two days later another commit removed the bytecode VM from scope, and a week after that the rule was written down: stay on the interpreter-only path until conformance is at 100%.

That is the moment Quench became an engine project. The interpreter we had deleted on 6 June for "becoming a custom JS engine" came back three weeks later as the whole point.

If your tool keeps growing an interpreter you keep deleting, the interpreter is probably the product.

The terminal UI work is still around in a sibling project. Everything in this blog from here on is about the engine.
