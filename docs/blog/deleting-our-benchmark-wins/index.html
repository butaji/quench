HONESTNUMBERS

blog / 27 August 2026 · 2 min read · performance

We deleted our benchmark-specific fast paths

Our Richards score was good because the engine recognised the workload. We removed every path like that, took the lower numbers, and wrote the rule into the repository.

By late August 2026 Quench had benchmark numbers we liked and should not have trusted. Some hot paths in the runtime were shaped like the benchmarks they ran. Richards had a native scheduler, task and packet kernel built from a snapshot of the workload. There was a dispatch path that knew about the Octane suite.

None of that is unusual. Engines have recognised benchmarks for as long as there have been benchmarks. But it meant our scores described how well we had modelled eight programs, not how fast we ran JavaScript.

On 26 and 27 August we deleted all of it.

What it cost

The commit messages from those two days record the give-back plainly. One reads: "honest score give-back to median 146 after deleting the private snapshot". Another: "Honest RayTrace median after deletion: 43.7; schema trace timed out at the enforced 180s limit".

The fixed kernels were replaced by generic building blocks where property names stay ordinary operands, so the same mechanism works for any program with that shape. On 27 August the last commit in the series, "remove benchmark-specific execution bypasses", took out the suite-aware dispatch and the checksum paths.

The rule

The repository rules now carry this sentence:

Production behavior must never depend on benchmark identity, fixture source, scores, checksums, suite markers or the comparison engine.

There is a lint for it. Nothing in the engine may be keyed on function or property names from a workload, on source text, on instruction counts or on bytecode shapes, and the allowance for exceptions is zero.

Why a whitelist cannot win

The deeper reason came into focus months later, when we started running JetStream 3 instead of the eight older V8 benchmarks. A design review in November put it this way: speed had been built as a whitelist. Each benchmark's hot handler got a fast variant, and every new program met a new edge of the whitelist. JetStream 3 has more than sixty workloads using modern JavaScript, and no whitelist covers that.

You cannot special-case your way out of a flat profile. The only thing that helps is making the general mechanism cheap: one way to call, one way to read a field, one way to allocate.

What we do instead

  • Tests stand in for programs, never the other way round. A benchmark is there to expose a general cost. When a fix helps only one row, it is suspect.
  • A change must help a whole benchmark. Later we made this a keep rule: a change stays only if fixed-work instructions drop on a whole benchmark, measured, with no other row regressing beyond a small budget.
  • Publish the losses. Every post on this blog that shows a number shows the ones that went the wrong way too.

Deleting your best numbers is unpleasant for about a day. After that it is a relief, because every number you have left means something.
