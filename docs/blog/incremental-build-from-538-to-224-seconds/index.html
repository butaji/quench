From 538 to 224 seconds: rebuilding a JavaScript engine faster

A one-line change in the arithmetic of Quench's interpreter took 538 seconds to rebuild. Two days of profiling LLVM, sharding generated code and refusing any change that cost a single instruction at run time brought it to 224 seconds. What worked and what we rejected.

Quench generates a lot of code. Each JavaScript operation is written once as a staged row, and the build expands those rows into the interpreter's handlers, thousands of copy-and-patch JIT stencils and the pieces the optimizing JIT and AOT reuse. That is how one definition feeds four outputs. It is also why touching the definition of + is expensive.

Our worst case is a one-line edit to arithmetic in staged/numeric.rs, rebuilt incrementally with the experiment profile on a 4-core machine. On 23 November 2026 it took 538 seconds. The project's rule is that an incremental build over five minutes is a bug, so this was a bug.

The rule that made it hard

Making a build faster is easy if run-time speed can drop: inline less, split more, let LLVM see less. Quench does not allow that trade. Every change runs through an instruction-count gate on hundreds of small operations in three tiers, and the build work is held to the same rule as any other change: nothing may get slower. Several of the most effective build-time ideas below were rejected for that reason.

Where the time went

The first profile settled one question: the build was CPU-bound. It spent about 1,850 CPU-seconds, so even perfect scheduling on 4 cores could not go below about 460 seconds. Tweaking job order was pointless. The code volume had to go down.

Most of that CPU was LLVM optimizing code it would soon throw away. Rows are built from #[inline(always)] pieces. A piece that dispatches over, say, 16 register placements gets copied into every row with all 16 arms, and only after inlining does LLVM discover that the row uses one of them. One family of 66 fused loop-test rows took about 7 seconds of LLVM each. In the stencils, the placement arms were 95% of a row's IR before optimization.

The line is not monotonic, and that is honest: the engine kept growing while the build work went on, and upstream changes added about 140 CPU-seconds between two of the steps. Each step was measured against its own base.

The last step shows the shape of most of the wins. About 75 numeric rows had been spread by hash across all 16 generated-row modules and all 8 shards of each sharded handler family. An edit to arithmetic therefore recompiled every one of them. Giving numeric rows their own modules meant the same edit recompiles only those, and the engine's share fell from 597 to 338 CPU-seconds.

What we rejected

The gate turned down more ideas than it accepted:

  • Re-hashing every row into new modules. Faster to build, but 12 no-JIT cells got 17 to 84 instructions slower because closures moved out of line. Only numeric rows moved in the end, and everything else stayed in place.
  • Always inlining runtime placement code in stencils. 27% less stencil CPU, but LLVM merged compare branches differently and one cell cost 25 more instructions.
  • Passing the stencil hole as a run-time value. 18% faster to build, and a register allocation change cost another cell 6 instructions.
  • Moving the Wasm GC call-out out of JavaScript rows. 302 KB less code, and 1 to 5 more instructions on 49 cells because LLVM spent the freed inline budget elsewhere.
  • Re-landing a codegen unit split. 535 cells got worse. Moving generic instances into other units costs inlining in many places at once.
LLVM's inline budget is a shared resource. Freeing it in one place spends it in another, which is why every build-time change runs through the same run-time gate.

What is next

224 seconds meets the five-minute rule with room to spare, and the remaining levers are already listed: the four out-of-line copies of the full Number step (about 74 CPU-seconds) and the arithmetic stencil shards (about 250). The broader lesson is about generated code in Rust. Compile time follows what LLVM sees before it optimizes, not what is left after, so the cheapest code to compile is the code that never gets inlined in the first place.
