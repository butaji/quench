Interpreter against interpreter: eight for eight, and the JIT that was not ready

With every engine's JIT turned off, Quench's interpreter led all eight classic V8 benchmarks. The same week its JIT trailed Node and Bun by 2 to 24 times. Both results are worth showing.

There are two different races in JavaScript performance. One is between optimizing compilers. The other is between interpreters, and it matters wherever a JIT is not allowed or not worth it: locked-down platforms, short-lived processes, serverless cold starts, anything memory-constrained.

On 28 October 2026 we ran the eight classic V8 benchmarks with every engine's JIT turned off.

Quench led every row, by 1.21 times (Splay) to 1.68 times (Crypto) over the best other engine.

How much to trust it

Less than the chart suggests, and here is why:

  • Another board the same day disagreed. A run on a different build read DeltaBlue at 1.08 and EarleyBoyer at 1.02 against Node, and an 11-round run that evening read 1.16 and 1.17. The ordering held. The margins did not.
  • One machine, one day. A single pinned A/B pair on that host ranged from 0.73 to 1.75 between runs. We later moved speed decisions to instruction counts for that reason.
  • Eight old programs. The V8 suite dates from 2012. It exercises prototypes, closures and arrays and almost nothing from modern JavaScript.

On JetStream 3, which is much broader, the picture is different: with the JIT off Quench currently sits between Bun and Node. The last post in this series has those numbers.

Why the interpreter was fast

Three design choices carry most of it:

  1. Register bytecode. Operands are register numbers in the instruction, so there is no operand stack to push and pop.
  2. Tail-call dispatch. Each handler ends by jumping straight to the next handler, with the interpreter's hot state held in machine registers across the jump. CPython 3.14 adopted the same technique.
  3. Quickening. An instruction that has only ever seen integers rewrites itself into an integer-only form, and the generic form stays as the fallback.

None of those are new. What made the difference was removing work between them: fewer checks per call, fewer loads per field.

The other scoreboard

The same week, with JITs on, the board looked like this.

On Richards, Quench with its JIT on scored lower than Quench with its JIT off. The compiled code was slower than the interpreter it was supposed to replace.

NavierStokes was the exception, and an instructive one. It is a numeric loop over typed arrays, the easiest thing for a compiler to get right. One change there computed two rows of the grid as a pair, which gave the processor two independent floating-point chains to overlap, with bit-identical results. In a later run that row reached 1.29 times the best other engine.

What we took from the two boards

The interpreter result said the foundation was sound: the bytecode, the object model and the dispatch were competitive. The JIT result said the tiers on top were not using that foundation. Later audits found the reason: for calls, field access and allocation the compiled code kept asking the runtime for help.

On 1 November the project wrote down three decisions in response: native execution is the primary target, every fact is checked once at the earliest point it can be known, and the engine is pure Rust with no embedded JavaScript. Most of the posts after this one are consequences of those three lines.
