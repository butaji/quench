Hello world in 4,896 bytes: AOT as the JIT run at build time

Quench now compiles a JavaScript hello world to a 4,896-byte native executable that starts in 0.96 ms with 1.3 MB of memory, level with C. No second compiler: the build runs the program through the same specializer as the JIT and keeps only what is left.

Here is the smallest program we care about:

// hello.js
console.log("Hello world!")

And here is what Quench does with it on 25 November 2026:

$ quench compile --strict-aot hello.js -o hello
$ ls -l hello

One 4-vCPU x86 Linux machine, wall time and peak resident memory from a small C harness that spawns the process and waits for it. A later rebuild on 25 November measured 4,880 bytes, 0.99 ms and 1.2 MB, which is the run-to-run noise of this box. The build itself takes 0.15 s.

Why it used to be 85 MB

Every Quench executable used to link the whole engine. Asking the linker why the parser stayed in a hello-world image gave a chain that explains everything: the image starts the generic VM, the VM can call a user function, a user function can hit code that was never compiled, and compiling it needs the parser. Once the VM is in, so are the interpreter, both JITs, WebAssembly, ICU, compression and TLS.

Trimming that graph edge by edge might reach a few megabytes. It can never reach C's size class, because the image still contains a JavaScript engine. To get there the image has to stop being "the engine plus your program".

The first Futamura projection, at build time

Quench's design rule is that the interpreter is the only definition of what JavaScript means, and every other tier is that interpreter specialized to what it knows. We wrote about it in One interpreter, four outputs and AOT without a second compiler. The JIT specializes to facts it learns while the program runs. AOT is the same specializer run earlier, against facts known at build time.

With one source of truth for everything, AOT is just a particular case of JIT.

Specializing an interpreter to a program is the first Futamura projection: the result is a compiled program. Its coarsest form is also the simplest. The build runs the entry file against the same realm the image would start with, and keeps going until the program reads its first dynamic input: something a later run could see differently, such as its arguments, the environment, a file, the clock or standard input.

Everything computed before that point is the same in every run, so the image does not need the code that computed it. It only needs the program's effects: which bytes went to which descriptor, in what order, and the exit status.

Hello world reads no dynamic input at all. Its residual program is one write of 13 bytes to descriptor 1 and an exit status of 0. Quench emits that as a no_std Rust program that calls write and returns, and links it with the system C library. That is the whole 4,896-byte executable. There is no engine inside it because nothing is left for an engine to do.

Why this is not a special case

Nothing in the compiler knows about console.log or about hello world. The rule is general: evaluate up to the first dynamic input, keep the effects. A program that builds a table, formats a report and prints it, reading nothing from outside, compiles the same way. The work it did at build time costs nothing at run time.

The rule is also strict in the other direction. If a program does read a dynamic input, the build stops there, says which input it was, and does not pretend. That half of the design is the subject of the companion post.

What it does not do yet

Most real programs read an input in the first few lines. A command-line tool reads its arguments, a REPL reads standard input. For those, the strict image is refused today and the compile falls back to the full image, which still works and is still large. Our current target is a readline REPL, and the gap there is wide: we wrote down where it stands.

The next stage keeps more than effects. The build saves the heap at the program's first wait for input, and the code that runs after it (the input handlers) is compiled against that saved heap by the same JIT specializer, linking only the runtime services it still calls. The hello-world image is the end point of that pipeline for a program with no inputs. Every other program should land somewhere between 4.9 KB and the full engine, in proportion to how much of it really depends on run time.
