Chasing a sub-megabyte readline binary

A small TypeScript compiler turns a readline REPL into a binary under 1 MB that starts in about 1 ms. Quench's is 71 MB and starts in 6.2 ms. Where the megabytes go, what we have cut so far, and the general plan to close the gap without a single readline-specific path.

This is a post about a benchmark we are losing.

The program is a 49-line TypeScript REPL built on node:readline: it prints a prompt, keeps history, completes command names, answers help, add, echo, upper and history, and exits on quit. It is the kind of program people want to ship as one small executable. scriptc, a compiler that translates a typed subset of TypeScript to native code, does that very well, and it is the bar we set ourselves for size and startup.

One 4-vCPU x86 Linux machine, median wall time and peak RSS of the process from start to exit with quit on stdin. We are about 80 times larger, 6 times slower to start and twice the memory. The goal is about 1 MB and about 1 ms, reached only with optimizations that help every program.

Where 85 MB went

The link map of the image, by origin:

WhatSize
Engine and runtime code20 MB

A REPL that never opens a database carried a SQL engine. The cause was one static table listing every host operation. Because the table referenced every module, the linker could not drop any of them. Turning off the JITs does not fix that: the no-JIT image was still 78 MB.

What we have cut so far

Link only the host operations a program can reach. Each image now gets its own operation table, built from what the program can actually call, and heavy module state such as SQLite is created on first use. The image went from 85.0 MB to 71.3 MB, and the linker confirms no SQL code is left. Startup did not move. Unused code costs disk, not time.

Lay out start-up code together. Profiling start-up showed about 2,600 page faults per run at roughly 1.2 µs each. Ordering the functions that start-up runs next to each other took readline from 7.0 to 6.2 ms in back-to-back runs and 5.35 to 4.42 MB, and a smaller tool that prints its arguments from 5.6 to 4.9 ms.

Save the program at its first wait. The build now runs the REPL until it blocks on standard input, saves the runtime there (a 257 KB snapshot) and records the prompt it printed. A resumed run restores the snapshot and enters the event loop without running the entry again. Its output is identical to a full run for every command, and it exits on quit in 5.8 ms against 9.4 ms for the full run in the same harness. The engine is still linked, so memory does not drop yet.

Why trimming is not the plan

Each of those cuts is real, and none of them gets to 1 MB. As long as the image contains a general JavaScript engine, it is the size of a general JavaScript engine. The way out is the same one that took hello world to 4,896 bytes: the image should contain only the code that is left after the build has used everything it knows.

For readline, what the build knows is a lot. At the first wait, the modules are loaded, the interface exists and the prompt is written. What remains is the line handler: split a line, look up a command, format a reply, write it. Three steps get there:

  1. Natives become staged rows. Much of Node's API in Quench is Rust code the specializer cannot see through. Each native the handler reaches (console writes, stream push, event emit, line splitting) is being rewritten as a staged row: a guard every tier runs, a small typed primitive the image can link on its own, and the general native as the fallback. The first row, the plain-string path of console.log, matches Node on all three tiers.
  2. Specialize the handlers at build time. The JIT specializer compiles the pending callbacks against the saved heap, so global lookups, method identities and constant strings fold.
  3. Link only what the residual calls. Runtime services become named symbols, the heap ships as read-only data mapped at a fixed address, and the linker keeps only what the handler code references.
The rule for this work: no optimization that only helps readline. Every change has to be one the interpreter, the JIT and AOT share.

Why publish a losing number

Because the number is the point. Quench's AOT design bets that one specializer, run at build time, can produce binaries in the same class as compilers that only accept a subset of the language, while keeping all of JavaScript. Hello world says the bet can pay off at the small end. Readline is the first program where the program does something after start-up, and it is where the bet is tested. We will update this table as it moves, including if it stops moving.
