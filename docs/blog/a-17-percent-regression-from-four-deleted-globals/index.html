BISECTEVERYTHING

blog / 8 November 2026 · 4 min read · debugging

A 17.6% regression that was four deleted globals

Thirty hours of running JetStream 3 every ninety minutes took the interpreter from 0.61 to 0.90 of the best competing engine, then lost a sixth of it overnight. The bisect led somewhere unexpected.

On 7 November 2026 we started running the whole of JetStream 3 in a loop. Each cycle built the current head, ran every test on Quench, Node and Bun with JITs off and on, and posted the scores. A cycle took about ninety minutes.

The line goes up, mostly. Three moments on it are worth describing.

22:07: a threshold, not a design

Between two cycles a method call got slower: 2.1 nanoseconds to 5.2. Bisect named a commit that allocated registers for function bodies in a single pass. One-pass allocation is cheaper to run, and on tiny hot methods what it gave up cost more than it saved.

The repair kept both: one-pass allocation only for bodies of 2,048 instructions or more. Method calls went from 5.20 to 2.21 nanoseconds and polymorphic calls from 15.9 to 8.63.

14:07: the JIT fell off a cliff and the interpreter did not notice

In one cycle the JIT-on score dropped 13.5%. Box2D went from 28.5 to 3.1, Splay from 67.6 to 7.2, DeltaBlue from 72.0 to 11.9. The interpreter-only scores for the same build were unchanged.

Our rule is that a regression needs two consecutive cycles to be confirmed, because single cycles are noisy. The rule has an exception for drops past 40%, and this was the reason for the exception. It was reported at once.

07:32: the drop

Then, overnight, the interpreter score fell from 53.4 to 44.0.

Bisect pointed at a commit about object dictionaries. Quench objects normally have a shape, which makes field access fast. An object that gets properties deleted repeatedly switches to dictionary mode, a hash table, which is slower but does not churn shapes. The commit changed the switch to happen at the second deletion.

That is a reasonable policy. Why would it cost a sixth of JetStream?

Each new realm was created with four helper globals. vm.createContext then deleted them. Four deletions on the global object, and under the new policy the global object itself became a dictionary. Every cached read of a global variable, which means every reference to Math, Array or a top-level function, lost its cache.

The fix was not to touch the deletion policy. It was to stop binding four globals only to delete them. JetStream went back up 15.2%, and EarleyBoyer went from 22 to 90.5.

The commit bisect names is where the cost appeared. The cause can be somewhere else entirely.

The regressions that were not real

Several other alarms in those thirty hours did not reproduce in isolation: a Set benchmark, a RegExp test, a Proxy test. They were code layout or machine noise. Two were "confirmed" by a second cycle that happened to overlap a bisect build competing for the same cores.

That produced a new rule: a cycle that overlaps other heavy work on the machine cannot confirm a regression. The current rules are:

  • A test has regressed when it is 8% below its range over the last four cycles, in two consecutive cycles.
  • A single cycle counts only past 40%.
  • Cycles that shared the machine with builds or bisects do not count.

A footnote from the same day: 88,374 system calls

One more fix landed on 7 November that is too good to leave out. The allocator returned freed pages to the operating system one page at a time. In a string-concatenation test that was 88,374 madvise calls in half a second.

Batching was two changes: return pages at most once every 10 milliseconds, and merge adjacent pages into one call.

Peak memory did not change. The idea is the same one mimalloc, jemalloc and Go's scavenger use: memory you just freed is the memory you are most likely to want back.

What the loop taught us

Running everything, constantly, with bisect on tap, moved the interpreter from 0.61 to about 0.85 of the best competing engine in a day and a half. It also showed how much of performance work is noticing. None of the three stories above involved a clever optimization. Each one was a regression someone would have shipped if the board had run once a week.
