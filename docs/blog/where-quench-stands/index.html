Where Quench stands: JetStream 3 with the JIT off

Against Node and Bun with all JITs disabled, Quench sits between them on speed and well below both on memory. The full picture, including the tests where its memory is far too high.

This is a status report. It covers one configuration, measured on 17 November 2026: every JetStream 3 test, with the JIT turned off in Quench, in Node (--jitless) and in Bun (BUN_JSC_useJIT=0).

Why JIT off? Because that is where Quench is closest to its goals today, and because interpreter performance and memory are what matter for short-lived processes and constrained environments. The JIT tiers are covered in other posts, and they are not competitive yet.

The headline

JetStream 3 has 75 tests in our harness. All three engines finish 56 of them. The comparison uses only those 56, because a geomean over different test sets per engine is not a comparison.

On speed Quench is 0.86 times Node and 1.07 times Bun. On memory it uses 26% of Node's peak and 60% of Bun's.

The goal for this mode is 1.5 times the score of the better engine at half its memory. That means a score near 60 and memory near 24 MB. Memory is close. Speed needs about 1.7 times more.

Test by test

The pattern is clear. Quench wins on tests that run a hot loop for a long time: numeric kernels, emulators, the classic object-oriented benchmarks. It loses on tests dominated by loading and compiling code, by promises and async functions, and by proxies.

What the losses are made of

Cold code. octane-code-load evaluates a large script repeatedly. Each evaluation compiles about 380 functions. On a cold run of EarleyBoyer, 28% of all instructions were in the front end (parsing, analysis and bytecode generation) and one analysis pass ran three to five times per function.

The principle we are working to is that cold cost should be proportional to the code that runs, not the code that loads. The first step was making class methods lazy and compiling a function's body on its first call:

Async and boundary crossings. A callback from native code into JavaScript (a forEach callback, for example) cost 827 instructions where Node's interpreter spends 385.

Proxies and dynamic objects. proxy-mobx exercises exactly the paths a shape-based object model is worst at. A trapped read went from 777 to 186 nanoseconds in one change and it is still one of the two slowest rows.

The memory outliers

The memory geomean covers the 56 tests every engine finishes. Outside that set there are tests where Quench's memory is plainly too high, and they should be shown.

On babylonjs-startup Quench's memory grows by about 54 MB per iteration: 97 MB after one iteration and 478 MB after eight. Part of it is retention: programs from earlier iterations stay reachable until the job ends. Part is how much an idle function costs. Quench holds about 2.8 KB per function across 18,655 functions, where V8 holds about 100 bytes for a function it has not needed yet. Laziness helps speed and memory at once here, which is why it is the current focus.

Inside the compared set, five tests have Quench above the lowest engine: Sunspider, mandreel, the two doxbee tests and babylonjs-scene.

What is solid

  • Conformance. test262 passes 53,353 tests with 53 waived and none failing, with the JIT off and on. The WebAssembly spec suite passes 67,124 of 67,124.
  • Memory on ordinary programs. On 51 of the 56 compared tests Quench has the lowest peak memory of the three engines.
  • Typical small-program footprint. Classic benchmarks such as Richards, DeltaBlue and Crypto peak at 12 to 14 MB, where Node needs 43 to 47 MB.

What is next

In priority order for the interpreter:

  1. Pay for code only when it runs: lazy bodies everywhere, one analysis pass, smaller idle functions.
  2. Make a call a frame push and a return a pop, with one frame layout shared by every tier.
  3. Make crossing between native code and JavaScript cost no more than a JavaScript call.
  4. Bring every primitive operation inside its instruction budget.

And for the tiers above it: every tier faster than the one below on every test, and the optimizing tier within five times of C.

If any of this is the kind of problem you like, the repository is open and every number in this post can be reproduced from it.
