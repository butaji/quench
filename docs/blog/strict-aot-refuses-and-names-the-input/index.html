Strict AOT: a compiler that refuses, and names the input

Running a program at build time is only safe if the build never bakes in something a later run would see differently. Quench's strict AOT mode is sound by construction: host operations off an allow-list are refused before they run, and the build names the input it could not fold.

Quench's strict AOT mode runs your program at build time and keeps only what it left behind. For a program that reads nothing from outside, that is a few kilobytes of output replay, as described in Hello world in 4,896 bytes.

Running code at build time has an obvious failure mode. If the build reads a file, the image contains the build machine's file. If it reads the clock, every run starts at the same instant. If it reads process.argv, every run gets the build's arguments. A compiler that does this produces a binary that is fast and wrong.

So strict AOT is built around one question: is this value the same in every future run? If the answer is not a proven yes, the build stops there.

An allow-list, not a deny-list

Every way a Quench program touches the outside world goes through a named host operation. Strict AOT lets a short list of them run at build time, in aot/prefix.rs:

  • Loading the program's own modules (require and the builtin module views). The sources are what the image is compiled from, so they are static by definition.
  • Writes to stdout and stderr. They run against a recorder, not the terminal. The recording becomes the image's effects.
  • Exit status: process.exitCode and process.exit(n).
  • Asking for standard input. This only marks a read as wanted. The wait for it is where evaluation ends.

Everything else is a dynamic input: files, the terminal, timers, the network, child processes. A host operation that is not on the list is refused before it runs, and the refusal ends the run. It cannot be caught. We checked that with fs.writeFileSync inside a try: the build stops and no file is written.

A new host operation is dynamic until someone proves otherwise. Forgetting to classify one makes the build refuse, never makes it wrong.

A deny-list would fail the other way: the first operation nobody thought about would be baked silently into every binary.

Inputs that hide in plain sight

Some inputs are not host calls at the point of use. They are values the runtime prepared at start-up. Quench handles those three ways:

  • Process identity and environment (process.argv, execPath, pid, process.env) are lazy. They are not filled in until the program reads them, and reading them is a refused host operation.
  • The clock, the local time zone and Math.random are noted by the runtime when used, so the build knows the result depended on them.
  • Whether a stream is a terminal. This one surprised us. console.log of a non-string colours its output when stdout is a terminal, so even a constant program depends on where it runs. Our first build baked process.stdout.isTTY from the build worker's own descriptors. That was a soundness bug, and it is now an input like any other.

Refusing with a name

A refusal is a diagnostic, not a crash. The compile report names the first dynamic input the run reached, then the compile falls back to the full image, which runs the program normally. These are four small programs on 25 November 2026:

ProgramStrict outcomeExecutable
console.log("hello")image, no engine linked4,880 B
print process.argvrefused: the process identity (process.argv, execPath, pid)full image
read a file named on the command linerefused: the process identityfull image
readline REPLrefused: standard input, after it waits for itfull image

The readline row is the interesting one. Its refusal is not "it reads stdin". The build evaluated everything up to the point where the program waits for a line: module loading, creating the interface, writing the prompt. Only then did it stop. That is exactly the prefix the next stage will keep as a saved heap instead of throwing away.

Small inputs become variants

Refusing every input would make strict AOT useless for anything that prints a number. But some inputs have only a few possible values. Whether descriptor 1 is a terminal has two.

For those, the build does what partial evaluation calls "The Trick": it evaluates the program once per value the program actually distinguishes, and the image starts with a guard that picks the matching variant. Quench asks up to three yes-or-no questions per image (today: whether each of stdin, stdout and stderr is a terminal), and only the ones the program really read. The image calls isatty() at start and replays the right recording. A fourth question refuses the strict image and names it.

The same mechanism is meant to carry other small inputs later: whether an environment variable such as NO_COLOR is set, platform facts, how many arguments were passed.

Why be this strict

Startup snapshots and build-time evaluation are not new. What we want from Quench is that the fast binary and the slow interpreter can never disagree. The interpreter is the only definition of JavaScript in the engine. The JIT and AOT are specializations of it, and a specialization is only correct if every fact it relied on holds in every run. For the JIT, a guard checks the fact at run time. For AOT, the fact has to be proved at build time, or the build has to say it could not.

That is the trade we picked: a strict build that sometimes says no, and names why, over a permissive one that is occasionally wrong.
