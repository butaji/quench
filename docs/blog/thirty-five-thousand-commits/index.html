35,000 commits in a month

In August 2026 the repository took 35,083 commits, 4,217 of them in one day. Here is what that much parallel work built, what it broke, and what we changed so it could keep going.

Between 2 and 31 August 2026 the Quench repository took 35,083 commits. The busiest day, 15 August, took 4,217. For scale, May, June and July together took about 3,500.

Most of that volume came from many branches working at once, much of it by coding agents. The history shows branches named quench-branch-01 through -10 being merged in waves, and the same change often appears two or three times with one timestamp on different parents. We are not going to pretend that is a normal way to build software. It is a very fast way to find out what your process cannot handle.

What got built

  • Node compatibility. The quench-node crate (now quench) arrived on 2 August, with Node's own test suite as a submodule and staged gates over it.
  • A 100% test262 goal with no skips. On 7 August the goal was rewritten to "100% test262 on quench-runtime (all 50K+ tests, no skips)", along with a budget of under 100,000 lines of Rust.
  • Intl and Temporal. 13 to 16 August, the peak of the chart, is mostly internationalization and the Temporal date and time API.
  • WebAssembly. On 28 August a WebAssembly VM was merged with the vendored spec-suite runner reporting 67,124 passed, 67,124 total, 0 failed.

What broke

15 August had 279 reverts. The log does not say why, but with ten branches merging into one line it is easy to guess. Some reverts appear six times with the same title.

The test loop was too slow to be a gate. Running one test262 stage took 38.6 seconds because every test started a new process. Moving the runner in-process, with an explicit reset of interpreter state between tests, took it to 3.2 seconds.

A stricter check regressed 959 tests. Tightening how the runner judged parse-phase negative tests looked obviously right and turned 959 already-green tests red across 25 stages. It was reverted the same day and recorded as a known override. The harness is code too, and it needs the same care as the engine.

An abstraction that fought the language. Moving 37,000 lines of polyfill JavaScript into Rust worked, at the cost of an 11% slower route load at first. The first attempt, one Rust file and one trait implementation per polyfill, did not: a polyfill named ref had to be renamed r_e_f to dodge a Rust keyword, and the commit that reverted it documents the dead end.

What we changed

The lesson from August is that throughput is limited by integration and measurement, never by typing speed. The changes that stuck:

  1. Checks have to be fast enough to run every time. The 12x runner speedup mattered more than any single feature that month.
  2. One line of integration. Later this became a hard rule: one trunk, one integrator, feature work on its own branches.
  3. Only one place runs the full suite. Many workers running the whole of test262 at once just produce contention. Workers run the directories they touched.
  4. Debt lists that only shrink. Skip lists, oversized-function lists and known-failure lists can lose entries and never gain them.

The month ended with an engine that had a lot of surface (Node APIs, Intl, Temporal, WebAssembly) and performance that nobody had honestly measured yet. That was the next problem.
