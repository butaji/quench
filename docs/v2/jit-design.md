# Quench JIT design

## Goal

Make JIT mode in `quench-node` beat JIT-enabled Node and Bun on JetStream 3.0 Score while using less maximum RSS, first on the server-side JavaScript fixtures. Keep the interpreted mode as the default and preserve its results. Use one OXC frontend, one residual bytecode representation and the same `Vm`, heap and host APIs in both modes. TypeScript is erased by the existing frontend; Wasm keeps its current decoder and enters that same VM.

The pass condition is workload-specific and measured: stock JetStream validation, 11 or more matched rounds, and a paired 95% bootstrap interval showing Quench's score ratio above 1 and its maximum-RSS ratio below 1 against each available JIT-enabled bar. Qualify on Linux x86_64 and M4 separately. A single run is a screen, not a win. JetStream 3 contains both compute-heavy JavaScript and Wasm, so continue to its Wasm fixtures after the JavaScript tier has a useful measured path.

## What the repository already has

At the `v2-merged` baseline, `quench-runtime` already used Cranelift to compile a subset of Wasm functions through `ExecutionMode::Compiled`; JavaScript and TypeScript still used the residual bytecode interpreter, and `quench-node` had no process-level JIT selector. This branch adds `--jit` to the existing runtime path and a lazy JS function-entry tier. The Wasm compiler remains a reference for executable memory, traps and host callouts.

The first memory risk is the granularity of code ownership: compiling all eligible functions when one Wasm function is first called makes cold code consume both compiler work and executable bytes. The JavaScript tier should compile a function only after it is hot, account for emitted bytes, and stop compiling when a named per-process budget is full. Keep no IR, AST or copied bytecode alongside native code unless a correctness invariant needs it. Code-cache exhaustion means interpreted execution.

## Research and the design it supports

Current engines use tiers because compilation speed, warm-up cost, code quality and code size pull in different directions. V8's Sparkplug emits a baseline from bytecode, Maglev is a faster mid-tier, and its top tier spends more work on hot code. JavaScriptCore keeps bytecode as the source of truth, then uses lightweight profiling and baseline/optimizing tiers. SpiderMonkey pairs its baseline compiler with Warp optimization. The inference for Quench is to add one small native tier first and measure its compile cost and code bytes before adding a second optimizing tier. [V8 Maglev](https://v8.dev/blog/maglev), [JavaScriptCore bytecode format](https://webkit.org/blog/9329/a-new-bytecode-format-for-javascriptcore/), [SpiderMonkey optimization tiers](https://d2r03xnqvbcxrv.cloudfront.net/js/how-we-optimize.html)

Futamura's first projection specializes an interpreter for a fixed program. Quench already has the useful static input: validated residual bytecode with fixed opcodes, operands, branch layout, constants and function boundaries. Lower that residual form to Cranelift, so native execution removes opcode dispatch, operand decoding and the generic register file where the function proves those facts. This is the practical projection; a general self-applicable partial evaluator or compiler generator is outside the goal. Dynamic JavaScript values remain dynamic: emit a guard only when it proves a fast representation, and use the same semantic slow path or resume the interpreter when it fails. [Futamura's paper](https://www.jstage.jst.go.jp/article/jssst/21/5/21_5_343/_article/-char/en), [practical partial evaluation for dynamic-language runtimes](https://dl.acm.org/doi/10.1145/3062341.3062381)

Ershov/Sethi-Ullman numbering estimates the register demand of expression trees and schedules the higher-demand child first. Use it to order tree-local evaluation or short straight-line expression regions when the values are unboxed. Do not use the tree number as a whole-function allocation strategy: JavaScript control flow has joins, loops, calls and deoptimization edges. Lower those to Cranelift's SSA graph and let its allocator handle live ranges and spills. [Optimal code generation for expression trees](https://doi.org/10.1145/800116.803770)

Use category theory as a correctness discipline for the one-VM architecture. Treat validated bytecode and Cranelift control-flow graphs as categories of composable state transitions. The interpreter and native lowerer are two interpretations of the same opcode/effect algebra: lowering should preserve identity and composition, and each emitted transition should commute with the interpreter's transition under a relation between their states. Model JavaScript effects explicitly in that relation: exceptions, heap writes, host calls, and collection safepoints are observable sequencing points. Guards restrict native execution to states for which the specialized transition is valid; a failed entry guard leaves the already-initialized frame at its original PC and resumes interpretation. This is a proof target and a review method, not a runtime abstraction or a claim that category theory itself improves speed. The same diagram composes OXC/TypeScript residualization and Wasm decoding with the shared VM, without requiring separate frontend VMs. The proof vocabulary follows algebraic compiler-correctness work on semantic homomorphisms and state relations. [Morris, “More on advice on structuring compilers and proving them correct”](https://doi.org/10.1016/0304-3975(81)90080-3), [correctness of speculative optimization and deoptimization](https://arxiv.org/abs/1711.03050)

Deegen supplies a useful meta-compiler pattern: write bytecode semantics once, generate interpreter and baseline-JIT implementations, and assemble fast baseline code from Copy-and-Patch stencils without running LLVM in the VM. Reuse the semantic single-source idea and the low runtime compilation cost. Keep Cranelift for the optimizing tier where CFG/SSA optimization pays off. Deegen's reported results are for Lua, and its paper leaves an optimizing tier outside its scope; they do not establish JavaScript performance or lower RSS for Quench. Treat stencils as a future baseline path only after opcode semantics have a shared definition and measured runtime compilation is the bottleneck. [Deegen paper](https://arxiv.org/abs/2411.11469), [Stanford Deegen project](https://compilers.stanford.edu/software/deegen/), [Copy-and-Patch](https://doi.org/10.1145/3485513)

Use online statistics for promotion and acceptance instead of a fixed “hot” intuition. A candidate is worthwhile when its estimated future execution savings exceed compile cost plus its code-memory charge: `E[remaining runs] × E[time saved per run] > compile time + λ × native bytes`. Start with saturating per-function invocation/backedge counts and a small sample of elapsed interpreter time; do not retain per-op histories in production. Promote only when the estimated payback is positive with adequate confidence, otherwise leave it interpreted. Apply an explicit process-wide code-byte/page budget and discard low-value code when full. For benchmark decisions, pair engine runs by fixture and round, randomize engine order, compare log score ratios and RSS ratios, and bootstrap the paired rounds; do not infer a win from unpaired averages or one run. Keep cold-start and warmed paths separately visible because compilation can raise both elapsed time and RSS before it pays back. These policies are Quench design inferences, not guarantees from the cited papers.

JetStream 3 is the acceptance workload, not a code-generation oracle. Its stock driver and per-test validation remain unchanged. The repo's runner already provides JetStream's shell surface through `node:vm`, fresh realms, on-demand resource loading and process-level maximum RSS, so benchmark changes should be limited to selecting the Quench execution mode and recording its identity. [JetStream 3 announcement](https://webkit.org/blog/17899/introducing-the-jetstream-3-benchmark-suite/), [pinned JetStream corpus](https://github.com/WebKit/JetStream/tree/JetStream3.0)

## Implementation sequence

1. Record the mode-specific JetStream control runs and compiler/runtime versions. Keep each fixture separate and start with the first server-side fixture in `docs/jetstream3.md`.
2. Add a process-level JIT selector to `quench-node`, defaulting to interpreted. It must set `ExecutionMode` on the existing runtime rather than create a JIT-specific VM. Confirm the Wasm tier remains reachable through JavaScript `WebAssembly` calls in the same runtime.
3. Add lazy JavaScript function entry counters and a budgeted compiled-code cache. Avoid per-op profiling metadata; retain only feedback needed to justify a compile decision. Make compile failure, unsupported bytecode, guard misses and budget exhaustion resume through the interpreter.
4. Compile a narrow, semantically safe JavaScript subset first. Start with pure numeric functions and entry guards checked after normal activation. The tier must return through the existing dispatch-loop unwind path. Extend to loops/control flow only with PC/state maps that permit exact interpreter reconstruction. Keep effects behind semantic helpers until ordering, roots and exception behavior are covered by the semantic-preservation relation.
5. Use JetStream's server-side fixtures one at a time. Profile score and peak RSS together, including compilation and executable memory. Keep a tier only when paired confidence intervals clear both score and RSS bars. After JavaScript, measure the Wasm-tagged fixtures with compiled mode and reduce cold code retention where RSS warrants it.
6. Qualify retained changes with at least 11 matched rounds on Linux and M4. Store raw reports and reproduction commands under `evidence/`; update the Linear scoreboard at its existing home. Do not claim a win from an unsupported competitor, a different host, or a one-round screen.

## First JS tier in this branch

`quench-node --jit` selects `ExecutionMode::Compiled` on the same runtime and VM; the default remains interpreted. The first JS tier is intentionally narrow: after at least 16 eligible entries, it promotes only when the 95% Wilson lower confidence bound for numeric inputs reaches 0.80. This treats observed call-entry shapes as representative future samples; it is a conservative profile filter, not a performance claim. Cranelift then lowers straight-line residual functions containing numeric constants, moves, `+`, `-`, `*`, `/`, and a terminal return. The caller guards each formal parameter as a Number. A failed guard leaves the initialized frame at PC 0, and a native result is written to the bytecode return register before the normal `Return` dispatch unwinds the frame. Unsupported bytecode compiles to no tier. This uses Futamura-style specialization of a fixed residual function, but does not yet generate the interpreter/compiler from one semantic source as Deegen does.

The current tier is a prototype, not a measured optimization strategy: the Wilson gate estimates input stability, but compilation cost, observed time saved and expected remaining calls are not yet included in the payback estimator above. Ershov/Sethi-Ullman scheduling is not yet applied because these functions are straight-line and Cranelift handles native register allocation. The category-theory state relation is the correctness/review discipline, not a runtime type or compiler abstraction. Control flow, heap access, calls, exceptions, non-number inputs, and OSR remain in the interpreter. The native region is limited to 256 bytecodes and has no internal poll; the shared dispatcher checks cancellation before entering and immediately after returning. Profiling-feature builds leave this JS tier disabled so native execution cannot omit interpreter instrumentation.

Tier metadata is sparse and capped at 256 functions per VM. At most eight functions and 64 KiB of page-rounded executable mappings are retained; unsupported functions, mapping failures and budget exhaustion continue in the interpreter. This bounds executable mappings and profile state, but does not include Cranelift's temporary compilation allocations in the RSS budget. Page-rounded mapping capacity is not a resident-set measurement; benchmark RSS remains the acceptance metric.

## Current measurement limits

The default PATH has Node 24.19.0. The Linux screen used Node 26.10.0 and Bun 1.4.2 from `.local/bench-runtimes`; the M4 comparison is unavailable in this host. The Node 26 build of Quench is 26.12.0. Full JIT qualification still requires the whole suite on both Linux and M4.

The 2026-10-17 Web SSR screen used 11 matched rounds per Quench mode and JIT-enabled Node/Bun. Quench JIT's median Score was 14.85 versus Bun 133.05 and Node 128.94. Its paired median Score ratios were 0.108 (95% bootstrap interval 0.106–0.118) and 0.115 (0.113–0.116). Quench JIT's median peak RSS was 124.11 MiB versus 239.79 MiB and 246.33 MiB; paired RSS ratios were 0.517 (0.485–0.530) and 0.504 (0.502–0.507). Against Quench interpreted mode, the JIT Score ratio was 0.991 (independent 95% interval 0.953–1.036), so this fixture shows no JIT score improvement. The JIT run used about 1 MiB more peak RSS than the interpreter. These results show a memory advantage against these two engines on this fixture, but fail the score condition by a wide margin and are a screen rather than a qualification: only one of 30 fixtures ran, the source tree was dirty, and there is no M4 result. Raw reports, paired bootstrap summary and the no-JIT control are under `evidence/jit-jetstream3-2026-10-17/`. The no-JIT JetStream lane control tracked by Linear TOD-121 remains separate.
