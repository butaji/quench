# v8-v7 score strategy

**The strategy this document teaches is a method, not a checklist.** Every
named algorithm, architecture fix, and per-benchmark suggestion below is a
**candidate hypothesis** — a starting point backed by the data available
when it was written, not an instruction to implement in order. The actual
skill this document exists to transfer is: **collect real data first
(§ Profiling/DWARF workflow), use it to tell an implementation bug from an
architectural bottleneck (§ Finding architectural bottlenecks), and decide
what to build from what the data says — independently, not by working
through a list.** If a suggestion below doesn't match what your own
profiling shows for the fixture you're working on, trust your data over
this document and say so in `architecture-evidence.md`; if a fixture's
actual bottleneck turns out to be something not listed here at all, finding
that *is* the point of this method, not a gap to fill in later. Treat the
per-benchmark sections as "here is what past profiling found, and what it
suggested" — confirm it still holds with a fresh profile before building on
it, since the codebase moves and a prior finding can go stale.

This document is a per-benchmark attack-vector plan for the classic v8-v7
suite (`quench-bench/js-engine-benchmark/v8-v7`), plus the cross-cutting
measurement, toolchain, and algorithm references needed to execute it without
violating [`benchmark-integrity.md`](benchmark-integrity.md). It is a planning
document, not an evidence log — reproducible measurements still belong in
[`architecture-evidence.md`](architecture-evidence.md), and the copy-and-patch
mechanics it assumes are described in
[`copy-and-patch-jit.md`](copy-and-patch-jit.md),
[`deegen-alignment.md`](deegen-alignment.md), and
[`cpython-copy-patch-notes.md`](cpython-copy-patch-notes.md).

## Scoring mechanics, read first

The suite's score is `score = reference_time / measured_time`
(`quench-bench/js-engine-benchmark/v8-v7/base.js:179`), calibrated against a
circa-2008 reference machine. It is **not** capped at 1000 — Node itself
currently scores in the tens of thousands on this host, because "1000" was
just what the reference machine scored when the suite was built, not a
target. The suite score is a **geometric mean** across all eight fixtures
(`BenchmarkSuite.GeometricMean`), which means the *weakest* fixture dominates
the aggregate far more than an arithmetic mean would: with one fixture stuck
an order of magnitude below the rest, the aggregate cannot reach a
proportionally high value no matter how far the other seven improve. Any
target expressed as "reach N on the aggregate" must be read as "close the gap
on every fixture roughly together," not "optimize whichever fixture is
easiest."

Every improvement claim in this document must be measured, in the tracked
runner, on the **same tree**, paired **fallback vs. candidate**, matching the
discipline already established in `architecture-evidence.md`'s rows (release
artifact, one run per fixture at the suite's 300 s timeout for full-suite
rows, three runs for the neutral corpus, one run for the curriculum). A lone
absolute score is not evidence; a paired same-tree delta is.

## Anti-cheat discipline (mandatory, every fixture, every change)

This restates [`benchmark-integrity.md`](benchmark-integrity.md) in
attack-vector-specific terms. Before any change below is considered done:

1. **Generalization check.** Build a synthetic clone of the same
   algorithmic/loop/dispatch shape that motivated the change, with different
   names, functions, and literal constants. The fix must help the clone by a
   comparable margin. A fix that only helps the literal fixture file is
   overfitting even without any explicit identity check.
2. **Identity scan.** After every change:
   ```sh
   grep -rniE "richards|deltablue|splay|crypto|raytrace|earley|navier|regexp" \
     crates/quench-runtime/src crates/quench-node/src
   ```
   must return zero new matches.
3. **Admission must generalize.** Per `benchmark-integrity.md`, a guard,
   quickening site, or cache tier's admission rule and bound must generalize
   to any JavaScript program with the same *runtime shape* (value tags,
   object layout, callee-identity diversity) — never sized to one benchmark's
   known shape count, call count, or loop trip count, even unnamed.
4. **Full gates before claiming a win**, not just the one fixture that
   motivated the work: `cargo test -p quench-runtime --lib` and
   `--features execution-trace`, the neutral corpus
   (`micros/verify.mjs`), the curriculum (`deegen-verify.mjs`), and the
   fixture(s) actually targeted. A default-on flip additionally requires the
   neutral corpus **and** curriculum **and** the relevant fixture(s) all
   net-positive on the same tree — matching task 068's documented fail
   condition. The full-suite run is expensive (Crypto/RegExp alone can run
   200+ s each); don't run it after every micro-change, but never claim a
   suite-level win without it.
5. **Never trust a synthetic microbenchmark alone.** It has already produced
   two false positives this project (a 5M-iteration numeric loop showing
   +6-7% while the neutral corpus and the real stencil subset both
   regressed). Treat a synthetic-only result as a hypothesis, not a
   conclusion, until the paired real-fixture run confirms it.

## Healthy optimization vs. benchmark cheating: a decision guide

The mechanical checks above (grep, generalization clone, full gates) catch
most violations, but they're a backstop, not a substitute for judgment while
designing a change. Use this test before writing code, not just after:

> **The one-question test**: if I described this admission rule, threshold,
> or code path to someone who has never seen the v8-v7 suite, using only
> JavaScript-language terms (value shapes, types, call patterns, loop
> structure) — would it still make sense as something worth building? If the
> honest description requires mentioning a specific fixture, input size, or
> "this happens to occur in benchmark X," it's cheating, even if no fixture
> name appears anywhere in the code.

**Concrete pairs, healthy vs. cheating, grounded in the fixtures above:**

- Healthy: a generic-IC fast path admitted whenever a property access site
  observes a monomorphic shape N times in a row, for any N chosen by
  measuring cache-miss cost generally. Cheating: the same fast path gated on
  "shape count ≤ the number of distinct shapes DeltaBlue's constraint
  objects happen to use" — the threshold is a property of one fixture's
  object model, not a general cost/benefit tradeoff, even though it never
  names DeltaBlue.
- Healthy: an NFA/Pike's-VM fast path for regex patterns without
  backreferences or complex lookaround, applied to every such pattern in any
  program (§ RegExp above). Cheating: special-casing the specific pattern
  strings used by the RegExp fixture, or widening the "simple pattern" fast
  path's definition just far enough to catch that fixture's patterns without
  a principled boundary (backreference/lookaround presence) behind it.
- Healthy: a loop-body fusion region admitted for any basic block matching a
  structural shape (bounded arithmetic + array access, no calls, no
  deopt-requiring operations), regardless of which benchmark produces that
  shape. Cheating: tuning the region's maximum size, iteration-count
  threshold, or admitted-op set to exactly cover NavierStokes's or
  RayTrace's specific loop bodies and no further.
- Healthy: an arena nursery scoped to a general JS execution boundary (a
  script evaluation, a microtask turn) with an escape check that's a real
  reachability property. Cheating: sizing the arena to exactly the
  allocation volume of one Splay run, or special-casing tree-node-shaped
  objects specifically.
- Healthy: profiling a real fixture to find where the interpreter's
  generic-dispatch cost is going (task 074's approach), then fixing the
  general dispatch-loop mechanism (IC, register pinning, specialization).
  Cheating: adding a fast path that recognizes Richards' specific
  `Task`/`Packet` call pattern and short-circuits it.

**Why "no fixture-identity string in the diff" is not sufficient by
itself**: `benchmark-integrity.md` already states this precisely — "sizing a
bound to a known benchmark's numbers, even without naming the benchmark, is
the same violation as inspecting its fixture name." The identity grep in the
anti-cheat checklist above catches the crude version of this; the
one-question test and the paired examples above are for catching the subtle
version, where a threshold or admission rule is *phrased* generally but was
*chosen* by reverse-engineering what makes one fixture fast.

**What "healthy" optimization work looks like, positively, not just as the
absence of cheating**:

- It starts from a profile of real, representative code (a fixture, a
  synthetic clone, or both), not from reading the fixture's score and asking
  "what change would move this number."
- It's justified by a general mechanism with literature or a reference
  implementation behind it (the algorithm/reference table below exists
  precisely so every change traces to a named, externally-motivated
  technique, not an ad hoc tweak invented to fit one score).
- Its generalization is verified on a *different* input before its fixture
  impact is trusted (§ anti-cheat discipline, item 1).
- It's willing to report a no-go. A profile that shows a technique doesn't
  apply (task 034's zero-sample gate) is a valid, complete result — resist
  the pull to force a change just to show suite-score movement after
  investing profiling time.
- It measures cost as well as benefit on every axis that matters for this
  project — RSS as well as speed (§ Keeping RSS low above), the full gate
  suite as well as the targeted fixture, the neutral corpus as well as the
  suite.

## Data to collect, and how to use it

- **DWARF/`sample` profiles**, isolating the actual call-boundary or hot-loop
  transition, not the whole dispatch loop — the pattern already used for
  task 068's ARM64 boundary work. Capture one currently-covered leaf case and
  one sequential/composed case per change, before and after.
- **Retired instructions and cycles**, not just wall time, for any
  microbenchmark claim — wall time alone hides whether a win is real
  amortization or measurement noise (the existing 2-3% host-noise band
  applies to every paired comparison).
- **Peak RSS per fixture**, not just aggregate RSS ratio — RegExp alone
  currently accounts for the majority of the suite's memory footprint
  (~1.7-1.8 GiB out of ~2.4x Node's total), so aggregate RSS ratio changes
  are meaningless without the per-fixture breakdown.
- **`QUENCH_EXEC_TRACE`** (the `execution-trace` feature) for handler-level
  attribution inside the interpreter dispatch loop — this is how task 074
  isolated Richards/DeltaBlue's cost to generic `Branch`/`TraceSite`/
  `CheckInitialized`/`Unary` handlers rather than property lookup.
- **Paired JSON output** from `verify.mjs`/`deegen-verify.mjs`/the v8-v7
  runner, diffed fallback vs. candidate on the same tree — this is the unit
  of evidence, not a single run's printed score.
- **Per-fixture subset geomeans**, tracked separately from the full 8-fixture
  aggregate, for any change that only reaches some fixtures (e.g. the
  Crypto/RayTrace/NavierStokes stencil-reachable subset). A real, isolated
  win must stay visible in `architecture-evidence.md` even when it doesn't
  move the full geomean yet.

## Profiling/DWARF workflow: how to collect it, and how to decide from it

This is the actual reproducible procedure behind every DWARF/`sample` entry
in `architecture-evidence.md` (tasks 016/019/030/034/039/047/068/073 all
follow this shape) — use it verbatim, don't invent a new profiling ritual
per task.

### 1. Build a DWARF-enabled artifact, never the scored one

```sh
cargo build --profile profiling -p quench-node
```

`Cargo.toml`'s `[profile.profiling]` inherits `release` (same optimizer
policy, so the code shape matches what's scored) but sets `debug = true` and
`strip = "none"` — full address-to-source attribution without changing
codegen. Per `performance-lanes.md`, this artifact **never supplies a score
number**; it exists only to be sampled. Keep it in a separate
`CARGO_TARGET_DIR` (e.g. `target/profiling/`) from the release artifact used
for scoring, so the two are never confused.

### 2. Capture a symbolized sample over the actual workload, not a proxy

On macOS (the documented host in this repo):

```sh
target/profiling/quench-node path/to/fixture.js &
PID=$!
sample $PID 5 -f target/my-profile.dwarf.sample
wait $PID
```

Five seconds is the standing convention (`/usr/bin/sample $PID 5`) —
long enough to gather hundreds to thousands of samples on a hot loop, short
enough to iterate. For a fixture that's timeout-bound or too short to hold
steady state for 5 seconds, wrap it in a synthetic driver that repeats the
same operation (matching the "isolate the call boundary, not the whole
run" principle above), and confirm with the anti-cheat generalization check
that the driver's shape, not its literal content, matches the real fixture.
For counter-level detail beyond symbol names (retired instructions, cycles),
use `xctrace` CPU Counters (already used for task 034's follow-up gate) or
`perf record`/`perf stat` on Linux hosts.

Keep the raw `.dwarf.sample` file as the artifact of record (matching
`target/add-chain.dwarf.sample`, `target/arm-stencil-chain.dwarf.sample` in
prior tasks) — it is the evidence, not just its summary.

### 3. Read the sample and classify what's actually hot

Open the `.sample` output and separate:

- **Symbolized runtime-owned frames** (e.g. `StencilArena::render_or_get`,
  `execute_f64`, `dispatch_callee`, `run_code_completion_step_from`) — real
  attribution to a specific function.
- **Anonymous/copied bytes** — samples landing in the rendered stencil
  region itself show as unsymbolized machine code; this is *expected and
  correct* for copy-and-patch output (task 073's own finding: "the rendered
  leaf is anonymous copy-and-patch code... no instruction-level attribution
  is claimed from that capture") — do not mistake an anonymous-code sample
  count for a missing measurement; it means the generated code itself is
  running, which is the good outcome once composition is correct.
- **Sample count as a proxy for CPU share**, not wall time directly — compare
  *counts* before/after in the same 5-second window on the same workload,
  the same way task 047's Ackermann profile compared `execute_call` (436
  samples) against `child_registers` (2 samples) to conclude call dispatch,
  not frame construction, was the real cost.

For AArch64 relocation-level questions specifically (confirming a stencil's
patched bytes match intent, not just that it ran), disassemble the object
file directly rather than trusting the codegen pipeline's intent:

```sh
llvm-objdump -dr target/profiling/build/*/out/*.o | less
llvm-dwarfdump --debug-line target/profiling/quench-node
```

This is the same tool pairing `cpython-copy-patch-notes.md` documents
CPython's own `Tools/jit/_targets.py` using to extract stencils and inspect
relocations — necessary when debugging *why* an ARM64 patch is wrong, not
just *that* a region is slow.

### 4. Turn the classification into a decision, not just a report

A profile only earns its keep if it changes what gets built next. Map the
observed shape to the decision it licenses:

| What the sample shows | What it means | What to do |
| --- | --- | --- |
| Hot samples in `StencilArena::render_or_get`/lifecycle code, not the rendered region | One-time setup cost is being paid repeatedly — caching/admission bug | Fix the cache/admission path (this is exactly what task 068/073's typed-entry cache addressed) |
| Hot samples in anonymous rendered bytes, region small (few ops) | The generated code is running correctly, but the region is too small to amortize entry/exit cost | Grow fusion depth (basic-block composition), not more caching |
| Hot samples in generic dispatch-loop symbols (`Branch`, `Unary`, `TraceSite`, `CheckInitialized`) | The interpreter's own dispatch cost dominates, not anything stencils touch | Redirect to Track B (interpreter IC/register-pinning), per the Richards/DeltaBlue section — do not add more stencils here |
| Near-zero samples on any rendered-region symbol at all | The admitted region is never reached in this workload (task 034's actual finding for its target case) | Don't implement the change; the profile is a valid "no-go," not a failure of the method |
| Sample counts unchanged before/after a change, wall time changed | The wall-time delta is likely host noise, not the change — cross-check against the paired same-tree run before trusting it | Re-run rather than record a claim |
| Counter vectors (`xctrace`) nonzero and materially different between two paths, but no applicable code shape to change | The cost is real but not addressable by the technique attempted (task 034 follow-up: no cold basic block existed yet to split) | Record the finding and the no-go explicitly in `architecture-evidence.md`; do not force an unjustified change to show activity |

### 5. Record the result the same way every time

Every profiling-informed decision — go or no-go — belongs as its own dated
entry in `architecture-evidence.md`, with: the exact command run, the
sample/counter numbers observed, the classification from the table above,
and the resulting decision. A profile that justifies *not* doing something
(task 034's zero-sample gate) is exactly as valuable a record as one that
justifies doing something — write both down, not just the wins.

### 6. The mechanical tool: a corpus-wide category ledger, not a single-run profile

A single `sample` run answers "what's hot in this one fixture, right now."
It does not answer the question that actually justifies large-scale
investment: **what fraction of everything we measure does each class of
check/handler account for, in aggregate?** Individually cheap, ubiquitous
checks (a type-tag check present in nearly every handler, say) can dominate
the real total while never looking dramatic in any one profile — and a
single-run profile has no way to show that, because it only sees one run's
mix of operations.

`tools/instruction-category-ledger.mjs` turns the `QUENCH_EXEC_TRACE`
snapshot (already emitted by any `--features execution-trace` build, one
JSON object per process on stderr — see `execution_trace.rs`) into that
aggregate view, mechanically, across the whole corpus instead of one run:

```sh
cargo build --profile profiling -p quench-node --features execution-trace
QUENCH_EXEC_TRACE=1 node tools/instruction-category-ledger.mjs \
  --engine target/profiling/quench-node \
  --corpus quench-bench/micros \
  --corpus quench-bench/deegen-curriculum \
  --out target/instruction-category-ledger.json
```

(v8-v7 fixtures load through `base.js`/`run.js` rather than running
standalone; pass pre-wrapped copies — the same kind of temp script the
tracked runner already writes under `/tmp/quench-v8-v7-*.js` per run — via
repeated `--fixture <path>` flags rather than a bare `--corpus` directory,
so the tool never has to guess at harness wiring.)

**What it does**: sums every opcode/handler counter across every fixture run
into one grand total, ranks categories (`compact`, `leaf_compact`, `slow`,
`binary`, `constant`) by their share of that total, and within each category
ranks the individual opcode/handler names by their share of the category.
Each category row also carries a `mechanism_hint` — a fixed lookup from
category to the general-mechanism class that reduces it (inline caching/
quickening for `compact`/`leaf_compact`/`binary`/`constant`, "generalize the
fast path" for `slow`) — so the ranking points directly at what kind of fix
to design, not just at what's expensive.

**The decision rule this licenses**: only invest in a general mechanism
(§ Finding architectural bottlenecks above) for a category/name pair that
shows up with a large share of the *grand total*, not a large share of one
run. This is the mechanical version of the fraction check from
§ Healthy optimization — it replaces "eyeball whether this looks hot" with
an actual computed percentage.

**Closing the loop — validate at the category level, not the symptom
level**: after building a mechanism, re-run the same command with
`--compare target/instruction-category-ledger.json` (the prior run's
output) added, and confirm the *targeted category's share actually dropped*
in the comparison table, not just that one fixture's score moved. A
mechanism that "worked" locally but only moved cost into a different
category (a cache-miss path costing more than the check it replaced, say)
shows up here as a category share that didn't fall, or fell less than
expected — exactly the signal that would have caught the `Weak::upgrade`
fix's near-zero effect *before* spending a full paired benchmark run to
discover it, since the aggregate share for that call-site category could
have been checked directly.

**Keep the ledger as a running record**: commit each significant run's
top-10 category table into `architecture-evidence.md` as a dated row, the
same way DWARF/sample findings are recorded — this is the "ledger" from
§ Finding architectural bottlenecks made concrete and reproducible, so the
project's understanding of where the remaining cost lives compounds across
sessions instead of resetting with every new profiling pass.

### 6a. Provenance: mapping stencils specifically, not just opcodes

The categories above (`compact`, `leaf_compact`, `slow`, `binary`,
`constant`) are interpreter opcode counters. The trace snapshot now also
emits `stencil`: each entry is keyed by code identity, bytecode offset, and
physical plan kind, with `{hits, misses}` for native execution versus the
complete canonical fallback. This is the same shape as `quickening`, so the
ledger ranks stencil volume and hit rate without any tool-side special case.
The key is runtime identity data only; it carries no fixture or source name.

**This gives you two distinct, useful facts per region, not one**: its
**share of the grand total** (is this region's execution
volume big enough to matter at all) and its **native hit rate** (is the
region actually being admitted/reached, or falling back so often that its
cost is mostly the fallback path, not the stencil). A region with a large
share and a low hit rate is a different, higher-priority finding than one
with a large share and a high hit rate — the first means the declared facts
and runtime validation/coverage do not line up (diagnose that mismatch; do
not add a runtime builder); the second means the *fused code's* cost is what
to attack next (fusion depth, ABI, per §3 of the per-benchmark section
above). Track both numbers, not just the aggregate share, on every ledger
run.

### 6b. Facts log and generalization check, mechanized

Two more flags close gaps the tool had at first cut:

- **`--facts-log target/instruction-facts.jsonl`** appends one line per
  `(fixture, category, name)` per run, in the shape
  `Fact{benchmark, build, machine, vm_unit, metric, value}` — an
  append-only, disposable raw record (kept under `target/`, per the
  disposable-reports convention at the top of this document) that the
  summary JSON is derived from. `build` and `machine` are captured
  automatically (`git rev-parse HEAD`, dirty-tree flag, platform, engine
  mtime) so a ledger run is self-describing without manual bookkeeping —
  necessary once ledger runs start compounding across sessions, so a later
  reader can tell which tree a given row came from without guessing.
- **`--synthetic-before`/`--synthetic-after`** mechanize the anti-cheat
  generalization check itself (§ Healthy optimization above), instead of
  leaving it as a manual step a reviewer might skip: run the ledger on the
  real corpus and on a synthetic clone of the motivating fixture's shape,
  both before and after a candidate change, and pass all four ledgers
  together (real-before via `--compare`, real-after is the current run,
  synthetic-before/-after via the new flags). The tool flags any category
  whose real-corpus share improved without a comparable improvement on the
  synthetic clone — printing an explicit `MISMATCH: does not generalize`
  line — which is the mechanical form of "this only helped the literal
  fixture file" that the anti-cheat checklist otherwise asks a human to
  notice by inspection alone.

## Keeping RSS low while chasing speed

Score is speed-only in the `base.js` formula above, but every row in
`architecture-evidence.md` also tracks peak RSS and an aggregate RSS ratio
against Node, and the current aggregate (~2.4x Node) is already a known
weak point — a speed win that inflates memory is not a clean win for this
project. Treat RSS as a co-equal constraint, not an afterthought, per
fixture:

- **RegExp historically dominated a trace-enabled RSS ratio** (~1.7-1.8 GiB
  in the retained diagnostic process). That number is not comparable to a
  scored artifact: a fresh production verification reports 31,162,368 B for
  RegExp versus Node's 70,664,192 B. The current implementation is deliberately hybrid: regular
  ASCII patterns use a narrow `regexp_native` matcher where its parsed shape
  fits, then the cached `regex` automata backend; unsupported constructs and
  Unicode-sensitive cases retain the repository-owned complete fallback. The
  automata path retains one reusable capture-location workspace for grouped
  patterns; grouped match results and object properties still allocate per
  call. It materially reduced targeted wall time but did not reduce this RSS
  outlier. The current trace identifies match-result/object construction,
  rather than compilation, as the next representation target.
- **Stencil arenas are bounded already** (`MAX_ARENA_BYTES`, 1 MiB per
  arena in `stencil_arena.rs`) — region-composition growth (RayTrace/
  NavierStokes/Crypto) must not remove or loosen that bound. A fused region
  that covers more code per arena is fine; an unbounded or per-call arena
  growth is a regression even if it's faster.
- **A Scavenger-style GC for Splay** (semi-space copying) trades peak RSS
  for throughput in the general case — a semi-space design reserves roughly
  2x the live set by construction. Measure peak RSS before and after
  adopting it, not just score; if Splay's score improves but its peak RSS
  moves adversely, size the space bound explicitly rather than accepting
  the default and calling it done.
- **Measure peak RSS per fixture, every time**, not just the suite
  aggregate — an aggregate ratio can hide one fixture's regression behind
  another's improvement. This is the same principle as the subset-geomean
  tracking above, applied to memory instead of speed.
- **`panic = "abort"` and LTO** (below) also reduce binary/metadata
  footprint slightly, but the fixture-level RSS story is dominated by
  runtime data structures (regex backtracking state, stencil arenas, GC
  space reservation), not codegen — don't expect toolchain flags to move
  RSS materially; expect the algorithmic fixes above to.

## How Bun actually reaches its score, and what transfers to Deegen's scope

Bun has no independent JS engine — it embeds JavaScriptCore (JSC), WebKit's
engine, under a Zig runtime layer. "How Bun scores well" is therefore mostly
"how JSC's tiering works," plus a real but separate contribution from Bun's
own runtime engineering. Both matter, but only one is transferable to a
Deegen-aligned interpreter-plus-baseline-JIT design; the other is a
different problem.

**JSC's four tiers, concretely**: every function starts in **LLInt** (Low
Level Interpreter), then tiers to **Baseline JIT** (~6 invocations or ~100
loop-back-edge executions), **DFG** (Data Flow Graph JIT, ~1,000
executions), then **FTL** ("Faster Than Light," ~10,000+ executions,
re-lowering DFG's SSA IR through JSC's own **B3 IR → Air** backend). Compile
cost scales with tier: DFG costs ~4x baseline compile time, FTL ~6x DFG
(<https://zon8.re/posts/jsc-internals-part2-the-llint-and-baseline-jit/>,
<https://webkit.org/blog/3362/introducing-the-webkit-ftl-jit/>).

This project's design already descends from JSC at the IC/register level —
the Deegen paper's own citations for tag registers, monomorphic IC, and IC
inline slabs are all Apple/JSC sources (§ per-benchmark Richards/DeltaBlue
section above). **What Deegen does not borrow from JSC, and Quench could
still adopt, is LLInt's shared-convention trick**: LLInt is written in
`offlineasm`, a portable macro-assembly DSL using logical register names
(`t0-t5`, `a0-a3`, `r0-r1`) mapped to physical registers per target,
specifically so the interpreter obeys the *same* calling/stack/register
convention the JIT tiers use. Tier-up from LLInt to Baseline JIT is
therefore a same-ABI jump to compiled code with an identical frame layout —
no state or frame translation step at all
(<http://wingolog.org/archives/2012/06/27/inside-javascriptcores-low-level-interpreter>,
<https://webkit.org/blog/9329/a-new-bytecode-format-for-javascriptcore/>).

**Concrete recommendation within Quench's 2-tier, no-optimizing-tier, no-deopt
scope** (matching `deegen-alignment.md`'s explicit design boundary): design
the interpreter's own stack/register/calling convention to be *identical* to
the fused-region stencil's external boundary convention (the same
`preserve_none`/GHCcc-equivalent convention already prescribed in the
RayTrace/NavierStokes/Crypto section above), so that promoting from
interpreted execution into a stencil region is a same-ABI jump, not a
marshalling step. This is distinct from, and complements, the register-
pinning fix already prescribed for Richards/DeltaBlue — that fix is about
the interpreter's own dispatch cost; this one is about making the
interpreter's frame shape pre-compatible with the JIT tier so tier-up itself
is free.

**B3/Air is explicitly not a borrowing target.** It is a full from-scratch
optimizing-compiler backend (SSA IR, instruction selection, register
allocation) built to be ~5x faster to compile than routing through LLVM
while matching its code quality
(<https://webkit.org/blog/5852/introducing-the-b3-jit-compiler/>) — a
different problem than copy-and-patch's fast, template-based codegen for
known shapes, and squarely inside the optimizing-tier scope Quench and
Deegen both deliberately exclude. Do not chase it.

**Startup/memory: only partly a JS-engine lesson.** Bun claims 8-15ms to
meaningful execution vs. Node's 40-120ms and roughly 40% lower memory. JSC's
LLInt-first design contributes near-zero interpreter startup cost by
construction (no compile-before-run step, matching Quench's own interpreter-
first posture already). But a real share of Bun's advantage is Zig-runtime
engineering independent of the JS engine — mimalloc, a scavenger thread that
frees memory during JS idle time, and lazy/partial-page zeroing, reported at
13-48% memory reduction on HTTP workloads specifically
(<https://bun.com/blog/bun-v1.4>). **This does not transfer as "build a
faster VM tier" alone** — allocator/runtime engineering is a separate lever
from anything in the stencil or interpreter sections above, worth tracking
as its own future item rather than folding into the JIT-tier work.

## Arena × GC: a hybrid memory design for web-app-shaped workloads

Two different things in this codebase are already called "arena" and must
not be conflated: `stencil_arena.rs` is a **code arena** (bump-allocated
executable memory for rendered stencil bytes, W^X, bounded at
`MAX_ARENA_BYTES`). This section is about a **different, currently
unaddressed** concern — how *JS value/object heap* memory should be managed,
which is what actually drives Splay's GC-bound cost and the suite's
allocation-heavy fixtures generally.

**Definitions, precisely:**

- **Arena allocation**: bump-pointer allocation into a contiguous region,
  with no per-object free — the entire region is discarded (or reset to its
  start pointer) at once when its *scope* ends. O(1) allocation, zero
  fragmentation, zero collection pause, but only correct when every object
  in the arena is guaranteed dead at scope exit — nothing may reference into
  it afterward.
- **GC (tracing/copying)**: allocation with no fixed lifetime scope;
  liveness is discovered dynamically by tracing reachability from roots.
  Necessary whenever an object's lifetime cannot be bound to a lexical or
  structural scope in advance — the general case for a JS heap, since
  closures, module-level state, and long-lived object graphs can outlive
  any single call or turn.

**Why this split matters specifically for "web app" shaped workloads**: web
request/response and UI-render workloads have a strongly **bimodal**
allocation lifetime distribution — a large population of objects that die
at a well-defined boundary (end of one HTTP request, end of one render
pass, end of one event-loop turn) and a much smaller population that
survives across many such boundaries (caches, session/app state, compiled
templates, module singletons). This is the same generational hypothesis
that motivates every generational GC (including V8's Scavenger, already
recommended for Splay above), but a request/turn-scoped **arena** can serve
the short-lived population *without paying any GC cost at all*, not just a
cheaper GC cost — the arena is simply reset, no tracing required, as long as
nothing escaped it.

**Prior art worth learning from directly**:

- **PHP's Zend Engine** is the canonical example of this pattern in a
  production web runtime: nearly all per-request allocation goes through a
  Zend Memory Manager arena that is discarded wholesale at request end, with
  no per-object collection needed for the common case at all — this is *the*
  reason PHP request handling has historically had very low GC pressure
  despite being a naively-written, heavily-allocating language runtime. See
  the [Zend Memory Manager internals](https://www.phpinternalsbook.com/php7/memory_management/zend_memory_manager.html).
- **jemalloc's arena model** (used by many high-throughput servers) shards
  allocation across per-thread arenas specifically to avoid cross-thread
  contention and to let an arena's memory be released back to the OS in
  bulk — a different axis (concurrency) from the lifetime-scoping axis
  above, but the same underlying idea that scoping allocation reduces
  bookkeeping cost. See [jemalloc's design doc](https://jemalloc.net/jemalloc.3.html).
- **V8's Scavenger young generation** (already cited above for Splay) *is*
  effectively a generational arena: bump-allocate into a semi-space,
  reclaim by copying survivors out and discarding the rest — the same
  mechanism as a request-scoped arena, except the "scope" is a size
  threshold and a collection pass rather than an explicit request/turn
  boundary, and it must still trace to find survivors, whereas a pure arena
  with no escapes needs no trace at all.

**Concrete hybrid design for Quench**:

1. **Nursery = arena, scoped to a natural JS-level boundary** — a top-level
   script evaluation, a microtask/turn, or (if Quench targets server-side
   request-handling patterns) one request handler invocation. Allocate all
   new JS values/objects into this arena by default.
2. **Escape detection at scope exit, not full tracing.** Rather than a full
   GC trace on every turn, check only what's reachable from the *few* known
   long-lived roots (module scope, closures returned to the host, objects
   stored into a global or into a promoted structure) — this is much
   cheaper than a full heap trace because the candidate escaping set is
   small relative to the arena's total allocation volume in a typical
   request/render-shaped workload.
3. **Promote survivors into a GC-managed (Scavenger-style, semi-space
   copying) heap** — exactly the mechanism already recommended for Splay.
   Everything that escapes moves once, from arena to GC heap; everything
   that doesn't escape is freed by simply resetting the arena's bump
   pointer — no per-object work at all.
4. **Bound the arena size explicitly** (matching `stencil_arena.rs`'s own
   `MAX_ARENA_BYTES` discipline for code memory) — an unbounded nursery
   arena defeats the RSS goal above; a request/turn that allocates
   pathologically should either spill to a fallback GC-direct path or be
   capped, not grow the arena without limit.
5. **Never make promotion or arena-boundary choice a fixture-shaped
   decision** — the scope boundary (turn/request/script) must be a property
   of the JS execution model applicable to any program, and the escape
   check must be a general reachability property, not a heuristic tuned to
   Splay's or any other fixture's specific object-graph shape (per
   `benchmark-integrity.md`).

This is additive to, not a replacement for, the Scavenger recommendation in
the Splay section above — the arena is the *fast path* that avoids invoking
the Scavenger at all for the common (non-escaping) case, and the Scavenger
remains the correct mechanism for whatever does escape.

## Using rustc/LLVM correctly for this workload

- **Release profile discipline**: measurements must come from
  `--release` builds (`cargo build --release`), never `debug` — the existing
  evidence rows already enforce this; don't regress it by measuring a debug
  artifact "just to check."
- **`--features execution-trace` is diagnostic-only.** It must never be the
  artifact a score is taken from (`performance-lanes.md`: "Diagnostic builds
  may trace, sample, or count the same VM, but never supply score numbers").
  Build a separate `CARGO_TARGET_DIR` for trace-enabled artifacts so they
  never get mistaken for the scored one.
- **LTO and codegen-units**: check `Cargo.toml`'s release profile for
  `lto = "fat"` (or at least `"thin"`) and `codegen-units = 1` before relying
  on any inlining-sensitive measurement (stencil call-boundary work
  especially) — cross-module inlining decisions change call-boundary cost
  measurements independent of any code change, so a profile flip alone can
  produce a false regression/win.
- **`target-cpu`**: pin an explicit `target-cpu` (e.g. `native` for local
  measurement, or a specific baseline like `apple-m1`/`x86-64-v2` for
  reproducibility across hosts) rather than the default generic target —
  default codegen leaves real SIMD/instruction-selection performance on the
  table for f64-heavy loops (RayTrace/NavierStokes) and won't match what a
  release binary built for distribution would get.
- **`panic = "abort"`** in the release profile removes unwind-table
  bookkeeping from every call boundary — directly relevant to the stencil
  call-boundary overhead this whole effort is chasing; verify it's set
  before concluding a boundary cost is irreducible.
- **Branch hinting**: `std::hint::likely`/`unlikely` (or
  `#[cold]` on slow-path functions) on interpreter dispatch hot/cold splits
  — this is the Rust-level equivalent of Deegen's hot/cold code splitting
  and JavaScriptCore's slow-path outlining; apply it to the generic
  `Branch`/`Unary` handlers task 074 already identified as Richards/
  DeltaBlue's bottleneck before assuming a bigger architectural change is
  needed.
- **Bounds-check elimination**: prefer iterator-based/`chunks_exact`-style
  array access over indexed loops where the access pattern allows LLVM to
  prove in-bounds statically — directly relevant to NavierStokes/RayTrace's
  array-heavy loops, and cheaper to try than region composition.
- **`cargo asm` / `cargo-show-asm` or raw `objdump -d`** on the release
  artifact to confirm a stencil's rendered bytes and a hot loop's compiled
  form actually match what the design intends, the same way the Deegen paper
  inspects real disassembly (its Figures 14/19) rather than trusting the
  optimizer's intent.
- **`llvm-objdump`/`llvm-readobj`** (already a documented toolchain
  requirement in `cpython-copy-patch-notes.md`'s CPython comparison) for
  inspecting stencil object-file relocations directly when debugging
  AArch64 relocation patching — the same tools CPython's own `_targets.py`
  build step uses to extract stencils.

## Finding architectural bottlenecks, not just implementation bugs

Most of the fixes above are implementation-level: tune a threshold, add an
IC, fuse more ops. Some of what limits this project's score is not
implementation-level at all — it's a consequence of an architectural
decision that no amount of local tuning inside that decision can escape.
Confusing the two wastes effort: patching an architectural bottleneck
produces diminishing, then negative, returns as the patch grows more
special-cased trying to compensate for a shape the architecture itself
imposes.

### How to tell the difference

Ask, about the component under investigation, **not** "how do I make this
faster" but: **"if this were designed today, from the profile data we now
have, would it have this shape at all?"** Three concrete signals that the
answer is no — i.e., that you're looking at an architectural bottleneck:

1. **The cost is concentrated at a structural seam, not in any function's
   own logic.** If a profile repeatedly shows time at a *boundary* — a
   bridge that re-enters a different execution mode, a call/return pair
   around otherwise-trivial work, a conversion step between two
   representations — no amount of optimizing what's on either side of that
   seam removes the seam itself. Only redesigning what's on each side of the
   boundary (or removing the boundary) does.
2. **Each fix requires more special-casing for a shrinking marginal gain.**
   A healthy optimization generalizes and its next increment is roughly as
   easy as the last (§ Healthy optimization above). An architectural
   bottleneck shows the opposite pattern: the first fix helps a little, the
   second fix requires carving out a special case to help a little more, and
   the third requires two more special cases for a shrinking gain. That
   trajectory is evidence the *shape* is wrong, not that more tuning is
   needed.
3. **A paired synthetic microbenchmark diverges from the real fixture
   result even after correctness is confirmed.** This has already happened
   twice in this project (the isolated numeric loop's +6-7% vs. the real
   subset's regression). When an isolated, correct measurement of "the
   mechanism works" doesn't predict the real-workload result, the gap is
   usually the architecture surrounding the mechanism — the boundary cost,
   granularity, or composition rule — not the mechanism itself.

### Known architectural bottlenecks in Quench today, and why patching them fails

These are not implementation bugs to fix in place — each requires
**stepping back to the design**, not iterating on the current code:

- **ARM64 stencil execution is still physically per-operation at the
  boundary, despite a general fact-keyed region table.** Most native leaves
  are one-operation entries; multi-operation `RegionRecord` rows currently
  enter one bridge that invokes canonical handlers per operation. The arena's
  lifecycle/caching code is clean (per the
  RayTrace/NavierStokes/Crypto evidence), so making that arena call cheaper
  cannot remove the seam. The scoped fix is to extend the existing
  build-time `RegionRecord.operations` sequences (tasks 048/049) and compose
  compatible templates with one entry/exit, not to add a runtime region
  builder.
- **The remaining RegExp fallback still has a tree-walking backtracking
  architecture with `Vec<State>` materialization at choice points.** This is
  now only one branch of the hybrid engine, not a description of every
  pattern. It remains a poor architecture for unsupported/capture-heavy
  cases because its state representation is allocation-heavy and can have
  exponential backtracking behavior. Optimize or replace that fallback only
  after a fresh profile identifies it as the source of the RSS/CPU cost; the
  regular ASCII path is already a compiled automata path (§ RegExp above).
- **The generic stencil region boundary still uses the platform C ABI.** The
  generic `NativeRegionPlan` enters an `extern "C"` context-pointer bridge;
  the Add→Add leaf has a local AArch64 preserve-none-equivalent shim, but
  that convention is not yet shared by the general region template. This is
  an architectural choice, not a hot-path inefficiency inside one function:
  every compatible region needs the same boundary contract
  (`preserve_none`/GHCcc-equivalent) before additional composition can pay.
- **The interpreter's dispatch loop and the stencil tier do not share a
  calling/register convention.** This is why tier-up (interpreter → stencil)
  costs a marshalling step at all (§ Bun/JSC section above, LLInt's
  shared-convention lesson). No amount of speeding up either side
  individually removes the translation between them; only making the two
  conventions the same, architecturally, does.
- **JS value/object heap allocation has no scope-bound fast path today**
  (§ Arena × GC above) — every allocation, short-lived or not, goes through
  the same general path. This is not a slow allocator to speed up; it's a
  missing architectural tier (an arena in front of the GC-managed heap) that
  no allocator micro-optimization substitutes for.

### Process: how to act on an architectural finding

1. **Name the architectural decision explicitly**, separate from any
   specific fixture or profile run — "regions are leaf-granular," not "the
   ARM stencil path is slow." A decision that can be named independent of
   any one measurement is the right unit to redesign.
2. **Reconcile the redesign with the existing task chain** before opening
   anything new. Tasks 044, 048, and 049 already own generated admission
   wiring, build-time whole-span growth, and bounded pre-rendered variants;
   extend those tasks in dependency order rather than creating a parallel
   architecture initiative.
3. **Re-profile after the redesign, not just after the last patch** — an
   architectural fix should be validated the same way as everything else in
   this document (paired same-tree, DWARF/`sample`, full gates), but expect
   the *shape* of the profile to change qualitatively (a seam disappearing
   from the hot path entirely), not just the magnitude of an existing
   symptom shrinking.
4. **Don't keep patching the old shape while the redesign is pending** — the
   diminishing-returns signal above is the cue to stop adding special cases
   to the current architecture and redirect the effort into the redesign
   task instead.

## Target architecture: as close to a JIT as possible, without a JIT

State this explicitly, as a named goal, rather than leaving it implicit
across the sections above: **the target is a system that gets as much of a
real JIT's throughput as possible using only build-time-enumerated,
copy-and-patch stencil composition — never speculation, never deopt.** A real
optimizing JIT
(V8 TurboFan, JSC's DFG/FTL) earns its speed by *speculating* — assume a
type/shape, compile against that assumption, unwind when wrong — which is
also where most of a JIT's complexity and correctness risk lives. Every
region this project admits is instead **described by build-time facts**
(for example, numeric types or a checked shape), and the runtime validates
those facts at the lookup boundary. Unknown or mismatching facts take the
complete interpreter path; there is no speculative code generation, unwind,
or deopt machinery. The bet is: how much of a real JIT's throughput does that
buy, with none of that complexity? This section names the redesign needed
to actually reach that ceiling, as opposed to the incremental fixes
elsewhere in this document.

### The hard constraint this section must not cross

This project's standing line, stated explicitly in two existing task
records, overrides everything below if there is ever a conflict:

- Task 048's non-goal: *"spans are chosen by build-time fact coverage,
  never runtime profile-guided selection of which code to compile."*
- Task 049's non-goal: *"Runtime-triggered generation of a new variant not
  already pre-rendered at build time... would cross this project's
  standing line into real-optimizing-JIT territory. Every variant is fixed
  at build time; only the selection among them happens at runtime."*

Every item below must be read through this constraint: **admission
generalization happens at build time, over declared fact coverage. Runtime
only ever performs a lookup/selection among build-time-enumerated
options — never a runtime walk, fusion, or codegen decision.** This is
precisely what keeps the whole approach on the "no speculation, no deopt"
side of the JIT-without-a-JIT bet stated above; crossing it would mean
building a real (and much more complex) optimizing JIT by accident.
Thus, any reference elsewhere to "walking a basic block" means the
build-time CFG/admission pass, never a runtime trace recorder or compiler.

The intended data flow is therefore one pipeline, not a second plan universe:

| Phase | Owner | Representation | Allowed effect |
| --- | --- | --- | --- |
| Declare coverage | `build.rs` / CFG facts | operation sequence + `FactState` coverage | enumerate bounded rows and render their stencils |
| Identify a row | `stencil_fact.rs` | `RegionKey` digest | derive one stable identity |
| Select at runtime | `stencil_select.rs` | `RegionKey → RegionRecord` | perform a lookup; miss goes to the complete VM |
| Execute | physical plan / arena | selected bytes + canonical fallback | patch, publish, and run while the record is valid |

The sequence, facts, and identity are consequently data. `machine.rs` may
have different physical wrappers where calling conventions or value layouts
really differ, but those wrappers consume the same `RegionRecord`; they must
not become another source of admission rules or workload-specific semantics.
`render_or_get` may copy and patch an already-declared stencil into the bounded
arena at runtime; that lifecycle operation does not create a new sequence or
variant.

### The finding, corrected — check the existing mechanism before assuming a gap

An earlier pass at this section diagnosed the redesign target purely from
`machine.rs`'s `Native*Plan` structs (`NativeBinaryPlan`,
`NativeAddChainPlan`, `NativeMovePlan`, `NativePropertyPlan`,
`NativeDispatchPlan`, `NativeRegionPlan`, `BaselinePlan`,
`OptimizingPlan` — `NativeAddChainPlan` is concretely a hand-authored
struct for exactly one fusion pattern, `Add→Add`), without first checking
whether a general mechanism already exists elsewhere. It does:
`stencil_fact.rs`/`stencil_select.rs` already define `RegionId`,
`RegionKey` (derived from **digested facts** or a declared opcode sequence via
`RegionKey::from_facts`/`from_opcodes`), `Stencil`, `RegionRecord`, and generic
`select_stencil(key)`/
`select_region(key)`/`dispatch_region(...)` lookup functions — a
fact-keyed, generic region-selection system, not a struct-per-pattern one.

**The audit answer is now clear**: the `Native*Plan` types are physical
lifecycle wrappers around the existing build-time `RegionKey` records. They
own arena/cache/lifecycle state and typed entry ABI; they do not define a
parallel fact selector. The remaining gap is to share the physical template
and boundary across longer build-time-enumerated sequences, not to invent a
new runtime selector or region walker.

### Reconcile with existing tasks before scoping new work

`tasks/index.json` already contains closely related, sequenced work — check
these records before creating anything new, and prefer extending them:

- **Task 044** — "Generate region-admission and CFG-soundness-test
  boilerplate," deliberately deferred until after tasks 040/041 land so the
  generated pattern is extracted from 3-5 real regions rather than guessed
  prematurely. This is close to (possibly exactly) the "route admission
  through one general, declarative mechanism instead of hand-written
  per-region wiring" idea.
- **Task 048** — "Grow region scope from hot glue sequence to whole loop
  body / small function," already scoped to `stencil_fact.rs`/
  `stencil_select.rs`/`build.rs`, already carries the build-time-only
  non-goal quoted above. Its seven-op `LOOP_BODY` declaration and bounded
  executor cover the admission/span side; the current bytes are still
  bridge-backed, so native fallthrough composition remains an explicit gap.
- **Task 049** — pre-rendered, build-time-enumerated variant selection via
  `RegionKey` lookup — already the correct shape for "more than one
  admitted case per region," bounded (2-4 variants, matching the existing
  `IcStubChain` ceiling elsewhere), explicitly not runtime codegen. Its
  evidence-backed no-go means no new variant family is justified until a
  reusable finite fact set is measured.

**No new task number is needed for this redesign.** The audit confirms that
044/048/049 cover the selector, the admission/span machinery, and the bounded
variant-selection discipline (with 049's current no-go preserved). This
section therefore accelerates and prioritizes that existing chain rather than
competing with it.

### What likely remains a real, additional gap either way

Independent of the reconciliation above, these are not currently covered
by 044/048/049's stated scope:

1. **A shared physical template and region boundary ABI**
   (`preserve_none`/GHCcc-equivalent, per § RayTrace/NavierStokes/Crypto) —
   belongs in the template interface itself so every build-time-enumerated
   sequence inherits the convention, rather than being retrofitted per-plan.
   The Add→Add leaf has a local AArch64 shim, but the current `LOOP_BODY` row
   is bridge-backed; the next implementation must prove that a compatible row
   can execute its operations in native fallthrough before broadening
   admission.
2. **Unifying the interpreter's and the composed region's calling
   convention** (the LLInt/Bun-JSC lesson, § How Bun actually reaches its
   score) — a prerequisite for region-scope growth to fully pay off, since
   a bigger region only helps if tier-up itself doesn't still cost a
   marshalling step at the boundary.
3. **Inlining the allocation fast path into composed regions**, once the
   § Arena × GC nursery exists — real JITs (V8's Sparkplug/TurboFan) inline
   a bump-pointer check directly into generated code for object
   construction, calling into the runtime GC only on overflow, rather than
   calling back into the general allocator per `new` inside a hot loop
   (RayTrace's `Vector`/`Point` construction, say).

### Validating any of this, not just the next incremental fix

Whichever of the above turns out to be real work, re-run
`tools/instruction-category-ledger.mjs` with the stencil category (§ 6a)
before and after, and expect a **qualitative** change, not just a magnitude
shrink: native hit rate should rise across a *broad* set of loop-shaped
fixtures at once, not one benchmark the way the original `NativeAddChainPlan`
did. Re-apply § Finding architectural bottlenecks' diagnostic questions
before declaring any of this done.

## Per-benchmark attack vectors

Read these as **prior findings to verify, not conclusions to execute.** Each
one records what a specific profile, on a specific tree, showed at the time
it was written — the classification tables and process in
§ Profiling/DWARF workflow and § Finding architectural bottlenecks are how
you check whether it still holds, extend it, or replace it with a better
answer your own data supports. The highest-value outcome from working
through a fixture below is not "I implemented the suggested fix" — it's "I
collected fresh data, confirmed or overturned the prior finding, and can
explain why" recorded in `architecture-evidence.md`.

### 1. RegExp — historical score 13.7; current targeted score 61.7

**Why it's the top-priority fixture**: geomean math. With RegExp an order of
magnitude below the other seven, no combination of gains elsewhere reaches a
high aggregate — RegExp must close by roughly the same proportion as
everything else, not be left behind as "someone else's problem."

**Current architecture and evidence** (`regexp_backend.rs`): Quench now has a
guarded hybrid. Narrow literal/class/repetition shapes use `regexp_native`;
other regular ASCII patterns use the cached `regex` automata backend;
unsupported constructs and Unicode-sensitive cases retain the repository-owned
tree-walking fallback. The compiled path still tracks
captures when requested, while that fallback's
`sequence_options`, `repeat_options`, `match_options`, and `reverse_options`
still materialize `Vec<State>` at choice points, which is consistent with the
allocation pressure seen in the trace-enabled diagnostic artifact (its
retained trace snapshot reached 1.7--1.8 GiB; that is not a scored-process RSS
value). The compiled ASCII path now reuses its
capture-location workspace and uses an allocation-free search for patterns
without captures; this is a physical representation cleanup, not a semantic
fork. The targeted automata comparison was output-equal and reduced wall
time, but the retained trace artifact did not provide a comparable RSS win. A
fresh trace attributes the remaining pressure
to match-result/object construction (1.17M match results and 3.21M object
property clones), not compilation (328 cache misses), so further work must
attack that representation rather than repeatedly changing the parser.
The repository fallback no longer applies a fixed 4096-state truncation: a
finite but adversarial pattern may consume more memory, yet it cannot silently
lose a valid alternative. The QuickJS comparison below is therefore a guide
to representation (compiled opcodes and inline choice-point storage), not a
reason to weaken ECMAScript completeness.

**Attack vector**: extend the compiled matching architecture and reduce the
remaining fallback cost, in two layers so the general (non-cheating) path
stays correct for every JavaScript program, not just the fixture's specific
pattern shape:

- **Fast path — extend or validate the existing Thompson-NFA/automata path**
  for the common case (no backreferences, no complex lookaround): compile the
  pattern once, then execute a linear-time NFA simulation with capture
  tracking. This is already the guarded path for regular ASCII patterns; any
  extension must preserve its AST-based classification and measure RSS as
  well as time. Reference implementation to study directly:
  `../quickjs/libregexp.c` (a local checkout) — Bellard's `REOP_*` opcode
  bytecode VM with a `DynBuf byte_code`, plus its own recorded TODO for a
  "lock step execution mode = linear time execution guaranteed" fast path
  for exactly this pattern class. Its `REExecContext` also embeds a 32-entry
  `static_stack_buf` and grows heap state only on overflow; that is a concrete
  representation pattern to consider for Quench's fallback choice points,
  subject to measuring retained capacity against RSS. Also study
  [Russ Cox, "Regular Expression Matching Can Be Simple and Fast"](https://swtch.com/~rsc/regexp/regexp2.html),
  [RE2's `nfa.cc`](https://github.com/google/re2/blob/main/re2/nfa.cc), and
  the Rust ecosystem's own
  [`regex-automata` PikeVM](https://docs.rs/regex-automata/latest/regex_automata/nfa/thompson/pikevm/index.html)
  (worth a build-vs-buy check: does project dependency policy allow adopting
  `regex`/`regex-automata` directly rather than hand-rolling the NFA
  simulation? If the license and dependency posture allow it, that is very
  likely less risk than a hand-written engine).
- **Fallback path — complete repository-owned semantics** for backreferences,
  unsupported lookaround, Unicode-sensitive behavior, and capture cases that
  the automata backend does not currently represent. This path is kept for
  correctness; its allocation/backtracking cost is the remaining algorithmic
  question, not permission to weaken JavaScript semantics.
- **What generalizes vs. what would be cheating**: the fast-path
  classification (does this pattern need backreferences/lookaround?) must be
  a property of the parsed pattern's AST, checked the same way for every
  regex literal in any program — never a check against the specific patterns
  used by the RegExp fixture. Codex has already landed a first cut of this
  split: narrow `regexp_native` handles simple literal/class/repetition
  patterns, the cached `regex` automata handles regular ASCII (including
captures), and the repository fallback handles unsupported or Unicode
cases. A same-tree targeted run measured the automata candidate at **59.3 /
54.17 s** versus **22.8 / 137.41 s** with the compiled backend disabled,
both output-equal; the **1.79 GiB** peak was from the retained trace artifact,
  not a production-process memory gate. Treat this as a targeted backend
  result, not a full-suite score, and confirm the classification boundary is
  pattern-shape-general before extending it further.
- **Data to collect**: per-fixture peak RSS before/after (not just
  aggregate), and a synthetic clone using different pattern text with the
  same structural class (same use of alternation/repetition/anchors) to
  confirm the fast path's win generalizes.

### 2. Richards — score 56.2; DeltaBlue — score 48.6

**Why grouped together**: both are dispatch-loop-bound, not stencil-reachable
or regex-reachable. Task 074 already profiled both and found the slow lane is
generic `Branch`, `TraceSite`, `CheckInitialized`, and `Unary` handler
overhead in the ordinary interpreter dispatch loop — not property lookup,
not method dispatch specifically, not anything the stencil tier currently
touches.

**Attack vector, layered by cost/risk**:

1. **Interpreter-level inline caching (call IC + generic IC), Deegen-style**
   (arXiv:2411.11469, §5). Deegen distinguishes *call IC* (monomorphic,
   optionally promoted to polymorphic, with "call IC check hoisting" to drop
   a redundant type-check once the IC has proven the callee is a function)
   from *generic IC* (a user-specified `λ_i`/`λ_e` pair covering arbitrary
   IC semantics, e.g. property access). Both are implemented as
   Copy-and-Patch stencils chained by direct `jmp` patching, not function
   calls. Check first whether Quench's interpreter has *any* IC today; if
   not, this is likely the single highest-leverage item in this whole
   document, because it turns Richards/DeltaBlue's method-dispatch and
   property-access sites from generic handler dispatch into a cached fast
   path **before** any JIT tier is involved.
2. **Register-pinned dispatch loop (GHCcc-equivalent).** Deegen pins six VM
   states (thread context, stack base, current bytecode, function context,
   two tag registers) into the six callee-saved registers of the *C*
   calling convention specifically so the interpreter never saves/restores
   them across a C call — using LLVM's `GHCcc` (guaranteed tail-call, no
   callee-saved registers, all arguments in registers) internally for
   continuation-passing dispatch, while presenting a normal C-ABI-compatible
   register set externally. If Quench's dispatch loop reshuffles registers
   on every bytecode, this compounds with item 1 as the two biggest levers
   for Richards/DeltaBlue specifically.
3. **CPython PEP 659-style per-instruction adaptive specialization**
   ([peps.python.org/pep-0659](https://peps.python.org/pep-0659/)):
   generalizes quickening to *any* generic opcode, not just IC sites — each
   handler carries a hit counter and rewrites itself in place to a
   specialized variant after N hits. CPython reports 25-30% of instructions
   specializable and up to 50% interpreter speedup from this alone. Apply it
   specifically to the `Branch`/`Unary` handler families task 074 already
   named.
4. **Computed-goto (indirect-threaded) dispatch** instead of switch-based
   dispatch — modest (~5% per the literature,
   [Eli Bendersky](https://eli.thegreenplace.net/2012/07/12/computed-goto-for-efficient-dispatch-tables)),
   because each dispatch point gets its own branch-predictor history instead
   of sharing one jump table. Cheap and low-risk; treat as a supplementary
   fix, not a primary lever.

**Why not stencils here**: confirmed by task 074's own profiling — nothing
in the region-composition/stencil-fusion work below reaches this bottleneck.
Do not redirect stencil effort at Richards/DeltaBlue; it will not move them.

**Literature gap, noted honestly**: no published algorithm targets
DeltaBlue's constraint-propagation shape or Richards' object-graph-traversal
shape specifically — items 1-4 above are the applicable *general* dispatch
levers, not benchmark-specific tricks, which is itself the correct anti-cheat
posture for these two fixtures.

### 3. RayTrace — score 166; NavierStokes — score 212; Crypto — score 16.9

**Why grouped together**: the only fixtures reachable by the copy-and-patch
region-stencil tier — numeric/array-heavy loop bodies. RayTrace and
NavierStokes are floating-point vector/array math; Crypto is
bigint/bitwise digit-array work.

**Current state, verified against the live code**: exactly one composed
region exists (`add_chain`: a 2-op `Add→Add` fusion, admitted only when the
second `Add` consumes the first result). Its own targeted subset regressed
on measurement: Crypto/RayTrace/NavierStokes subset geomean went from
84.0963 (fallback) to 82.1625 (native) — not diluted, actually worse. A
synthetic isolated 5M-iteration loop shows +12% in isolation; that gain does
not survive contact with real benchmark code.

**Root causes, in priority order** (per direct code inspection, not
speculation):

1. **Wrong calling convention at the region's external boundary.** The
   fused entry point is `extern "C" fn(f64, f64, f64)` — the standard
   platform C ABI. The Copy-and-Patch paper
   ([arxiv.org/pdf/2011.13127](https://arxiv.org/pdf/2011.13127)) is
   explicit that this is the wrong choice: it prescribes the GHC calling
   convention specifically (all registers caller-saved, all parameters in
   registers, no prologue/epilogue assumptions) to avoid exactly the
   marshalling cost a standard C ABI call pays. Fix this once, correctly, at
   the boundary before any further fusion work — every subsequent stencil
   inherits the same boundary cost if it's wrong.
2. **Fusion depth is far below any production break-even point.** No
   published copy-and-patch implementation reports a win at 2-op
   granularity. The WebAssembly copy-and-patch baseline compiler that beats
   Liftoff by 39-63% fuses whole basic blocks
   ([sillycross/WasmNow](https://github.com/sillycross/WasmNow)); the
   original paper's highest-impact stencils are 2KB+/80+ holes — whole
   operations, not instruction pairs. The 2-op regression is expected at
   this granularity, not evidence the approach is broken.
3. **The arena implementation itself is clean** — `stencil_arena.rs`
   correctly gates `mprotect`/icache-flush behind a one-time `executable`
   flag (not per-call), has no redundant `Rc` cloning on the hot path, and
   does a single cache lookup per hit. Do not spend further effort
   re-auditing the arena's lifecycle/caching code; the loss is structural
   (ABI + fusion depth), not hidden inefficiency there.

**Sequencing**:

1. Fix the region boundary ABI (item 1) first — cheapest, most
   literature-certain fix, and a prerequisite for every later measurement to
   mean anything.
2. Grow fusion to whole loop-body basic blocks using fallthrough/tail-jmp
   dispatch *inside* the region (direct branch between ops, one `ret` only
   at the region's exit — Deegen's "Jump-to-Fallthrough" pattern, §3/§6 of
   arXiv:2411.11469), not more 2-3 op micro-chains. Mirror
   [V8 Sparkplug's](https://v8.dev/blog/sparkplug) trick of keeping the
   region's internal state layout identical to the interpreter's frame
   layout, so no marshalling is needed until the region's single exit.
3. Re-run **both** the synthetic loop **and** the real
   Crypto/RayTrace/NavierStokes subset, paired same-tree, after every step —
   the synthetic loop has now produced two false positives and must not be
   trusted alone.
4. For Crypto specifically, once loop-body fusion covers the numeric-loop
   shape it shares with RayTrace/NavierStokes, evaluate **Karatsuba
   multiplication** for BigInt digit arrays (O(n^1.585) vs. schoolbook
   O(n²), the threshold-gated approach V8's own BigInt implementation uses;
   see [BearSSL's bigint design notes](https://www.bearssl.org/bigint.html)
   for the Karatsuba/Montgomery-reduction pairing) — but only after
   confirming the fixture's actual bottleneck is large multiplication or
   modular exponentiation, not just shifts/bitwise ops that loop-body fusion
   already covers.

**ARM64-specific note**: the Deegen paper (arXiv:2411.11469, Limitations §3
and Conclusion) is explicit that Deegen **targets x86-64 only** and lists
ARM portability as unstarted future work — *"portability still requires
non-trivial work due to our lack of access and experience with other
ISAs."* The AArch64 relocation/trampoline mechanics Quench needs (direct
branch when in range, else `ldr x8, literal; br x8` trampoline plus explicit
I-cache maintenance — `sys_icache_invalidate` on macOS, `__clear_cache`
elsewhere, both already correctly implemented in `stencil_arena.rs`) come
from CPython's own AArch64 JIT work instead, which is a mature reference:
[PR #123872](https://github.com/python/cpython/pull/123872) (AArch64
trampoline generation, reports **0.8-1.5%** wall-time and **0.6-0.8%**
memory improvement — small, because it only pays off once composed regions
already exist), [PR #120250](https://github.com/python/cpython/pull/120250)
(trampoline reuse), and
[issue #146128](https://github.com/python/cpython/issues/146128) (a real
`patch_aarch64_33rx` relocation safety bug found in production — useful
precedent for what to test defensively once Quench's AArch64 relocation
patching grows past single-leaf stencils). Budget ARM-specific trampoline
polish *last*: it is real, necessary work, but the register-pinning/ABI and
fusion-depth fixes above must land first, and CPython's own numbers set the
expectation that pure trampoline tuning is a low-single-digit-percent lever,
not the primary one.

### 4. Splay — score 373 (closest to the reference machine)

**Attack vector**: GC/allocation-bound, not arithmetic or dispatch-bound —
none of the above tracks reach it. Adopt a **V8-style Scavenger**: bump-
pointer allocation into a "From" semi-space for young objects, with a Cheney
copying collection that traces live objects from roots and compacts them
into an empty "To" semi-space on collection — O(1) allocation, zero
fragmentation, no free-list bookkeeping. See
[v8.dev/blog/trash-talk](https://v8.dev/blog/trash-talk) and
[Wingolog's account of V8's GC evolution](https://wingolog.org/archives/2023/12/07/the-last-5-years-of-v8s-garbage-collector).
Before investing, check whether Quench's current allocator already does
something equivalent — this is only worth building if it doesn't.

### 5. EarleyBoyer — score 73.8

**Attack vector**: recursion/call-boundary and frame-allocation cost, not a
numeric-loop or dispatch-generic problem. The same call-IC infrastructure
from the Richards/DeltaBlue track (§2 above), applied to call sites
specifically — monomorphic call IC plus cheap fixed-arity frame setup that
skips `arguments`-object materialization when arity and calleesite shape are
statically known and monomorphic. No separate algorithm class needed beyond
what's already prescribed for Richards/DeltaBlue; this fixture shares the
same underlying fix.

## What this document does not claim, and what it asks of you instead

No item above is a mandate to implement blind — each requires the
generalization check and identity scan in the anti-cheat section before it
counts as done, and several are explicitly gated on verifying the fixture's
actual bottleneck first (Karatsuba on Crypto; the Scavenger on Splay's
current allocator). A high score on this suite is evidence of closing real,
general performance gaps; it is never itself the goal ahead of
`benchmark-integrity.md`'s constraints.

This document cannot substitute for the judgment it took to write it, and it
will go stale as the codebase changes — a per-benchmark finding recorded here
reflects one profile on one tree at one point in time. **The strategy is,
and remains: collect your own data before deciding, use the profiling and
architectural-bottleneck methods above to interpret it, treat everything
named in this document as a hypothesis your data can confirm, refine, or
overturn, and record what you actually found — not what this document
predicted — in `architecture-evidence.md`.** The named algorithms and prior
findings exist to save you from starting cold, not to save you from having
to look.
