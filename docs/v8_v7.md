# V8-v7 measurement

Run from the repository root with the clean production build and the exact
V8-v7 submodule revision pinned by the repository. Use Apple M4 for the primary
performance qualification; the same runner also supports Linux x86_64 so the
`v2` and `v2-cloud` branches can use one source and report format. Start with
an engine preflight; it records versions and proves that Node and Bun are
running without JIT:

```sh
cargo build --profile production -p quench-node
cargo run --release -p quench-bench -- --preflight-only \
  --quench target/production/quench-node \
  --qjs /path/to/qjs --node node --bun bun
cargo run --release -p quench-bench -- --all --runs 11 --timeout-ms 300000 \
  --quench target/production/quench-node \
  --qjs /path/to/qjs --node node --bun bun \
  --checkpoint target/v8-v7-qualification.checkpoint.json \
  --out target/v8-v7-qualification.json
cargo run --release -p quench-bench -- --analyze target/v8-v7-qualification.json \
  --out target/v8-v7-qualification-analysis.json
```

`--checkpoint PATH` atomically records each completed fixture. If the runner is
interrupted, resume with the same engine, round, and timeout arguments, replace
`--checkpoint PATH` with `--resume PATH`, and keep the final `--out` path. Resume
rejects checkpoints whose source revision, host, pinned corpus, engine identity,
round count, timeout, or fixture inputs differ. Completed valid fixtures are
reused; an incomplete or invalid fixture is rerun from its first round.

The runner accepts one fixture path or `--all`, plus engine paths, `--runs`,
`--timeout-ms`, `--checkpoint` or `--resume`, and `--out`. Each matched round stores all four raw engine
samples together with execution order, exit status, score, wall time and
external process accounting. The report records executable hashes, versions,
effective argv and the sanitized measurement environment, JIT proof, fixture
hashes, source revision and host. Linux reports include the visible cgroup CPU
quota and memory limit. Quench and QuickJS use their interpreters; Node runs with
`--jitless`; Bun sets `BUN_JSC_useJIT=0` and verifies `useJIT=false` with a
JSC option dump before timed runs. `--preflight-only` performs these checks
without running a benchmark.

Every sample needs a finite Score and measured maximum RSS. The report's
`qualification_ready` is true only for all eight fixtures, at least eleven
matched rounds, a clean checkout of the pinned benchmark submodule, and a clean
source tree. One-fixture and short-round runs are diagnostics only. `--out`
uses create-new semantics so existing evidence is never overwritten. The runner
uses the operating system's `wait4` accounting directly, with its own process
group timeout. Linux reports peak RSS in KiB and macOS reports it in bytes; the
runner normalizes both to bytes and stores available page-fault and context
switch counts.

The single report schema records `host.process_metrics_backend` so platform
counters keep their provenance. macOS uses `/usr/bin/time -l`, recording
instructions and cycles along with RSS. Linux uses `wait4` resource accounting;
it normalizes `ru_maxrss` from KiB to bytes and records available page faults,
reclaims, and context switches. Linux instruction and cycle counters remain
unavailable instead of being presented as M4-equivalent data. Checkpoints bind
to the same source, host, engine identities, corpus, rounds and timeout, so a
partial M4 campaign cannot be resumed as Linux64 work or vice versa.

The eight fixtures are Crypto, DeltaBlue, EarleyBoyer, NavierStokes, RayTrace,
RegExp, Richards and Splay. Each engine executes the same materialized suite
wrapper. Never alter the stock harness iteration counts or validations to
manufacture a qualification score.

The analysis command rejects incomplete, dirty, unpinned, or mismatched reports.
It compares each engine median with Quench's median and uses 100,000 paired
bootstrap resamples of the difference between medians for a 95% percentile
interval. It resamples the same round indices for Quench and the comparator,
uses a deterministic recorded seed per fixture and metric, and fails a fixture
comparison when either interval includes a tie or either median ranks lower.
The analysis JSON retains ordered raw Score, RSS and wall-time rows, engine
commands and JIT proofs, and hashes for the suite inputs and runner binary; it
also binds the full four-engine report by SHA-256.

Operational defaults and host dependencies: the default timeout is five
minutes; the runner clears inherited variables and supplies only `PATH`,
`HOME`, `TMPDIR`, `LANG`, `LC_ALL`, `TZ`, and the explicit Bun no-JIT setting.
It uses `shasum -a 256` or `sha256sum` for hashes. Linux uses `wait4` for RSS
and process status; macOS uses `timeout` and `/usr/bin/time -l` to retain its
instruction and cycle counters. The runner refuses to start when
`QUENCH_EXEC_TRACE` is inherited; diagnostic counters belong in a separate
instrumented run.

`valid` requires successful scored runs with finite scores and RSS; it does not
establish full conformance. `output_equal` ignores scores and benchmark result
lines, so it is a smoke check rather than a semantic verdict.
Timeouts remain missing performance evidence. Retain partial results without
publishing them as a complete aggregate. The Rust runner stops repeating a
fixture after the first invalid engine round, records the partial samples, and
continues with the remaining fixtures; this bounds failure diagnosis without
turning an incomplete fixture into a valid result.

## Fixed-work diagnostics

For fixed-work A/B gates, add `--fixed-work`. This measurement-only mode uses
the same materialized `base.js` and fixture, calls each benchmark's own
`Setup`, invokes its `run()` either the plan's named number of times or zero
times, and calls `TearDown` in `finally`. The counts are recorded in the separate
`fixed_work_diagnostic` schema 4. Each raw sample also records host load averages
and the top five CPU consumers immediately before and after the child process;
host-snapshot command failures remain explicit in the sample. This metadata is
collected outside the child's measured interval. A fixture's Setup may itself
perform warmup work, so zero-work measures process startup, parse, Setup and
TearDown together. The report preserves both process totals and derives a paired
marginal cost per `run()` from `(work - setup_only) / total run calls`; RSS
remains a raw process maximum because subtracting maxima has no useful memory
interpretation. `--runs` still selects paired rounds, not benchmark
iterations. Fixed-work reports verify completion markers and compare semantic
output for both work counts, but do not compute Score and can never set
qualification readiness. Use the stock adaptive harness for task-61 milestones
and qualification.

For contention-aware all-eight fixed-work change gates, use the resumable
`task61-fixed-work-guard` tool. It retains the same runner and pinned Quench
pair, tops up only fixtures below seven clean pairs, and records each raw report
and the derived decision together. The checkpoint can be resumed in a later
quiet window; its policy and current evidence are documented in the
[resumable guard record](../evidence/task61-fixed-work-resumable-guard-2026-10-10/README.md).

Run a diagnostic against all four engines:

```sh
cargo run --release -p quench-bench -- --all --fixed-work --runs 3 \
  --quench target/production/quench-node \
  --qjs /path/to/qjs --node node --bun bun \
  --out target/v8-v7-fixed-work.json
```

For an alternating Quench-only pair, set `--quench` to the baseline and
`--quench-peer` to the candidate. The two binaries run in rotated order for
each round with identical fixture work. This mode does not launch reference
engines, so correctness remains covered by the regular Node-oracle and
conformance gates:

```sh
cargo run --release -p quench-bench -- --all --fixed-work --runs 11 \
  --quench target/pinned/baseline/quench-node \
  --quench-peer target/pinned/candidate/quench-node \
  --out target/v8-v7-fixed-work-pair.json
```

The current work plan is explicit in `quench-bench/src/main.rs`: Crypto 4,
DeltaBlue 40, EarleyBoyer 3, NavierStokes 5, RayTrace 10, RegExp 1, Richards
100, and Splay 300 calls to `run()` per benchmark. These values were adjusted
from one-round Quench instruction and cycle pilots to target
roughly one to three seconds of guest work in Quench and should be recalibrated
only with a recorded fixed-work pilot when benchmark or runtime behavior
changes materially. macOS reports instructions and cycles; Linux leaves those
fields absent and reports `wait4` RSS/process accounting. Compare identical-work
Quench cycles and elapsed time for mechanism gates, retaining instructions as
attribution. For cross-engine interpreter-speed triage, compare paired marginal
per-`run()` cycles and elapsed time; use setup-only totals to assess startup and
fixture-setup cost.

The older Quench-only recorder remains available for focused diagnostics:

```sh
node tools/record-v8-evidence.cjs --binary target/production/quench-node --runs 5 --timeout-ms 300000 --out target/v8-new-attempt.json
```

Choose a new filename: this tool does not prevent overwrites and does not
provide the Rust runner's external RSS accounting. Use the Rust runner for
reproducible four-engine reports.

For attribution, use a separate trace build and the micros `diagnose` command.
Raw V8 fixture files and micros registration modules are not standalone
workloads. Counters do not measure CPU shares.
