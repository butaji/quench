# Shared array operations

`Array.prototype.shift` uses the shared VM builtin in every execution mode. Its dense path applies only to an ordinary extensible array with writable length, no mapped arguments or indexed descriptors, no sparse length, and a present own data element at every index below the observed length. These facts prove that all reads and writes address ordinary own data properties, deletion succeeds, and prototype getters or setters cannot run.

The operation mutates the existing copy-on-write element storage through its canonical mutation boundary. Moving existing values within the same array introduces no new collector edges. Removing the first element updates the intrinsic dense length; no guest callback or allocation occurs between removal and returning the value. The result remains the original value, including object identity and explicit `undefined` elements.

Receivers outside the guard use the original ordered property algorithm. Holes and prototype properties, proxies, indexed accessors and attributes, mapped arguments, readonly length, sealed/frozen arrays, and ordinary array-like objects retain their original effects, exceptions, and partial mutations. No stream, fixture, benchmark, or source identity participates in dispatch.

The specialized and unspecialized regression `regression_array_shift_guards_preserve_order_and_copy_on_write` checks identity, literal storage isolation, inherited getter/setter order, own accessors, readonly-length partial mutation, integrity constraints, ordinary objects, and mapped arguments. Node stream fixture deadlines and iteration benchmark diagnostics do not establish a production performance claim.

The retained full pinned Node parallel sweep after this change measured 1,418 passes, 676 skips, 2,518 failures, 115 timeouts and zero crashes across 4,727 fixtures, with four workers and unchanged 30-second deadlines. Queue wraparound gained a pass and no prior passes were lost. [Full outcomes and provenance](../evidence/task20-node-dense-shift-full-2026-10-13.json) retain the actual failing runner exit, binary hashes, inventory, fixture restoration and memory counters. This is a functional checkpoint; the complete Node compatibility goal remains open.

# Array storage proofs

A lane loop's element reads and in-place stores of a register base the loop does not redefine run through the lane run's array storage proofs (`heap/array_proofs.rs`, `specialize_proved_arrays`). The first access proves the record array the base names: where its elements live, its length, and whether a store of a value the write barrier passes may replace a present element in place (not frozen, no indexed descriptors or mapped arguments, backing not shared). Each later access checks only that its slot still proves the base value and the index is below the proved length; a hole, any other value or a missed proof runs the generic record, which is exact.

The heap retires every proof of the running lane before any change that could falsify one: structural access to an array's elements (`ArrayObject::elements_mut`, the only path that replaces, grows, shrinks or detaches a backing), a backing gaining an owner, the array being frozen or gaining indexed descriptors or an arguments map, and every collection. The lane retires them when a nested run enters and when it restores a context a native's callback copied. No profile, fixture or benchmark identity participates; a record's base register only selects its proof slot. The regression `proved_element_records_keep_semantics_when_array_storage_changes` checks reads and stores against Node across truncation, growth, freezing, sharing, holes, splices, accessors, inherited elements, in-lane appends and truncation, and non-array bases.
