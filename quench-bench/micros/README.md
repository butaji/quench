# VM micro-corpus

This directory contains 500 standalone, numbered JavaScript programs:
`001.js` through `500.js`. They are generated by [`generate.mjs`](./generate.mjs),
which is the single source of truth for the cases and their manifest.

The corpus is arranged as ten groups of 50. Each group targets a different VM
surface, and depth increases from 1 to 50 within that group. The first five
cases of every ten rotate through semantic properties; the other half of each group runs bounded,
workload-shaped kernels. This combines increasingly deep hot paths and
distinct observable semantics with realistic dynamic-language behavior:

| Cases | Surface |
| --- | --- |
| 001–050 | primitives and numeric operations |
| 051–100 | control flow and abrupt completion |
| 101–150 | dense/sparse arrays and algorithms |
| 151–200 | object shapes, descriptors, prototypes, accessors, symbols |
| 201–250 | closures, calls, recursion, constructors, classes |
| 251–300 | Unicode strings, templates, RegExp, normalization |
| 301–350 | iterators, generators, destructuring, spread |
| 351–400 | Map, Set, WeakMap, identity, iteration |
| 401–450 | typed arrays, buffers, DataView, BigInt |
| 451–500 | Proxy, Reflect, JSON, Date, errors, Function |

The workload kernels deliberately cover the shapes of the classic V8 v7
benchmarks already vendored in this repository: numeric relaxation (Navier–
Stokes/raytrace), constraint propagation (DeltaBlue), task queues (Richards),
lexing/regular expressions (Regexp/Earley-Boyer), and hash/table lookup
(Crypto/Splay). They are fresh bounded kernels rather than benchmark-name
dispatch or copied score logic, so optimizations that help them are reusable
JavaScript optimizations.

The exact upstream-style inputs remain available in
`js-engine-benchmark/v8-v7/`; the manifest records all eight source fixtures.
This corpus uses smaller deterministic kernels so each numbered case can be
measured independently without turning the VM into a benchmark dispatcher.

## Design-neutrality guard

These files are intentionally not a VM design specification. They use only
observable ECMAScript behavior and make no assumptions about bytecode format,
dispatch strategy, value tagging, object layout, inline caches, JIT tiers, or
garbage collector. The 200-point performance checklist is a source of
hypotheses to measure in the VM; it is not encoded as fixture-specific hints.
An optimization is valid only when it improves a general operation and falls
back to complete ordinary semantics for other programs. There are no browser
or web-framework APIs here, so the corpus remains useful for scripts, CLIs,
servers, workers, and embedded hosts alike.

Generate or refresh the files:

```sh
node micros/generate.mjs
```

Check that the numbered files match the generator, then execute all 500 cases
with an engine (Node is the default oracle):

```sh
node micros/generate.mjs --check
node micros/verify.mjs --runs 3 --out micros-results.json
node micros/verify.mjs --engine path/to/quench-node --runs 3 --out quench-micros-results.json
```

`verify.mjs` runs every case under an oracle (Node by default) and the candidate
engine, requiring matching exit status and stdout. Each run records wall-clock
nanoseconds and peak resident memory (RSS on Linux; peak memory footprint on
macOS, via `/usr/bin/time`, when available). The JSON report contains per-case measurements, candidate/oracle
ratios, aggregate totals, optional retired-instruction/cycle/page-fault
counters, and a V8-style score. Wall and memory values include process startup
and host overhead; compare engines on the same machine. The score is versioned and
computed as geometric means: `speed_score = 100 * GM(oracle wall / engine
wall)`, `memory_score = 100 * GM(oracle RSS / engine RSS)`, and
`overall_score = GM(speed_score, memory_score)` for available components.
Thus 100 means parity with the oracle, above 100 is better, and below 100 is
slower or larger. Scores are comparable only on the same machine and corpus
version. Use `--runs 3` or more for less noisy medians.

The supplied 200-point VM checklist is an implementation and measurement plan,
not fixture input. This runner covers its externally measurable baseline (time,
peak RSS, retired instructions, cycles, faults, and differential correctness).
VM-side metrics such as dispatch misses, allocation bytes, GC pauses, and cache
events should be collected by instrumentation around these same cases. No
checklist item requires a particular bytecode, Value, shape, dispatch, JIT, or
GC design.
The executed programs emit only a generic `ok:` record; numbering and metadata
never affect their result.
The cases are measurement and compatibility evidence only; they do not enter
Quench host or VM dispatch and contain no benchmark-name special cases.

A green run is strong, reproducible evidence for the covered behavior. It is
not a 10/10 proof that Quench is V8-compatible: that claim also needs the local
Node oracle, upstream source checks, and broad test262/differential coverage,
including behavior outside these 500 deliberately focused programs.
