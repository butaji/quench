# 45: Extract engine-independent legacy algorithms into shared crates

## Outcome

Move legacy Quench's proven algorithms into small workspace crates that both
runtimes consume, so the next core gains them by adoption instead of
reimplementation. Algorithms with no engine coupling move as plain Rust;
algorithms that touch guest values through a narrow set of operations move
generic over one algorithm boundary trait that both runtimes implement.

## Current gap

Legacy `quench-runtime` passes large Test262 families whose behavior lives in
code with little or no engine coupling. As of 2026-09-24, the former
`regexp_backend.rs` (1,898 lines) has been moved into the runtime-independent
`quench-regexp` crate, which both runtimes consume; the next core now uses its
ECMAScript parser/interpreter instead of its direct Rust `regex` backend. This
has closed stage 19's forward-reference and Unicode decimal-backreference
failures. The extraction is partial: the legacy validation facade and the
next runtime's host-string call sites still need consolidation around exact
UTF-16 data. Intl, Temporal, and Date remain in the legacy runtime (about 36k
lines, mostly primitive/data algorithms). Together these areas are roughly 10k
Test262 files (RegExp 1,879, Temporal 4,603, intl402 3,341, plus Date and the
String methods that route through RegExp).

In `target/test262-next-task08-parallel.json` (2026-09-22), `Temporal is not
defined` fails 3,053 files and `Intl is not defined` 1,100. RegExp accounts
for 1,425 more, including 612 in `property-escapes` and 375 `invalid code
point` rejections by the `regex` backend. This lane is the largest single
source of next-core passes that needs no new semantics. In the next core, each
extracted algorithm is exposed through task 46 registry rows, not a new
`impl Vm` module.

## Coupling measurement

The 2026-09-24 audit of legacy `temporal/`, `intl/`, and `date/` found that
every file names `Value`, but the engine surface they use is small (see the
[README](README.md#migrating-legacy-semantics) for call-site counts): intrinsic
identities (`ops::Builtin`, `realm_intrinsic`), `throw_range_error` and
`throw_type_error`, `get_property_result`, `to_string`, `to_number`,
`to_primitive`, `to_object`, `is_object`, `is_symbol`, and `ObjectData`
construction for results. Typical entry points already have a uniform shape,
`fn(receiver: Option<&Value>, args: &[Value]) -> Result<Value, VmError>`, and
reach the VM through legacy's thread-local machine. These modules are
value-boundary code, not engine-bound code: they move by making them generic
over the boundary, not by porting them onto `impl Vm`.

## Algorithm boundary

One trait, `AlgorithmBoundary`, is the only way a shared crate touches guest
values. It lives in a small shared crate that depends on neither runtime.

- An opaque `Value: Copy` and `Error` associated type; the shared crate never
  inspects their representation.
- Conversions and tests: ToString (UTF-16), ToNumber, ToPrimitive, ToObject,
  is-object, is-symbol.
- Property read (`Get`), which is `reenters`: it may run guest getters and
  Proxy traps, so effect order stays the legacy order.
- Errors: construct a realm-intrinsic `TypeError` or `RangeError` with a
  message.
- Intrinsic identities by an enum index, never by name.
- Result objects: allocate a guest object of a named intrinsic kind carrying a
  typed slot record (for example a Temporal ISO date and calendar), and read
  that record back from a receiver with a brand check. Allocation happens in
  the runtime's implementation; the shared crate never allocates guest
  objects itself.

Each operation is a row of task 46's kernel primitive table, with its effect
class. The next core's implementation roots any boundary value that is live
across a `reenters` or `allocates` operation; the trait signature makes that
explicit (for example by returning rooted handles scoped to the call), so a
moved algorithm cannot hold an unrooted handle across a collection. Legacy's
implementation wraps its existing thread-local calls and `Rc` values.

## Scope and implementation sequence

1. Classify legacy modules by engine coupling: pure algorithm (no `Value`,
   heap, realm, or interpreter types), value-boundary (only the operations
   listed above), or engine-bound. Pure and value-boundary modules move here;
   engine-bound code is ported through task 08's internal-method contract
   instead (see the [README](README.md#migrating-legacy-semantics)).
2. Finish the RegExp extraction: move remaining validation rules to the shared
   crate, thread exact UTF-16 source/input units through the next VM API, and
   keep `RegExp` objects, `lastIndex`, and capture arrays in the next core.
3. Declare `AlgorithmBoundary` and implement it for legacy. Move legacy
   `temporal/duration.rs` and `duration_helpers.rs` as the pilot: replace
   `Value` with the boundary's value type, add an explicit `cx` parameter in
   place of ambient engine calls, and store Duration state as a slot record
   instead of named properties. Legacy Test262 outcomes for
   `built-ins/Temporal/Duration` must be unchanged.
4. Implement the boundary for the next core, install the Duration intrinsics
   through task 46 registry rows, and verify the Duration families gain passes
   with no ratchet regressions. The pilot fixes the rooting and slot-record
   patterns before the bulk move.
5. Move the rest of Temporal (plain date/time/year-month/month-day, instant,
   zoned, calendars, rounding, time-zone math), then Intl services and Date,
   one module family at a time, each checked against legacy's frozen outcomes
   and the next-core ratchet.
6. Extract the remaining helpers that legacy already proves: number to
   string and radix formatting, string to number parsing, BigInt arithmetic
   and formatting, URI codecs, and Unicode case mapping and normalization.
7. Point legacy `quench-runtime` at the same crates so each algorithm has one
   authority until cutover (task 27), when the legacy crate is deleted and the
   shared crates remain.

Shared crates must not depend on either runtime, name either runtime's types,
expose heap handles, or allocate guest objects except through the boundary.
Guest-visible objects, slots, and effect ordering stay in the runtime's
boundary implementation and the next core's intrinsics (tasks 14 and 15).

## Verification

Legacy Test262, Node-compat, and unit results are unchanged after each
extraction (task 48's frozen legacy Test262 outcomes; task 19's Wasm and
Node outcomes). On the next core, the affected Test262
families gain passes with no ratchet regressions elsewhere. Crate-boundary
checks show neither runtime's types appear in a shared crate's public API.

## Definition of done

- RegExp, Intl, Temporal, Date, and numeric/string conversion algorithms each
  have one implementation, used by both runtimes.
- The next core no longer uses the `regex` crate for JavaScript RegExp.
- No shared crate depends on `quench-runtime` or `quench-runtime-next`.
- `AlgorithmBoundary` is the only guest-value API used by shared crates, and
  each of its operations is a kernel primitive table row.

## Implementation evidence

The pure Gregorian civil-date/day-number conversion is now owned by the
runtime-independent `quench-temporal` crate and consumed by both legacy and
next runtimes. Next-core `PlainDate` Test262 slices remain at add 39/39,
until 84/86, and since 85/87 under positive 30,000 ms timeouts and batches no
larger than 100. The two difference-family failures are unchanged and remain
the missing calendar-carrying Temporal constructors and ZonedDateTime slots;
this extraction does not complete the Temporal migration or task 45. Both
runtime crates compile against the shared crate. No harness or unit tests
were changed or run.

The relative-date `Temporal.Duration.prototype.total` calendar-balancing
algorithm has now also moved into `quench-temporal`; both runtimes call the
same implementation. This adopts the legacy algorithm rather than duplicating
its calendar arithmetic in the next VM, including calendar-to-time balancing.
The Stage 74 Duration subtree improved 410/540 → 416/540, and the full current
stage improved 997/4,603 → 1,003/4,603 in batches capped at 100. The legacy
oracle passes the affected PlainDateTime-relative case.
Timezone validation and Temporal object/slot coverage remain open.

Relative duration nanoseconds now use the same shared ISO calendar transition
as duration totalization, replacing the next runtime's separate `NaiveDate`
month/day arithmetic and its narrower representable range. The shared path
validates both the relative date and resulting date-time against Temporal's
supported endpoints. Existing Stage 74 out-of-range-relativeTo cases pass
3/3, and the affected legacy Test262 total case passes through `run-test`.
Remaining ZonedDateTime construction, ISO time-zone parsing, and Temporal slot
adoption remain open; no tests or harness changes were made.

The 2026-09-27 audit confirms the planned `AlgorithmBoundary` is not implemented
yet: Temporal algorithms remain in legacy `quench-runtime/src/temporal.rs` and
`temporal/instant.rs`, while the next VM has separate relative-date conversion
in `quench-runtime-next/src/vm/temporal.rs`. The next migration slice is the
legacy ISO time-zone/offset parsing and validation path, extracted as pure
`quench-temporal` data transformations before adding more next-VM branches.
That seam directly targets the current Duration `total` failures for invalid,
offset-mismatched, and timezone-annotated `relativeTo` strings. The missing
ZonedDateTime guest slot/constructor remains a separate boundary concern and
must not be faked as a PlainDate.

The shared offset slice is now materialized in `quench-temporal/src/offset.rs`:
legacy relativeTo validation uses its offset validators/converters, while the
next PlainDate ISO parser uses the distinct date-time offset grammar (including
hour-only and compact second forms). The next-runtime Stage 74 result rose
1,008/4,603 → 1,012/4,603 with no harness or unit-test changes. The legacy
Temporal stage completed 4,602/4,603; its sole failure was the unrelated
`Temporal.Now.instant` clock-order assertion. The `AlgorithmBoundary` and
ZonedDateTime slots remain open.

The next core's ZonedDateTime guest slots are now represented by a typed heap
cell (epoch nanoseconds, time-zone identifier, calendar, and object prototype),
with local date/time fields derived from that authority. This is runtime
boundary work only; Temporal algorithms have not moved into a shared crate,
and task 45 remains open. The Stage 74 next-core sweep rose to 1,134/4,603;
3,469 failures remain. No unit tests, new tests, or harness changes were made.

The first behavior-bearing ZonedDateTime statics (`from` and `compare`) now
consume an internal epoch/zone/calendar record for branded values and
supported RFC3339 strings. This is not yet task 45's shared-crate extraction:
property-bag conversion, full ISO parsing, offset agreement, and broader
calendar behavior remain open. Stage 74 is 1,175/4,603; no unit tests, new
tests, or harness changes were made.

ZonedDateTime property-bag conversion now reuses the next core's PlainDate
integer, month-code, and date-bound authority before applying time-zone
resolution. This reduces duplicated date semantics but does not complete the
shared Temporal extraction; full calendar resolution, option semantics, and
ISO parsing remain. Stage 74 is 1,214/4,603, with 3,389 failures. No unit
tests, new tests, or harness changes were made.

ZonedDateTime string conversion now parses basic/extended ISO date-time fields,
compact offsets, fractional seconds, leap seconds, and annotations into the
same epoch/zone/calendar record used by the runtime boundary. The parser still
needs critical-annotation validation and complete offset matching, and has not
yet been extracted into `quench-temporal`. Stage 74 is 1,223/4,603. No unit
tests, new tests, or harness changes were made.

The next-core ZonedDateTime `equals` and `withTimeZone` methods now share the
typed slot/epoch-zone-calendar record path and the pure timezone identifier
normalization boundary. This remains guest/runtime logic rather than a shared
Temporal algorithm extraction. Stage 74 is 1,295/4,603; no unit tests, new
tests, or harness changes were made.

The next-core ZonedDateTime `toString` and `toJSON` methods now derive output
from the same epoch/zone/calendar slot authority, including string options and
local-time rounding. This is still runtime implementation, not the shared
`quench-temporal` algorithm boundary. Stage 74 passes 1,368/4,603; no unit
tests, new tests, or harness changes were made.

The next core's `Temporal.Instant` slot and time-only arithmetic now reuse its
existing Temporal Duration record conversion; epoch nanoseconds remain the
single stored authority. This improves Stage 74 to 1,559/4,603, but the new
Instant logic remains VM-bound and does not yet satisfy this task's shared
`quench-temporal` extraction. No unit tests, new tests, or harness changes.
Instant rounding reuses the next VM's existing pure signed-integer rounding
operation rather than introducing a second implementation. Instant option
conversion and mode mapping still live in the VM, so task 45's engine-neutral
`quench-temporal` extraction remains open. Its focused Test262 cohort passes
41/41; no unit tests, new tests, or harness changes.
After that slice, the complete bounded Stage 74 rerun is 1,599/4,603, up 40;
the Instant subtree is 235/465 and `round/` is 41/41. The reusable rounding
primitive is still in the VM boundary rather than `quench-temporal`.
The new shared `since`/`until` VM path also reuses that rounding primitive and

The remaining cases are string-input parsing gaps, and engine-neutral
