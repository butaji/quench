# 45: Extract engine-independent legacy algorithms into shared crates

## Outcome

Move legacy Quench's proven, engine-independent algorithms into small
workspace crates that both runtimes consume, so the next core gains them by
adoption instead of reimplementation.

## Current gap

Legacy `quench-runtime` passes large Test262 families whose behavior lives in
code with little or no engine coupling. As of 2026-09-24, the former
`regexp_backend.rs` (1,898 lines) has been moved into the runtime-independent
`quench-regexp` crate, which both runtimes consume; the next core now uses its
ECMAScript parser/interpreter instead of its direct Rust `regex` backend. This
has closed stage 19's forward-reference and Unicode decimal-backreference
failures. The extraction is partial: the legacy validation facade and the
next runtime's host-string call sites still need consolidation around exact
UTF-16 data. Intl, Temporal, and Date remain in the legacy runtime (about 36k
lines, mostly primitive/data algorithms). Together these areas are roughly 10k
Test262 files (RegExp 1,879, Temporal 4,603, intl402 3,341, plus Date and the
String methods that route through RegExp).

In `target/test262-next-task08-parallel.json` (2026-09-22), `Temporal is not
defined` fails 3,053 files and `Intl is not defined` 1,100. RegExp accounts
for 1,425 more, including 612 in `property-escapes` and 375 `invalid code
point` rejections by the `regex` backend. This lane is the largest single
source of next-core passes that needs no new semantics. In the next core, each
extracted algorithm is exposed through task 46 registry rows, not a new
`impl Vm` module.

## Dependencies

See this task's `depends_on` in [index.json](index.json). Only the next core's
string representation (task 06) is required; this lane does not wait for the
VM foundation tasks.

## Scope and implementation sequence

1. Classify legacy modules by engine coupling: pure algorithm (no `Value`,
   heap, realm, or interpreter types), value-boundary (only primitive
   conversions), or engine-bound. Only the first two move; engine-bound code
   is ported through task 08's internal-method contract instead (see the
   [README](README.md#migrating-legacy-semantics)).
2. Finish the RegExp extraction: move remaining validation rules to the shared
   crate, thread exact UTF-16 source/input units through the next VM API, and
   keep `RegExp` objects, `lastIndex`, and capture arrays in the next core.
3. Extract the Intl/ICU services, Temporal arithmetic, calendars, rounding,
   and time-zone math, and Date algorithms into shared crates whose APIs take
   and return plain Rust data (numbers, UTF-16 slices, option records).
4. Extract the remaining pure helpers that legacy already proves: number to
   string and radix formatting, string to number parsing, BigInt arithmetic
   and formatting, URI codecs, and Unicode case mapping and normalization.
5. Point legacy `quench-runtime` at the same crates so each algorithm has one
   authority until cutover (task 27), when the legacy crate is deleted and the
   shared crates remain.

Shared crates must not depend on either runtime, expose heap handles, or
allocate guest objects. Guest-visible objects, slots, and effect ordering stay
in the next core (tasks 14 and 15).

## Verification

Legacy Test262, Node-compat, and unit results are unchanged after each
extraction (task 19's frozen outcomes). On the next core, the affected Test262
families gain passes with no ratchet regressions elsewhere. Crate-boundary
checks show neither runtime's types appear in a shared crate's public API.

## Definition of done

- RegExp, Intl, Temporal, Date, and numeric/string conversion algorithms each
  have one implementation, used by both runtimes.
- The next core no longer uses the `regex` crate for JavaScript RegExp.
- No shared crate depends on `quench-runtime` or `quench-runtime-next`.
