# 45: Extract engine-independent algorithms into shared crates

## Outcome

Each engine-independent algorithm has one implementation in a small workspace
crate: RegExp, Intl, Temporal, Date, numeric/string conversion, BigInt, URI,
and Unicode casing and normalization. The crate reaches guest values only
through one `AlgorithmBoundary` trait. **Where the next core already holds a
complete implementation, that implementation is the authority to extract.**
Legacy code is extracted only for algorithms the next core has not rewritten.
When the legacy runtime is deleted (task 27), nothing is lost, because nothing
it owned remains unique to it.

## Current gap

Legacy `quench-runtime` passes large Test262 families whose behavior lives in
code with little or no engine coupling. As of 2026-09-24, the former
`regexp_backend.rs` (1,898 lines) has been moved into the runtime-independent
`quench-regexp` crate, which both runtimes consume; the next core now uses its
ECMAScript parser/interpreter instead of its direct Rust `regex` backend. This
has closed stage 19's forward-reference and Unicode decimal-backreference
failures. The extraction is partial: the legacy validation facade and the
next runtime's host-string call sites still need consolidation around exact
UTF-16 data. Intl, Temporal, and Date remain in the legacy runtime (about 36k
lines, mostly primitive/data algorithms). Together these areas are roughly 10k
Test262 files (RegExp 1,879, Temporal 4,603, intl402 3,341, plus Date and the
String methods that route through RegExp).

In `target/test262-next-task08-parallel.json` (2026-09-22), `Temporal is not
defined` fails 3,053 files and `Intl is not defined` 1,100. RegExp accounts
for 1,425 more, including 612 in `property-escapes` and 375 `invalid code
point` rejections by the `regex` backend. This lane is the largest single
source of next-core passes that needs no new semantics. In the next core, each
extracted algorithm is exposed through task 46 operation rows, not a new
`impl Vm` module.

### 2026-09-29 re-baseline

The original plan was to move legacy Temporal, Intl and Date into shared crates
and have the next core adopt them. The work went a different way. The next core
now passes every Temporal, Intl and Date Test262 stage (0–113 green) with its
own implementation:

| Area | Next core | Legacy | Shared crate today |
| ---- | --------- | ------ | ------------------ |
| Temporal | `vm/temporal*.rs`, about 14.2k lines | `temporal/`, about 21k lines | `quench-temporal`, 814 lines (duration, offset) |
| Intl | `vm/intl_*.rs` | `intl/` | `quench-intl`, about 2.4k lines (locale data, collator, plural, digits) |
| Date | `vm/date.rs` | `date/` | none |

Only 26 of the next core's 374 Temporal function names appear in legacy, so
the two are separate implementations, not copies. Extracting legacy now would
replace code that passes the suite with code that has not been run on the next
core. The direction is reversed: the next core's code moves into the shared
crates behind the boundary, and the legacy copies are deleted at task 27.

## Coupling measurement

The 2026-09-24 audit of legacy `temporal/`, `intl/`, and `date/` found that
every file names `Value`, but the engine surface they use is small (see the
[README](README.md#migrating-legacy-semantics) for call-site counts): intrinsic
identities (`ops::Builtin`, `realm_intrinsic`), `throw_range_error` and
`throw_type_error`, `get_property_result`, `to_string`, `to_number`,
`to_primitive`, `to_object`, `is_object`, `is_symbol`, and `ObjectData`
construction for results. Typical entry points already have a uniform shape,
`fn(receiver: Option<&Value>, args: &[Value]) -> Result<Value, VmError>`, and
reach the VM through legacy's thread-local machine. These modules are
value-boundary code, not engine-bound code: they move by making them generic
over the boundary, not by porting them onto `impl Vm`.

## Algorithm boundary

One trait, `AlgorithmBoundary`, is the only way a shared crate touches guest
values. It lives in a small shared crate that depends on neither runtime.

- An opaque `Value: Copy` and `Error` associated type; the shared crate never
  inspects their representation.
- Conversions and tests: ToString (UTF-16), ToNumber, ToPrimitive, ToObject,
  is-object, is-symbol.
- Property read (`Get`), which is `reenters`: it may run guest getters and
  Proxy traps, so effect order stays the legacy order.
- Errors: construct a realm-intrinsic `TypeError` or `RangeError` with a
  message.
- Intrinsic identities by an enum index, never by name.
- Result objects: allocate a guest object of a named intrinsic kind carrying a
  typed slot record (for example a Temporal ISO date and calendar), and read
  that record back from a receiver with a brand check. Allocation happens in
  the runtime's implementation; the shared crate never allocates guest
  objects itself.

Each operation is a row of task 46's operation table, with its effect
set. The next core's implementation roots any boundary value that is live
across a `reenters` or `allocates` operation; the trait signature makes that
explicit (for example by returning rooted handles scoped to the call), so a
moved algorithm cannot hold an unrooted handle across a collection. Legacy's
implementation wraps its existing thread-local calls and `Rc` values.

## Scope and implementation sequence

1. Classify each algorithm by who holds the passing implementation: next core
   only, legacy only, or both. The next core's implementation wins wherever
   it passes the owning Test262 stages. Legacy code moves only when the next
   core has no implementation of that algorithm.
2. Finish the RegExp extraction: move the remaining validation rules into
   `quench-regexp`, pass exact UTF-16 source and input units through the next
   VM API, and keep `RegExp` objects, `lastIndex`, and capture arrays in the
   next core.
3. Declare `AlgorithmBoundary` with its operations as operation-table rows
   (task 46). The next core provides the first implementation.
4. Pilot the move on the next core's Temporal Duration. Move the
   `vm/temporal*.rs` Duration code into `quench-temporal` behind the boundary,
   with state kept as a slot record. The Test262 Temporal/Duration stages stay
   green on the task 48 ratchet. The pilot settles the rooting and slot-record
   patterns before the bulk move.
5. Move the rest of the next core's Temporal, then Intl services and Date, one
   module family at a time, each checked against the ratchet.
6. Extract numeric/string conversion, BigInt, URI and Unicode helpers from
   whichever runtime holds the passing implementation.
7. Legacy either adopts a shared crate through its own boundary implementation
   (when that is cheap and keeps the Node gate green until cutover), or keeps
   its copy until task 27 deletes it. Legacy is not improved in parallel.

Shared crates must not depend on either runtime, name either runtime's types,
expose heap handles, or allocate guest objects except through the boundary.
Guest-visible objects, slots, and effect ordering stay in the runtime's
boundary implementation and the next core's intrinsics (tasks 14 and 15).

## Verification

On the next core, the task 48 ratchet shows zero regressions after each
extraction. Node-compat outcomes are compared with task 19's frozen baseline. Crate-boundary
checks show neither runtime's types appear in a shared crate's public API.

## Definition of done

- RegExp, Intl, Temporal, Date, and numeric/string conversion algorithms each
  have one implementation, in a shared crate. At cutover, the next core is its
  only runtime consumer.
- No algorithm that exists only in legacy remains when task 27 starts.
- The next core no longer uses the `regex` crate for JavaScript RegExp.
- No shared crate depends on `quench-runtime` or `quench-runtime-next`.
- `AlgorithmBoundary` is the only guest-value API used by shared crates, and
  each of its operations is an operation-table row.
