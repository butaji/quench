# 039: Native AArch64 stencil execution backend (this machine's actual architecture)

- **Theme:** deegen_full_jit
- **Executor:** codex
- **Depends on:** 037
- **Priority: above remaining lower-priority backlog items (tag-register #6, further breadth widening) until closed.**

## Context

Every stencil byte the build script emits today is literal x86_64 machine
code (`build.rs` `X86_EXECUTABLE = cfg!(target_arch = "x86_64")`, and the
`_BYTES`/`_HOLES` consts it generates are x86_64-only; `stencil_arena.rs`,
`machine.rs::executable_optimizing_plan`, and `vm_runtime.rs`'s OSR/optimizing
execution paths all gate on `target_arch = "x86_64"`). This machine — and
this project's actual dev/CI environment — is ARM64 macOS. The practical
consequence, confirmed by rerunning the full curriculum
(`quench-bench/deegen-curriculum/`) against the current build: the baseline
JIT, the SMC IC stub chain, OSR-entry's actual code transfer, and the
`Optimizing` tier all pass their unit/differential tests (their *logic* is
correct) but never execute real compiled code here, because there is no
compiled code for this CPU to run. Every "not justified" or "not a measured
net win" result from tasks 034/036 is confounded by this: Gate-0 profiling on
this machine cannot see a cost that doesn't exist yet, not because the
optimization genuinely has no benefit.

**This is now the priority**: get the JIT tier actually executing on the
architecture this project is developed and measured on, before spending more
effort on x86_64-only refinements (tag register optimization, further
breadth widening) whose payoff can't even be verified here.

## Scope
- crates/quench-runtime/build.rs (stencil byte/hole generation)
- crates/quench-runtime/src/stencil_arena.rs
- crates/quench-runtime/src/machine.rs (`executable_optimizing_plan`)
- crates/quench-runtime/src/vm/vm_runtime.rs (OSR/optimizing execution gates)
- crates/quench-runtime/src/stencil_select.rs

## Deliverables
- Start with the 8 opcodes that already have a specialized x86_64 leaf
  (`Move`, `Add`, `AddConst`, `Return`, `Sub`, `Mul`, `Div`, `GetN` — per
  `docs/deegen-stencil-coverage.md`) and every region built from them
  (`MOVE`, `LOOP`/`FALLTHROUGH`, `ADD_CONST`, `SUBTRACT`, `MULTIPLY`,
  `DIVIDE`, `PROPERTY`). Do not widen opcode coverage as part of this task —
  that's task 035's job; this task is about making the *existing* covered
  set executable on this architecture, not growing the set.
- Emit real AArch64 machine code for each of those stencils: same
  hole-patching model (`Hole`/`HoleKind` from `stencil_fact.rs` stays
  architecture-agnostic — only the byte encoding and register/calling
  convention are AArch64-specific), same bump-pointer RW→RX arena lifecycle,
  same one-way protection transition. Confirm AArch64's calling convention
  and register set for whatever ABI the stencils assume (this may require
  choosing a concrete, documented AArch64 calling convention analogous to
  whatever the x86_64 stencils currently assume — check how those were
  originally hand-written/generated before deciding the AArch64 equivalent)
- Flip the relevant `cfg!(target_arch = "x86_64")` gates to
  `cfg!(any(target_arch = "x86_64", target_arch = "aarch64"))` only once the
  AArch64 bytes are real and tested — never flip a gate ahead of having real
  executable bytes behind it
- Every stencil keeps the complete ordinary-interpreter fallback exactly as
  the x86_64 path already does — this task adds a second executable backend,
  it does not change the fallback discipline

## Validation

1. `cargo test -p quench-runtime --lib` on this ARM64 machine — the existing
   `stencil_select.rs` tests that assert `record.executable ==
   cfg!(target_arch = "x86_64")` need updating to the new any(...) gate, and
   must still pass
2. A differential test per newly-executable stencil: same program, same
   observable output, with the stencil forced-executable vs. forced-fallback
   — proves the AArch64 bytes compute the same result as the interpreter,
   not just that they run without crashing
3. Re-run `docs/architecture-evidence.md`'s DWARF/`sample` Gate-0 method from
   task 034 on this machine now that rendered regions actually execute —
   confirm it now sees real samples in `StencilArena`/`render_selected`/
   `execute_f64` (previously zero, per task 034's finding) — this is the
   direct proof the architecture gap, not a genuine absence of cost, was
   what blocked task 034
4. Re-run task 036's paired neutral-corpus measurement (`Optimizing`
   promotion reachable vs. forced-unreachable) on this machine now that the
   optimizing view can actually execute — record whether it's now a measured
   net win, replacing the "not measured on ARM64" caveat with a real result
5. Re-run `quench-bench/deegen-curriculum/deegen-verify.mjs --from 1 --to 38`
   end to end — record before/after wall-time ratios for every case, and
   specifically report on cases 025/026/027 (OSR's own motivating single-
   invocation hot-loop shape) and 017/019 (arithmetic-heavy, admitted
   regions) since those are exactly the cases this backend should move

**Fail condition**: flipping the `cfg!` gates without step 2's per-stencil
differential proof is not acceptable — a wrong AArch64 encoding that merely
doesn't crash is worse than staying on the interpreter fallback, since it
would silently corrupt results instead of falling back.

## Non-goals
- Widening opcode/region coverage beyond the 8 already-specialized leaves
  (task 035's job, do after this if still valuable)
- Tag register optimization (task 031, still legitimately blocked on a
  pinned-register mechanism regardless of target architecture)
- Any change to the interpreter, tier-up, or IC logic — this task is purely
  "make the already-correct stencil logic executable on this CPU"
