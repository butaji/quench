# 54: Unify required time-zone and locale facts


## Outcome

Give the time-zone and locale facts observed by pinned Test262 or the frozen
implemented Node cases one authority each. Preserve required Date, Intl and
Temporal behavior in the recorded environment. Broader OS discovery and
locale coverage are outside Stage A unless required by those cases.

## Current gap

Audit the observations below against the frozen inventories before implementing
changes. Fix only remaining required behavior; existing correct paths need no
replacement. Historical observations are not proof of a current failure.

For the local time zone, three places give three different answers:

- `quench-runtime-next/src/vm/intl_datetime.rs` defines `DEFAULT_TIME_ZONE =
  "America/Lima"` plus a hardcoded short name, long name, long offset and
  `-300` minute offset. The legacy `quench-runtime/src/intl/datetime.rs`
  repeats the Lima default.
- `quench-runtime-next/src/vm/temporal.rs:temporal_now_native` returns `"UTC"`
  for `Temporal.Now.timeZoneId()`, and uses UTC as the zone for the other
  `Temporal.Now.*` calls when no zone argument is given.
- `quench-runtime-next/src/vm/date.rs` uses chrono `Local`, which reads the
  OS zone.

On any machine that is not in Lima, `getTimezoneOffset()`,
`resolvedOptions().timeZone` and `Temporal.Now.timeZoneId()` disagree.

- The default locale is a hardcoded `"en-US"` fallback in
  `intl_display_names.rs`, `intl_list_format.rs` and
  `intl_duration_format.rs`.
- In the legacy host, `process.env.TZ = ...` updates a separate runtime
  override (`quench_runtime::date::set_local_timezone`). That override is a
  second authority for the zone.

## Dependencies

See `depends_on` in [index.json](index.json). Task 43 defines the host facade
that carries the fact into the engine. Task 15 owns the guest objects that
read it.

## Required scope and optional mechanisms

Stage A implements only the behavior observed by the pinned Test262 inventory
or task 19's frozen implemented Node cases, and the internal lifecycle/safety
invariants needed to run them on the single VM. The mechanisms below are
implementation options within that scope, not a requirement to expand Node
coverage or finish a broader host/architecture rewrite.

1. Add one host capability that returns the resolved local zone: a canonical
   IANA identifier, or a fixed offset. Add one for the default locale. Resolve
   both once at startup and again when `process.env.TZ` is assigned, as Node
   does. Keep them as a single record.
2. Make `Date` local time, the `Intl.DateTimeFormat` default zone,
   `Temporal.Now.timeZoneId()` and the `Temporal.Now.*` defaults read that
   capability. Derive zone display names from the shared ICU/tz data, not
   from Lima constants.
3. Replace the `"en-US"` fallbacks with the host default locale. Keep the
   spec's `DefaultLocale` fallback, owned by a named constant, only for when
   the OS locale is missing or unsupported.
4. The Test262 and Node runners set `TZ` and `LANG` explicitly as recorded
   harness inputs, so conformance runs are reproducible (task 15). Production
   code never reads a value that only a runner supplies.

## Verification

- Run affected Test262 stages with `TZ` pinned by the runner and compare-runs
  against the matching baseline inventory.
- Check against the local Node oracle for `TZ=UTC`, `TZ=America/Lima`,
  `TZ=Asia/Kolkata`, `TZ=Europe/London` (across DST), and `TZ` unset. For
  each, `getTimezoneOffset()`, `resolvedOptions().timeZone`/`.locale` and
  `Temporal.Now.timeZoneId()` must match Node.

## Definition of done

- Affected pinned Test262 and frozen implemented Node cases pass with the
  recorded runner environment and match the local Node oracle where relevant.
- Zone and locale facts required by these paths each have one authority.
- Broader OS locale integration is not a separate gate when the required
  behavior and internal correctness obligations already pass.
