# 61: Lead no-JIT engines on every V8-v7 benchmark

## Outcome

After Stage A is verified, on the Apple M4/macOS execution host recorded in
the evidence, Quench achieves the highest median Score
and lowest median maximum RSS on each V8-v7 benchmark: Crypto,
DeltaBlue, EarleyBoyer, NavierStokes, RayTrace, RegExp, Richards, and Splay.
Compare against QuickJS, Bun/JSC with JIT disabled, and Node/V8 --jitless.
Both targets must hold on every benchmark, not just the aggregate.

## Active working lens: Splay

Work one V8-v7 fixture at a time, starting with Splay. Keep Splay active until
it clears both the Score and RSS bars below; the all-eight fixed-work run is a
regression guard, not a reason to switch fixtures. This lens does not change the
task queue's critical-path order. Production behavior remains fixture-agnostic.

The 2026-10-09 Step 0 baseline uses fixed-work schema 2, 11 rounds, and 300
Splay `run()` calls per work process, paired with `Setup`/`TearDown` only at
K=0. On the M4 host, the marginal-cycle target is Node `--jitless` at
**4,590,844 cycles per run**; the RSS target is Bun with JIT disabled at
**57,950,208 bytes median maximum RSS**. Quench starts at 10,254,433 marginal
cycles per run and 217,825,280 bytes median maximum RSS. Its initial distance
is **2.23x** the Node speed target and **3.76x** the Bun RSS target. The exact
four-engine report, executable hashes, host details, and raw paired samples are
in [the Splay Step 0 baseline](evidence/task61-splay-step0-2026-10-09/current-head-four-engine-11.json).

Use fixed-work K/K=0 marginal cycles per `run()` and median maximum RSS for
daily Splay gates. A Task 61 win still requires a fresh 11-round stock-harness
check on the same host with Splay median Score strictly above Node `--jitless`
and Splay median maximum RSS strictly below Bun no-JIT. Re-take those stock
bars when declaring the fixture won. Every retained change also runs the
all-eight fixed-work regression guard; no fixture may regress beyond its
measured noise band.

The first retained Splay-focused change derives `may_have_gc_roots` once per
shape, scans root-bearing shapes once per collection, and gathers live shapes

samples before and one after; the candidate had one additional sample at
`gc.rs:30`. The full gate, guard, sample and exact hashes are
in [the Splay GC-root metadata record](evidence/task61-splay-step0-2026-10-09/gc-roots-candidate/README.md).

## Splay GC headroom diagnostic on Apple M4

A temporary `profile-memory` snapshot recorded 20 collections on the current
materialized Splay input. Collections 14–20 repeatedly reached about 1.562M
occupied slots before collection and retained about 781K cells after sweep.
That stable survivor set is about 512K objects, 256K arrays and 11K strings,

and runtime baseline. This does not show a large extra reachable set.

Correction: the earlier completion summary called 1.466M occupied cells
“live.” The completion checkpoint does not force a collection, so that count
includes allocations made after the last sweep. The profile high-water count
is likewise peak occupied cells. The meaningful collection-boundary ratio is
1.562M occupied before GC to 781K survivors after GC, about 2.00x. The
150.0 MB slot arena therefore reflects the heap's high-water occupancy and
retained slot capacity, not 1.466M reachable cells. The JSON preserves the raw
checkpoint data and now marks this distinction explicitly. This restores GC
pacing/slot high-water as a plausible RSS contributor, but does not yet justify
changing policy: the prior Linux `live/2` trial reduced RSS by 54.4 MB while

counts, hashes and instrumentation provenance are in the [M4 GC snapshot
record](evidence/task61-splay-live-peak-m4-2026-10-09.json).

A post-sweep histogram rejected releasing whole slot slabs as a shortcut. At

high-water collection, 781,054 live slots were spread across 763 slabs; most
slabs were 25–75% occupied, with none empty. The 96-byte slots therefore
