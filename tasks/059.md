# 059: Bump-pointer arena allocation for provably-scoped short-lived values

- **Theme:** vm_completeness
- **Executor:** codex
- **Depends on:** none

## Context

Quench already has exactly this pattern in one place: `stencil_arena.rs`'s
bounded RW→RX bump-pointer arena for JIT code (allocate, use, reset —
bounded, no per-allocation bookkeeping). The user wants this generalized
beyond JIT code to the *object/value* heap, specifically because the target
deployment (long-running web-backend processes) has a lot of naturally
short-lived, provably-scoped allocation: call frames, closures/environments
that don't escape their call, string-building scratch, temporary parse
buffers — the same shape of allocation `stencil_arena.rs` already handles
well for code, just for data instead.

This is safe and scopeable *only* where non-escape is provable — never a
general-purpose arena for arbitrary JS objects (a plain object literal can
always escape into a closure, a global, or a longer-lived structure; that
case stays on the `Rc`+cycle-collector heap from tasks 056/057). This task
is about the subset where escape is already structurally impossible or
already tracked.

## Scope
- crates/quench-runtime/src/register_file.rs (call/environment frames —
  confirm current allocation strategy first, this may already be
  arena-like via the existing register-file reuse)
- crates/quench-runtime/src/machine.rs (frame lifecycle)
- Any parser/string-building scratch allocation path that's already
  scoped to one call/one operation

## Deliverables
- Audit first: which allocations are already provably scoped to one call,
  one expression, or one operation, and are they already arena/bump-pointer
  allocated, or do they go through the general `Rc` path unnecessarily?
  Do not assume — check `register_file.rs` and frame lifecycle code
  directly.
- For any confirmed non-escaping, provably-scoped allocation still going
  through the general heap: move it to a bounded bump-pointer arena, reset
  (not individually freed) when its scope ends (call return, operation
  completion) — same discipline as `stencil_arena.rs`'s existing lifecycle
- Escape must be structurally impossible for anything moved to this arena
  — if a value *can* be captured by a closure, stored in a longer-lived
  object, or returned in a way that outlives its scope, it does not qualify
  and stays on the general heap. This is a build-time/type-level
  guarantee, not a runtime check to add later.

## Validation

1. Differential tests: identical observable behavior for every code path
   touched, including deeply nested/recursive calls stressing the arena's
   reset boundary
2. `cargo test -p quench-runtime --lib` and `--features execution-trace` —
   all pass
3. A long-running-process-shaped test (same shape as task 057's): repeated
   calls/operations over a long run, confirm the arena's memory stays
   bounded (reused, not growing) rather than needing periodic collection
   at all for this subset
4. Before/after measurement on call-heavy curriculum cases (010, 029) and
   v8-v7's Richards/DeltaBlue (call/object-heavy) once task 052 lands

**Fail condition**: moving any value to this arena that *can* escape its
proven scope is a use-after-free-class correctness bug, not a performance
regression — err toward leaving something on the general heap if escape
can't be proven with the same rigor as this project's Proven/Guarded/Unknown
fact discipline elsewhere.

## Non-goals
- Any arena for values whose lifetime isn't build-time/structurally
  provable — that's task 060's much harder, opt-in, host-level territory,
  not this task's
