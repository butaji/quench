# 057: Bounded cycle-collection pass (only if task 056 confirms a real leak)

- **Theme:** vm_completeness
- **Executor:** codex
- **Depends on:** 056

## Context

Gated entirely on task 056's finding. If 056 confirms quench's pure-`Rc`
object model leaks on ordinary user-created reference cycles, this task
closes it — not with a full tracing garbage collector (a large
architectural change this backlog has consistently avoided proposing
without hard justification), but with a bounded, periodic trial-deletion
pass over suspected cyclic structures, the same general approach Python's
and QuickJS's refcounting-plus-cycle-collector designs use: refcounting
handles the common case cheaply, an occasional bounded sweep over
*candidate* cyclic objects (not the whole heap) reclaims what refcounting
alone cannot.

## Scope
- crates/quench-runtime/src/value.rs (object/environment representation)
- New: a cycle-candidate tracking + trial-deletion module

## Deliverables
- A bounded candidate set: objects whose refcount decremented but didn't
  reach zero are candidates for a cycle (the standard trial-deletion
  trigger condition), tracked in a bounded buffer — never an unbounded
  full-heap scan
- A trial-deletion pass: for each candidate, tentatively decrement internal
  references and check reachability from actual roots (the stack, globals,
  registers); if unreachable, the candidate and its cycle are genuinely
  garbage and get freed; if reachable, restore the tentative decrements
- Triggered periodically (bounded interval — by allocation count or
  explicit checkpoints, not continuously) so this stays a bounded, periodic
  cost, not a per-allocation tax
- Every existing correctness invariant (drop order, finalizer-like behavior
  if any JS semantics depend on it, WeakRef/FinalizationRegistry semantics
  if implemented) must hold exactly — a cycle collector must not change
  *when* an object becomes collectible in an observably different way that
  JS code could detect, beyond what the spec already allows for GC timing
  (FinalizationRegistry callbacks are explicitly unordered/timing-unspecified
  per spec, but nothing else should become observably different)

## Validation

1. Task 056's constructed leak tests now show RSS returning to baseline
   after the cycle becomes unreachable and the periodic pass runs
2. `cargo test -p quench-runtime --lib` and `--features execution-trace` —
   all pass, no behavior change for acyclic (the common case) object
   graphs
3. Full v8-v7 suite (task 052) — no regression in wall time (the periodic
   pass must be genuinely bounded-cost, not a hidden throughput tax) and
   `DeltaBlue`'s RSS specifically improves if 056 found it leaking
4. RSS measurement across the full neutral corpus, curriculum, and v8-v7
   suites — confirm no regression for the (likely common) acyclic case,
   only improvement for the cyclic case

**Fail condition**: any change to observable JS semantics (finalization
timing where the spec constrains it, e.g. non-`FinalizationRegistry`
observable effects) is a correctness bug. An unbounded or continuously-
running collection pass that measurably taxes throughput on ordinary
(non-cyclic) programs is also unacceptable — bounded and periodic, not
free-riding on every allocation.

## Non-goals
- A full tracing garbage collector replacing `Rc` entirely — that's a much
  larger architectural change than this leak fix requires; refcounting
  stays the primary mechanism, this task only adds the missing
  cycle-cleanup half
