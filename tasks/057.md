# 057: Periodic full-pass cycle collector (only if task 056 confirms a real leak)

- **Theme:** vm_completeness
- **Executor:** codex
- **Depends on:** 056

## Context

Gated entirely on task 056's finding. If 056 confirms quench's pure-`Rc`
object model leaks on ordinary user-created reference cycles, this task
closes it — with the same algorithm the local `../quickjs` checkout
actually uses (verified by reading `quickjs.c` directly, not from memory),
corrected from an earlier, wrong description of this task: **QuickJS's
cycle collector is a full pass over every live GC object, not a bounded
candidate-only scan.** The three phases (`gc_decref`, `gc_scan`,
`gc_free_cycles`, `quickjs.c:6687-6832`, classic Bacon-Rajan trial
deletion):
1. `gc_decref`: walk every live object, decrement each child's refcount by
   the number of internal (object-to-object) references pointing to it.
2. `gc_scan`: for every object whose refcount is still nonzero after step
   1 (meaning something *outside* the traced object graph — a root — holds
   it), re-increment everything reachable from it.
3. `gc_free_cycles`: anything still at zero after both passes was only
   ever kept alive by other garbage — free it as a cycle.

This is bounded in *frequency*, not *scope*: QuickJS triggers a full pass
only when allocated bytes since the last run exceed a threshold
(`malloc_gc_threshold`, defaults to 256KB, adaptively grows after each
run — `quickjs.c:2083`, `:1787-1795`), so the O(live-heap-size) cost is
amortized and rare, not per-allocation. **This project explicitly targets
long-running processes (web backend apps), not just short benchmark
scripts** — a periodic full-pass collector is the right fit for that
target: predictable, bounded-frequency pauses that don't compound over a
process's lifetime, rather than needing an incremental/generational scheme
whose complexity isn't justified without evidence it's needed (per this
backlog's standing profile-first discipline — build the simple thing that
QuickJS has already proven works in production, don't invent complexity
ahead of evidence it's required).

## Scope
- crates/quench-runtime/src/value.rs (object/environment representation)
- New: a full-pass trial-deletion cycle collector module

## Deliverables
- The three-phase algorithm above, over the actual full set of live
  refcounted objects (not a bounded candidate subset) — implement it as
  QuickJS does, don't reinvent
- An allocation-byte threshold trigger (adaptive, same shape as QuickJS's:
  grow the threshold after each run based on how much survived), invoked
  from the same kind of periodic checkpoint this project already uses
  elsewhere (e.g. `TierState`'s retired-bytecode counting is the same
  "amortized periodic check" pattern, not per-op)
- Every existing correctness invariant (drop order, finalizer-like behavior
  if any JS semantics depend on it, WeakRef/FinalizationRegistry semantics
  if implemented) must hold exactly — a cycle collector must not change
  *when* an object becomes collectible in an observably different way that
  JS code could detect, beyond what the spec already allows for GC timing

## Validation

1. Task 056's constructed leak tests now show RSS returning to baseline
   after the cycle becomes unreachable and a collection pass runs
2. A long-running-process-shaped test: repeatedly create and drop cycles
   in a loop for far longer than any single benchmark run (simulating a
   web-backend process handling many requests over time) — confirm RSS
   stays bounded/flat over the run, not just recovers once
3. `cargo test -p quench-runtime --lib` and `--features execution-trace` —
   all pass, no behavior change for acyclic (the common case) object
   graphs
4. Full v8-v7 suite (task 052) — no regression in wall time (the
   periodic pass must be genuinely amortized, not a hidden throughput tax)
   and `DeltaBlue`'s RSS specifically improves if 056 found it leaking
5. RSS measurement across the full neutral corpus, curriculum, and v8-v7
   suites — confirm no regression for the (likely common) acyclic case,
   only improvement for the cyclic case

**Fail condition**: any change to observable JS semantics (finalization
timing where the spec constrains it) is a correctness bug. A collection
pass invoked so frequently it becomes a per-op tax (defeats the point of
amortized triggering) is also unacceptable.

## Non-goals
- A full tracing garbage collector replacing `Rc` entirely — refcounting
  stays the primary mechanism, this task only adds the missing
  cycle-cleanup half, same division of labor as QuickJS
- Incremental or generational collection — not justified without evidence
  the simple periodic full-pass approach (proven in production by QuickJS)
  is insufficient for this project's long-running target
