# 38: Extend binding-time materialization to Wasm immutables

## Outcome

Apply the existing `compile::binding_time` constant/call-target
materialization pass to Wasm's statically-known facts — immutable globals,
known `ref.func` targets, and monomorphic `call_indirect` table slots —
instead of leaving them as runtime lookups.

## Current gap

`compile/binding_time.rs` already implements a working binding-time lattice
(`BindingTime<T>: Unknown | Static(T) | Dynamic`) and a materialization pass
that rewrites captured-constant loads to `LoadConst` and known-callee calls to
`CallKnown` once analysis proves them single-assignment. Wasm has direct
analogs with no current handling: a `global` declared immutable is provably
static at every read, `ref.func` of a fixed function index is a known call
target, and a `call_indirect` through a table slot that is never mutated after
initialization is effectively monomorphic. Building a separate Wasm-specific
analysis for these would duplicate the same lattice and materialization logic
task 10 already established for JS captures.

## Dependencies

See this task's `depends_on` in [index.json](index.json).

## Scope and implementation sequence

1. Extend `binding_time::apply` (or add a Wasm-specific analysis feeding the
   same `BindingTime<T>` lattice and `materialize_constants`/
   `materialize_calls` machinery) to classify Wasm module globals as
   `Static`/`Dynamic` from their mutability flag and initializer, without
   introducing a second lattice type.
2. Materialize `global.get` of a `Static` immutable global to `LoadConst`, and
   `ref.func`/monomorphic `call_indirect` to `CallKnown`, using the same
   dead-instruction elimination (`dead.push(...)` / `Op::Nop` rewrite) already
   used for JS capture materialization.
3. Prove table-slot monomorphism only from facts available at module-link
   time (no table entry mutation after initialization observed in the
   module); anything else stays dynamic and falls back to generic
   `call_indirect` dispatch exactly as JS falls back to generic `Call`.
4. Preserve the existing integrity rule: materialization may use only
   semantic facts (mutability, initializer values, table contents at link
   time), never fixture identity or benchmark vocabulary.

## Binding-time boundary

Specialization happens before instantiation, so module bytes are static and
imports are dynamic. Table contents and imported globals are
instantiation-time facts: a third binding time. Either specialize once per
instance, and justify the extra residual by measurement, or treat them as
dynamic with a guarded fallback. A defined immutable global with a constant
initializer is static at module time and needs neither.

## Definition of done

- Wasm immutable-global and known-call-target materialization reuses the
  existing `BindingTime`/materialization machinery rather than a parallel
  implementation.
- Every case that must remain dynamic (imported values, mutated tables) is
  covered by a test proving it does not get incorrectly materialized.

## Performance evidence
