# 35: Finish typed-array unification: natives, prototypes, and installers by kind

## Outcome

`TypedArrayKind` is the only per-element-type authority, from heap cell to
native identity, intrinsic prototype, and installer. The same applies to
`DataView` element accessors and `Atomics` operations.

## Current gap

The cell half is done (see Implementation evidence): `Cell::TypedArray { kind,
.. }` replaced the nine variants, and construction flows through one
descriptor-parameterized path. The 2026-09-23 core review found that the kind is
still spelled out per type above the cell:

- `Native` keeps 11 typed-array constructor variants (`Uint8Array` …
  `Float64Array`, `BigInt64Array`, `BigUint64Array`), 16 `DataView`
  get/set variants, and 10 `Atomics` variants.
- `Vm` keeps 11 per-kind prototype fields (`uint8_array_proto` …
  `float64_array_proto`).
- `typed_array_signed.rs`, `typed_array_float.rs`, and `typed_array_uint16.rs`
  remain as thin per-type native entry wrappers.

## Dependencies

See this task's `depends_on` in [index.json](index.json). Task 46 supplies the
parameterized registry rows and the enum-indexed intrinsic table; this task
moves the typed-array, `DataView`, and `Atomics` families onto them.

## Scope and implementation sequence

1. Replace the per-kind constructor variants with one registry row
   parameterized by `TypedArrayKind`. Constructor name, `BYTES_PER_ELEMENT`,
   and prototype are derived from the kind.
2. Replace the per-kind prototype fields with intrinsic-table entries indexed
   by kind.
3. Collapse `DataView` get/set into rows parameterized by element kind, and
   `Atomics` into rows parameterized by operation.
4. Delete the three per-family wrapper files. Per-element behavior is selected
   from `TypedArrayKind`, as the access layer already does.
5. Preserve exact observable behavior per kind: rounding and clamping on
   store, signed and unsigned reads, byte width, constructor name, and
   prototype identity. This is a representation change, not a semantic one.

## Verification

Differential tests against Node/Test262 for every typed array kind: construction
from length/buffer/iterable, element read/write clamping and rounding
(`Uint8ClampedArray`), `DataView` interop, `Atomics` operations, `length_tracking`
resizable-buffer behavior, and prototype/constructor identity per kind. Confirm
no behavioral difference before/after the variant collapse via a full oracle
run.

## Definition of done

- `Cell` has one typed-array variant; `TypedArrayKind` is the sole
  per-element-type authority.
- Installer/constructor logic exists once, parameterized by a data table, not
  duplicated per kind across three files.
- No `Native` variant, `Vm` field, or source file exists per typed-array kind,
  `DataView` element kind, or `Atomics` operation.
- All existing typed array Test262/Node-oracle coverage passes unchanged.

## Performance evidence

Report binary size and match-arm count delta for typed-array-touching code
paths; this task has no required speed claim, only a representation-size and
maintainability claim, consistent with functional work not owning a
performance gate.

## Implementation evidence

The heap representation now has one `Cell::TypedArray` variant carrying the
existing `TypedArrayKind` authority; heap tracing, object access, JSON,
iterators, memory accounting, construction, and typed-array get/set/metadata
paths all dispatch through that tag. The focused runtime matrix remains green.
Constructor registration and construction now flow through one descriptor-
parameterized install/construct path; the family files retain only thin native
entry wrappers. Element conversion, byte width, clamping, signedness, and
floating-point encoding are all selected from `TypedArrayKind`.
