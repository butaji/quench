# 042: Build genuine multi-op sequential stencil execution

- **Theme:** deegen_full_jit
- **Executor:** codex
- **Depends on:** 039

## Context

`docs/copy-and-patch-jit.md`'s design section claims: "Stencils are fused
**regions** (a loop body, a property-access chain)... not one-stencil-per-
bytecode as the paper does." Task 040.1 (widen the arithmetic region to
cover its own dominant surrounding glue — `LoadLocalChecked`, `Binary`,
`UpdateLocal`, `StoreLocal`, `LoadConst`) hit a real blocker while trying to
act on that claim: the current region stencil executes **one numeric leaf
and advances one instruction** — it is not actually a multi-op fused
executor. Adding more opcodes to its metadata without a real execution
mechanism behind them would falsely claim multi-op semantics and risk
incorrect results. This is the same class of finding as task 032's
quickening-naming gap: a name/doc claim ahead of what the implementation
does. This task closes that gap for real, rather than patching around it.

This is genuinely new mechanism, authorized explicitly (not implied by task
040's "no new mechanism" framing, which assumed the executor already
existed) — track it as its own task with its own soundness bar.

Implementation note (2026-09): the first production-composed shape is the
guarded two-`Add` numeric chain, emitted as one AArch64/x86-64 stencil with a
single typed entry and return. The larger LoadConst/LoadLocal/Binary glue span
remains bridge-backed because those operations carry observable VM effects and
cannot be represented by the floating-point ABI without a separately proven
register/exception convention.

## Scope
- crates/quench-runtime/src/stencil_arena.rs (execution entry point —
  currently single-leaf `execute_f64`-shaped calls)
- crates/quench-runtime/src/stencil_fact.rs (`RegionKey`/admission — the
  CFG single-entry-point proof already exists and should be reused, not
  rebuilt, for the multi-op case)
- crates/quench-runtime/build.rs (sequential byte emission for a chain of
  ops, using task 039's const-fn encoder discipline for every instruction in
  the chain, not just the first)
- crates/quench-runtime/src/stencil_select.rs

## Deliverables
- A real sequential-execution mechanism: given a build-time-admitted region
  spanning N canonical instructions (starting with the concrete `LoadConst →
  LoadLocalChecked → Binary(Add) → UpdateLocal → StoreLocal`-shaped glue
  task 040.1 identified as the actual hot sequence), emit one stencil whose
  native bytes execute all N operations in sequence before returning/
  advancing the PC by N — not N separate leaf calls, and not a single leaf
  claiming to cover more than it does
- Reuse the existing single-entry-point CFG admission proof (already sound
  for the current one-leaf case) — extend it to prove the *whole chosen
  instruction span* has no externally-reachable interior entry point, not
  just its first instruction
- Every hole/patch value for every instruction in the chain uses task 039's
  const-fn bit-packed encoder discipline — no hand-typed hex for the new,
  longer byte sequences either
- Complete ordinary-interpreter fallback remains reachable per-instruction
  within the chain, not just at the chain's boundary — if a fact this chain
  depends on later goes stale mid-sequence in a way the existing degrade
  path doesn't already handle, that's a correctness bug to catch here, not
  defer

## Validation

1. A CFG-soundness unit test proving multi-instruction span admission
   correctly rejects a span with an externally-reachable interior entry
   point (construct a synthetic counter-example spanning at least 3
   instructions, not reuse the single-instruction test)
2. A differential test comparing: (a) the ordinary interpreter executing the
   N-instruction sequence one at a time, (b) the new fused multi-op stencil
   executing the same sequence — identical observable output, register
   state, and PC advancement, for the concrete glue sequence from 040.1
3. A differential test for a program whose facts almost but don't quite
   match the admitted span (one instruction in the middle has an Unknown
   fact) — must correctly fall back to the ordinary interpreter for the
   whole span, not partially execute the fused stencil
4. `cargo test -p quench-runtime --lib` and `--features execution-trace` —
   both pass
5. Before/after measurement on `quench-bench/deegen-curriculum/017.js` and
   `019.js` (the arithmetic-heavy cases task 040.1 was aimed at) — record
   the wall-time delta in `docs/architecture-evidence.md`
6. Update `docs/copy-and-patch-jit.md`'s design section if the actually-built
   mechanism differs from the sentence quoted above in any material way —
   the doc must describe what's real, not what was aspirational

**Fail condition**: a "fused" stencil that silently executes fewer
instructions than its admitted span claims, or that partially executes
before falling back mid-sequence, is a correctness bug — worse than the
current single-leaf-only state, since it would look like it fused and
didn't. Validation item 3 (partial-match fallback) is the specific test that
must catch this.

## Non-goals
- Widening which opcodes get *any* coverage at all — this task makes the
  existing arithmetic-glue sequence actually fused; task 040's items 2-5
  (Call, Property, Array, ForI) can proceed as new single-leaf regions in
  the existing pattern without waiting on this task, since they weren't
  claiming multi-op fusion in the first place
- Tag register, hot-cold splitting — separate, already-tracked items
