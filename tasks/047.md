# 047: Reduce call-frame allocation overhead for the Call/CallN region

- **Theme:** deegen_full_jit
- **Executor:** codex
- **Depends on:** 040

## Context

External research check (2026-09): general interpreter/JIT literature on
call overhead identifies frame-allocation cost (building a full ABI-
compliant stack frame, saving/restoring registers the callee may not even
touch) as a persistent, non-speculative cost distinct from dispatch
overhead itself — reducible when the callee's shape is already known,
without needing type speculation or a deopt path. This is relevant because
task 040 landed `Call`/`CallN` region bridges, but curriculum measurements
(case 010, recursive fib; case 029, ackermann) still show 13-16x wall time
vs. Node on call-heavy recursive code even with those bridges present — the
bridges close a *coverage* gap (calls now go through a proven region
instead of pure `DISPATCH` fallback) but haven't been measured for whether
they reduce *frame-allocation* cost specifically, which is a separate
question from admission/coverage.

A separate, directly relevant finding from the same research pass: a 2025
paper ("An Attempt to Catch Up with JIT Compilers: The False Lead of
Optimizing Inline Caches") found that IC/coverage refinement has minimal
impact on overall JIT performance versus speculative optimization — which
this project has correctly decided not to build (see
`docs/deegen-alignment.md`'s closed "will not build" decision). This task
is scoped specifically to NOT be another round of coverage work chasing
that same diminishing return — it targets a different, non-speculative
lever (frame-allocation cost within an already-admitted region), not more
IC refinement.

## Scope
- crates/quench-runtime/src/stencil_arena.rs (bridge stencil execution)
- crates/quench-runtime/src/register_file.rs (call-frame layout)
- The `Call`/`CallN` region bridges landed by task 040

## Deliverables
- Profile first: with the existing `Call`/`CallN` bridges active, isolate
  frame-setup/teardown cost specifically (not general dispatch, not
  argument marshaling logic) for a monomorphic recursive call site — if
  frame allocation isn't a measured share of the cost, record that finding
  and stop; do not implement speculatively
- If justified: reduce redundant frame-setup work for the case where the
  callee's frame shape is already known from the region's admitted facts
  (e.g., a monomorphic recursive call to the same function doesn't need to
  re-derive layout each call) — reuse/pool frame storage where the existing
  bounded-arena/register-file discipline allows it safely, never an
  unbounded pool
- Keep the complete ordinary call path as fallback for any call shape the
  region doesn't admit (polymorphic/megamorphic callees, unknown arity,
  etc.) — this task only optimizes the already-admitted, already-proven
  monomorphic case

## Validation

1. The profiling step above, recorded with the actual measured frame-setup
   share of call cost — go/no-go, not assumed
2. Differential tests: identical observable output and correct frame
   isolation (no leaked state between calls) for recursive, non-recursive,
   and re-entrant call patterns
3. `cargo test -p quench-runtime --lib` and `--features execution-trace` —
   both pass
4. Before/after measurement specifically on curriculum cases 010 (fib) and
   029 (ackermann) — record the delta; a small or null delta is an
   acceptable, honest outcome if step 1's profiling already showed limited
   headroom
5. Confirm no unbounded frame pool/cache — bounded per this project's
   standing discipline (same bound class as `IcStubChain`'s megamorphic
   ceiling)

**Fail condition**: any frame-state leak between calls (a stale value
visible in a reused frame) is a correctness bug, not a performance
shortfall — recursive/re-entrant call tests must specifically probe for
this, not just check the top-level return value.

## Non-goals
- Any speculative type guessing about callees — that's the explicitly
  closed optimizing-JIT/deopt decision, not reopened here
- Widening which call shapes get region coverage — that's task 040's
  completed job; this task only optimizes cost within already-admitted
  shapes
