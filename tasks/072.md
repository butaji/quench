# 072: Prototype-chain method-dispatch cost, isolated from own-property access cost

- **Theme:** vm_completeness
- **Executor:** codex
- **Depends on:** 062, 071

## Context

Richards/DeltaBlue (and most idiomatic OO JS) are built almost entirely on
the `constructor.prototype.method = function` pattern — every method call
walks at least one prototype level to find the method, distinct from a
plain own-property read. Task 071 targets the IC-miss/layout-mismatch
constant factor broadly; this task asks a sharper, narrower question that
071's framing doesn't isolate: **does `GetN`'s fast/compact path even cover
a one-level prototype hit, or does every prototype-chain method lookup
already take the slow path regardless of shape stability** — independent
of whether the *shape itself* is stable (which 062's invariant suite
already covers for own-properties, but not specifically for a lookup that
must walk to the prototype to succeed).

The real Richards profile (`target/richards-profile-current.json`) shows
`GetN` as the single largest opcode by volume (6.3M occurrences) with a
`Slow`-lane fallback count of 4.28M in the same trace — a large absolute
number of expensive fallbacks, some unknown fraction of which is plausibly
prototype-chain method dispatch specifically, not own-property misses.
This task isolates that fraction.

## Scope
- crates/quench-runtime/src/properties.rs (property/prototype resolution)
- crates/quench-runtime/src/shape_cache.rs
- crates/quench-runtime/src/quickening.rs (IC state for prototype hits)

## Deliverables
- Build a minimal, isolated reproduction: a constructor function with one
  prototype method, many instances, called in a hot loop — measure whether
  this specific pattern (stable shape, but requiring a one-level prototype
  walk to resolve) hits the fast/compact `GetN` path or falls to `Slow`,
  using `execution-trace` counters
- If it falls to `Slow` even with a fully stable shape and prototype: that
  is the finding — the fast path's guard facts don't currently admit
  "found via one prototype level," only "found as an own property." Close
  the gap by extending the existing guard/fact vocabulary to cover a
  stable one-level prototype hit as its own admitted case, reusing the
  existing `Certainty::Proven/Guarded` discipline — not inventing a new
  representation
- If it already hits the fast path: report that finding plainly (this
  narrows where Richards/DeltaBlue's actual `Slow`-lane volume comes from,
  which is valuable evidence for task 071 even if this task itself finds
  nothing to fix)

## Anti-cheat validation (mandatory)

1. **Generalization check**: the isolated reproduction above (constructor +
   one prototype method) must use variable/function/method names distinct
   from Richards/DeltaBlue's actual identifiers, and the fix (if any) must
   help this generic synthetic case, not just Richards/DeltaBlue's literal
   classes (`TaskControlBlock`, `Scheduler`, etc. for Richards;
   `Constraint` subclasses for DeltaBlue).
2. `grep -rniE "richards|deltablue|TaskControlBlock|Scheduler" crates/quench-runtime/src crates/quench-node/src` — zero matches.
3. Full gates: `cargo test -p quench-runtime --lib` and
   `--features execution-trace`, neutral corpus, curriculum (especially
   stage-3 property-IC cases 011-016 and any prototype-shaped case), and
   the full v8-v7 suite — a fix must show general improvement on any
   prototype-method-dispatch-heavy workload, not just the two motivating
   benchmarks.
4. Before/after measurement recorded specifically for the isolated
   synthetic reproduction *and* Richards/DeltaBlue together — both must
   move, not just the benchmarks.

**Fail condition**: same as 071 — a fix that improves Richards/DeltaBlue's
score without a comparable improvement on the isolated synthetic
reproduction is disqualifying regardless of score improvement.
