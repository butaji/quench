# 67: Compile functions lazily and bound startup cost

## Outcome

Startup cost scales with the code a program runs, not with the code it loads.
Function bodies are specialized on first call, and realm setup does not
materialize intrinsics that are never used. Retained only where the paired
gate shows a benefit.

## Current gap

The OXC specializer compiles a whole script or module graph before execution,
and every realm builds all intrinsics eagerly. Node applications load large
`node_modules` graphs and run a small fraction of them. The eight V8-v7
fixtures do not exercise this, so tasks 26 and 61 do not measure it.

## Dependencies

See this task's `depends_on` in [index.json](index.json). This is phase C
(make it efficient). Startup measurement may run in any phase.

## Scope and implementation sequence

1. Measure startup (time and maximum RSS) for an empty script, a Node
   bootstrap, and a large real-world module graph. Record them next to the
   no-JIT reference engines through task 62's runner.
2. Split specialization so that static facts across function boundaries
   (captures, `arguments`/`eval` use, early errors) come from one pre-pass,
   and body lowering happens on first call. Early errors stay eager, as the
   spec requires. The residual store is append-only, as in task 18.
3. Instantiate intrinsic families lazily behind the realm's intrinsic table,
   installing from the operation table's install columns (task 46), where
   this does not change observable identity or ordering.
4. Evaluate a startup heap snapshot of the initialized realm against lazy
   intrinsics. Keep one mechanism. A snapshot is the first Futamura
   projection of realm initialization with no guest input. It is produced at
   build time by running the same table-driven initialization code, and it is never
   edited by hand. The build proves it by checking the snapshot against a
   fresh initialization.

## Verification

The full conformance ratchet over all three suites. Task 42's gate with lazy
and eager compilation. Test that each early error still reports before
execution.

## Definition of done

- Every retained mechanism has a paired startup report showing its benefit.
  Otherwise it is removed with a recorded negative result.
- Lazy compilation preserves early errors, identity, and ordering exactly.

## Performance evidence

Paired startup time and maximum RSS reports under `target/`, with provenance.
