# 094: Reclaim ownership graphs and executable code safely

## Outcome

Reclaim released JS/host/native ownership graphs and executable code while
retaining every live owner described by the activation and value-ownership
authorities.

## Current gap

Reference counting, cycle collection, environments, code stores and executable
leases have different physical ownership populations; none may silently invent
an identity or frame representation.

## Dependencies

See this task's `depends_on` in [index.json](index.json); status and ordering live there.

## Scope and implementation sequence

1. Audit owning edges and root enumeration, including multiplicity, shared captures, weak references, host state and suspended frames.

2. Repair mismatched lifecycle gauges and retention defects before tuning collector scheduling.

3. Measure collection frequency, visited edges, pauses, temporary memory and retained/released scenarios; implement the best-supported traversal/capture correction.

4. Evaluate moving/generational or other collector changes without an architectural ban, but migrate roots, barriers, weak references and safepoints together when selected.

## Verification

`cargo test -p quench-runtime`; `cargo test -p quench-node`; reserved lifetime/construction/closure micros with retained and released graph controls. Exercise code disposal, cycles, alias multiplicity, suspension and active native leases.

Apply the shared [completion checks](README.md), including named baseline failures
and independent semantic controls. Record commands and artifact identity.

## Definition of done

- Live owners survive collection and released graphs/code reclaim without unrelated global resets.
- Allocation/live gauges use consistent populations and lifecycle boundaries.
- Selected collector/capture changes have complete root/barrier coverage and controlled pause/RSS/throughput evidence.

## Performance evidence

Require a repeatable improvement in the declared retention or collection-cost metric; report throughput and pause tradeoffs. Proposal-only work does not close implementation.
