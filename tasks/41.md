# 41: Verify Wasm lowering consumes validator-derived types

## Outcome

Confirm that Wasm operator lowering reads operand/result types and block
arities from `wasmparser::Validator`'s already-proven results, rather than
re-inferring stack types independently during lowering.

## Current gap

`quench-wasm::decode::inspect_binary_with` runs full `wasmparser::Validator`
type validation before any lowering happens, establishing operand types at
every program point, block result arities, and `call_indirect` type-match
facts. It has not been confirmed whether the existing lowering
(`wasm/emit/ops.rs`, and its replacement under task 37) consumes these
validator-derived facts directly or re-derives stack types from the operator
stream a second time. If it re-derives, that is a second authority for a fact
the validator already proved — a "one fact, one representation" violation
that also risks the two type-inference paths silently disagreeing.

## Dependencies

See this task's `depends_on` in [index.json](index.json).

## Scope and implementation sequence

1. Trace whether task 37's operator lowering (the legacy `emit/ops.rs` is
   not ported and needs no audit) receives typed information from the validation pass
   (`wasmparser` exposes typed operator/function-body visitors for this
   purpose) or recomputes stack types from raw `Operator` values during
   lowering.
2. If lowering re-derives types independently, thread the validator's
   per-instruction type information through to the lowering pass so it
   becomes the sole authority, and delete the redundant inference.
3. If lowering already consumes validator-derived types, record that as the
   verified state so future changes don't accidentally introduce a second
   inference path.

## Verification

Add a regression test using a module that would type-check differently under
a naive re-inference than under the validator's actual result (e.g. a case
involving Wasm's subtyping/reference-type rules), confirming lowering matches
the validator's judgment rather than an independently recomputed one.

## Definition of done

- Lowering has exactly one source of operand/result type facts, and that
  source is verified in-session to be the validator's output, not a
  parallel inference.
- A regression test exists distinguishing correct validator-derived behavior
  from naive re-inference.

## Performance evidence

No speed claim required. Report whether removing a redundant inference pass
(if one is found) changes lowering time.
