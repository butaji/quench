# 46: Declare the kernel watermark

## Outcome

Split the next core into a small kernel of primitive operations and a library
defined entirely on top of it, with an enforced boundary between them. The
kernel can then be changed or replaced for experiments (representations,
dispatch, caches, specialization) without touching the library, and the
library cannot tell which kernel it runs on.

The model is metacircular in the Lisp sense. The kernel is the minimal set of
primitives, like `eval`/`apply` plus `car`/`cons`/`eq`. Everything else,
including the generic semantics of the kernel's own opcodes, is defined in
terms of those primitives. Implementation stays in Rust per the
[repository rules](../AGENTS.md); "defined on top" means written against the
kernel API, not self-hosted in JavaScript.

## Current gap

All next-core semantics are methods on one `Vm` type in one `vm` module:
heap, GC, shapes, and dispatch sit beside `array_builtins`, `date`, `json`,
`promise`, `regexp`, `typed_array_*`, and `reflect`. Any builtin can reach any
kernel internal, so a representation experiment touches everything, and
legacy ports (task 45 and the README's migration routes) have no fixed target.

The 2026-09-23 core review found that builtins, the registry's first
consumer, have no single authority. `Native` has 335 variants, and each
builtin is described in five places: the enum (`heap/cell.rs`), the `NATIVES`
list (`vm/builtins.rs`), the name at its `install_*` site, `native_length`
(in `vm/promise.rs`), and the family predicates (`is_collection_native`,
`is_disposal_native`, `is_object_static`, …) that `call_native` tests one after
another. `Vm` holds 25 separate `*_proto` fields, one per intrinsic prototype.
Per-kind variants (11 typed-array constructors, 16 `DataView` get/set, 10
`Atomics` operations) repeat what `TypedArrayKind` and an operation tag
already express.

The drift is visible in Test262 (`target/test262-next-task08-parallel.json`):
2,742 failing files are per-builtin metadata tests (`name.js` 743,
`prop-desc.js` 717, `length.js` 676, `not-a-constructor.js` 535, `proto.js`,
`prototype.js`). About 3,100 more fail with `Expected a undefined …` or
`different error constructor with the same name`. That is consistent with
error constructors lacking `name` or with errors created outside the realm's
intrinsics. Legacy Quench already records the name and length of each builtin
in `crates/quench-runtime/src/builtin_meta/`.

## The watermark as data

### 1. Kernel primitive table (downward)

One macro-declared table is the single authority for the kernel API. The
Rust API module, its documentation, and the boundary test are generated from
it. Each entry records:

| Column            | Meaning                                                                                                              |
| ----------------- | -------------------------------------------------------------------------------------------------------------------- |
| name, signature   | the Rust entry point the library calls                                                                               |
| spec counterpart  | essential internal method or abstract operation it realizes                                                          |
| effect class      | `pure`, `allocates` (a safepoint), `throws`, `reenters` (may run guest code); specializers read this, never infer it |
| role              | `fundamental` or `accelerated`                                                                                       |
| static evaluation | whether the generating extension may run it on static inputs (see below)                                             |

Fundamental primitives cannot be expressed through other primitives: tag
inspection, primitive constructors, cell allocation with a trace visitor,
string code-unit access, the essential internal methods (GetPrototypeOf,
SetPrototypeOf, IsExtensible, PreventExtensions, GetOwnProperty,
DefineOwnProperty, HasProperty, Get, Set, Delete, OwnPropertyKeys, Call,
Construct), throw/completion, rooting, and job enqueue.

An accelerated primitive (for example a dense-array element read) must name
its **reference definition** in the library, written with fundamental
primitives only. That keeps the kernel minimal: adding speed never adds
semantics, and any accelerated entry can be dropped with correct behavior
unchanged.

### 2. Library operation registry (upward)

The library declares every operation it defines in one registry. The kernel
reaches library semantics only through this registry, resolved statically
when the realm is built, with no name lookup at run time. Each entry states
its exposure:

- `intrinsic`: installed on a guest object, for example `Array.prototype.push`.
  Name, length, attributes, and constructor behavior are derived from the
  entry.
- `fallback`: the generic path of an opcode, for example ToPrimitive for `+`
  on objects, GetIterator for `for-of`, or OrdinaryHasInstance for
  `instanceof`.
- both, for example `Function.prototype[@@hasInstance]`.

Builtins and opcode fallbacks are one concept, library-defined operations,
so they have one registry and one metadata authority.

### 3. Object-kind dispatch table

The kernel owns storage kinds and internal-method dispatch. Exotic behavior
(Array `length`, Proxy traps, TypedArray indexing, arguments mapping, String
indices, module namespaces) is a library row keyed by object kind that
supplies overrides for specific essential internal methods. The kernel has no
per-kind branches. Where it carries a fast path for a kind, that path is an
accelerated primitive with the kind's library row as its reference definition.

## Futamura and Ershov across the watermark

The compiler is already a cogen-style generating extension doing Futamura's
first projection (P1), as [the v2 architecture](../docs/v2/architecture.md)
describes: `mix(interpreter, program) = residual`. After the split, the
"interpreter" in that equation is the kernel plus the library. The watermark
tables are therefore the generating extension's inputs, and each
binding-time class has one home in them:

| Binding time               | Watermark mechanism                                                                                                                                                                                                                                                     |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Static                     | A primitive or registry entry marked statically evaluable runs inside the generating extension on static inputs. Examples: ToNumber or ToString of a literal, string concatenation of constants, `typeof` of a literal. The residual receives the result as a constant. |
| Specialization environment | Intrinsics are addressed by index into the realm's intrinsic table, not by name. `[]` allocates with `%Array.prototype%` by index. Library registry entries, object-kind rows, and accelerated-primitive sites are compact tables indexed by instruction operands.      |
| Dynamic                    | An accelerated primitive is emitted either unguarded, when a `StaticValue` proof covers its precondition, or guarded. Its exact fallback is its reference definition, so the generic residual is the library's own semantics.                                           |

Rules that follow from this:

- **Mixed computation, one definition.** Ershov's mixed computation: one
  definition serves both binding times. Constant folding calls the same
  primitive or library definition that runs at execution time, and task 45's
  shared algorithms serve both too. There is no separate folder to drift from
  runtime semantics.
- **Statically evaluable means safe to run early.** An entry qualifies only
  if it is `pure` on primitive inputs, terminates, and is independent of realm
  state. It touches no objects, heap identity, or intrinsics that guest code
  can replace. Anything that can observe guest-mutable state stays dynamic,
  whatever values were seen in profiles or training runs.
- **Congruence from effect classes.** The binding-time analysis reads effect
  classes from the tables and never infers them. A `reenters` or `throws`
  operation ends static facts about the heap, the same way captured writes do
  today. A value computed from a dynamic input is dynamic. New proofs remain
  `StaticValue` variants plus transfer rules in `compile/binding_time.rs`.
- **The projections are closed over kernel data.** There is no
  self-application. The generating extension's derivable parts are generated
  by the Rust macros from the kernel's declared tables: opcode identities,
  effect tables, rewrite legality, fold eligibility, and guard/fallback pairs.
  This is the practical form of the second and third projections. A kernel
  experiment edits the tables, and the matching generating extension follows
  without hand changes to the compiler.
- **Correctness is the Futamura equation.** For every program `p` and input
  `d`, `⟦residual(p)⟧(d) = ⟦interpreter⟧(p, d)`. The reference kernel, with no
  accelerations, no specialization, and no static folding, is the closest
  executable form of `⟦interpreter⟧`. The default kernel is checked against
  it (task 47).

These rules bind from the first row: every table entry is declared with its
effect class, role, and static evaluability, even before task 47 derives
anything from them. A row without them is incomplete.

## Scope and implementation sequence

1. Declare the primitive table from the operations that exist today,
   classifying each entry's effect class, role, and static evaluability.
   Generate the API module from it. Add task 08 and 09 operations as rows when
   they land.
2. Split `quench-runtime-next` into a kernel crate and a library crate so the
   compiler enforces the watermark. The library depends on the kernel; the
   kernel depends on nothing above it.
3. Declare the library operation registry, with the same binding-time columns.
   Move existing builtins and abstract operations into it module by module,
   keeping Test262 passes unchanged (the task 20 ratchet).
4. From the split onward, new builtins and abstract operations land only in
   the library crate, as registry entries.

The registry replaces the five hand-maintained builtin views:

- One row per library operation carries owner intrinsic, property key, length,
  attributes, constructor behavior, effect class, and handler. The `Native`
  identity, installation, `name`/`length`/descriptor metadata, and
  `call_native` dispatch are generated from the rows. No `NATIVES` list,
  `native_length`, or family predicate remains.
- Seed names and lengths from legacy `builtin_meta`. It is metadata, not
  engine-bound code, so transcribing it into rows is migration, not
  reimplementation.
- Rows may be parameterized. A typed-array constructor carries its
  `TypedArrayKind`, and `DataView` get/set and `Atomics` carry an element kind
  or operation tag. The handler receives the parameter, and task 35 removes
  the per-kind variants and wrappers that remain.
- Intrinsics form one enum-indexed realm table that replaces the `*_proto`
  fields. Each row names its owner by that index. Errors raised by the kernel
  are constructed from the current realm's intrinsic, never a free-standing
  object.

## Verification

- The crate graph shows no library-to-kernel-internal edge and no kernel
  dependency on the library.
- A structural test rejects `pub` kernel items that are not in the primitive
  table, and table or registry rows missing an effect class, role, or static
  evaluability.
- Every opcode's generic path resolves to a registry entry.
- The metadata-test cluster (`name.js`, `length.js`, `prop-desc.js`,
  `not-a-constructor.js`) and the error-constructor identity cluster leave the
  task 48 failure report for every builtin that has a row.
- The Test262 ratchet shows no regressions after each move.

## Definition of done

- The kernel API, the library registry, and the object-kind table are each one
  declared table, and everything that crosses the watermark is derived from
  them.
- Every builtin and abstract operation lives above the watermark and uses only
  the kernel API.
- Every row carries its binding-time and effect facts.
