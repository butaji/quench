# 46: Declare the kernel watermark

## Outcome

Split the next core into a small kernel and a library defined entirely on top
of it, with an enforced boundary between them. The kernel can then be changed
or replaced for experiments (representations, dispatch, caches,
specialization) without touching the library, and the library cannot tell
which kernel it runs on.

The model is metacircular in the Lisp sense. The kernel is the minimal set of
primitives, like `eval`/`apply` plus `car`/`cons`/`eq`. Everything else,
including the generic semantics of the kernel's own opcodes and of ordinary
objects, is defined in terms of those primitives. Implementation stays in Rust
per the [repository rules](../AGENTS.md); "defined on top" means written
against the kernel API, not self-hosted in JavaScript.

The watermark is three declared tables: **operations**, **brands**, and
**facts**. Meaning lives in operation rows. Memory layout lives in brand rows.
Every fast path is guarded by fact rows. Everything that crosses the
watermark is generated from these three tables.

## Current gap

All next-core semantics are methods on one `Vm` type in one `vm` module:
heap, GC, shapes, and dispatch sit beside `array_builtins`, `date`, `json`,
`promise`, `regexp`, `typed_array_*`, and `reflect`. Any builtin can reach any
kernel internal, so a representation experiment touches everything, and
legacy ports (task 45 and the README's migration routes) have no fixed target.

The 2026-09-23 core review found that builtins, the registry's first
consumer, have no single authority. `Native` has 335 variants, and each
builtin is described in five places: the enum (`heap/cell.rs`), the `NATIVES`
list (`vm/builtins.rs`), the name at its `install_*` site, `native_length`
(in `vm/promise.rs`), and the family predicates (`is_collection_native`,
`is_disposal_native`, `is_object_static`, …) that `call_native` tests one after
another. `Vm` holds 25 separate `*_proto` fields, one per intrinsic prototype.
Per-kind variants (11 typed-array constructors, 16 `DataView` get/set, 10
`Atomics` operations) repeat what `TypedArrayKind` and an operation tag
already express.

The drift is visible in Test262 (`target/test262-next-task08-parallel.json`):
2,742 failing files are per-builtin metadata tests (`name.js` 743,
`prop-desc.js` 717, `length.js` 676, `not-a-constructor.js` 535, `proto.js`,
`prototype.js`). About 3,100 more fail with `Expected a undefined …` or
`different error constructor with the same name`. That is consistent with
error constructors lacking `name` or with errors created outside the realm's
intrinsics. Legacy Quench already records the name and length of each builtin
in `crates/quench-runtime/src/builtin_meta/`.

Layouts and guards have the same problem. Internal slots, private elements,
and environment records each use their own storage path. Cache checks and
invalidation are written separately at each fast path, and no declared
authority records which facts they rely on.

only crossing points. Layer 2 reaches guest values only through task 45's
`AlgorithmBoundary` trait. Each of its operations is an operation row with its
effect set: conversions, `Get`, realm-intrinsic errors, intrinsic identities,
and branded-slot allocation and reads. The next core's implementation of the
trait is derived from those rows.

## The watermark as data

### 1. Operation table

One macro-declared table is the single authority for every operation:
kernel primitives, abstract operations, brand handlers, opcode fallbacks, and
builtins. Each row records:

| Column           | Meaning                                                                                                                                                                            |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| selector         | an operation name, or an (internal method, brand) pair for a brand handler                                                                                                        |
| signature        | the Rust entry point                                                                                                                                                               |
| spec counterpart | the internal method or abstract operation it realizes                                                                                                                              |
| body             | `kernel` (fundamental), a library function, or a layer-2 algorithm                                                                                                                 |
| effect set       | a subset of `allocates` (a safepoint), `throws`, `reenters` (may run guest code), `realm` (reads realm state guest code can replace), `host`; the empty set is `pure`             |
| fast paths       | optional list of `when(facts) => kernel body`, each with its own effect set, which must be a subset of the row's                                                                   |
| install          | for intrinsics only: owner intrinsic, property key, length, attributes, and constructor behavior                                                                                   |

Roles are derived, not stored:

- A row is **fundamental** if and only if its body is `kernel`. A new
  kernel-bodied row must name the representation it creates or inspects that
  no library row can reach; otherwise it is a fast path on a library row.
- A row is **accelerated** if it has fast paths. Fast paths attach only to rows
  with a library or algorithm body, and that body is their exact fallback: the
  **reference definition**. Adding speed never adds semantics, and deleting a
  fast path never changes behavior.
- A row is **statically evaluable** if its effect set is empty. See the staging
  rules below.
- A row is an **intrinsic** if it has an `install` column, and a **fallback**
  if an opcode row names it. `Function.prototype[@@hasInstance]` is both.

The Rust kernel API module, its documentation, the `Native` identity,
installation, `name`/`length`/descriptor metadata, dispatch, and the boundary
tests are all generated from this table.

**Send.** JavaScript's message send is the spec's `Invoke(V, P, args)`:
`Call(Get(V, P, V), V, args)`. Unlike in Self, the lookup and the call are
separate, observable steps. Property keys and the well-known symbols
(`@@iterator`, `@@asyncIterator`, `@@toPrimitive`, `@@hasInstance`,
`@@species`, `@@match`, `@@unscopables`, `@@isConcatSpreadable`, …) are the
language's selectors. Every opcode whose generic path consults a protocol names
a fallback row composed of sends and value operations. Examples are `+` and
template literals (ToPrimitive), `instanceof`, `for-of`, spread,
destructuring, and `yield*`. No opcode may reach a protocol method except
through brand dispatch of `Get` and `Call`. That keeps the spec's order of
observable lookups and calls in one place, and it lets task 29's site caches
key sends by internal method.

**Opaque, cache-friendly API.** Kernel signatures expose results that caches
can hold, never records built only for a single spec step:

- Property lookup returns a lookup result (holder, shape, slot, attributes),
  not a freshly built descriptor.
- Key enumeration goes through a kernel-owned cursor, not a `Vec`.
- Values and cells are opaque handles, so value encoding and reference
  compression stay kernel-private (task 50).

Spec records such as property descriptors and completion records are library
values built from these results where the spec makes them observable.

### 2. Brand table

A brand is a named cell layout with optional behavior. Each row records:

| Column    | Meaning                                                                                                     |
| --------- | ----------------------------------------------------------------------------------------------------------- |
| brand     | the name, for example `Ordinary`, `Array`, `Proxy`, `MapData`, `BoundFunction`, or a class or scope brand   |
| slots     | fixed fields with their representation and trace behavior                                                   |
| overrides | internal methods whose handler is an operation row keyed by (method, brand)                                 |

Internal slots, private names, environment records, and exotic kinds are all
brands:

- `MapData` has slots and no overrides.
- `Proxy` has target and handler slots and overrides all internal methods;
  its handler rows call into the guest handler object.
- `Array` overrides `DefineOwnProperty` for `length` and indices.
- A class body derives a brand whose slots are its private fields. The layout
  is fixed per class body, and each evaluation of the class creates a new brand
  identity.
- A scope derives a brand whose slots are its bindings.

**Ordinary is a brand too.** Ordinary objects and ordinary functions are the
default brands, and their handlers are library rows written from the spec's
`Ordinary*` algorithms over kernel property storage. Every object therefore
answers internal methods the same way, as in Self, where an object's map
decides its behavior. Each brand row is a Proxy handler with fixed traps that
guest code cannot see. Proxy shows that the internal methods are a complete
object protocol, so a brand may override only internal methods.

The brand is stored once: in the shape for objects, and in the cell header
for cells that are not objects. Dispatch keys on it, and an inline cache hit
on a shape skips dispatch entirely. The kernel derives each brand's cell layout
from its row. Generic slot maps and identity-keyed side tables are not layouts
(task 44).

### 3. Fact table

A fact is a named predicate that fast paths depend on. Each row records:

| Column                   | Meaning                                                                                    |
| ------------------------ | ------------------------------------------------------------------------------------------ |
| predicate                | for example `ArrayProtoNoIndexed`, `ArrayIteratorPristine`, "receiver has shape S"          |
| owner                    | the shape, cell, brand, or realm whose state decides it                                    |
| invalidating transitions | the named mutations that make it false                                                     |
| state machine            | `Valid → Invalidated`; a new owner state yields a new fact instance, never a revived one    |

Protectors and prototype validity cells (the README's dependency-guarded row)
are fact rows, and so are the shape checks of inline caches. The same fact
serves every binding time. A proof removes its guard. Otherwise it is guarded
by one cell or shape read. A site cache learns which instance holds at that
site. No mechanism defines its own guard vocabulary.

## Futamura and Ershov across the watermark

The compiler is already a cogen-style generating extension doing Futamura's
first projection (P1), as [the v2 architecture](../docs/v2/architecture.md)
describes: `mix(interpreter, program) = residual`. After the split, the
"interpreter" in that equation is the kernel plus the library. The three
tables are therefore the generating extension's inputs, and each binding-time
class has one home in them:

| Binding time               | Watermark mechanism                                                                                                                                                                                                                         |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Static                     | A statically evaluable row runs inside the generating extension on static inputs. Examples: ToNumber or ToString of a literal, string concatenation of constants, `typeof` of a literal. The residual receives the result as a constant. |
| Specialization environment | Intrinsics are addressed by index into the realm's intrinsic table, not by name. `[]` allocates with `%Array.prototype%` by index. Operation rows, brands, and fact cells are compact tables indexed by instruction operands.          |
| Dynamic                    | A fast path is emitted unguarded when a proof covers its facts, and guarded otherwise. Its exact fallback is its row's reference definition, so the generic residual is the library's own semantics.                                    |

Rules that follow from this:

- **Mixed computation, one definition.** Ershov's mixed computation: one
  definition serves both binding times. Constant folding calls the same row
  body that runs at execution time, and task 45's shared algorithms serve both
  too. There is no separate folder to drift from runtime semantics.
- **Statically evaluable means safe to run early.** The empty effect set means
  the row touches no objects, heap identity, realm state, or intrinsics that
  guest code can replace. Folding runs it only on primitive inputs and under
  the fold budget (task 47), so a row that does not terminate cheaply stays
  dynamic. Anything that can observe guest-mutable state stays dynamic,
  whatever values were seen in profiles or training runs.
- **Congruence from effect sets.** The binding-time analysis reads effect sets
  from the tables and never infers them. A fragment's effects are the union of
  its parts. A `reenters` or `throws` operation ends static facts about the
  heap, the same way captured writes do today. A value computed from a dynamic
  input is dynamic. Facts narrow effects: a fast path's effect set applies only
  where its facts hold, so a data-slot `Get` on a guarded shape is `pure`. New
  proofs remain `StaticValue` variants plus transfer rules in
  `compile/binding_time.rs`, and each names the fact row it proves.
- **The projections are closed over kernel data.** There is no
  self-application. The generating extension's derivable parts are generated
  by the Rust macros from the three tables: opcode identities, effect tables,
  rewrite legality, fold eligibility, and guard/fallback pairs. This is the
  practical form of the second and third projections. A kernel experiment
  edits the tables, and the matching generating extension follows without
  hand changes to the compiler.
- **Correctness is the Futamura equation.** For every program `p` and input
  `d`, `⟦residual(p)⟧(d) = ⟦interpreter⟧(p, d)`. The reference kernel, with no
  fast paths, no packed layouts, no specialization, and no static folding, is
  the closest executable form of `⟦interpreter⟧`. The default kernel is checked
  against it (task 47).

These rules bind from the first row: every operation row is declared with its
body and effect set, and every fast path with its facts, even before task 47
derives anything from them. A row without them is incomplete.

## Scope and implementation sequence

1. Declare the operation table from the operations that exist today, with
   each row's body and effect set. Generate the kernel API module from it. Add
   task 08 and 09 operations as rows when they land. Declare the
   `AlgorithmBoundary` operations first, so task 45's Temporal pilot and bulk
   migration target rows rather than `impl Vm` methods.
2. Split `quench-runtime-next` into a kernel crate and a library crate so the
   compiler enforces the watermark. The library depends on the kernel; the
   kernel depends on nothing above it.
3. Declare the brand table for the existing object kinds, internal-slot
   records, private elements, and environment records. Derive their cell
   layouts from it, and move exotic behavior into brand handler rows.
4. Declare the fact table for the guards that exist today: method and site
   cache checks, and the protectors and validity cells tasks 29 and 34 add.
   Each existing fast path names its facts.
5. Move existing builtins and abstract operations into operation rows module
   by module, keeping all three pass sets unchanged (task 48's ratchet).
6. From the split onward, new builtins, abstract operations, brands, and guards
   land only as table rows.

The operation table replaces the five hand-maintained builtin views:

- One row per operation carries its install column, effect set, and body. The
  `Native` identity, installation, `name`/`length`/descriptor metadata, and
  dispatch are generated from the rows. No `NATIVES` list, `native_length`, or
  family predicate remains.
- Seed names and lengths from legacy `builtin_meta`. It is metadata, not
  engine-bound code, so transcribing it into rows is migration, not
  reimplementation.
- Rows may be parameterized. A typed-array constructor carries its
  `TypedArrayKind`, and `DataView` get/set and `Atomics` carry an element kind
  or operation tag. The body receives the parameter. This task removes the 11
  per-kind typed-array constructor variants, 16 `DataView` get/set variants,
  10 `Atomics` variants, the 11 per-kind `*_array_proto` fields, and the
  `typed_array_signed.rs`, `typed_array_float.rs`, and `typed_array_uint16.rs`
  wrappers. Per-kind rounding, clamping, signedness, byte width, constructor
  name, and prototype identity stay exactly as they are. (`Cell::TypedArray`
  already carries one `TypedArrayKind`.)
- Intrinsics form one enum-indexed realm table that replaces the `*_proto`
  fields. Each row names its owner by that index. The table is the source for
  lazy installation and the derived startup heap (task 67). Errors raised by
  the kernel are constructed from the current realm's intrinsic, never a
  free-standing object.

## Verification

- The crate graph shows no library-to-kernel-internal edge and no kernel
  dependency on the library.
- A structural test rejects:
  - `pub` kernel items that have no operation row;
  - rows missing a body or effect set;
  - fast paths on kernel-bodied rows, fast paths whose effect set is not a
    subset of their row's, and fast paths naming facts that have no row;
  - brand overrides of anything other than an internal method.
- Every opcode's generic path resolves to an operation row. A protocol
  consulted by an opcode is reached only through brand dispatch of `Get` and
  `Call`.
- The metadata-test cluster (`name.js`, `length.js`, `prop-desc.js`,
  `not-a-constructor.js`) and the error-constructor identity cluster leave the
  task 48 failure report for every builtin that has a row.
- The Test262, Wasm, and Node ratchets show no regressions after each move.

## Definition of done

- Operations, brands, and facts are each one declared table, and everything
  that crosses the watermark is derived from them.
- Every builtin, abstract operation, and brand handler, the ordinary ones
  included, lives above the watermark and uses only the kernel API.
- Every operation row carries its body and effect set, every brand its layout,
  and every fast path its facts.
