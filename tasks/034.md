# 034: Hot-cold code splitting by block-frequency analysis

- **Theme:** deegen_full_jit
- **Executor:** codex
- **Depends on:** 028

## Context

Paper §7.2: Deegen parses generated assembly, uses debug info to map lines
back to LLVM basic blocks, runs LLVM's block-frequency analysis to identify
cold blocks, and physically reorders assembly to move cold code to a separate
text section — plus, where the fast path can fall through to the next
bytecode, reorders so that fallthrough eliminates a branch entirely. Audit
found: `CodeView::cold`/`cold_at` (`machine.rs:2006-2013`) is an unrelated
compact-instruction operand-overflow table, not this. `docs/copy-and-patch-jit.md`
explicitly disclaims hotness-triggered mechanisms for the current tier — this
is genuinely unbuilt, not misnamed.

## Scope
- The build-time stencil-rendering script (wherever stencil bytes are
  produced — check for a `build.rs` step or codegen tool feeding
  `stencil_*.rs`'s static data)

## Deliverables
- Profile the neutral corpus first to identify whether cold-path code density
  inside rendered regions is a measured cost (icache pressure, branch
  misprediction) before implementing — this project's standing
  profile-before-implement discipline
- If justified: at stencil build time, classify basic blocks within a region
  as hot/cold (a static heuristic is acceptable if runtime profiling data
  isn't available at build time — document which), and lay out rendered
  region bytes so cold blocks are physically separated from the hot path
- Implement fallthrough branch elimination where a region's fast path already
  flows directly into the next dispatched region, per the paper's technique

## Validation

**Gate 0 (profile-first, mandatory before implementing):** Measure icache
pressure / branch misprediction around rendered-region execution on the
neutral corpus (`perf stat -e icache-misses,branch-misses` or equivalent).
Record the number. If it's below measurement noise, **stop here** — record
"not a measured cost, no implementation attempted" and do not proceed.

If Gate 0 justifies proceeding:
1. Implement build-time hot/cold block classification and layout separation.
2. Differential tests: identical observable output for every opcode whose
   rendering changed — this must be a pure layout change, verify no branch
   target or fallthrough semantics shifted.
3. `cargo test -p quench-runtime --lib` — all pass.
4. Re-run the Gate 0 profiling method and show the measured icache/branch
   cost dropped.
5. `node tools/architecture-size-report.cjs target/debug/quench-node > target/architecture-size-after.json` — record in `docs/architecture-evidence.md`.
6. `node quench-bench/micros/verify.mjs ... --from 1 --to 100 --runs 3` — 100/100, geomean improves or unchanged.

**Fail condition**: any semantic difference between hot and cold layout
variants of the same region (not just performance) is a correctness bug —
verify byte-for-byte that only block *placement* changed, not block content.

## Non-goals
- Runtime profiling-driven hot/cold reclassification — that would be a
  tier-up-adjacent mechanism and is out of this task's scope; static
  build-time classification is sufficient to match the paper
