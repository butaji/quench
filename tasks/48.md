# 48: Make the full next-core Test262 run fast and ratcheted

## Outcome

A full Test262 run on the next core is fast enough to repeat after every
kernel change or experiment, and its result is compared automatically against
the last recorded pass set. This is what keeps Test262 at 100% while the kernel
changes behind the watermark (tasks 46 and 47).

## Current gap

Runner behavior, per-test reports, and the pass-set ratchet are implemented.
Closure still requires task 20's complete 100% result to seed the ratchet, plus
the full-run wall-time and peak-RSS evidence. No full inventory is run as part
of this focused regression work.

## Dependencies

See this task's `depends_on` in [index.json](index.json). It needs only the
existing `run-all-next` runner. Task 46 depends on it: every move across the
watermark is checked against this ratchet.

## Scope and implementation sequence

1. Run cases in parallel with a configurable job count defaulting to available
   cores. The coordinator owns discovery and sends each exact path directly to
   its case process; store outcomes by discovery index so reports are
   identical to a serial run's.
2. Give each test its own deadline and record expiry as `timed_out`. Remove
   chunk bisection and the redundant chunk-worker process layer. Each test's
   process is already the crash and timeout isolation boundary.
3. Write a per-test outcome file with provenance: source revision, binary, and
   host. Make `compare-runs` report newly failing tests against the last
   recorded pass set and exit nonzero on any regression.
4. Report pass/fail counts per stage and per failure cluster (shared reason,
   missing builtin, missing syntax feature, harness include). This is the
   worklist that task 20 picks from. Cluster on the thrown error's message
   text, normalized for digits, quoted values, and `«…»` operands, not on the
   whole `JsError { … thrown: Some(heap(N)) }` debug rendering, which puts
   most failures into one opaque group. Also report metadata-test clusters by
   file basename (`name.js`, `length.js`, `prop-desc.js`,
   `not-a-constructor.js`).

what this step should produce, and it maps the largest groups to their owning
tasks:

5. Freeze the next core's own pass set as the ratchet baseline once task 20
   closes: every discovered test, with source revision, binary, host, and
   timeout provenance. The legacy-pass/next-fail worklist is retired. The next
   core passes every stage that legacy passed, and the legacy runtime is
   deleted at task 27, so a legacy baseline would compare against something
   that is about to disappear.

## Verification

- Serial and parallel runs produce identical inventories and
  classifications.
- An existing Test262 case run with an intentionally short configured
  deadline is recorded as `timed_out` without changing suite files.
- Comparing successive existing Test262 reports detects any newly failing
  case; do not inject a code regression or add a fixture for this check.
- The full suite completes in minutes on an M4. Record the wall time.

## Definition of done

- One command produces a full next-core report and its ratchet verdict.
- A frozen next-core 100% outcome file exists. Every full run diffs against it,
  and any newly failing test fails the command.
- Timeouts, crashes, and failures are classified per test.
- A full run is routine after every kernel change.

## Implementation evidence

`run-all-next` sends each discovered path directly to a killable child process.
A fixed worker pool claims cases from one shared index and merges outcomes by
discovery order, so scheduling does not change report ordering. Every child
requires a positive `TEST262_TEST_TIMEOUT_MS`; stderr is drained while it runs
so a full pipe cannot turn a failure into a timeout. The sequential stage
runner uses deterministic batches of at most 100 cases and the same configurable
worker count.

The durable report records source and binary provenance, host, timeout, worker
count, per-test outcomes, stage counts, normalized failure families, and
metadata-test basename clusters. Full clean runs create or advance the next
core pass-set ratchet; incomplete and batch runs cannot mutate it. The saved
baseline remains gated on task 20's 100% result.

Focused verification covers byte-identical serial and four-worker reports for
eight existing files, stage 0's 116 cases under one and four workers, an
eight-case parallel subset, pass-set loss detection, incomplete-run baseline
preservation, failure normalization, metadata basenames, timeout
classification, and concurrent stderr draining. `cargo test -p quench-test262
--bin run-all-next` passes 6/6, `cargo check -p quench-test262 --bins` passes,
and an existing case with a 1 ms deadline is reported as `timed_out after 1ms`.
No full Test262 inventory run was performed.

A historical uncapped sweep completed 53,404 discovered files with 20,169
passing and 33,235 failing. That partial result is retained at
`target/test262-next-task08-parallel.json` as runner evidence, not a conformance
claim or ratchet baseline.

The default Cargo `dev` profile uses `opt-level = 0` for faster incremental
builds; conformance uses the separate level-one `iteration` profile, and the
iteration and production settings are unchanged. On the recorded M4 build,
the stage runner took 20.65 seconds on its first build and 0.20 seconds on an
unchanged rebuild. This measures edit/build time, not suite throughput.
