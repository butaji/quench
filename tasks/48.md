# 48: Make the full next-core Test262 run fast and ratcheted

## Outcome

A full Test262 run on the next core is fast enough to repeat after every
kernel change or experiment, and its result is compared automatically against
the last recorded pass set. This is what keeps Test262 at 100% while the kernel
changes behind the watermark (tasks 46 and 47).

## Current gap

The runner isolates each test in a child process. Closure still requires a
complete run, a durable outcome/provenance file, a pass-set ratchet, and
failure summaries grouped by stage and family. Each test process has a required
positive deadline; no runner silently starts with an unbounded wait.

## Dependencies

See this task's `depends_on` in [index.json](index.json). It needs only the
existing `run-all-next` runner. Tasks 19 and 20 depend on it.

## Scope and implementation sequence

1. Run cases in parallel with a configurable job count defaulting to available
   cores. The coordinator owns discovery and sends each exact path directly to
   its case process; store outcomes by discovery index so reports are
   identical to a serial run's.
2. Give each test its own deadline and record expiry as `timed_out`. Remove
   chunk bisection and the redundant chunk-worker process layer. Each test's
   process is already the crash and timeout isolation boundary.
3. Write a per-test outcome file with provenance: source revision, binary, and
   host. Make `compare-runs` report newly failing tests against the last
   recorded pass set and exit nonzero on any regression.
4. Report pass/fail counts per stage and per failure cluster (shared reason,
   missing builtin, missing syntax feature, harness include). This is the
   worklist that task 20 picks from. Cluster on the thrown error's message
   text, normalized for digits, quoted values, and `«…»` operands, not on the
   whole `JsError { … thrown: Some(heap(N)) }` debug rendering, which puts
   most failures into one opaque group. Also report metadata-test clusters by
   file basename (`name.js`, `length.js`, `prop-desc.js`,
   `not-a-constructor.js`).

## Verification

- Serial and parallel runs produce identical inventories and
  classifications.
- An existing Test262 case run with an intentionally short configured
  deadline is recorded as `timed_out` without changing suite files.
- Comparing successive existing Test262 reports detects any newly failing
  case; do not inject a code regression or add a fixture for this check.
- The full suite completes in minutes on an M4. Record the wall time.

## Definition of done

- One command produces a full next-core report and its ratchet verdict.
- Timeouts, crashes, and failures are classified per test.
- A full run is routine after every kernel change.

## Implementation evidence

`run-all-next` requires a positive `TEST262_TEST_TIMEOUT_MS` before starting.
Each test runs in a killable child process and is
recorded independently when it fails or times out. Eight existing Test262
files produced byte-identical serial and four-worker reports. The first
uncapped sweep completed all 53,404 discovered
files with 20,169 passed and 33,235 failed. Its largest reported families were
`language/expressions` (5,637), `language/statements` (4,836),
`built-ins/Temporal` (4,603), and `intl402/Temporal` (2,029). The most common
normalized causes were assertion mismatches (8,705), unbound names (5,738),
syntax/parse errors (5,080), and non-callable values (3,054). The report is at
`target/test262-next-task08-parallel.json`; task 20 still needs the pass-set
ratchet and stage/failure-family report format.

The coordinator now passes each discovered path directly to its per-case
process; it no longer launches chunk workers that rediscover the full suite or
write intermediate JSON reports. A fixed thread pool claims the next case
from a shared index, so a slow case no longer creates a wave barrier. Results
are stored and merged by discovery index, independent of scheduling. The
`wait-timeout` crate supplies deadline-aware child waits instead of 2 ms
polling loops. The sequential stage runner caches its executable path once and
runs each bounded (at most 100-case) batch through the configurable
`TEST262_JOBS` thread pool, restoring results to their original slots before
reporting. Per-case timeout remains mandatory; the removed chunk-worker
timeout is no longer applicable. `cargo check -p quench-test262 --bins`
passes. Stage 0 passes 116/116 with both `TEST262_JOBS=1` and
`TEST262_JOBS=4`; an 8-case `run-all-next` subset has byte-identical JSON
reports under both schedules. These runs verify runner invariants only; they
do not claim broader conformance. An existing first-inventory case with a
1 ms configured deadline is recorded as `timed_out after 1ms`, with one explicit
failure record and no suite changes.

The default Cargo `dev` profile now uses `opt-level = 0` while retaining
incremental compilation; conformance execution remains on the separate
level-one `iteration` profile. Building the next-runtime stage runner with the
dev profile took 20.65 seconds on the first build including dependency
compilation, then 0.20 seconds on an unchanged rebuild. The iteration profile
and production profile are unchanged. This improves the local Rust edit/build
cycle, not Test262 runtime throughput. Build contract is documented in
`docs/README.md` and configured in the workspace `Cargo.toml`.
