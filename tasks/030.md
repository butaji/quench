# 030: Register pinning for VM dispatch state

- **Theme:** deegen_full_jit
- **Executor:** codex
- **Depends on:** 028

## Context

Paper §6.1: Deegen uses a guaranteed-tail-call calling convention (GHCcc, no
callee-saved registers, all arguments in registers) and pins core VM state
(bytecode pointer, frame pointer, etc.) into fixed registers across the
entire dispatch loop, so the interpreter never needs to save/reload them
across calls. Audit confirmed: quench's dispatch (`vm_dispatch.rs`,
`vm_runtime.rs`) passes `CodeView`/`RegisterFile`/`VmContext` as ordinary Rust
function parameters, leaving register allocation to rustc/LLVM — no pinning.

## Scope
- crates/quench-runtime/src/vm/vm_dispatch.rs
- crates/quench-runtime/src/vm/vm_runtime.rs

## Deliverables
- Profile first: confirm register spill/reload around the hot dispatch path
  is a measured cost before implementing (this project's standing
  profile-before-implement discipline, per task 019/026)
- If justified, investigate whether Rust/LLVM exposes a comparable mechanism
  (e.g. a custom calling convention attribute, or restructuring hot state
  into a single pointer-sized struct passed in one register) to approximate
  the paper's pinning without unsafe ABI hacks that would compromise
  correctness or portability
- Document the concrete mechanism chosen and why, since Rust has no direct
  equivalent to LLVM's `GHCcc` used by Deegen's C++/LLVM pipeline

## Acceptance
- Neutral corpus geomean improves or is unchanged; never regresses
- No unsound `unsafe` register-pinning hack — if no safe mechanism achieves a
  measurable win, document that as the honest outcome rather than force it
- Differential tests unchanged

## Non-goals
- Rewriting the dispatch loop's control-flow model (task 026's CPS work
  already did that) — this is a register-allocation-level change only
