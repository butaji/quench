# 073: Close the loop — track and reach a 60k v8-v7 aggregate score

- **Theme:** vm_completeness
- **Executor:** codex
- **Depends on:** 052, 068, 070, 071, 072

## Context

This is the capstone task for the `north_star` field in `tasks/index.json`:
a mature JS VM reaching V8-comparable performance on the real v8-v7 suite,
minimal RSS, zero benchmark-specific cheating. Every other task in this
backlog is a lever toward that number; this task is the single place that
states, explicitly, what the number is, exactly how it's measured, which
areas move it, and what "done" means — so progress toward 60k is tracked
as one coherent trajectory instead of scattered across dozens of task
files and evidence-doc paragraphs.

Starting point (most recent recorded baseline): aggregate ~92.70 across
only 3 of 8 benchmarks completing (Richards 52.1, DeltaBlue 46.9, Splay
326) inside a 10-second timeout. Target: ~60,000 aggregate across all 8
benchmarks completing with verified output, roughly matching Node's own
local aggregate (68,723) — "V8-comparable," not "beats V8."

## Measurement methodology (the only source of truth for progress)

Use the v8-v7 tracked runner from task 052, run against the same optimized
`target/debug/quench-node` artifact each time, same `--runs` count, escalate
timeout per task 070's findings (not the original 10s). For every run,
record in `docs/architecture-evidence.md`:
- Per-benchmark: score, peak RSS, output-equality vs. Node, completion time
- Aggregate score across all 8 (only meaningful once all 8 complete —
  per task 070, a partial aggregate is explicitly not a whole-suite score)
- Aggregate RSS ratio vs. Node (the other half of the north_star — a score
  win that regresses RSS is not progress)
- Cross-check: the same run's neutral-corpus (`micros/verify.mjs`) and
  curriculum (`deegen-verify.mjs`) scores, every time — a v8-v7 improvement
  that isn't accompanied by a neutral-corpus/curriculum improvement (or at
  minimum no regression) is a signal of overfitting to specifically flag,
  not silently accept

## Explicit areas where tuning moves this number, and how each is measured

1. **Stencil/JIT execution being real, not opt-in-disabled** (task 068).
   Measured by: neutral-corpus + curriculum score with native execution
   default-on vs. the current interpreter-fallback-only default.
2. **IC/property-dispatch constant factor** (071) and **prototype-chain
   dispatch specifically** (072). Measured by: absolute instruction/cycle
   cost of one isolated IC-miss/prototype-dispatch event
   (`execution-trace` counters), plus curriculum stage-3 cases 011-016 and
   Richards/DeltaBlue moving together (per 071/072's anti-cheat
   requirement — one without the other is a red flag, not a win).
3. **Region-scope growth and multi-variant regions** (048/049) — grown
   only once 067's stencil-tier invariants and 068's execution-is-real fix
   land. Measured by: curriculum cases matching the grown region shapes,
   plus the same v8-v7 cross-check already required by 048/049's own files.
4. **Benchmark completion itself** (070, 069 for Crypto specifically) —
   the prerequisite for the other 4 having anything to measure against for
   5 of the 8 benchmarks. Measured by: completion time and output-equality,
   not a score, until completion is established.
5. **Regex** (053), **TypedArray/array coverage** (054), **allocation
   throughput** (055) — each profile-gated; measured by their own before/
   after numbers on the specific v8-v7 benchmark they target (RegExp,
   NavierStokes, RayTrace/EarleyBoyer respectively), cross-checked against
   neutral corpus/curriculum per their own anti-cheat sections.
6. **Memory correctness** (056/057, cycle leaks) — measured by RSS
   specifically, not score: does aggregate RSS stay bounded across a
   long-running-process-shaped test, not just a single benchmark pass.
7. **Shape hash-consing** (058) and **arena allocation** (059) — measured
   by RSS primarily, score secondarily, per their own task files.

## Deliverables
- A running trajectory table in `docs/architecture-evidence.md`: one row
  per full-suite measurement (date/commit, aggregate score, aggregate RSS
  ratio, benchmarks-complete count, neutral-corpus score, curriculum
  score) — append to it as levers above land, don't just overwrite the
  latest number
- Re-run the full measurement after each of this task's dependencies
  (052/068/070/071/072) lands, and after any of the profile-gated tasks
  (053-060) produces an implemented change (not after a no-go — no-go
  findings don't move the number and don't need a new trajectory row)
- When the aggregate reaches or approaches 60,000 with all 8 benchmarks
  output-verified: a closing summary in `docs/architecture-evidence.md`
  stating which levers contributed how much, so the trajectory is
  explainable, not just a final number

## Anti-cheat validation (mandatory, applies to the whole trajectory, not just one task)

1. Every row in the trajectory table must show the paired neutral-corpus
   and curriculum numbers alongside the v8-v7 number — a row with a v8-v7
   jump and no corresponding neutral-corpus/curriculum movement is a red
   flag to investigate before recording it as genuine progress, not to
   celebrate.
2. `grep -rniE "richards|deltablue|splay|crypto|raytrace|earley|navier|regexp" crates/quench-runtime/src crates/quench-node/src` must stay clean (zero matches referring to fixture identity) at every point this task records a trajectory row — run it as part of each measurement cycle, not just once.
3. Any single benchmark's improvement must be explainable by a named,
   general mechanism (cite the task number that produced it) — "score went
   up" with no attributable cause is not acceptable evidence for this
   task's trajectory table.

**Fail condition**: recording a v8-v7 score improvement in the trajectory
table without the paired neutral-corpus/curriculum numbers, or without the
anti-cheat grep check for that measurement cycle, is incomplete — this
task's entire purpose is to keep the score honest, not just high.

## Non-goals
- Implementing any of the levers itself — this task tracks and closes the
  loop across the tasks that do; it does not duplicate their scope
