# 90: Decide how quench-node implements the Node API

## Plan scope

Deferred and outside the two-stage plan; nothing depends on it. It records a
strategy decision to make after cutover. It adds no Stage A gate and does not
override task 21's rule to migrate the existing host rather than fork it.

## Question

Which of these should own Node API behavior?

- **A. Hand-written (current):** Node APIs implemented in Rust plus about
  37k lines of hand-written JavaScript embedded in 258 `checked_js!` sites in
  `crates/quench-node/src`.
- **B. Upstream library:** run Node's own `lib/*.js` from the pinned
  `tests/node` checkout as guest code. Rust then implements only the
  `internalBinding` surface: fs, TCP/pipe/TTY wraps, timers, crypto, zlib, the
  HTTP parser, os, process, module wrap, buffer, URL, serdes and the
  V8-specific `util`/`v8`/`errors` bindings.

## Evidence to gather

- **Compatibility:** upstream `test/parallel` results for one module family
  (start with `http` plus `stream`) under A and under B, against the local
  oracle.
- **Cost:** startup time and maximum RSS for `require('http')` and a minimal
  server on the interpreter, with lazy compilation ([task 67](67.md)).
- **Binding surface:** the exact `internalBinding` and `primordials` set the
  chosen family needs, and which V8-specific behaviors must be emulated.
- **Code size:** Rust and guest lines removed and added; `quench-js-check`
  disappears under B.

## Trade-offs

B matches Node by construction: error codes, validation order, stream and
http state machines, and the behavior the upstream suite asserts. The Rust
code shrinks to OS-bound bindings. Its costs are interpreter startup work for
library code, heavy `primordials` use, and emulating V8-specific bindings.
A keeps startup small but must reproduce every observable Node detail by
hand.

## Definition of done

A recorded decision with the measurements above. If B is chosen, a migration
plan proceeds module family by module family, each keeping
`quench_runtime::embed` as the only runtime boundary and each passing its
affected inventories before the next starts.
