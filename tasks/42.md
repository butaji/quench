# 42: Prove specialization is behavior-preserving via a disable-specialization gate

## Outcome

Mechanically prove, across the full Test262, Wasm, and Node-compat suites,
that every specializer (inline caches, numeric arming, superinstruction
fusion, closure binding-time opcode selection, call-site argument binding,
Wasm binding-time materialization) is behavior-preserving relative to the
generic/unspecialized interpreter path — not merely covered by each
specializer task's own hand-picked differential cases.

## Current gap

Every specializer task (29-34, 37-39) is built as a guard-and-exact-fallback
construction: this is the standard partial-evaluation correctness
requirement (a specialized residual must compute the same result as the
unspecialized interpreter for every input) but nothing currently turns "the
generic path is ground truth" into an automated, suite-wide check. Each
task's Verification section asks for targeted differential cases (shape
flips, megamorphic sites, deopt mid-loop), which is necessary but is
sampling, not a proof over the full conformance surface. Task 19 already
built the reusable machinery this needs: shared differential-result records
and shared suite discovery so runs are directly comparable.

## Dependencies

See this task's `depends_on` in [index.json](index.json).

## Scope and implementation sequence

1. Add a build/runtime configuration that forces every specializer to always
   take its generic fallback path (property/method cache lookup always
   treated as miss, numeric opcodes never armed, superinstruction fusion
   never applied, closure locals never opcode-selected ahead of time,
   call-site argument binding never specialized, Wasm constants never
   materialized) — the pure-interpreter configuration that already has to
   exist as every specializer's fallback target.
2. Run Test262, the pinned Wasm testsuite, and the tracked Node-compat
   inventory through both the fully-specialized and the
   specialization-disabled configuration, using task 19's existing
   differential-record format and suite-discovery machinery rather than a
   new comparator.
3. Require byte-identical differential records (values, output, errors,
   descriptors, ordering, exit status, host effects) between the two
   configurations for every fixture in all three suites; any divergence is a
   specializer correctness bug, independent of whether it was caught by an
   individual specializer task's targeted tests.
4. Exclude specialization-disabled runs from any performance parity claim
   (task 26): this configuration exists solely to prove behavior
   preservation and is expected to be slower.
5. Wire this gate to run whenever a specializer/simplification/frontend task
   lands, using whatever suite coverage exists at that point (task 19/20/22/23
   need not be at 100% yet), so a specializer bug is caught at landing time
   rather than deferred to task 24's full convergence.

## Verification

Confirm the disable-specialization configuration actually disables every
specializer covered by tasks 29-34 and 37-39 (a specializer left armed by
mistake would silently defeat this gate's purpose). Run the gate against a
deliberately broken specializer (introduced and reverted) to confirm it
reports the mismatch rather than passing silently.

## Definition of done

- One gate runs both configurations across all three suites and reports any
  divergence as a failure.
- The gate is re-run at every specializer/simplification/frontend task's
  landing, not only at task 24.
- Task 26's Score/RSS parity measurements are taken only from the
  fully-specialized configuration.

## Performance evidence

Report the specialized-vs-disabled runtime delta as evidence the gate is
actually exercising specialized code paths, not as a parity claim.

## Implementation evidence

`Engine::specialize_unspecialized` now runs the same OXC parser/compiler and
residual validator with binding-time, rewrite, numeric, and dispatch-class
specialization disabled. This is the staged generic-path foundation without a
second compiler or runtime; a focused compiler test confirms its functions
remain on the general dispatch class. Residual programs now carry an explicit
specialization mode through the binary ABI, and the shared VM bypasses field
and method caches in disabled mode; the focused API comparison therefore
exercises the actual generic property path. Suite-wide differential execution
remains open, so this task is not done. The runtime API comparison covers a
cached computed property, a method call, and arithmetic operation.
