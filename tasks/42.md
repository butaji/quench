# 42: Check existing specialization against the shared generic path

## Outcome

Verify that the single VM's existing specializations preserve behavior through
its generic fallback. This supplies affected-path evidence to task 24;
it does not require implementing future Stage B optimizations or deferred
watermark machinery.

## Current gap

Generic compilation and property-cache bypass exist. Required affected-path
comparisons must accompany changes; task 24 owns integrated suite closure.

## Dependencies

See `depends_on` in [index.json](index.json).

## Scope and verification

Use the same parser, compiler, residual validator, VM and suite discovery in
normal and specialization-disabled development configurations. Disable only
mechanisms actually present. Compare observable values, descriptors, identity,
ordering, errors, exit status and host effects through the existing result
records; preserve raw outcomes and exact inventory provenance.

During changes, run only affected Test262 stages plus compare-runs and affected
Wasm/implemented Node cases. Verify that the relevant specialized path is
actually bypassed and that the comparator detects mismatches. The three
complete production inventories run at gates 24/27 and stage transitions. A separate full generic-mode campaign is not a Stage A closure
requirement. Unimplemented Node cases are outside the gate.

New Stage B mechanisms extend this check when selected by measured gaps. They
are not Stage A prerequisites. Both modes execute in the sole VM; production
has no old/new engine selector. Generic-mode runs are correctness evidence,
not performance qualification.

## Definition of done

- Existing specialization and its generic path have matching observable
  outcomes on affected cases, with exact inventory provenance.
- Ordinary changes use affected scopes and regression comparisons.
- No second compiler or execution core is introduced, and no future
  optimization or deferred architecture proposal blocks Stage A.

## Implementation evidence

`Engine::specialize_unspecialized` now runs the same OXC parser/compiler and
residual validator with binding-time, rewrite, numeric, and dispatch-class
specialization disabled. This is the staged generic-path foundation without a
second compiler or runtime; a focused compiler test confirms its functions
remain on the general dispatch class. Residual programs now carry an explicit
specialization mode through the binary ABI, and the shared VM bypasses field
and method caches in disabled mode; the focused API comparison therefore
exercises the actual generic property path. `quench-next --generic` exposes
that mode to the development runner, and `diff-next.mjs` records optimized,
generic, legacy, and Node outcomes plus an optimized-vs-generic equality for
each fixture. Recorded focused controls do not establish a complete audit
of every existing specialization, so this task remains open. The runtime API comparison covers a cached prototype property, a
method call, and arithmetic operation.
