# 036: Verify and document the beyond-paper Optimizing tier as a kept, measured net win

- **Theme:** deegen_full_jit
- **Executor:** codex
- **Depends on:** 035

## Context

`machine.rs` has a third promotion tier (`ExecutionTier::Optimizing`,
`OptimizingPlan`) beyond the paper's two tiers. Its own doc comment is
explicit: "a physical execution view, not a second semantic IR" — it
re-wraps the same baseline entries/stencil plans, gated to `x86_64`, with no
real instruction selection, register allocation, or speculation (so it needs
no deopt — it never speculates). User decision: keep it. This task is to
confirm it earns its keep and stop it from being mistaken for the paper's
(unimplemented) optimizing JIT.

**Note (superseded gate):** this task's original `x86_64`-only gate is
widened by task 039 to `any(x86_64, aarch64)`. Task 039's validation
explicitly re-runs this task's paired measurement once AArch64 execution is
real — the "not a measured net win" result recorded below was ARM64-
confounded (no compiled code executed on this host at the time), not a final
verdict.

## Scope
- crates/quench-runtime/src/machine.rs
- docs/deegen-alignment.md

## Deliverables
- Measure the neutral micro-corpus with the `Optimizing` promotion enabled
  vs. disabled (e.g. clamp `OPTIMIZATION_WARMUP_MULTIPLIER` effectively to
  never promote) to confirm it's a real, positive delta and not dead weight
  carried for free
- Document it plainly in `docs/deegen-alignment.md` (already drafted) and in
  a code comment at `ExecutionTier::Optimizing`'s definition: this is a
  quench-specific extra layer, not part of Deegen's own two-tier design, and
  never claims to be an optimizing compiler

## Validation

1. Run the neutral corpus with `Optimizing` promotion reachable (normal
   config) vs. forced-disabled (clamp `OPTIMIZATION_WARMUP_MULTIPLIER`/
   threshold so `TierState` never reaches `Optimizing`): record both full
   `quench-bench/micros/verify.mjs --from 1 --to 100 --runs 3` results
   side-by-side in `docs/deegen-alignment.md`.
2. The comparison must show a real, positive aggregate delta from having the
   tier enabled — if the two runs are statistically indistinguishable (within
   ~2-3% noise), that's a fail: report it plainly rather than calling a wash
   a "win".
3. `grep -rn "optimizing" crates/quench-runtime/src` (case-insensitive) and
   review every hit's surrounding comment/doc for language implying this is
   Deegen's paper-defined optimizing JIT; fix any that do.
4. Add or confirm a code comment directly at `ExecutionTier::Optimizing`'s
   definition in `machine.rs` stating plainly: quench-specific extra
   promotion layer, re-wraps baseline entries, not a second semantic IR, not
   the paper's (nonexistent) optimizing JIT.
5. `cargo test -p quench-runtime --lib` — all pass, no behavior change from
   this task (it's measurement + documentation only).

**Fail condition**: proceeding to mark this task done without the two-run
comparison numbers actually recorded — "it's probably fine" is not
acceptable evidence here.

## Non-goals
- Building it out further into a real optimizing compiler (out of scope
  unless separately requested) — this task only verifies and documents what
  already exists
