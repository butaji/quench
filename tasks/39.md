# 39: Share a structured control-flow scope stack across front ends

## Outcome

Give both the OXC statement lowering and the Wasm operator lowering one
canonical "open control scope" representation (exit label, result arity,
pending jump-patch sites) instead of each front end maintaining its own
independent scope-stack shape.

## Current gap

The legacy Wasm lowering's `emit/mod.rs` defines `Ctrl`/`CtrlKind`
(Func/Block/Loop/If/Try with height/results/params/result_regs/param_regs/
end_jumps/else_jump/catch_fixups) to track structured control flow while
compiling. The JS side solves the same class of problem across
`control_flow.rs`/`control_flow_collect.rs`/`statement_control.rs` in the
legacy `quench-runtime` crate, and `compile/ast/statement.rs` in the next
engine. These are independently derived solutions to the same fact: an open
control scope with a known exit target and result shape.

## Dependencies

See this task's `depends_on` in [index.json](index.json).

## Scope and implementation sequence

1. Define one control-scope-stack type in `quench-runtime-next` (or a shared
   module both `compile/ast/statement.rs` and the Wasm lowering from task 37
   depend on) carrying exit label, result arity, and pending jump-patch
   sites, generalized enough to express JS's `break`/`continue`/labeled
   statements and Wasm's `block`/`loop`/`if`/`try`/`catch` without either
   side special-casing the other's needs into it.
2. Migrate `compile/ast/statement.rs`'s control-flow handling onto the shared
   type first (JS lands before Wasm per the critical path), then have the
   Wasm lowering (task 37) push/pop against the same type instead of
   `Ctrl`/`CtrlKind`.
3. Keep exception/`try`-scope handling (JS `try`/`catch`/`finally`, Wasm
   `try`/`catch`/`delegate`) expressed as the same kind of scope-stack entry
   with a catch-target field, rather than a separate mechanism per language.
4. Do not force a shared type where the facts genuinely differ (e.g. Wasm's
   typed multi-value block results vs. JS's untyped completion values) —
   model that difference as data on the shared scope entry, not as two scope
   stacks.

## Verification

Run against task 42's disable-specialization gate and whatever suite coverage
already passes at landing time, as a regression check independent of this
task's own targeted cases below.

Differential tests against Test262 (JS labeled break/continue, nested
try/finally, loop scoping) and the pinned Wasm spec suite (nested
block/loop/if, br/br_if/br_table target resolution, try/catch/delegate)
before and after migrating each front end onto the shared type.

## Definition of done

- One control-scope-stack type is shared by the JS and Wasm lowering paths.
- `Ctrl`/`CtrlKind` and any duplicate JS-side scope-stack logic are removed,
  not kept as a parallel implementation.
- Jump-patch resolution is correct for every block/loop/if/try nesting case
  in both spec suites.

## Performance evidence

No speed claim required; this is a representation-unification task. Report
lowering-time delta if the shared type changes allocation behavior materially.
