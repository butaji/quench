# 53: Drive the Node event loop from OS readiness as an explicit phase machine

## Outcome

`quench-node` runs its macrotask loop as a named libuv-style phase state
machine (timers → pending → poll → check → close, with `nextTick` and
microtask checkpoints between callbacks). It blocks in one kqueue wait whose
timeout is the next timer deadline, instead of sleeping on fixed intervals.
ECMAScript jobs stay in the runtime's single job queue. The host schedules
checkpoints but does not own a second microtask queue.

## Current gap

- `modules/pump.rs:sleep_until_next` sleeps a fixed 4 ms whenever a network
  handle exists, and otherwise sleeps until the next timer. Socket readiness,
  child exit and signals are found by re-polling, not by waiting on events.
- `modules/child_process.rs` waits in 1 ms and 5 ms `thread::sleep` loops.
- `queueMicrotask` (`dispatch_handlers.rs:queue_microtask`) enqueues into the
  host `EventLoop.microtasks`, not the runtime's promise job queue
  (`promise_drain.rs`). In Node, `queueMicrotask` callbacks and promise
  reactions share V8's FIFO microtask queue. Only `process.nextTick` has its
  own queue, which runs first. Two queues for one fact can reorder
  `queueMicrotask` against `.then` reactions.
- Phase order is implicit in the pump's control flow, not a named state
  machine.

## Decision: OS readiness, not Tokio

Promises and microtasks are spec queue semantics. They never wait, so no
reactor is involved. For the macrotask layer, Tokio was rejected:

- Host values are `Rc`/`!Send`, so only `current_thread` plus `LocalSet`
  would work.
- Tokio's scheduler owns task order and cannot express Node's phase order or
  same-deadline timer ordering.
- It adds per-task allocation and startup cost with no semantic need.

The loop uses kqueue through `mio`, or raw `libc` if that is smaller. kqueue
provides `EVFILT_READ`/`WRITE` for sockets and pipes, `EVFILT_PROC` for child
exit, `EVFILT_SIGNAL` for signals, and a user event or `mio::Waker` for
worker completions. Blocking fs, DNS and crypto work runs on a small
`std::thread` pool that mirrors libuv's threadpool and posts completions back
to the loop thread. Keep existing behavior on other platforms. `mio` covers
epoll; anything else falls back to the current mechanism as an explicit,
checked transition.

## Scope and implementation sequence

1. Declare the loop phases and their transitions as one named state machine.
   Derive "loop alive" from referenced handles and pending requests, not from
   scattered `has_pending` predicates.
2. Replace fixed-interval sleeps with one readiness wait whose deadline comes
   from a timer min-heap. Timers keep Node's ordering for equal deadlines and
   its clamping rules, each owned by a named constant.
3. Register net, pipe, child-process and signal sources with the reactor.
   Remove the 4 ms net polling and the child-process sleep loops.
4. Move blocking host operations that Node runs on its threadpool onto the
   worker pool, with completions delivered in the pending/poll phase.
5. Route `queueMicrotask` into the runtime job queue. Keep the `nextTick`
   queue in the host, drained before microtasks at each checkpoint, as in
   Node's `processTicksAndRejections`. Remove the host microtask store once
   it has no other semantic role, or give it a named, Node-cited one.

## Verification

Run the complete tracked `tests/node-compat` inventory and require outcomes
to match task 19's frozen baseline. Compare callback ordering with the local
Node oracle for `nextTick`, `queueMicrotask`, promise reactions,
`setImmediate` versus `setTimeout(0)` inside and outside I/O callbacks,
same-deadline timers, socket FIN/close, child exit, and signals. Check
against pinned libuv (`src/unix/core.c` `uv_run`) and Node
(`lib/internal/process/task_queues.js`) sources.

## Definition of done

- No fixed-interval sleep or busy-poll remains in the event loop, net, or
  child-process paths.
- Loop phases are one named state machine, and liveness is derived from
  handle and request state.
- One microtask queue is shared by promise reactions and `queueMicrotask`.
  `nextTick` ordering matches Node.
- Tracked Node outcomes are identical to or better than the frozen baseline.

## Performance evidence

Report idle CPU while waiting on a socket or child, event-loop wake latency,
and bootstrap time/RSS before and after. No threshold applies, and this is
not performance tuning under the task-24 rule: it removes polling from host
waiting.
