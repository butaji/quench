# 53: Preserve implemented Node scheduling on the shared VM

## Outcome

Preserve scheduling, callback ordering and handle liveness required by task 19’s
frozen implemented Node cases. Promise reactions and `queueMicrotask` use the
runtime job queue; the host owns `nextTick` and required I/O phases. A reactor
or threadpool replacement is optional unless a required case or internal
lifecycle invariant needs it.

## Current gap

Audit the observations below against the frozen inventories before implementing
changes. Fix only remaining required behavior; existing correct paths need no
replacement. Historical observations are not proof of a current failure.

- `modules/pump.rs:sleep_until_next` sleeps a fixed 4 ms whenever a network
  handle exists, and otherwise sleeps until the next timer. Socket readiness,
  child exit and signals are found by re-polling, not by waiting on events.
- `modules/child_process.rs` waits in 1 ms and 5 ms `thread::sleep` loops.
- `queueMicrotask` (`dispatch_handlers.rs:queue_microtask`) enqueues into the
  host `EventLoop.microtasks`, not the runtime's promise job queue
  (`promise_drain.rs`). In Node, `queueMicrotask` callbacks and promise
  reactions share V8's FIFO microtask queue. Only `process.nextTick` has its own
  queue, which runs first. Two queues for one fact can reorder `queueMicrotask`
  against `.then` reactions.
- Phase order is implicit in the pump's control flow, not a named state machine.

## Decision: OS readiness, not Tokio

Promises and microtasks are spec queue semantics. They never wait, so no reactor
is involved. For the macrotask layer, Tokio was rejected:

- Host values are `Rc`/`!Send`, so only `current_thread` plus `LocalSet` would
  work.
- Tokio's scheduler owns task order and cannot express Node's phase order or
  same-deadline timer ordering.
- It adds per-task allocation and startup cost with no semantic need.

The loop uses kqueue through `mio`, or raw `libc` if that is smaller. kqueue
provides `EVFILT_READ`/`WRITE` for sockets and pipes, `EVFILT_PROC` for child
exit, `EVFILT_SIGNAL` for signals, and a user event or `mio::Waker` for worker
completions. Blocking fs, DNS and crypto work runs on a small `std::thread` pool
that mirrors libuv's threadpool and posts completions back to the loop thread.
Keep existing behavior on other platforms. `mio` covers epoll; anything else
falls back to the current mechanism as an explicit, checked transition.

## Required scope and optional mechanisms

Stage A implements only the behavior observed by the pinned Test262 inventory or
task 19's frozen implemented Node cases, and the internal lifecycle/safety
invariants needed to run them on the single VM. The mechanisms below are
implementation options within that scope, not a requirement to expand Node
coverage or finish a broader host/architecture rewrite.

1. Declare the loop phases and their transitions as one named state machine.
   Derive "loop alive" from referenced handles and pending requests, not from
   scattered `has_pending` predicates.
2. Replace fixed-interval sleeps with one readiness wait whose deadline comes
   from a timer min-heap. Timers keep Node's ordering for equal deadlines and
   its clamping rules, each owned by a named constant.
3. Register net, pipe, child-process and signal sources with the reactor. Remove
   the 4 ms net polling and the child-process sleep loops.
4. Move blocking host operations that Node runs on its threadpool onto the
   worker pool, with completions delivered in the pending/poll phase.
5. Route `queueMicrotask` into the runtime job queue. Keep the `nextTick` queue
   in the host, drained before microtasks at each checkpoint, as in Node's
   `processTicksAndRejections`. Remove the host microtask store once it has no
   other semantic role, or give it a named, Node-cited one.

## Definition of done

- Affected frozen implemented Node cases preserve callback ordering, liveness,
  errors and required host effects on the shared VM.
- Promise reactions and `queueMicrotask` preserve the observed FIFO order;
  `nextTick` checkpoints match the local Node oracle.
- Lifecycle and root invariants needed by those paths pass. A reactor or
  threadpool replacement is required only if these obligations demand it.
