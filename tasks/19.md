## Scope and implementation sequence

Keep separately named shared-VM development runners until task 27 makes them
canonical. Share discovery and result records with the existing suite runners;
report each case, preserve raw outcomes, and reject empty or incomplete runs.

Reuse the runner operations needed for discovery, outcome classification,
process isolation/deadlines, provenance, ratchets and compare-runs. Node fixtures
execute through `quench-node`. Consolidate equivalent operations when touched;
extracting every runner into a new crate is not an inventory or closure gate.
Do not add another executor or a production backend selector.

Provide a separately named `run-compat-next` development binary that uses the
shared runtime with the existing `NodeHost`. Share `run-compat`'s CLI and its
`NodeInventory` path projection, validation and subset labeling; every
inventory-backed selection derives from it. Reuse `observe_case` for isolated
workers, deadlines, raw outcomes and result records, while each binary keeps its
own worker entry. Do not add an engine-selection flag or duplicate case lists.
The shared worker calls the public file/eval entry owned by task 43. Keep
fixture policy and inventory access in `quench-node-test`. Keep execution closed
until membership is `implemented_frozen`. Included observation cases require
matched local-Node traces and comparison through the observation path before
they qualify. This makes the eventual Node gate exercise the same reviewed case
identities on the shared VM as the legacy runner.

Freeze the implemented Node case set from all three input sources recorded in
[the entry inventory](node-compat-inventory.json): tracked `tests/node-compat`
inputs, local `quench-node-test/node-tests` inputs and the curated upstream
manifest. Membership follows the APIs and behavior already implemented, not
whether a case currently passes. Classify helpers separately and record an implementation
owner for included cases and the missing capability for excluded cases.
Compare included cases against the local Node oracle and retain existing
failures in the baseline. Record the exact cases and task 01 provenance fields
before migration closure. Cases cannot leave this set because either engine
fails them. Unimplemented upstream Node cases do not add work to Stage A except
for the explicit 26-case framework profile, whose selected Node behaviors are
implementation obligations needed to run the three named frameworks. Tasks
[88/89](88.md) retain only the superseded broad proposal and add no gate.

Test262 and Wasm keep their complete pinned inventories, including current
failures. Their shared-VM outcomes are the ratchet owned by tasks 20, 23 and 48.
A complete legacy Wasm replay or a new migration-comparison framework is not a
prerequisite: use focused legacy comparisons only when they help resolve a
specific failure. Required evidence proves the final shared VM, not parity
with a legacy engine that will be deleted.

During implementation, run affected scopes and compare-runs. Complete suites
run only at the designated gates and stage transitions in the
[execution contract](README.md#checks-and-evidence).
