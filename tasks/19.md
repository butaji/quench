# 19: Build next-engine runners and differential oracles

## Outcome

Exercise the next engine across existing suites without adding a production backend selector.

## Current gap

The imported crate has a standalone ES5 CLI, while Quench runners and hosts are coupled to legacy runtime APIs.

## Dependencies

See this task's `depends_on` in [index.json](index.json).

## Scope and implementation sequence

Add separately named `quench-next`, `quench-node-next`, `run-all-next`, and Wasm-next development targets. Build reusable result records for value/output/error/descriptor/order/exit/effect comparisons against legacy Quench and local Node. Keep suite discovery shared so old/new runs have identical inputs.

## Verification

Prove runner self-tests, nonzero discovery, deterministic ordering, timeouts/crash classification, residual round trips, and deliberate mismatch reporting. Verify production `quench-node` contains no runtime engine flag.

## Definition of done

- Every migration lane can target the next engine explicitly.
- Differential records preserve raw outcomes and provenance.
- Development selection cannot affect production behavior.

## Performance evidence

Measure runner overhead separately from guest execution and exclude it from parity binaries.
