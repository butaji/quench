# 91: Lead no-JIT Wasm interpreters on CoreMark

## Plan scope

Side lane, non-blocking. Stage B still measures only V8-v7; this task adds a
Wasm speed target without changing either stage gate. Every step keeps the one
VM, one heap, one opcode vocabulary and one dispatch loop. A step that changes
shared dispatch or frame layout must also bring paired V8-v7 Score/RSS evidence.

## Outcome

On one host and in one run, Quench's median CoreMark score is the highest among
the no-JIT Wasm interpreters: Wasmi v2, Stitch, Wasm3, WAMR fast interpreter,
Pulley and Tinywasm. All 67,124 pinned Wasm directives still pass.

## Benchmark and comparators

CoreMark 1.0 is the standard single-number CPU benchmark used by Wasm
interpreter authors (Wasm3, Wasmi, Stitch, WAMR), and it exercises the paths
real guests depend on: linear memory, i32 arithmetic, branches, calls and
`call_indirect`. [wasm-coremark-rs](https://github.com/wasmi-labs/wasm-coremark-rs)
pins the module and links every comparator through one harness. That gives
identical input, identical clock import and the same scoring.

| Stitch 0.1             | interpreter | 2076           |
| Wasm3 0.5              | interpreter | 1944           |
| WAMR fast interpreter  | interpreter | 1825           |

The baseline is recorded in
[evidence](evidence/task91-coremark-baseline-2026-10-10.json): Linux x86-64,
4 vCPU Xeon @ 2.10 GHz, rustc 1.97. Wasmi v2 is the reference to beat. JIT
results such as Wasmtime Cranelift are context only and never comparators,
under the no-JIT constraint in [index.json](index.json).

CoreMark alone can be overfitted. Before any score is claimed, also run the
`execute` group of [wasmi-benchmarks](https://github.com/wasmi-labs/wasmi-benchmarks)
(calls, recursion, globals, memory, branches) on the same comparators. No step
may use benchmark identity, module hashes or export names to select behavior.

## Current gap

Measured with callgrind on the production build; see the evidence file.

1. **64-bit cells drive GC (27%).** `WasmMemoryAddress` boxes every effective
   address as `Cell::WasmBits64`, and every i64/f64 result allocates through
   `encode_wasm_value`. In a 32-bit-address guest, the dominant cost of a load
   is therefore a heap allocation.
2. **Instance binding loads (~15%).** Each memory or global access starts with
   `LoadCapture`, which walks the closure environment
   (`capture`/`load_local_binding`/`load_environment_binding`) to find a
   binding that is fixed for the life of the instance.
3. **Three dispatches per memory access.** The sequence is `LoadCapture` +
   `WasmMemoryAddress` + `WasmMemoryLoad`. The load also locks the
   `MemoryStorage` mutex even for unshared memory.
4. **Recursive calls.** `allow_inline_calls` is false for `ProgramKind::Wasm`,
   so every Wasm→Wasm call recurses through `call_user` and
   `call_user_maybe_async`.
5. **Double dispatch and copies.** Numeric ops match the opcode and then decode
   an operator tag from the immediate. `local.get`/`local.set` become register
   copies, and compare-then-branch is two instructions.
6. **Dispatch loop self cost (~40%).** Each instruction does a `frames[f]`
   indirection per register access, a per-instruction `pc` store, wide-instruction
   checks and a `Result<StepResult>` round trip.

## Scope and implementation sequence

Order follows the measured share and the cost of the change. Re-run the
baseline and callgrind after every step, and re-rank the remaining steps from
that new profile instead of following this list blindly.

1. **Harness and baseline (done).** Add `quench-wasm-test --bin coremark`, record
   the comparator table and the callgrind profile.
2. **Unboxed effective addresses.** Fold the static offset and bounds check into
   the load/store instruction. Memory32 addresses stay i32 immediates; only
   memory64 needs a 64-bit path. Remove `WasmMemoryAddress` from the memory32
   path. Expected impact: removes most allocation from load/store-heavy code.
3. **Raw 64-bit frame slots ([task 87](87.md)).** Slot class derives from the
   validated type. Raw slots get no root and no cell. Boxing happens only at
   dynamic boundaries, through `ScalarBits`. Expected impact: GC share near zero.
4. **Direct instance access.** Resolve memory and global bindings once per
   activation, from an instance slot fixed in the frame, instead of
   `LoadCapture` through the environment chain. Materialize immutable globals
   as constants (task 38). Unshared memory skips the mutex. Shared memory keeps
   it, and the decision comes from the memory type, not from a flag.
5. **Inline Wasm calls.** Allow inline frame push for `ProgramKind::Wasm`. Wasm
   functions are never async, so calls skip `call_user_maybe_async` and Rust
   recursion while still using the shared stack budget and the
   `CallStackExhausted` trap.
6. **First-class hot operators.** Generate dedicated opcodes for the hot i32
   operators, loads/stores and compare+branch from the existing operator tables
   in the `opcodes!` macro. The operator table stays the one authority, and the
   tagged generic opcode remains the fallback. Make Wasm locals addressable
   registers so operators read locals directly. Fuse `op + local.set` and
   `cmp + br_if` where the lowering proves the stack shape. Choose fusions from
   the CoreMark and wasmi-benchmarks dispatch-pair census, not by guessing.
7. **Dispatch loop cost.** Hold the active frame's register base in a local
   instead of `frames[f]`, store `pc` only at GC/throw points (root maps allow
   this), and keep the `Result` off the hot path. This touches JS dispatch too:
   paired V8-v7 evidence is mandatory. A direct-threaded or tail-call handler
   form is a later option, adopted only if it is measured on both workloads and
   still keeps one dispatch loop.

## Progress

Same host and harness as the baseline; CoreMark medians of 3 interleaved runs.
Fixed-work instruction counts use `COREMARK_CLOCK_STEPS_MS=1,1,10000` under
cachegrind. On that fixed work Wasmi v2 executes 0.94 G instructions.

| Step                                                   | CoreMark | Fixed-work instructions |
| ------------------------------------------------------ | -------- | ----------------------- |
| Baseline                                               | 48       |                         |
| Direct memory32 loads/stores                           | 102      |                         |
| Register locals, i32 opcodes, select/fill              | 234      |                         |
| Lock-free unshared memory                              | 282      |                         |
| Straight-line lane, inline Wasm calls                  | 674      |                         |
| Globals, out-of-line Wasm arms, constant jumps         | ~850     | 4.00 G                  |
| Frame stack, register parameters, `br_table` fusion    | ~990     | 4.00 G                  |
| Threaded lane handlers, raw memory view                | ~1356    | 2.63 G                  |

The threaded lane keeps the one dispatch loop: the general loop still owns
every instruction and enters the lane before each one; lane handlers cover
only register, memory32 and jump effects and return any other instruction to
the general loop unchanged. Each handler dispatches its successor itself, as a
sibling call in optimizing builds (`quench_lane_tail_calls` from
`crates/quench-runtime/build.rs`), so each opcode predicts its successor at
its own branch. JavaScript never enters the lane, and V8-v7 fixed-work
instruction counts are unchanged (ratios 0.9998 to 0.9999).

## Verification

Run the full pinned Wasm suite through the shared VM after every step (67,124
directives, unchanged inventory). For steps 3 and 7, also run affected Test262
stages and paired V8-v7. GC stress across mixed raw/tagged frames. Exact NaN
payloads and signed zero at host boundaries. Traps for out-of-bounds offsets
near `u32::MAX`, for memory64, and for shared memory.
