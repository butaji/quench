# 049: Pre-render multiple specialized variants per hot pattern (build-time-enumerated, not speculative)

- **Theme:** deegen_full_jit
- **Executor:** codex
- **Depends on:** 048

## Context

Today a region admits one canonical specialization plus a fallback — e.g. a
property-access region only fires for the monomorphic case; 2-3-shape
polymorphism falls straight through to `DISPATCH`. The closest thing to
"adaptive" behavior achievable without runtime code generation or
speculation: pre-render *several* variants for a bounded, realistic set of
fact combinations at build time (e.g. a property region specialized
separately for 2-shape and 3-shape polymorphism, not just monomorphic),
with runtime fact-observation selecting among them via `RegionKey` lookup —
still 100% build-time-proven, still a lookup not a guess, no deopt needed
because nothing is being speculated.

## Scope
- crates/quench-runtime/src/stencil_fact.rs (`RegionKey` — extend to key on
  a bounded fact-combination set, not just single-shape admission)
- crates/quench-runtime/src/stencil_select.rs
- crates/quench-runtime/build.rs (multiple variant byte emission per
  pattern)

## Deliverables
- Identify, from curriculum/neutral-corpus evidence, which currently-
  fallback-only polymorphic patterns (property access, call sites) see a
  small, bounded number of distinct shapes/callees in practice (2-4, same
  ceiling as the existing `IcStubChain` bound) — this is the same bounded
  degrade-tier discipline already used elsewhere in the tier, applied to
  build-time variant selection instead of a runtime chain
- Pre-render one variant per admitted combination (not unbounded — same
  ceiling as the polymorphic IC bound elsewhere in this tier)
- Runtime selects the matching variant via `RegionKey` lookup; any
  combination outside the pre-rendered set falls through to the complete
  ordinary path exactly as today

## Validation

1. CFG-soundness test per variant (same discipline as every other region)
2. Differential test: each pre-rendered variant produces identical output
   to the ordinary interpreter for its exact fact combination, and a
   combination outside the pre-rendered set correctly falls through
3. `cargo test -p quench-runtime --lib` — all pass
4. Before/after measurement on the curriculum's polymorphic cases (013,
   021) — record the delta
5. Code-size evidence: N variants means N× the rendered bytes for that
   pattern — confirm the size growth is bounded and worth the measured win,
   not unconditional

**Fail condition**: an unbounded variant set (code-size blowup) or any
variant that silently mismatches its claimed fact combination is
unacceptable regardless of benchmark numbers.

**Cross-check once task 052 exists**: re-run the v8-v7 suite's polymorphism-
heavy benchmarks (DeltaBlue's constraint dispatch, EarleyBoyer's generic
object access) before/after, same reasoning as task 048's cross-check — the
curriculum is a proxy, v8-v7 is the actual comparison target.

## Non-goals
- Runtime-triggered generation of a *new* variant not already pre-rendered
  at build time — that would be runtime codegen and cross this project's
  standing line into real-optimizing-JIT territory. Every variant is fixed
  at build time; only the *selection* among them happens at runtime.
