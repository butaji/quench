# 40: Unify the OXC and Wasm engine and diagnostic types

## Outcome

Give the OXC specializer and the Wasm front end one shared `Engine`-style
entry point and one shared diagnostic type, so both produce the same
`ResidualProgram`/error shape task 25's two-mode residual execution consumes
uniformly.

## Current gap

`quench_wasm::Engine::compile`/`compile_wat` (in the `quench-wasm` crate,
returning `quench_wasm::Error` and a `Module`) and
`quench_runtime_next::compile::Engine::specialize` (returning
`compile::Diagnostic` and a `ResidualProgram`) are unrelated types in
unrelated crates today, despite task 37 making both front ends target the
same `ResidualProgram`. Left as-is, task 25's static/dynamic residual
execution split would need Wasm-specific plumbing bolted on separately
instead of falling out of one shared contract.

## Dependencies

See this task's `depends_on` in [index.json](index.json).

## Scope and implementation sequence

1. Once task 37 lands Wasm lowering onto `bytecode::{Op, Instr,
   ResidualProgram}`, give the Wasm entry point the same
   `Engine::specialize(source, name) -> Result<ResidualProgram,
   Vec<Diagnostic>>` shape as the OXC specializer, reusing `compile::
   Diagnostic` (source/message/span) as the one error representation instead
   of a second `Error` enum.
2. Keep parse/validate (via `wasmparser`) as the Wasm-specific first stage
   feeding this shared entry point — the front-end-specific analysis stays
   front-end-specific; only the entry-point shape and error type unify.
3. Update task 25's static-file/exec-mode and in-process dynamic-compilation
   paths to route both JS and Wasm sources through the one shared entry
   point, removing any Wasm-specific special-casing that predates this
   unification.

## Verification

Confirm existing OXC specializer tests and the pinned Wasm spec suite both
pass unchanged through the unified entry point. Add a test that mixes JS and
Wasm sources through task 25's static/dynamic split to confirm neither path
special-cases the source kind beyond front-end selection.

## Definition of done

- One `Engine` entry-point shape and one `Diagnostic` type serve both front
  ends.
- Task 25's residual execution modes require no Wasm-specific branching
  beyond selecting which front end parses the source.

## Performance evidence

No speed claim required; report whether unification changes compile-time
allocation behavior for either front end.
