# 40: Unify the OXC and Wasm engine and diagnostic types

## Outcome

Give the OXC specializer and the Wasm front end one shared `Engine`-style
entry point and one shared diagnostic type, so both produce the same
`ResidualProgram`/error shape, and the JS and Wasm entry into the one shared
VM is a single contract. This is a Stage A task: task 24 depends on it, so the
single-VM requirement is proven at the correctness gate. Task 25's two-mode
residual execution later consumes it uniformly.

## Scope and implementation sequence

1. Once task 37 lands Wasm lowering onto `bytecode::{Op, Instr,
ResidualProgram}`, give the Wasm entry point the same
   `Engine::specialize(source, name) -> Result<ResidualProgram,
Vec<Diagnostic>>` shape as the OXC specializer, reusing `compile::
Diagnostic` (source/message/span) as the one error representation instead
   of a second `Error` enum.
2. Keep parse/validate (via `wasmparser`) as the Wasm-specific first stage
   feeding this shared entry point — the front-end-specific analysis stays
   front-end-specific; only the entry-point shape and error type unify.
3. Route the CLI, the Node host (`WebAssembly.*` and `vm`/`eval`-style dynamic
   compilation), and the conformance runners through the one shared entry
   point, removing any Wasm-specific special-casing that predates this
   unification. Task 25 (Stage B) later builds its static/dynamic modes on
   this entry point.
4. Keep JS⇄Wasm adapters independent of how frames store scalars: transport
   values only through the shared `ScalarBits` encode/decode operation, never
   by assuming `Cell::WasmBits64`/`Cell::WasmV128` boxes. Deferred task
   [87](87.md) can then derive raw frame slots without changing this contract.

## Verification

Confirm existing OXC specializer tests and the pinned Wasm spec suite both
pass unchanged through the unified entry point. Add a test that mixes JS and
Wasm sources in one realm (JS calling Wasm exports and Wasm calling JS imports)
to confirm neither path special-cases the source kind beyond front-end
selection, and that both run on the same heap, roots, and dispatch loop.

## Definition of done

- One `Engine` entry-point shape and one `Diagnostic` type serve both front
  ends.
- No host or runner path branches on source kind beyond selecting which front
  end parses the source.
- `quench-wasm` has no execution code; its crate docs name the shared runtime
  as the only VM. It parses and validates, then calls `quench-runtime` to lower,
  instantiate and execute.
- One surviving Wasm format path supplies validated module facts and operators
  to shared lowering. Keep decoding/validation in `quench-wasm` and execution
  semantics in the runtime. Parser types may serve as the operator data; a new
  runtime-owned copy of that vocabulary is not a completion requirement.
- JavaScript `WebAssembly` compilation reaches that decoding path through the
  runtime embedding boundary. CLI/host composition installs it; a new CLI
  crate is not required. Delete the legacy runtime parser at task 27.
