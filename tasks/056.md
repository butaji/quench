# 056: Audit for reference-cycle memory leaks (no cycle collector exists)

- **Theme:** vm_completeness
- **Executor:** codex
- **Depends on:** none

## Context

Direct code check: quench's object model is `Rc<RefCell<...>>` throughout
(`value.rs`, `machine.rs`), with `Weak` used only at specific known
structural points (`WeakObject`, `WeakFunctionValue` — prototype/function
back-references). There is no general-purpose cycle collector anywhere in
the codebase (no mark-sweep pass, no trial-deletion, no periodic collection
of any kind). This is a real, different-in-kind gap from task 055's
allocation-*throughput* survey: it's not "allocation is slower than V8's
nursery," it's "a user JS program that creates an ordinary reference cycle
(`let a={}, b={}; a.b=b; b.a=a;` with no external reference to either) never
frees that memory, for the lifetime of the process."

QuickJS (this project's closest architectural relative — refcounting-based,
not tracing-GC-based) explicitly documents handling this with a periodic
cycle-removal pass on top of its refcounting, precisely because pure
refcounting alone leaks on cycles. Quench appears to have skipped that half
of the design. The v8-v7 suite's `DeltaBlue` benchmark is exactly the kind
of workload (a constraint graph with bidirectional references between
constraints and variables) that plausibly creates such cycles at real scale.

## Scope
- Investigation only — no code changes in this task
- crates/quench-runtime/src/value.rs, machine.rs (object/environment model)

## Deliverables
- Construct minimal, deliberate reference-cycle test cases (plain object
  cycle, closure-capturing-cycle, the DeltaBlue-shaped
  constraint/variable-mutual-reference pattern specifically) and confirm
  whether they actually leak (RSS grows and never comes back down after the
  cycle becomes unreachable from any root) or whether some existing
  mechanism this audit hasn't found already handles it
- If they leak: quantify with a scaling test (create N cycles, drop all
  external references, measure RSS growth as N increases) — this is the
  evidence a follow-on implementation task would need
- Check specifically whether v8-v7's `DeltaBlue` benchmark's own RSS grows
  unbounded over repeated runs within one process (Octane-style benchmarks
  loop many iterations in-process) — if this benchmark specifically leaks,
  that's directly relevant to the v8-v7 score effort, not just a
  theoretical concern

## Validation

1. A minimal, reproducible leak test committed (even if the fix is a
   separate task) — this needs to be a real regression test that fails
   today and can be reused when task 057 (or whatever the fix task becomes)
   lands
2. A recorded finding in `docs/architecture-evidence.md`: confirmed leak
   with quantified scaling data, or confirmed no leak with the mechanism
   that prevents it identified — either is an acceptable, honest outcome,
   but it must be backed by the actual constructed test, not inferred from
   reading the code alone

**Fail condition**: concluding "probably fine" without actually running the
constructed cycle test and measuring RSS is not acceptable — this is
exactly the kind of claim that needs the differential/measured-evidence
discipline used everywhere else in this backlog.

## Non-goals
- Implementing a fix — that's a separate task (057), scoped only if this
  audit confirms a real leak
