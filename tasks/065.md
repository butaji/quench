# 065: Closure/call-frame algorithmic-complexity invariants

- **Theme:** architecture_invariants
- **Executor:** codex
- **Depends on:** none

## Context

Same technique as 062, scoped to closures and call-frame overhead —
directly relevant to task 061's finding (DeltaBlue's cost was bounded per-
site IC/layout-mismatch cost, in a workload dominated by method dispatch
across many object shapes) and to tasks 048/049's whole-function region
growth, which needs a sound frame-cost foundation to build on.

## Scope
- `crates/quench-runtime/src/architecture_invariants.rs` (same module)

## Deliverables — invariants to pin
1. Closure creation cost is proportional to the number of variables it
   actually captures, not to the depth of its enclosing scope chain or
   the total number of closures ever created in the program.
2. Per-call-frame overhead (setup/teardown) is constant regardless of
   recursion depth — i.e. the *marginal* cost of the Nth recursive call is
   the same as the 2nd, not growing with N (stack depth itself is
   necessarily O(N) space, this invariant is about per-frame *time* cost).
3. Argument marshaling cost is proportional to argument count only, not to
   the total number of distinct functions defined in the program (the
   call-target equivalent of 062's shape-count/callee-count tests, applied
   to the marshaling step specifically rather than dispatch resolution).

## Validation

Same bar as 062: validate each test fails against a deliberately-broken

against curriculum cases 010 (fib) and 029 (ackermann) — if either
invariant fails, that's likely part of why those cases still show
13-16x wall time vs. Node.
