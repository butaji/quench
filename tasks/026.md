# 026: Move hot dispatch from a driver-owned loop to callee-directed tail transitions

- **Theme:** deegen_codegen
- **Executor:** codex
- **Depends on:** 019

## Context

Deegen's interpreter (§6.1) is continuation-passing: each bytecode is a standalone
function that ends in a tail call directly to the next bytecode's function — there
is no driver loop owning `pc` as mutable state the handler can't see. Quench's
current architecture, even after task 019's `DispatchTransition` return value, still
has `run_code_completion_step_from` (`vm/vm_runtime.rs`) as a `while let` loop that
calls `run_instruction` and reads the returned transition itself; handlers hand
control *back to the loop*, they never hand it directly to the next handler. Task
019 named this gap explicitly as future work ("groundwork... without implementing
CPS/tail-call dispatch"). This task is that follow-up, gated on 019's evidence.

This is a **prerequisite for the copy_patch_jit tier's fast-path fallthrough
elimination** (tasks 023/025): Deegen's JIT stencils end with a direct jump to the
next bytecode's JIT address specifically because the interpreter already treats
"what runs next" as a callee-supplied address, not a value threaded through a loop.
Building stencils on top of quench's current loop-owned dispatch would mean every
stencil still needs a driver to consult after each region, defeating the dispatch
elimination the region-stencil design (022) depends on for its actual performance
win.

## Scope
- crates/quench-runtime/src/vm/vm_runtime.rs
- crates/quench-runtime/src/vm/vm_dispatch.rs

## Deliverables
- Profile the neutral microbenchmark corpus first; proceed only if driver-owned
  dispatch overhead is a measured cost (this task inherits task 019's
  profile-before-implement discipline, it does not skip it)
- If justified, let each opcode/region handler's `DispatchTransition` (019) resolve
  directly to a callee address it tail-calls into, instead of returning to
  `run_code_completion_step_from` for every step. The driver becomes a thin
  entry/exit shim (function-call boundary, exception unwinding, coroutine
  yield points) rather than the per-instruction control-flow owner
- Preserve every existing completion, exception, iterator, proxy, accessor, and
  coercion behavior exactly; this is a control-transfer mechanism change, not a
  semantic change
- Keep the ordinary (non-quickened, non-stencil) interpreter path as the complete
  fallback semantics owner throughout; this task changes *how* control reaches the
  next operation, never *what* the next operation computes

## Acceptance
- Neutral corpus geomean does not regress after the change
- A handler that hands control to the next operation does so via a direct
  call/jump target it receives or computes, never via a value silently
  interpreted by an external loop
- No JIT, executable memory, or benchmark-specific code path is introduced; this
  stays a control-transfer mechanism change within the existing interpreter
- Differential tests confirm identical observable behavior (values, exceptions,
  control-flow exits) before and after

## Non-goals
- Implementing register pinning via a specific calling convention (that is an
  implementation detail of *how* this is achieved, decide during implementation,
  not a separate task)
- Any JIT, OSR, or deoptimization work — this task is interpreter-only groundwork
  that the copy_patch_jit tier (021-025) depends on, but it does not itself touch
  executable memory
