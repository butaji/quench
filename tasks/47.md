# 47: Derive the generating extension from the watermark tables

## Outcome

The compiler's folds, specialization-environment addressing, and guarded fast
paths are derived from task 46's tables instead of hand-written beside them.
Every fast path is a guarded acceleration of a library-bodied row, so the
specializer tasks (57, 70–76, 85) add speed by adding table entries, never by
adding semantics. A reference kernel with every fast path and specialization
removed passes all three suites, which is the oracle every later
optimization is checked against.

## Current gap

Task 46 declares the watermark tables and their binding-time columns, but the
compiler still carries its own folds, fast paths, and exotic-object branches.
Kernel bodies can still sit outside a fast path with no reference definition,
and nothing runs the conformance suites with the accelerations removed.

## Dependencies

## Futamura and Ershov rules

This task carries out the rules in
[task 46](46.md#futamura-and-ershov-across-the-watermark):

- **P1 over kernel + library.** `mix(interpreter, program) = residual`, where
  the interpreter is the kernel plus the library.
- **Ershov's one definition, two binding times.** Every compiler fold runs a
  statically evaluable operation row (empty effect set) on static inputs. No
  compiler-side copy of a semantic definition survives.
- **Binding-time classes read from the tables.**
  - Static: statically evaluable operation rows.
  - Specialization environment: intrinsics, operation rows, brands, and fact
    cells addressed by index.
  - Dynamic: fast paths, emitted unguarded when a `StaticValue` proof covers
    their facts or guarded otherwise, with their row's reference definition as
    the exact fallback.
- **One fact vocabulary, three binding times.** A fact row (task 46) is proved
  by a `StaticValue` transfer rule, guarded by one cell or shape read, or
  learned by a site cache. Each proof, guard, and cache entry names the fact
  row it relies on; none defines its own.
- **Congruence from effect sets.** `reenters` and `throws` end static heap
  facts. A fast path's narrower effect set applies only where its facts hold.
  Observed values never become unguarded static facts.
- **Budgeted staging.** Folding and specialization have explicit budgets: fold
  steps per expression and residual size per function. When a budget runs out,
  the generic residual is emitted, which is always correct. This task provides
  the mechanism and its exhaustion behavior; the consumer tasks set the values
  by paired measurement.
- **Derived, not self-applied.** Opcode identities, effect tables, rewrite
  legality, fold eligibility, and guard/fallback pairs are generated by Rust
  macros from the tables.
- **Correctness.** The residual run equals the reference-kernel run on every
  suite input, for both front ends.

## Realm lifecycle

Library installation is a named state machine, so no operation runs against a
half-built realm:

`Allocated → KernelReady → LibraryInstalled → Running → ShuttingDown → Released`

`KernelReady` means the heap, shapes, and fundamental rows are usable.
`LibraryInstalled` means the operation, brand, and fact tables are resolved
and every intrinsic is installed or lazily reachable (task 67).
Opcode fallbacks and guest code are legal only in `Running`. Each transition
is explicit and checked; a failed installation goes straight to `Released`.

## Scope and implementation sequence

1. Move exotic-object semantics into brand handler rows. Turn every remaining
   kernel body that is only a faster form of a library operation into a fast
   path on that library-bodied row, naming its facts.
2. Model the realm lifecycle transitions above.
3. Derive the generating extension from the tables:
   - route constant folding through statically evaluable rows;
   - address intrinsics, rows, brands, and fact cells by index;
   - emit each fast path as a fact guard plus reference-definition fallback,
     and drop the guard where a proof names the fact;
   - drive binding-time congruence from effect sets;
   - apply the fold and residual budgets, with the generic residual on
     exhaustion;
   - delete any compiler-side duplicate of a library or kernel definition.

   This reroutes the folds and fast paths that already exist; new ones belong
   to the specializer tasks.
4. Build the reference kernel: every fast path removed, brands laid out
   without packing, specialization and static folding disabled (task 42). Run
   the full Test262 inventory, the pinned Wasm suite, and the frozen Node set
   on it with an unchanged library crate.

## Verification

- A structural test rejects fast paths on kernel-bodied rows, fast paths
  without facts, guards that name no fact row, library bodies that call a
  fast path directly, and compiler code that reimplements a row's semantics.
- Every fold the compiler performs calls a statically evaluable row.
  A differential test compares folded and unfolded residuals of the same
  source.
- The reference kernel and the default kernel agree on all three suites
  (task 48 ratchet format).

## Definition of done

- Every exotic behavior lives above the watermark. The kernel has no per-brand
  semantic branches, only fundamental rows and fast paths with reference
  definitions.
- Static folding, specialization-environment addressing, and guarded
  acceleration each read their binding-time facts from the tables.
- The reference kernel passes the same three-suite run as the default kernel.
