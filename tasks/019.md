# 019: Make the opcode transition an explicit return value, not loop-owned state

- **Theme:** deegen_codegen
- **Executor:** codex
- **Depends on:** 006

## Scope
- crates/quench-runtime/src/vm/vm_runtime.rs
- crates/quench-runtime/src/vm/vm_dispatch.rs

## Deliverables
- Profile the neutral microbenchmark corpus first; this task proceeds only if the dispatch loop in run_code_completion_step_from (vm/vm_runtime.rs) shows up as a measured cost, not on assumption
- If justified, have each opcode handler return an explicit next-pc/Completion transition value instead of the driving while loop owning pc as mutable local state the handler cannot see
- Keep run_code_completion_step_from as a thin driver that consumes the returned transition; do not change opcode semantics, only how the next step is communicated
- Document whether this groundwork is later exploitable for tail-call or computed-goto dispatch, without implementing either now

## Acceptance
- Neutral corpus geomean does not regress after the change
- Every opcode handler's return type carries its own next-transition; no handler relies on the driver's private pc mutation to know what happens next
- No JIT, tail-call codegen, or executable memory is introduced; this stays a data-shape change within the existing interpreter loop

## Non-goals
- Implementing real CPS tail-call dispatch or a computed-goto backend
- Any JIT or executable-memory work
