# 032: True bytecode quickening — instruction-stream rewrite on IC hit

- **Theme:** deegen_full_jit
- **Executor:** codex
- **Depends on:** 028

## Context

Paper §6.2: quickening replaces the bytecode *instruction itself* in the
instruction stream with a specialized variant once its IC has a confirmed
λe, so future dispatches hit the specialized opcode directly instead of an
indirect IC check. Audit found: despite the name, `quickening.rs` implements
a **side-table IC** (guard state keyed by call/property site, checked inline
on every dispatch) — it never rewrites the opcode/instruction bytes in the
stream. This is the clearest naming-vs-mechanism mismatch found in the audit;
either the mechanism needs building, or the name needs correcting to stop
overclaiming paper parity.

## Scope
- crates/quench-runtime/src/quickening.rs
- crates/quench-runtime/src/ir.rs (`vm_op!` catalog — quickened variants need
  their own opcode IDs, matching how the existing catalog already generates
  IDs from one declaration)

## Deliverables
- Decide, with evidence: is literal instruction-stream rewrite worth building
  given quench's callee-directed dispatch (task 026) already avoids much of
  the indirect-dispatch cost the paper's quickening targets? Profile a
  representative guard-hit-heavy microbenchmark with the current side-table
  IC vs. a prototype rewritten-opcode dispatch before committing to the full
  build
- If justified: add quickened opcode variants to the `vm_op!` catalog (one
  declaration generates both the generic and quickened dispatch paths, per
  this project's existing "generate mechanical consequences from one
  declaration" rule), and have `QuickeningSite` actually mutate the stored
  instruction on confirmed hit, with the ordinary generic opcode remaining
  the complete fallback for degrade/miss
- If not justified: rename `quickening.rs`'s public API away from
  "quickening" terminology and document plainly in
  `docs/deegen-alignment.md` that this is the paper's generic-IC mechanism
  (§4/§5.2), not its quickening mechanism (§6.2) — don't let the name imply
  work that isn't there

## Validation

**Gate 0 (decision measurement, mandatory before choosing a path):**
Build or identify a guard-hit-heavy microbenchmark (e.g. a monomorphic
property-get loop, a repeated call site). Measure dispatch cost with the
current side-table IC vs. a small prototype that rewrites the opcode in
place on hit. Record both numbers in `docs/deegen-alignment.md`.

**Path A — build it (if Gate 0 shows a real win):**
1. Add quickened opcode variants to `vm_op!` in `ir.rs`.
2. `QuickeningSite` mutates the stored instruction on confirmed hit.
3. Differential tests: same program executed with quickening forced-on vs.
   forced-off produces identical output, including for sites that later
   degrade (Polymorphic/Megamorphic) — the generic opcode must remain a
   working fallback, not just a historical artifact.
4. `cargo test -p quench-runtime --lib` — all pass.
5. `node quench-bench/micros/verify.mjs ... --from 1 --to 100 --runs 3` —
   100/100, geomean improves, guard-hit-heavy case shows the Gate 0 delta.

**Path B — rename, don't build (if Gate 0 shows no real win):**
1. Rename `quickening.rs`'s public API away from "quickening" terminology
   (e.g. to reflect "generic IC" / "site cache").
2. Update every call site and doc reference (`docs/copy-and-patch-jit.md`,
   `docs/deegen-alignment.md` item 8) to match.
3. `cargo build -p quench-runtime` — clean, no broken references.
4. `cargo test -p quench-runtime --lib` — all pass, zero behavior change (a
   pure rename must not alter any test outcome).

**Fail condition**: choosing neither path — i.e. leaving the misleading name
in place with no Gate 0 measurement recorded — fails this task outright.

## Non-goals
- Removing the existing side-table IC — it's the paper's separate,
  legitimate generic-IC mechanism (§4/§5.2) and stays regardless of this
  task's outcome
