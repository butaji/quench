# 021: Define canonical stencil facts and data shapes

- **Theme:** copy_patch_jit
- **Executor:** codex
- **Depends on:** 011, 016, 019

See `docs/copy-and-patch-jit.md` for the full design and its relationship to
the Deegen paper (arXiv:2411.11469).

## Data model (define before any function)

- `Fact` — reuse the existing `vm_op!`/`Proven`/`Guarded`/`Unknown` classification as-is; a stencil never gets a second fact representation.
- `RegionKey` — a canonical specialization key: `hash(region_id, fact_vector)`. Same facts must always hash to the same key (one fact, one representation).
- `Hole` — `{ offset: u16, kind: HoleKind }`.
- `HoleKind` — a closed enum: `Imm32 | Disp32 | Rel32 | Ptr64`. No generic relocation type.
- `Stencil` — `{ bytes: &'static [u8], holes: &'static [Hole] }`, pure data.
- `PatchValues` — a read-only *view* into the existing `QuickeningSite`/`ShapeCache`/`CallableCache` state (`quickening.rs`); it is never a second copy of shape/callee/slow-path facts.
- `BoxingFact` — a declared description of the existing `JsValue` tagged-struct layout (task 017): the set of base types, and for each a type-checker predicate and (optional) decode/encode pair, expressed as data so build-time passes can reason about it generically (mirrors Deegen §4.2/Appendix A.2's boxing-scheme description APIs, which §5.1's type-based optimization then consumes). This is not a new boxing scheme — it is a data-level *description of* the one already implemented in `dynamic/jsvalue.rs`, so type-check strength-reduction (task 022) has a single source of truth to consult instead of hardcoding per-stencil assumptions about the tag layout.

## Scope
- crates/quench-runtime/src/facts.rs
- crates/quench-runtime/src/ir.rs
- crates/quench-runtime/src/stencil_fact.rs (new, data only, target ≤150 lines)

## Deliverables
- Implement `RegionKey`, `Hole`, `HoleKind`, `Stencil`, `PatchValues`, `BoxingFact` as plain data in `stencil_fact.rs` with no `unsafe`, no allocation, no I/O
- Extend the `vm_op!`/region-fact schema so a `RegionKey` is derivable from existing declared facts (effects, guards, control, Proven/Guarded/Unknown), not a parallel declaration
- `PatchValues::from_site(&QuickeningSite) -> PatchValues` is the only constructor; there is no path that builds `PatchValues` from anything other than the existing quickening state
- `BoxingFact` is derived once from `dynamic/jsvalue.rs`'s existing `Tag`/payload layout, not hand-duplicated as a second description

## Acceptance
- `stencil_fact.rs` compiles standalone, is unit-testable, and stays under the file-size/complexity caps (functions ≤40 lines, complexity ≤10, file ≤500 lines)
- `RegionKey` computation is a pure function: identical fact vectors always produce identical keys, tested directly
- `BoxingFact`'s type-checker predicates agree with `JsValue`'s actual runtime behavior for every base type, verified by a direct test, not by inspection
- No executable memory, `mmap`, code-copying, or patch-application logic exists yet — this task is data shapes only

## Non-goals
- Region/stencil generation (task 022)
- Any runtime copy, patch, or execution logic
- Changing the boxing scheme itself (task 017's layout is frozen input here, not renegotiated)
