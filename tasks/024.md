# 024: Wire the stencil lifecycle state machine to existing quickening state

- **Theme:** copy_patch_jit
- **Executor:** codex
- **Depends on:** 023, 013, 014

## Scope
- crates/quench-runtime/src/stencil_lifecycle.rs (new, named state machine, target ≤150 lines)
- crates/quench-runtime/src/quickening.rs

## Deliverables
- Implement an explicit named state machine `Cold -> Rendered -> Installed -> Repatch -> Retired`, mirroring the existing `Cold -> Polymorphic -> Megamorphic` naming style already used for interpreter-side quickening (013/014) rather than inventing a second cache-state vocabulary
- Name the idempotent/effectful split this lifecycle relies on: a `Repatch` transition is only ever the effectful half (`λe`-equivalent: cheap, `(new_fact, cached_state) -> patched_bytes`) of the same idempotent/effectful decomposition already documented for `QuickeningSite::observe` (the `λi`-equivalent: `fact -> state`, GOAL.md/quickening.rs). Define this as one named, reusable interface (`IdempotentProbe` / `EffectfulApply`) that any future IC — interpreter-side or stencil-side — implements, rather than letting each site independently reinvent its own version of the same split (one fact, one representation, applied to the *shape* of an IC, not just its data)
- **Patch data before patching code**: a `Repatch` transition rewrites only `PatchValues` (the view into `QuickeningSite`'s existing shape/callee/slow-path state) via the `stencil_patch.rs` writers from task 023, without touching instruction bytes, whenever the current `Stencil`'s hole set still covers the new fact
- Fall back to `Rendered` (re-select and re-copy a `Stencil`, i.e. a code-bytes change) only when the fact vector has changed enough that no hole in the currently installed stencil can express it — this is a data-vs-code decision made by comparing `RegionKey`s, not a tunable threshold
- A site exceeding the same bounded degrade limit as its interpreter-side counterpart (014's `MAX_MISSES`) transitions to `Retired` and runs the complete ordinary interpreter path permanently for that installation, exactly as an interpreter-side site degrades — no separate unbounded JIT cache
- Ensure `Repatch` is safe under concurrent execution of the installed code (synchronization or generation-counter scheme), or restrict it to safepoints if concurrent data-patching cannot be made safe

## Acceptance
- A property-access region observed against `Shape17` can gain a `Shape31` case as a `Repatch` (data-only) transition when the installed stencil's hole table already has room for it; only a hole-table miss forces a `Rendered` (code-copy) transition
- The `IdempotentProbe`/`EffectfulApply` interface has at least two implementers (interpreter-side `QuickeningSite::observe` and stencil-side `Repatch`), proving it is a shared shape, not documentation of one specific site
- `Repatch` never executes torn or partially written data teardown; `Rendered` never executes torn or partially written code
- Every transition is named and testable in isolation as a pure function of `(current_state, fact_delta) -> next_state`, satisfying "behavior = state machines" rather than ad hoc flags
- Retirement bound matches rule 13/14 in GOAL.md; a retired site never silently re-enables without going through `Cold` again

## Non-goals
- A tracing or optimizing JIT tier
- Cross-region inlining or speculative deoptimization
