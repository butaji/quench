# 070: Get real completion numbers for all 8 v8-v7 benchmarks (completion-focused, not a survey)

- **Theme:** vm_completeness
- **Executor:** codex
- **Depends on:** 052

## Context

Distinct from tasks 053/054/055/069, which are profile-*gated surveys*
that are explicitly allowed to conclude "not justified, no implementation."
That's the right discipline for tuning questions. It is **not** an
acceptable end state for "does this benchmark produce a score at all" —
right now 5 of 8 v8-v7 benchmarks (Crypto, RayTrace, EarleyBoyer, RegExp,
NavierStokes) have no recorded completion time because the tracked runner's
10-second timeout cut them off. This task's job is narrower and harder to
dodge than the surveys: get every benchmark to a real, recorded number,
however large, before any of 053/054/055/069's tuning surveys are trusted
to have complete information to work from.

## Scope
- Measurement only — this task does not fix anything itself, it establishes
  ground truth for 053/054/055/069 to work from
- The v8-v7 tracked runner (task 052)

## Deliverables
- Re-run the full v8-v7 suite with an escalating timeout (60s, then 300s if
  still incomplete, then 900s if still incomplete) until every one of the
  8 benchmarks either completes with a real score/RSS/output-equality
  result, or is confirmed non-terminating (distinguish "very slow" from
  "actually hung" the same way task 061 did for DeltaBlue — a `sample`
  profile showing distributed activity across many functions means slow;
  concentrated in one function with no progress across repeated samples
  means hung)
- Record every benchmark's real number in `docs/architecture-evidence.md`,
  replacing the "exceeded timeout, no score" entries with actual data
- If any benchmark is confirmed genuinely non-terminating (not just slow),
  that's a P0 finding on its own, same treatment task 061 got — flag it
  immediately, don't bury it in this task's closing note

## Validation

1. All 8 benchmarks have a recorded completion time, score, RSS, and
   output-equality result — "exceeded timeout" is not an acceptable final
   state for this task, only an intermediate one before escalating the
   timeout further
2. For any benchmark that took an extremely long time: a `sample`/DWARF
   profile confirming it's genuinely making progress (matches 061's
   DeltaBlue methodology), not stuck
3. `docs/architecture-evidence.md` updated with the real numbers, clearly
   superseding the earlier 10-second-timeout snapshot

**Fail condition**: leaving any benchmark as "unknown, exceeded timeout"
without at least one attempt at a much longer timeout and a profile check
is incomplete — the whole point of this task is to remove that blind spot.

## Non-goals
- Fixing anything found slow — that's 053/054/055/069's job, working from
  this task's ground-truth numbers
