# 053: Regex engine performance survey (Irregexp-informed)

- **Theme:** vm_completeness
- **Executor:** codex
- **Depends on:** 052

## Context

External research: V8's regex engine (Irregexp) is architecturally a
separate compiler entirely — parses a pattern to its own AST, compiles to a
proprietary bytecode, interprets that on a dedicated VM, and promotes hot
patterns to per-architecture native code (nine separate backend
implementations upstream). This is nothing like the stencil tier's
opcode-level fusion; regex performance is effectively its own VM problem.
The v8-v7 suite's `RegExp` benchmark and curriculum case 032 (string/regex,
~27-30x slower than Node in every measurement this session) both point at
this as a real, currently completely unaddressed gap — no task in this
backlog touches regex execution at all.

This is a survey task, not a commitment to build a second bytecode VM —
scope the real cost first.

## Scope
- Wherever quench-runtime's current regex matching lives (profile first to
  find it — likely delegates to a Rust regex crate or has a hand-rolled
  matcher; identify which before assuming the fix)

## Deliverables
- Profile the v8-v7 `RegExp` benchmark and curriculum case 032 specifically
  to find where time actually goes: pattern compilation cost (paid once) vs.
  match execution cost (paid per call) vs. string-representation overhead
  (already covered by task 046's now-closed no-go finding — confirm that
  finding still holds specifically for regex-heavy code, not just
  concatenation)
- Report findings: is the current regex implementation a backtracking
  interpreter, a compiled-pattern approach, or delegating to an external
  crate — and where the measured cost actually concentrates
- Only if profiling shows compilation or match-execution cost (not just
  general string overhead already covered elsewhere) is a real, substantial
  share of case-032/RegExp-benchmark time, scope a follow-on implementation
  task with a specific target (e.g., pattern-compilation caching, a
  match-execution fast path for common pattern shapes) — do not scope that
  follow-on speculatively in this task

## Validation

1. A recorded profiling breakdown (compile vs. match vs. string-overhead)
   for both the v8-v7 `RegExp` benchmark and curriculum case 032, in
   `docs/architecture-evidence.md`
2. A clear recommendation: implement (with a specific, narrow target) or
   defer with a stated reason — not a vague "regex is slow, needs work"

**Fail condition**: proposing a regex-engine rewrite (a second bytecode VM,
matching V8's Irregexp architecture) without profiling data justifying that
scale of work — this is exactly the kind of speculative, unscoped
implementation this project's discipline exists to prevent.

## Non-goals
- Building anything resembling Irregexp's native-code-per-architecture tier
  — out of scope regardless of profiling results; if match-execution
  genuinely needs that level of investment, that's a decision for a future,
  much larger task, not this survey
