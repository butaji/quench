# 09: Unify activation, realms, jobs, and the host ABI

## Outcome

Create one activation/lifecycle model and a narrow, GC-safe capability boundary for Node, Test262, and Wasm.

## Current gap

V2 owns simple frames and two host effects; Quench requires realms, suspended execution, jobs, interrupts, re-entry, and persistent host-held values without exposing VM internals.

## Dependencies

See this task's `depends_on` in [index.json](index.json).

## Scope and implementation sequence

1. Define one frame, continuation, handler, and completion representation for calls, returns, throws, yield/await, and resumption.
2. Move globals, intrinsics, module state, and job queues into explicit runtime-owned realms rather than thread-local semantic authority.
3. Define `Host`, `HostContext`, `CapabilityId`, and `RootId`; capability calls receive borrowed arguments and return values/errors through the runtime.
4. Require persistent roots for callbacks or values retained beyond a call; make release, cancellation, interruption, and shutdown named transitions.
5. Support safe host-to-guest re-entry and separate VM instances for workers; share only explicitly thread-safe external backings.

## Verification

Use existing Test262 cases and the unchanged harness for observable call,
completion, realm, job, and suspension behavior. Do not add tests or run
unit-test suites during this phase. Inspect host-root, interrupt, worker, and
allocation transitions directly where they have no existing Test262 oracle.

## Closure boundary

Promise and module producers belong to tasks 17 and 18, which depend on this
task. This task closes when the frame/continuation/completion representation,
realm-owned state, `HostContext`/`CapabilityId`/`RootId` contract, rooted job
queue, and re-entry/interrupt transitions exist and are tested; tasks 17, 18,
21, and 43 adopt them.

## Definition of done

- Hosts cannot inspect heap cells or retain raw `Value` handles across safepoints.
- Every activation and job transition has one owner and root set.
- No implicit current-VM global is needed for semantics.

## Performance evidence

Measure frame/root/job bytes and call/host-boundary overhead; no cutover threshold applies.

## Implementation evidence

The next runtime now exposes stable `CapabilityId` values and a borrowed
`HostContext`. Print and clock effects route through that context, whose API
accepts only typed host-boundary data and never exposes heap cells or guest
handles. Root handles are generation-checked and owned by the same runtime.

The runtime now exposes generation-checked root lookup and rooted job enqueue /
drain operations. Hosts submit callback and argument roots, the VM copies those
values into its single pending-job owner, and the shared interpreter drains the
queue after roots may be released; stale roots are rejected before enqueue.
Promise/module producers and realm persistence remain pending dependencies.

The VM now groups the realm's global object and host-visible pending-job queue
under one explicit `Realm` owner. Frame entry, environment resolution,
builtin installation, GC roots, execution, and job draining all consume that
owner rather than a parallel VM-level global/job authority; existing Test262
stage evidence remains unchanged.

Constructor activations now capture their `new.target` in the frame's explicit
dynamic binding, then clear the ambient construction marker before executing
nested ordinary calls. Derived `super()` reads the captured activation value
and forwards it to the superclass construction; this prevents accessors and
other nested functions from accidentally inheriting the caller's target. The
existing stage-10 `new.target` subtree passes 14/14. Broader activation and
realm work remains incomplete.

The Test262 realm factory now exposes realm-bound `parseInt` and `parseFloat`
function objects from a data-driven intrinsic list, matching the corresponding
old-core realm globals instead of returning `undefined` for those names. The
existing cross-realm non-constructor case
`language/expressions/new/non-ctor-err-realm.js` now passes. This is a narrow
realm bootstrap slice, not a claim that realm-owned intrinsics are complete.

Arrow activations no longer install their own `new.target = undefined` entry;
they resolve the enclosing function's dynamic binding through the captured
environment. Ordinary functions still establish their own activation binding.
Direct eval from a class-field initializer likewise observes `undefined` for
`new.target`, without suppressing execution of the rest of the eval source.
The existing stage-10 `new.target` filter passes 16/16, covering returned and
immediately invoked arrows as well as field-initializer eval. This is one
activation-state rule, not a source-pattern exception. Broader frame, realm,
and job ownership remains incomplete.

Synchronous constructor completion now carries the activation's final `this`
alongside its return value. Derived constructors no longer allocate a throwaway
base receiver: an object return wins, `undefined` returns the `this` established
by `super()`, and a primitive return throws. `GetPrototypeFromConstructor`'s
fallback for user functions now reads `%Object.prototype%` from the
`newTarget` function's realm. The existing cross-realm `super/realm.js` case
passes; ordered Test262 stages 0–9 remain green. This advances activation and
realm ownership but does not close task 09.

Derived-class implicit constructors now use the VM's super-construct operation
instead of loading a captured `super` value and routing through guest
`Reflect.construct`. The superclass is read from the active constructor's
internal prototype, and the shared construct path applies `newTarget.prototype`
to native-built-in results. `IsConstructor` uses compiled constructibility
metadata, with async/generator kind facts excluding their non-constructible
callables; it no longer guesses from the mutable prototype property. The
existing Test262 class path filter passes 4,048/4,059 (the 11 remaining class
failures are other known families), and the stage-0 `isConstructor.js` filter
passes 1/1. Fresh ordered 0–10 evidence is 11,036/11,101 (65 remaining); no
stages 0–9 regress. Full activation/realm/job task completion remains open.

Environment cells now retain the owning residual-program identity alongside
the function index, allowing dynamically compiled direct-eval functions to
resolve and update captured activation slots across program boundaries. A
root-eval scope marker is carried by the environment wrapper, not ambient VM
state, so root block bindings remain reachable by eval-created closures
without exposing expired root slots to function-scoped eval. The existing
`tagged-template/cache-eval-inner-function.js` and
`block-scope/leave/outermost-binding-updated-in-catch-block-nested-block-let-declaration-unseen-outside-of-block.js`
cases both pass. Ordered Test262 stages 0–9 pass 1,157/1,157; stage 10 is
11,084/11,101 (17 failures across 10 families). Evidence:
`target/test262-next-prefix-0-10-dynamic-eval-scope-final.log`; timeout was
900,000 ms per case and batches were capped at 100. This advances the
activation environment model but does not close task 09.

Residual programs now retain the Script/Module source goal through binary
serialization, and `ProgramStore` derives the root module environment from that
goal. A dynamic self-import of an executing root module joins its pending
module record; the record settles after root evaluation and its namespace
exports are views of the root's live slots. Module-name normalization is a
single shared identity function used by compiler graph resolution and runtime
module caching. This closes the observed once-only, default-generator, and
live-self-binding cohort (four existing cases), but not the broader
activation/realm/job model.

The dynamic module namespace linker stores export provenance as retained
program/environment slots and composes local bindings with named, star, and
namespace reexports. Nested namespace property cases now verify exported names
survive evaluation; module reads are sourced from the module activation, not the
caller frame. This is partial module-lifetime progress, not completion of
realm/job ownership.

Module-root `var` bindings now remain in their module activation instead of
being mirrored onto the shared global object. This keeps imported module
declarations from mutating the importing script's globals; the existing
`dynamic-import/eval-self-once-script.js` case now reaches `$DONE`. This is a
scoped source-goal binding fix, not closure of the broader activation/realm/job
contract. Verified in the ordered 0–10 prefix at
`target/test262-next-prefix-0-10-module-root-var-scope.log`; timeout was
900,000 ms per case and stage batches were capped at 100.

The Test262 `$262.evalScript` host method now compiles Script-goal source into
the active VM realm and runs it on the new core. Dynamic program identity is
installed for the call and restored afterward; root declarations use the same
global-instantiation transition as ordinary Script execution. Realm lexical
declaration names are tracked separately from evalScript lexical values, so
redeclaration checks do not capture ordinary activation locals. Existing
global-code evalScript cohorts, including function redefinition, lexical
initialization, deletion, and var/lexical collision cases, pass. This remains a
partial realm-lifetime model; escaped closures and broader cross-script
lexical-cell behavior are not claimed complete.
