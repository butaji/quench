# 055: Allocation-throughput survey for allocation-heavy workloads (Splay, RayTrace, EarleyBoyer)

- **Theme:** vm_completeness
- **Executor:** codex
- **Depends on:** 052

## Context

External research: V8 (and most production engines) use a generational
collector with a bump-pointer "nursery" — allocating a young object is
just an increment-and-return, with no per-object bookkeeping cost paid at
allocation time; cost is paid later, only for objects that survive a minor
collection. Quench's memory model (per this session's own measurements) is
Rc-based (refcounting), which pays a small, deterministic cost on every
allocation *and* every drop, regardless of how short-lived the object is —
a structurally different tradeoff, not obviously worse (refcounting avoids
GC pause latency and quench's RSS is consistently ~0.5x Node's), but
allocation-heavy, short-lived-object workloads (Splay's tree node churn,
RayTrace's per-ray vector allocation, EarleyBoyer's Scheme-compiled
closures) are exactly where a nursery's near-zero allocation cost would
show up as a real, measurable difference.

This is a survey, not a commitment to rebuild quench's memory model —
that would be a large architectural change with correctness and RSS
implications far beyond this backlog's scope.

## Scope
- Profiling only, no code changes unless a narrow, bounded opportunity is
  found (e.g., a specific hot allocation site amenable to a bounded local
  pool, not a generational-collector rewrite)

## Deliverables
- Profile the v8-v7 `Splay`, `RayTrace`, and `EarleyBoyer` benchmarks
  (once 052 wires them up) specifically for allocation/drop cost share vs.
  other costs (dispatch, property access, etc.)
- Report findings: is allocation/refcounting overhead a measured, material
  share of these benchmarks' cost, or is the gap dominated by something
  else (coverage, dispatch, etc. — already-tracked territory)?
- If a specific, bounded hot allocation site is found (e.g., one object
  shape allocated and dropped at very high frequency in a tight loop),
  scope a narrow, targeted follow-on task for *that* site only — not a
  general memory-model change

## Validation

1. A recorded profiling breakdown per benchmark, in
   `docs/architecture-evidence.md`
2. A clear recommendation: a specific narrow follow-on task (with a named
   hot site and measured cost), or a decision that allocation isn't the
   bottleneck here — either is an acceptable, honest outcome

**Fail condition**: proposing a generational-GC rewrite or any change to
quench's core memory-ownership model (Rc-based, per
`docs/architecture-evidence.md`'s representation invariants) without
evidence that it's the dominant cost — this is exactly the scale of change
this project's profile-first discipline exists to gate.

## Non-goals
- Any change to quench's fundamental memory-safety model (Rc-based
  ownership) — this survey may recommend a narrow, local allocation
  optimization at most, never a GC architecture change
