# 022: Generate region stencils and a RegionKey -> Stencil dispatch table

- **Theme:** copy_patch_jit
- **Executor:** codex
- **Depends on:** 021

See `docs/copy-and-patch-jit.md` for the full design.

## Scope
- crates/quench-runtime/build.rs
- crates/quench-runtime/src/stencil_select.rs (new, pure dispatch, target ≤150 lines)
- tools

## Deliverables
- At build time, compile stencil-eligible **regions** — not single opcodes — to relocatable machine-code fragments plus `Hole` tables; a region is a provably fusible operation sequence (e.g. a loop body, a property-access chain) admitted only by existing Proven/Guarded facts, following the "region stencils, not opcode stencils" principle: dispatch elimination is the point, not merely a copy/patch replacement for one opcode.
  **This is a deliberate divergence from the Deegen paper, which stencils strictly per-bytecode (Appendix B compiles one bytecode at a time) — region fusion is this project's own extension and needs its own correctness argument, not an inherited one.** Specifically: prove that every fused region's control-flow graph has no external entry into its interior blocks (only the region's declared entry point is reachable from outside), so hot-cold splitting and jump-to-fallthrough (task 023) remain sound across the fused boundary.
- Implement the build-time type-based optimization pass as a named, reusable algorithm (not ad hoc per-operation logic), mirroring Deegen §5.1's algorithm 𝒜: given a region's semantic function and a type predicate over its `BoxingFact`-typed operands (from task 021), remove or strength-reduce type checks that the predicate makes trivially true/false, and produce the reduced function. State this as one algorithm callable for any region/predicate pair, not reimplemented per operation.
- Emit a `RegionKey -> Stencil` dispatch table in `stencil_select.rs`; selection is one table lookup, never a branch chain on operand type
- Use only the four closed `HoleKind`s from task 021; reject any region whose patch sites don't reduce to `Imm32`/`Disp32`/`Rel32`/`Ptr64`, falling back to per-opcode interpretation for that region
- Reuse the same semantic function/declaration that already generates the interpreter and IC views for each op in the region; never a second semantic body
- Where a stencil body is generic over a fact dimension (e.g. `fn add<T: Number>(a: T, b: T) -> T`), the generic type/const parameters may be instantiated **only** by this build script, iterating the same canonical fact enumeration that produces `RegionKey`; no other code path may name or instantiate a concrete `Stencil<Op, Lhs, Rhs, Ty, Overflow>`-shaped combination. The generic function is a derivation mechanism, not a second eligibility surface — "which specializations exist" has exactly one answer (the fact table), never two

## Generics discipline
- Do not expose a nameable generic `Stencil<Op, Lhs, Rhs, Ty, Overflow>` type; keep one generic function per operation and let only the build script's fact-driven loop monomorphize it
- Genericize only fact dimensions with demonstrated runtime payoff (start with `Ty`/numeric representation); share one stencil body across every dimension without measured payoff instead of taking the full `operation x type x location x shape x IC state x control pattern` cross product
- A generic parameter combination the fact table does not admit must not compile into the binary; if it does, the eligibility enumeration and the generic instantiation set have drifted apart and that is a build failure, not a size-tuning problem

## Acceptance
- `stencil_select.rs` contains no `if`/`match` on fact contents beyond the single dispatch-table lookup and its miss fallback
- Region fusion depends only on runtime-independent, build-time-provable fact combinations (never on fixture name, source text, or benchmark identity)
- Every fused region passes the single-entry-point CFG check before it is admitted to the dispatch table; a region that fails the check is rejected at build time, not patched around at runtime
- The type-based optimization pass is exercised by at least two distinct regions with different predicates, proving it is one reusable algorithm and not per-region logic
- Two calls with an identical fact vector for the same region always select the identical `Stencil` (canonicalization, not re-derivation)
- Build fails clearly if a declared-eligible region cannot be reduced to closed-hole-kind relocatable bytes
- Every monomorphized instantiation of a generic stencil body traces back to exactly one entry in the fact enumeration that also produced its `RegionKey`; no instantiation exists in the compiled binary that the fact table does not admit

## Non-goals
- Runtime copy, patch, or execution (task 023)
- Rendered-region caching across process lifetime (task 025)
