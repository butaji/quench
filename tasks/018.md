# 018: Hash shape transitions and property-slot lookup

- **Theme:** quickjs_perf
- **Executor:** codex
- **Depends on:** 003, 007

## Scope
- crates/quench-runtime/src/dynamic/shape.rs
- crates/quench-runtime/src/dynamic/atom.rs

## Deliverables
- Give Shape a content hash derived once at construction from (proto, props); ShapeTable::intern looks the hash up instead of re-deriving shape identity by linear PartialEq scan on every call
- Replace Shape::slot's linear property scan with a hashed per-shape property-to-slot lookup, following the QuickJS shape-hash-chain precedent
- Model property addition as an explicit transition edge (from_shape, atom, flags) -> to_shape, cached on the originating shape, so repeated 'same base shape plus this property' paths are a state-machine lookup rather than rediscovered by rebuilding and re-interning the whole prop array
- Audit dynamic/atom.rs's growth strategy against the same pattern and hash it if it is currently linear
- Keep the shape/atom identity vocabulary shared by caches and the dynamic adapter (GOAL.md baseline) unchanged in meaning, only in lookup cost and derivation

## Acceptance
- Shape transition and property lookup are O(1) amortized instead of O(shape count)/O(property count)
- A shape's identity (hash) is computed once and reused, never recomputed as a side effect of interning or transitioning
- Object-heavy neutral microbenchmarks (property-add, megamorphic-free property read) show measured improvement
- No change to shape/property observable identity or enumeration order

## Non-goals
- Changing property enumeration order or descriptor semantics
