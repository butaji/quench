# 028: OSR entry into a lower-tier-compiled loop

- **Theme:** deegen_full_jit
- **Executor:** codex
- **Depends on:** 027

## Context

The paper's tier-up can promote a hot loop *while it is already running*
(§3): execution transfers on-stack from the interpreter/baseline tier into
optimizing-JIT code without waiting for the loop to exit and the function to
be re-entered. Quench has no such mechanism today — the stencil tier's
`RegionKey` lookup only ever happens at region entry, never mid-loop. This
task builds the OSR entry point mechanics using the loop-header counters from
027, ahead of there being an optimizing-JIT target to jump into (029/031) —
it should land on a synthetic/no-op target first so the entry mechanism is
independently testable.

## Scope
- crates/quench-runtime/src/vm/vm_runtime.rs
- crates/quench-runtime/src/loops.rs / loops_run.rs
- crates/quench-runtime/src/stencil_lifecycle.rs (for the eventual real target)

## Deliverables
- A defined OSR entry point ABI: what live state (locals, stack, iterator
  position) must be materialized/read at the transfer point, and in what
  layout the target tier expects it
- Transfer mechanics that work into a placeholder/no-op target first
  (correctness of the *entry protocol*, decoupled from having a real
  optimizing tier yet)
- Complete fallback: any state that can't be safely reconstructed for OSR
  keeps the loop running in its current tier rather than transferring

## Acceptance
- Differential tests confirm identical observable behavior with OSR wired to
  a no-op target vs. OSR disabled entirely
- The entry-point ABI is documented as a named data shape (mirrors this
  project's Proven/Guarded/Unknown fact discipline), not an implicit calling
  convention
- Neutral corpus geomean does not regress

## Non-goals
- Deoptimization (029) — this task only handles *entering* a higher tier, not
  bailing back out
- The optimizing JIT tier itself (031)
