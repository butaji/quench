# 37: Lower Wasm operators to the shared residual bytecode

## Outcome

Compile Wasm functions directly into the same `bytecode::{Op, Instr,
ResidualProgram}` vocabulary the OXC specializer emits, extended only with the
opcodes genuinely absent from JavaScript, instead of introducing a second
register IR for Wasm inside the next engine.

## Current gap

The legacy `quench-runtime` crate lowers Wasm's `wasmparser::Operator` stream
into its own independent register IR (`crate::hir::{Inst, Reg, Kind}`) via
`wasm/emit/{mod,ops,atomic}.rs`, with its own structured-control-flow stack
(`Ctrl`/`CtrlKind`). This has nothing in common with `quench-runtime-next`'s
`bytecode::{Op, Instr}` that the OXC specializer (task 10, `compile.rs`)
already produces. Porting Wasm without unification would create a third
representation alongside JS's residual bytecode and the legacy `hir`, all
feeding the same conceptual target: a register-based instruction stream a
single interpreter executes.

## Dependencies

See this task's `depends_on` in [index.json](index.json). This task is the
next engine's only Wasm execution path; task 23 depends on it rather than
first porting the legacy IR. It is on the critical path of phase A: JavaScript
and Wasm share one VM (one heap, `Value`, root set, `opcodes!` vocabulary,
dispatch loop, and activation stack), and this task is where that sharing is
established.

## Scope and implementation sequence

1. Enumerate `wasmparser::Operator` variants and map each to an existing
   `bytecode::Op` where semantics coincide: numeric ops (`i32.add` etc. onto
   the same binary/numeric opcodes the OXC specializer's `numeric.rs` pass
   produces), locals (`local.get`/`local.set` onto `LoadLocal`/`StoreLocal`),
   calls (`call`/`call_indirect` onto `Call`/`CallKnown`, reusing
   `method_cache.rs`-style call-site caching for `call_indirect` through a
   table), and structured control flow (`block`/`loop`/`if`/`br`/`br_if` onto
   `Jump`/`JumpFalse`/`JumpBinaryFalse`).
2. Add residual opcodes only for what has no JS analog: multi-value return,
   explicit trap conditions, linear-memory bulk operations, table/element
   operations, and any SIMD/GC-proposal operators the pinned spec suite
   requires. Declare these through the existing macro-declared opcode
   vocabulary rather than a parallel enum.
3. Reuse the heap/typed-array element-access primitives from
   `typed_array_access.rs` (and the unified typed-array representation from
   task 35, if landed) for linear memory access rather than a separate memory
   model.
4. Retire `crate::hir` and `wasm/emit/*` once the next engine's Wasm lowering
   covers the pinned spec suite; do not carry the legacy IR past cutover
   (task 27/28), consistent with the "no permanent legacy backend"
   constraint.
5. Keep Wasm's own type/stack validation (via `wasmparser::Validator`) as the
   static-correctness authority feeding this lowering; task 41 covers
   verifying that.

## Binding time and v2 constraints

The Wasm front end is a second generating extension for the same interpreter.
Its static facts are richer than JavaScript's: the validator proves every
operand type, block arity, and `call_indirect` signature. Those facts are
consumed at lowering time and encoded in the residual (typed opcode rows,
static root maps that mark untagged slots), so Wasm residual code does not
re-dispatch on value tags. Share an `Op` row only where semantics coincide
exactly: `i32.add` wraps and is not JavaScript `+`, and i64 has no JavaScript
immediate form. Wasm-specific rows are added to the same `opcodes!` table. Keep
v2's three [addressing domains](../docs/v2/addressing-domains.md) separate;
Wasm locals, globals, and linear-memory addresses map into the existing domain
that matches their operation, not into a universal address.

## Definition of done

- Wasm functions compile to `ResidualProgram` via the same `Op`/`Instr` types
  JS uses, with only genuinely Wasm-only opcodes added.
- The pinned Wasm spec suite passes through the unified lowering.
- `crate::hir` and the legacy `wasm/emit` module are removed, not kept as a
  parallel path.
- Wasm frames are ordinary activations on the shared activation stack, and
  JS-to-Wasm and Wasm-to-JS calls go through the shared Call path without a
  second interpreter loop.

## Initial shared execution slice

`quench-wasm::Module::lower_shared_i32` decodes validated i32 module functions with a selected
export and feeds operators directly to the next runtime's `Engine` lowering.
Constants, locals, drop/nop and function return reuse existing residual rows;
i32 unary/binary operations use typed selector rows in the same `opcodes!`
authority. One Rust macro table owns all 31 selectors and their semantics;
lowering, validation, disassembly and execution consume that table.
The lowering derives GC maps through the existing liveness operation and uses
ordinary frames and the existing dispatcher. Packed instruction overflow uses
the shared wide encoding rather than an independent Wasm instruction format.
`Runtime::execute_wasm_i32` is a typed host boundary with exact argument arity.
Unsupported module state, block parameters, multiple results and operators fail explicitly. This
slice does not establish module instantiation, linking, reference lifetimes,
general traps, cross-language calls or complete spec-suite parity, and does not authorize legacy
Wasm deletion or a correctness-gate transition.

Focused regressions cover wrapping arithmetic, local zero initialization and
tee, repeat execution, void results, argument counts, wide instruction encoding,
unsupported semantics, and alternating JS/Wasm on one Runtime. The reproducible
command is `cargo test -p quench-wasm --lib shared:: -- --nocapture`.

The pinned `i32.wast` file passes all 460 directives through shared execution:
364 return assertions, 10 typed traps, 83 invalid modules, two malformed
modules and the valid module. The test rejects unsupported directives and
never invokes the legacy executor. Parse-negative diagnostics retain the
parser-error class; their decoder-specific wording is not a trap message.
Numeric trap text and trap class are both verified. Residual tests also
cover unknown selector rejection and serialization/decoding before execution.
This is a focused i32 correctness milestone, not the full Wasm conformance gate.

Structured i32 control flow now lowers blocks, loops, if/else, br, br_if,
br_table, select and return into the existing Jump/JumpFalse/Move rows.
Control labels and reachability exist only during lowering; forward targets
patch the shared packed or wide instruction encoding. Unreachable uses a
terminal throwing row in the same opcode authority and a typed Wasm trap.
Blocks support zero or one i32 result without parameters. Branch results move
only on the taken edge, preserving operand prefixes on conditional fallthrough.
The control stack also owns function termination, replacing the separate ended
flag. Eight new frontend unit tests cover nested result branches, loop backedges,
unsigned table defaults and duplicate targets, select truth, polymorphic dead
stacks, trap recovery and wide forward jumps. A runtime boundary regression
rejects malformed control structures, out-of-range labels and block stack
underflow. These extend the initial slice; full module lowering and legacy
retirement remain pending.

The staged snapshot was verified in an isolated checkout: 33 quench-wasm unit
tests (including all 460 i32 directives), five lowering boundary/serialization
regressions, two direct activation-unwind tests, 12 bytecode tests and 43 API
regressions passed. `cargo check -p quench-node -p quench-wasm-test
-p quench-test262 --all-targets` passed. No full Test262 run or new performance
claim accompanies this control-flow slice.

Direct calls between supported i32 functions now lower through the existing
CallKnown row. The frontend keeps module function order, the Engine emits one
residual program and constant table, and root maps derive across all functions.
A selected export is an entry index into that program; standalone lowering is
a one-function invocation of the same module operation. Calls use the existing
argument windows, frames, dispatch and shared stack budget. Ordinary Wasm calls
retain callers even directly before Return, preserving exhaustion rather than
silently becoming tail calls. Exhaustion is a typed CallStackExhausted trap.
Six new frontend regressions cover forward targets, argument order and operand
prefixes, nested void calls, recursive local/operand isolation, traps crossing
call frames, result-returning recursion exhaustion/recovery and wide argument
windows. A direct VM test verifies every activation unwinds on a nested trap;
invalid call targets and argument underflow also fail at the lowering boundary.
Imports, indirect calls, module state and cross-language calls remain pending.

Shared scalar signatures and payloads now cover i32, i64, f32 and f64 through
constants, locals, direct calls, select and structured branches. The frontend
passes validated declared parameter/result/local types in WasmFunctionBody;
WasmSignature owns the entry boundary contract. Function parameter counts and
local initialization code derive from these types. ScalarBits owns the exact
32/64-bit encoding, from which constants and execution slots derive. 32-bit
payloads use existing immediates; immutable WasmBits64 cells preserve all 64
bits on the shared tracing heap, including values outside JS's integer range
and NaNs colliding with Value tags. The extra cell has no outgoing roots or
external allocation, and both profiling views account for its existing slot.
The 64-bit zero constant is created only when a local requires it and reused
from the constant table. There is no second numeric heap or stack.

Module::lower_shared and Runtime::execute_wasm provide the typed boundary;
i32 convenience APIs delegate to it and reject incompatible entry types.
The i32 artifact name is a compatibility alias, with one program/signature
representation. Six frontend regressions cover constants and bit boundaries,
NaN payloads/signed zero, calls and locals, typed zero initialization, branch
and select payloads, boundary misuse and explicit unsupported arithmetic/types.
Direct runtime regressions cover raw-bit serialization and strong-root
survival/release. Remaining arithmetic families, multi-results, block parameters,
references and module state are still pending; this is not full Wasm parity.

The isolated scalar snapshot passes 45 quench-wasm tests (including all 460
