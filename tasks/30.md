# 30: Arm numeric opcode specialization from profile feedback

## Outcome

Make `dispatch_numeric.rs` consume the feedback `profile_edges.rs` already
records instead of re-checking operand types on every execution of a binary
opcode.

## Current gap

`profile_regional_binary` now owns a per-VM `(function, pc)` state machine. The
remaining gap is suite-wide differential and performance evidence; the state
machine itself is deliberately bounded to one execution and is reset at each
program initialization.

## Dependencies

See this task's `depends_on` in [index.json](index.json).

## Scope and implementation sequence

1. Establish whether `dispatch_numeric.rs` currently reads `profile_edges.rs`
   output; if not, this confirms the gap rather than assumes it.
2. Define an arming rule: after N consistent fast-path observations at a site
   with no interleaved slow-path hit, mark the site specialized in the residual's
   per-site state so the interpreter can skip the generic type check and go
   straight to the typed operation.
3. Guard every specialized site with an exact type check that, on failure,
   deoptimizes the site back to generic dispatch and clears its armed state
   rather than trapping or producing divergent results.
4. Keep the specialized and generic numeric paths sharing one semantic
   implementation of the actual arithmetic (per AGENTS.md: share semantics
   across interpreter/specialized/native), differing only in the guard that
   selects them.
5. Do not let arming or deoptimization depend on fixture identity, source
   provenance, or benchmark markers—only on observed operand types at the site.

## Verification

Run against task 42's disable-specialization gate and whatever Test262/
Node-compat/Wasm fixture coverage already passes at landing time, as a
regression check independent of this task's own targeted cases below.

Differential tests against Node/Test262 for numeric operators across
Number/BigInt/String-coercing operand mixes, NaN/Infinity/-0 edge cases,
polymorphic sites that flip type mid-loop, and repeated arm/deoptimize cycles at
one site. Confirm deoptimized sites remain correct indefinitely, not just once.

## Definition of done

- Numeric opcodes have one authoritative arithmetic implementation with a
  specialized entry and an exact generic fallback.
- Arming and deoptimization are exercised by tests, including adversarial
  operand-type flips.
- Feedback recorded by `profile_edges.rs` is demonstrably read by dispatch, not
  write-only.

## Performance evidence

Report arm rate, deoptimization rate, and dispatch-time delta for
arithmetic-heavy workloads, plus the existing four-benchmark suite.

## Implementation evidence

`profile_edges.rs` now records eight consecutive integer-fast observations per
site before arming. The dispatch path consumes that state and enters the shared
integer arithmetic implementation behind an exact `Value::int_pair` guard;
guard failure deoptimizes the site and routes through the ordinary binary
operation. Generic programs never arm sites. Focused tests cover arming,
type-flip deoptimization, and generic-mode suppression; the runtime-next
matrix (52 unit, 1 module-size, 162 subset) and strict all-feature clippy pass.
