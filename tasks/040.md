# 040: Widen specialized stencil leaves by real hotness evidence (call, property, loop glue, array, ForI)

- **Theme:** deegen_full_jit
- **Executor:** codex
- **Depends on:** 039

## Context

Task 035 closed by reconciling catalog *admission* bookkeeping (31/31 opcodes
route through the `DISPATCH` fallback region, which was already true) but did
not add new specialized machine-code leaves — the specialized-leaf count is
still 8/31 (`Move`, `Add`, `AddConst`, `Return`, `Sub`, `Mul`, `Div`, `GetN`;
see `docs/deegen-stencil-coverage.md`). This task is the real breadth-widening
work task 035's evidence pointed at but didn't do, now sequenced after 039 so
new leaves actually execute on this machine's architecture instead of being
verified logic-only.

Priority order below is evidence-based, not convenience-based, from two
sources: (1) `quench-bench/deegen-curriculum/`'s real measured regressions
against a compiled build, and (2) raw per-opcode dispatch counts captured
from `execution_trace` during that calibration — which showed the *current*
arithmetic loop region's dominant cost isn't the arithmetic op itself but the
surrounding local-variable glue that isn't covered by any region yet (a
single arithmetic-loop trace: `LoadConst` 12151, `LoadLocalChecked` 8011,
`Binary` 8007, `UpdateLocal` 4000, `StoreLocal` 4006 hits — an order of
magnitude above the `Add`/`Mul` counts the existing region actually
specializes).

## Deliverables, in this order — do not skip ahead

1. **Widen the existing `LOOP`/`FALLTHROUGH` arithmetic region to actually
   cover its own surrounding glue**: `LoadLocalChecked`, `Binary`,
   `UpdateLocal`, `StoreLocal`, `LoadConst` where they appear inside an
   already-admitted arithmetic region's CFG, instead of letting them fall
   through to `DISPATCH` mid-region. **Unblocked**: task 042 (closed,
   `ab738f909`) built the bounded sequential region executor this item
   needs — use it, don't reinvent it. Admit the measured glue span through
   042's mechanism (validated span, per-instruction fallback check) rather
   than adding opcodes to the old single-leaf metadata.
2. **`Call` / `CallN` region stencils.** The largest confirmed regression in
   the curriculum (recursion: 13-15x vs. Node; closure-heavy workloads:
   27-47x). Build-time admission needs a callable-identity fact (reuse the
   existing call-IC guard facts from `quickening.rs`, don't invent a second
   representation), with the complete ordinary call path as fallback on any
   Unknown/polymorphic/megamorphic callee.
3. **`GetProperty` / `SetN` region stencils** (property read and write).
   Reuse the existing shape-guard facts the generic IC already establishes;
   do not build a second shape-fact representation for the stencil tier.
4. **`AGetI` / `ASetI` / `AGetIInc` region stencils** (array element
   access) — common iteration pattern, currently uncovered.
5. **`ForI` fast-path admission.** Currently `ForI` has zero specialized
   coverage *and* is excluded from OSR-entry (no bytecode back-edge to
   resume from). This is the most idiomatic JS loop shape
   (`for (let i=0; i<n; i++)`) and currently gets no fast-path treatment at
   all regardless of hotness. This needs its own admission strategy keyed on
   the structured-loop control shape, not leaf specialization by opcode —
   scope the design during implementation; do not force it into the same
   `RegionKey` shape as the other items above if it doesn't fit.
6. Quickened-variant leaves (`GetPropertyQuickened`/`GetNQuickened`/
   `AGetIQuickened`) only after their base op (3) has a leaf — give the
   confirmed-shape quickened path its own tighter leaf as a small follow-on,
   not a separate investigation.

Stop and record status after each numbered item lands and is measured — do
not batch all six into one unverified commit.

## Validation

Repeat per item, not once at the end:

1. A build-time CFG-soundness unit test for the new region's single-
   entry-point proof (same discipline as task 035's item 2).
2. A differential test: identical observable output with the region admitted
   vs. forced-fallback, for both the covered case and a hostile case that
   must correctly fall through.
3. `cargo test -p quench-runtime --lib` — all pass.
4. Before/after measurement on the relevant curriculum case(s) — item 1
   against the arithmetic-loop cases (quench-bench/deegen-curriculum
   017/019), item 2 against 010/029, item 3 against 011-016, item 4 against
   any array-heavy case, item 5 against any `for`-loop-shaped case. Record
   the wall-time delta per item in `docs/architecture-evidence.md`.
5. `node quench-bench/deegen-curriculum/deegen-verify.mjs --from 1 --to 38`
   — no regression in cases outside the one being improved.
6. Update `docs/deegen-stencil-coverage.md`'s specialized-leaf count and
   table after each item.

**Fail condition**: a region added without its own CFG-soundness test and
before/after measurement is incomplete, regardless of whether it "looks
right" — this backlog has already found real gaps hiding behind plausible-
looking but unverified claims (task 032's quickening naming, task 034's
architecture-confounded Gate-0 result); don't add another one.
