# 16: Port collections, iterators, and weak lifecycles

## Outcome

Implement collection and iterator protocols, including weak reachability, on the new heap.

## Current gap

V2 has arrays but no Map, Set, weak collections, WeakRef, FinalizationRegistry, or complete iterator-helper surface.

The current Map, Set, WeakMap, and WeakSet cells store entry vectors and look
keys up with a linear `position(same_value_zero)` scan (`vm/collections.rs`).
ECMA-262 requires collections to provide access times that are sublinear in
the number of elements on average (§24.1, §24.2, §24.3, §24.4). This is a
conformance requirement, not tuning.

## Dependencies

See this task's `depends_on` in [index.json](index.json).

## Scope and implementation sequence

Port Map/Set storage and iteration, WeakMap/WeakSet ephemerons, sync and async iterator protocols/helpers, WeakRef, FinalizationRegistry, and collection species/constructor behavior. Preserve insertion order and mutation-during-iteration rules. Back Map/Set/WeakMap/WeakSet with an ordered hash table (a hash index over an insertion-ordered entry vector with tombstones and compaction) keyed by the single SameValueZero/identity authority, so live iterators keep their ordering semantics.

## Verification

Run all collection/iterator/weak Test262 families plus GC-forced ephemeron cycles, deletion/reinsertion, iterator mutation, abrupt close, finalizer ordering, and no-premature-finalization controls.

## Definition of done

- Strong and weak containers use one key equality/identity authority.
- Weak behavior follows the heap's explicit weak/finalization phases.
- Iteration and callback effects are exactly ordered.

## Performance evidence

Report collection storage, hashing, GC ephemeron work, and iterator allocation.

## Implementation evidence (2026-09-21)

- Added heap-native `Map` and `Set` cells with insertion-ordered entries; GC traversal marks the collection object metadata and every key/value entry.
- Added constructor/prototype installation and native `get`, `set`, `has`, `delete`, `clear`, and `add` methods. Map and Set lookup share a SameValueZero authority, including primitive string content and `NaN` handling.
- Added live `size` accessors, JSON object treatment, allocation census names/bytes, and a subset regression covering object identity, duplicate Set insertion, deletion, and size transitions.
- Added heap-backed Map/Set iterator cells for `keys`, `values`, and `entries`; `next()` returns ordered `{ value, done }` records and retains the source collection as a GC child. Mutation after iterator creation is observed through the live insertion-ordered entry vector.
- Added WeakMap/WeakSet heap cells and object-key validation. The GC now performs an ephemeron fixpoint and prunes entries whose keys are unreachable, while retaining values only when their keys remain marked; direct heap and runtime regressions cover this lifecycle.
- Added heap-backed WeakRef targets with `deref()` and GC clearing when the target is unreachable, with direct heap/runtime regressions. Async iterator helpers, FinalizationRegistry, and disposal/finalizer ordering remain pending.
- Map and Set constructors now consume array-backed entry/value iterables, preserve first insertion order, update duplicate Map keys, and deduplicate Set values through the shared SameValueZero authority.
- Built-in `for...of` now obtains heap-backed iterators for arrays, strings, Maps, and Sets and consumes their `.next()` result records through the residual loop path; custom symbol iterators and abrupt `break` closing now share the same protocol.
- `Map.prototype.forEach` and `Set.prototype.forEach` now invoke callbacks with the
  ECMAScript argument order and collection receiver, preserving insertion order
  and SameValueZero deduplication. Their cursor is live across callback effects:
  additions are visited and deletions do not skip the shifted successor.
- The shared `GetIterator` path now consults the realm-stable `Symbol.iterator`
  value before selecting heap-backed array/string/collection iterators. Custom
  iterator methods return ordinary iterator objects whose `next()` method is
  dispatched through the same residual call path; `Array.from` and `for...of`
  share this protocol. `Array.from` now closes an acquired iterator on abrupt
  `next`, result-property, or mapper completion, and the shared protocol
  rejects primitive iterator, `next()`, and `return()` results. Iterator
  closing for return/throw completion now runs through the compiler's active
  iterator stack; async iterator helpers remain pending.

String.prototype now owns the well-known `Symbol.iterator` method, producing
the existing heap-backed `IteratorKind::String` state. Primitive symbol-key
lookup derives a wrapper's prototype from the intrinsic constructor, so
custom Boolean iterators and built-in String iteration use ordinary
`[[Get]]`/`GetIterator` flow. Existing Test262 coverage passes the 159-case
array-destructuring subtree (including string iterables) and the previously
failing `yield*` relational-expression case. The stage-10 aggregate is the
authoritative gate for this slice; no later prefix was run.
