# 071: Attack the IC/layout-mismatch constant factor directly (Richards/DeltaBlue-class gap)

- **Theme:** vm_completeness
- **Executor:** codex
- **Depends on:** 062, 067
- **Priority: high — this is most of the remaining gap to a competitive
  v8-v7 score on the benchmarks that DO complete.**

## Context

Task 061 identified Richards/DeltaBlue's cost as "bounded single-entry IC/
layout-mismatch cost" — real, measured (Richards scores 52.1 vs. Node's
~65,000+; a ~1000x-class gap), and *not* a complexity-class bug (the
architecture-invariant suite, tasks 062-067, proves the relevant paths
don't scale badly with N). That leaves exactly one explanation: the
**constant factor** per IC miss/layout-mismatch event is far larger than
it needs to be. Tasks 045 (shared megamorphic cache) and 047 (call-frame
pooling) already investigated two specific hypotheses and correctly closed
no-go — but those were narrow, targeted questions answered against
*today's* small-scale profiling. This task is the broader, more aggressive
follow-up: profile the actual IC-miss/layout-mismatch code path itself,
end to end, and find what makes each occurrence expensive, independent of
whether a cache or a frame pool would help.

## Scope
- crates/quench-runtime/src/quickening.rs (IC state, degrade path)
- crates/quench-runtime/src/properties.rs (layout-mismatch handling)
- crates/quench-runtime/src/shape_cache.rs
- Wherever the actual per-miss work happens — profile first, don't assume

## Deliverables
- Build a minimal, isolated reproduction of "one IC miss / layout mismatch"
  — a single property access that deliberately misses its cache — and
  measure its absolute cost in instructions/cycles (via `execution-trace`
  counters), not just relative scaling
- Break down where that cost goes: shape lookup, descriptor resolution,
  guard re-installation, fallback dispatch overhead, allocation — get a
  real breakdown, not a guess
- Compare against what an equivalent single miss should cost in principle
  (order-of-magnitude reasoning from the operations actually required —
  a handful of comparisons and one write, not hundreds of instructions)
- Close whatever gap the breakdown reveals, reusing existing mechanisms
  (the generic IC's λi/λe split, existing guard facts) rather than
  inventing a new one — this is about making the existing, correct
  mechanism cheap, not replacing it

## Anti-cheat validation (mandatory)

1. **Generalization check**: construct a synthetic microbenchmark
   exercising the same IC-miss pattern (polymorphic property access with
   the same shape-transition shape) with different property names, object
   shapes, and constant values than Richards/DeltaBlue's actual code.
   Confirm the fix reduces per-miss cost comparably on the synthetic case —
   if it only helps Richards/DeltaBlue's literal code, that's overfitting.
2. `grep -rniE "richards|deltablue" crates/quench-runtime/src crates/quench-node/src` — zero matches.
3. Full gates: correctness suites, neutral corpus, curriculum, and full
   v8-v7 suite — the fix must show general improvement on *any* polymorphic
   property-access-heavy workload, verified via the curriculum's stage-3
   cases (011-016, already exist for exactly this pattern) in addition to
   Richards/DeltaBlue themselves.
4. Before/after measurement recorded per benchmark, not just "Richards
   improved" — confirm DeltaBlue, and any curriculum case with the same
   shape, move together, since a fix that only helps one specific benchmark
   despite a shared root cause is a red flag for accidental overfitting.

**Fail condition**: a fix that improves Richards/DeltaBlue's v8-v7 score but
does *not* improve curriculum cases 013-015 (the existing polymorphic
property-IC stage) by a comparable margin is disqualifying — it means the
"fix" found something specific to those two benchmark files rather than the
general mechanism this task is supposed to be improving.

## Latitude to extend

If profiling for this task surfaces another clear, general, evidence-backed
performance contributor outside this task's literal scope, don't just note
it and drop it: fix it now if it's small and covered by this task's same
anti-cheat discipline, or write it up as its own new task (next available
number, same mandatory anti-cheat validation section this task uses) so the
finding doesn't evaporate. Profile-gated no-go remains a fine outcome for
the original scope either way -- this is about not losing a real adjacent
finding, not about forcing extra work that isn't justified.
