# 060: Host-level opt-in request-scoped arena (web-backend memory bound)

- **Theme:** vm_completeness
- **Executor:** codex
- **Depends on:** 059
- **Speculative — needs a real use case before implementation, see Gate 0.**

## Context

The user's stated target is web-backend apps: long-running processes
handling many independent, bounded units of work (HTTP requests) where a
huge fraction of allocation is naturally scoped to one request and provably
garbage the moment the response is sent. Task 059 only covers allocation
whose non-escape is provable *inside the VM* (call frames, closures that
structurally can't escape). "One HTTP request" is an *application-level*
concept `quench-runtime` has no inherent knowledge of — arbitrary JS code
running inside a request handler can always stash a reference somewhere
that outlives the request (a module-level cache, a `Promise` chain that
resolves later, a `setTimeout`). The VM cannot prove non-escape for this
case the way it can for task 059's call frames.

This means a real per-request arena needs the *application/framework* to
make an explicit promise ("nothing created while handling this request is
retained past its end") that the runtime cannot verify automatically — the
same tradeoff Zig's `ArenaAllocator`-per-request pattern and similar designs
in other ecosystems make. This is a legitimate, valuable pattern for the
target use case, but it changes the safety contract in a way that needs a
real API design decision, not a silent internal optimization.

## Gate 0 (mandatory before any implementation)

This is speculative until there's a concrete framework/use case driving it.
Before writing any code: identify a specific host API shape (likely
something like `quench-node` exposing an explicit
`withRequestArena(fn)`-style scope, analogous to `AsyncLocalStorage` but for
memory) and confirm, with the user, that this is worth building now versus
waiting until a real web-framework integration surfaces the actual
requirements. **Do not implement speculatively past this gate.**

## Scope (if Gate 0 passes)
- crates/quench-node/src/ (new host-level API surface)
- Whatever escape-safety-net mechanism is chosen (see Deliverables)

## Deliverables (if Gate 0 passes)
- An explicit, opt-in host API: the application declares a scope
  ("everything allocated between entering and leaving this scope is
  request-local"), not an automatic/transparent optimization
- A safety net for a broken promise (application code that *does* let a
  reference escape despite the declared scope): at minimum, detect the
  violation at scope-exit time (an arena-allocated object with an external
  reference still live when the arena would reset) and choose a safe
  behavior — copy the escaping value out to the general heap defensively
  (correct but adds cost only in the violation case) rather than silently
  corrupting memory. Silent corruption on a broken promise is not
  acceptable at any performance cost.
- Full fallback: an application that never uses this API sees no behavior
  change at all — this is purely additive/opt-in

## Validation (if Gate 0 passes)

1. A test proving the escape safety net actually catches a violation
   (deliberately let a reference escape a declared scope) and produces
   correct output, not corrupted memory, even if slower in that case
2. Differential tests: identical observable behavior with and without the
   API in use, for code that doesn't use it at all
3. A synthetic "many requests over a long run" test showing bounded,
   flat memory for the common (non-escaping) case
4. `cargo test -p quench-runtime --lib` — all pass

**Fail condition**: any implementation path where a broken escape promise
produces incorrect output or memory corruption rather than a detected,
safely-handled violation is unacceptable regardless of the performance
story — this feature's entire value proposition depends on being safe to
recommend to real application authors.

## Non-goals
- Automatic, transparent request-scope detection with no application
  opt-in — the VM structurally cannot prove this without cooperation, don't
  pretend otherwise
- Building this speculatively without Gate 0's real-use-case confirmation
