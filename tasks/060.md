# 060: Evaluate request-scoped allocation only for a demonstrated use case

## Outcome

Determine whether a concrete host workload benefits from request-aware allocation without breaking escaping JS values.

## Current gap

No approved request-lifetime/API contract exists. HTTP request completion cannot establish that closures, globals, promises or timers released their references.

## Dependencies

See this task's `depends_on` in [index.json](index.json); status and ordering live there.

## Scope and implementation sequence

1. Activation condition: a concrete host/framework workload and explicit user direction establishing its API/ownership requirements.

2. Once activated, measure current allocation/retention and compare existing mechanisms with a safe request-aware design.

3. If justified, implement explicit escape handling and lifecycle integration; otherwise close with reproducible evidence that no new API is warranted.

## Verification

`cargo test -p quench-node`; `cargo test -p quench-runtime`; Node-oracle workload checks and long-running retained/released requests, timers, promises and escaping closures.

Apply the shared [completion checks](README.md), including named baseline failures
and independent semantic controls. Record commands and artifact identity.

## Definition of done

- Activation requirements are satisfied before implementation.
- Either a safe measured implementation preserves escaping references and host behavior, or a documented reproducible rejection closes the proposal.
- No automatic request detection or unsupported non-escape assumption enters production.

## Performance evidence

Deferred host proposal; not a prerequisite for VM/JIT milestones.
