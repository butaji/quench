# 054: TypedArray fast-path coverage (NavierStokes-class workloads)

- **Theme:** vm_completeness
- **Executor:** codex
- **Depends on:** 052

## Context

Task 040's `AGetI`/`ASetI`/`AGetIInc` region bridges were built and measured
against plain-array curriculum cases. The v8-v7 suite's `NavierStokes`
benchmark is `Float64Array`-heavy (fluid-simulation numeric grids), and it's
unconfirmed whether the existing array-element stencil coverage applies to
typed arrays at all, or only to plain (`ArrayKind`-tagged) arrays — task
041's survey covered packed/holey/dictionary *plain* array elements
specifically, not typed arrays.

## Scope
- crates/quench-runtime/src/value_array_data.rs (or wherever TypedArray
  storage lives)
- crates/quench-runtime/src/stencil_select.rs (confirm/extend `GET_INDEX`/
  `SET_INDEX` admission for typed-array element access)

## Deliverables
- Confirm, don't assume: does a `Float64Array`/`Int32Array`/etc. element
  read/write currently admit into the existing `GET_INDEX`/`SET_INDEX`
  region bridges, or fall straight to `DISPATCH`? Check the actual guard
  facts these regions require.
- If typed arrays are currently uncovered: extend admission to cover them,
  reusing the existing region mechanism and CFG-soundness proof — this
  should be a coverage extension, not a new mechanism, since typed-array
  element access is structurally similar to packed-numeric plain-array
  access (fixed element width, no holes, no prototype-chain fallback)
- If typed arrays are already covered: profile NavierStokes specifically to
  find where its remaining cost concentrates instead (loop-body glue not
  covered by task 048's not-yet-started whole-function scope, allocation
  cost of the grid arrays themselves, etc.)

## Validation

1. A differential test confirming typed-array element access produces
   identical output whether the region is admitted or forced to fallback
2. `cargo test -p quench-runtime --lib` — no regressions
3. Before/after measurement on the v8-v7 `NavierStokes` benchmark specifically
   (via task 052's wiring) — record the delta
4. If typed arrays turn out already-covered: record the profiling finding
   and what's actually costing time instead, per this project's standing
   honest-negative-finding discipline

**Fail condition**: assuming coverage without checking the actual guard
facts, or extending coverage without a differential test against every
typed-array element kind (`Int8Array` through `Float64Array`, not just
`Float64Array`).
