# 044: Generate region-admission and CFG-soundness-test boilerplate

- **Theme:** deegen_full_jit
- **Executor:** codex
- **Depends on:** 040, 041

## Context

The Deegen paper's stronger single-source-DSL claim (§2-3: one description
generates interpreter + JIT + IC bodies) is correctly out of scope in full —
handler bodies are irreducible JS semantics, not glue, and auto-generating
them would need a Deegen-scale build-time semantic-analysis pipeline, not
worth the cost (see `docs/deegen-alignment.md` item 1). But a narrower,
real gap exists: each new stencil region (tasks 021-042) hand-writes its own
`RegionKey` construction and its own CFG single-entry-point soundness test,
with no shared, generated wiring between them. This is exactly the kind of
duplication that lets a region's declared admission drift from what it
actually does — the same class of bug this session found twice (task 032's
quickening-naming gap, task 040.1's design-doc-vs-implementation gap).

This task is queued behind 040/041 specifically so the generated pattern is
extracted from 3-5 *real* regions, not guessed from the 2-3 that exist
today — a premature abstraction here would be worse than the duplication it
tries to remove.

## Scope
- crates/quench-runtime/src/stencil_fact.rs (`RegionKey` construction)
- crates/quench-runtime/src/stencil_select.rs (per-region admission)
- A new declarative macro or attribute (exact shape decided during
  implementation, following `vm_op!`'s existing pattern of generating
  metadata from a short declaration)

## Deliverables
- Inventory every region added by tasks 021-042 (plus 040/041's additions)
  and identify what's genuinely identical boilerplate across them (the
  `RegionKey::from_opcodes`/`from_facts` call shape, the CFG single-entry-
  point proof's test scaffolding) versus what's genuinely region-specific
  (the actual opcode sequence, the specific facts required)
- Generate the boilerplate half from a declaration (opcode sequence + fact
  requirements), following `vm_op!`'s existing "one declaration, generated
  mechanical consequences" pattern — do not invent a second macro DSL with
  different conventions
- Migrate existing regions to the generated path as a pure refactor (no
  behavior change) to prove the abstraction actually fits real cases, not
  just new ones

## Validation

1. `cargo test -p quench-runtime --lib` — all pass, including every
   existing region's CFG-soundness and differential tests, unchanged in
   behavior after migrating to the generated path
2. A new region added via the generated declaration produces byte-identical
   `RegionKey` construction and an equivalent CFG-soundness test to what
   would have been hand-written — verified by migrating at least one
   task-040/041 region through both the old hand-written path and the new
   generated path and diffing the result
3. `node quench-bench/deegen-curriculum/deegen-verify.mjs --from 1 --to 38`
   — no regression from the refactor
4. Code-size evidence (`tools/architecture-size-report.cjs`) shows no growth
   from the generated path duplicating rather than replacing the hand-written
   one — the hand-written per-region boilerplate must actually be deleted,
   not left alongside the generated version

**Fail condition**: generating wiring that coexists with, rather than
replaces, the hand-written per-region boilerplate defeats the purpose (two
sources of truth instead of one) — this is a hard requirement, not a nice-to-
have.

## Non-goals
- Generating handler semantic bodies — still correctly out of scope,
  permanently (see `docs/deegen-alignment.md` item 1)
- Widening region coverage — that's tasks 040/041's job; this task only
  changes how existing and future regions declare their admission wiring
