# 68: Audit the static facts available before execution

## Outcome

One report states, for every domain in the
[static-facts catalogue](README.md#static-facts-before-execution), how many
sites in real residuals could consume a static fact and how many dynamic
checks, allocations, or dispatches that fact would discharge. Consumer tasks
70–76 start in the order of these counts, and a domain with no opportunity is
closed with a recorded negative result.

## Current gap

`compile/capture_profile.rs` and `compile/register_profile.rs` already
report capture and register facts for one program. No report covers the
other catalogue domains, and nothing joins static opportunity with execution
frequency. Task 57's step 1 plans an audit for value kinds only. A separate
audit per consumer task would repeat the same residual walk several times.

## Dependencies

See this task's `depends_on` in [index.json](index.json). This task is
measurement only, like task 62, so it may run in any phase. It changes no
residual and admits no consumer.

## Scope and implementation sequence

1. Add one report pass next to the existing profile reports. It has one
   counter row per catalogue domain, and the rows come from the catalogue.
   `capture_profile` and `register_profile` become rows of this report
   rather than separate passes.
2. Count static opportunities per domain with the analyses that exist when
   the audit runs. Where a domain's analysis does not exist yet, count its
   syntactic candidates (for example, object literals with only static keys,
   calls whose callee binding has a single assignment, RegExp literal sites,
   `try` bodies containing only pure opcodes) and label the count as an
   upper bound.
3. Run the report over the pinned Test262 inventory, the frozen Node set, and
   the eight V8-v7 fixtures. Store the raw output under `target/` with
   provenance.
4. Once task 25's instrumentation exists, weight each static site by its
   execution count, and rank the domains by discharged dynamic work per
   fixture.
5. Record the ranking in this file, and update each consumer task's
   "Current gap" with its row.

## Verification

- The pass is off in production builds, and production binaries are identical
  with and without the report feature.
- Negative control: a fixture written to contain a known number of candidates
  per domain reports exactly those numbers.
- The report never reads fixture names, source paths, or benchmark vocabulary.

## Definition of done

- Every catalogue row has static and, where available, weighted counts on all
  three suites and the V8-v7 fixtures.
- The existing capture and register reports are rows of this report, not
  separate passes.
- Consumer task order in `index.json` follows the recorded ranking.
