# 68: Audit the static facts available before execution

## Plan scope

Stage B candidate after task 86 verifies Stage A. Select this work only for a
measured V8-v7 Score or RSS gap; finishing it is not a stage-completion gate.
Use affected-stage checks plus compare-runs during changes. The current
dependencies in [index.json](index.json) supersede older prerequisite claims.

## Outcome

For a domain selected by a measured Stage B gap, one report states how many
sites in real residuals could consume its static facts and how many dynamic
checks, allocations, or dispatches those facts could discharge. Consumer work
is selected by measured cost; unselected catalogue domains need no census.

## Current gap

`compile/capture_profile.rs` and `compile/register_profile.rs` already
report capture and register facts for one program. No report covers the
other catalogue domains, and nothing joins static opportunity with execution
frequency. Task 57's step 1 plans an audit for value kinds only. A separate
audit per consumer task would repeat the same residual walk several times.

The optional `profile-aggregate,profile-memory` library run exposed 57 failures
in dispatch-accounting reports for multi-program/eval paths
([evidence](evidence/task37-wasm-tables.json)). `Profile.site_counts` stores
function/PC counts without a program identity, while the reporter derives its
opcode matrix from one residual program. Before using those counters for a
selected experiment, preserve each program's identity and derive matching
physical/semantic totals; do not suppress the consistency assertions or treat
the failed reports as measurements. This is an instrumentation gap, not an
additional Stage A architecture gate.

## Dependencies

See `depends_on` in [index.json](index.json). This is Stage B diagnostic
work. A bounded correctness census may run earlier to illuminate an affected
path; no performance campaign or catalogue completion blocks Stage A.

## Scope and implementation sequence

1. Add one report pass next to the existing profile reports for selected
   catalogue domains. Its rows come from the catalogue. Reuse existing
   `capture_profile` and `register_profile` rows when selected rather than
   walking the same residual twice.
2. Count static opportunities for each selected domain with the analyses that
   exist when the audit runs. Where a domain's analysis does not exist yet,
   count its syntactic candidates (for example, object literals with only
   static keys, calls whose callee binding has a single assignment, RegExp
   literal sites, or `try` bodies containing only pure opcodes) and label the
   count as an upper bound.
3. Census only the selected domains on the measured V8-v7 paths. Use bounded
   scopes to check classification and store raw counts under `target/` with
   provenance. Reuse task 77's matching attribution rows when available; do not
   require all-domain or all-engine attribution.
4. Rank selected opportunities by discharged work per measured fixture.
   Record the decision here and update only the selected consumer task.

## Verification

- The pass is off in production builds, and production binaries are identical
  with and without the report feature.
- Negative control: a fixture written to contain a known number of candidates
  per domain reports exactly those numbers.
- The report never reads fixture names, source paths, or benchmark vocabulary.

- The existing capture and register reports are rows of this report, not

- Share matching raw rows with task 77 when attribution exists; derive only the
  static-opportunity projection owned by this task.
- Consumer task order in `index.json` follows the recorded ranking.
