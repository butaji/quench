# 046: String concatenation representation (rope/cons-string)

- **Theme:** deegen_full_jit
- **Executor:** codex
- **Depends on:** none (independent of the stencil-tier tasks)

## Context

Task 041 flagged this explicitly and correctly declined to attempt it as
part of its stencil survey: curriculum case 032 (string/regex processing)
is a persistent measured wall-time outlier (27.41x vs. Node in the latest
38-case sweep) — per `docs/deegen-stencil-coverage.md`'s task-041 findings,
"this is a rope/cons-string representation issue, not stencil admission."

External research check (2026-09): eager string concatenation is O(n) per
op, O(n²) over a loop — the standard production fix (V8, and most mature
engines) is a rope/cons-string representation: concatenation creates a
lazy node referencing both operands rather than copying bytes immediately,
flattened only when the string is actually read character-by-character or
passed somewhere requiring a flat buffer. This is a representation change
to `value.rs`'s string type, not a dispatch/stencil-tier change — hence its
own task, independent of the `deegen_full_jit` theme's stencil work,
scoped separately per task 041's own recommendation.

## Scope
- crates/quench-runtime/src/value.rs (string representation)
- Any string-consuming site that currently assumes a flat contiguous buffer
  (concatenation, indexing, iteration, regex, `String.prototype` methods)

## Deliverables
- Profile first: confirm concatenation (not regex, not iteration) is the
  actual dominant cost in case 032 and similar string-heavy workloads —
  isolate with a concatenation-only microbenchmark before attempting a
  representation change
- If justified: a lazy rope/cons-string node (two child references + cached
  length) alongside the existing flat string representation, with explicit,
  bounded flattening triggers (character access, `charCodeAt`, regex match,
  anything requiring contiguous bytes) — never an unbounded rope depth;
  document the flattening/rebalancing bound
- Every existing string-consuming call site either handles the rope
  transparently (flattens on demand) or is updated to do so — no silent
  wrong-length/wrong-content result from a site that assumes flat storage

## Validation

1. Differential tests: every existing string test passes unchanged,
   including Unicode/surrogate-pair edge cases, `String.prototype.slice`/
   `charAt`/iteration boundaries, and empty-string/single-char concatenation
2. A test proving deep repeated concatenation (the exact curriculum case 032
   shape) no longer costs O(n²) — measure operation count or timing scaling
   across increasing concatenation counts, not just a single before/after
   number
3. `cargo test -p quench-runtime --lib` and `--features execution-trace` —
   both pass
4. Before/after measurement on curriculum case 032 specifically, and the
   full 38-case sweep to confirm no regression elsewhere (rope overhead on
   short/one-shot strings must not make simple cases slower)
5. RSS measurement — a rope adds per-concatenation node overhead; confirm
   the memory tradeoff is net-positive for realistic concatenation patterns
   (many small appends), not just synthetic worst-case loops

**Fail condition**: any change to observable string semantics (length,
content, encoding, comparison, or iteration order) is a correctness bug —
this is a representation change under the same observable string, never a
semantic one. An unbounded rope depth causing pathological flatten cost on
read is also a fail — bound it.

## Non-goals
- Changing string encoding (UTF-8/UTF-16/WTF-8, whatever quench currently
  uses) — this task only changes how *concatenation* is represented, not
  the underlying byte encoding
