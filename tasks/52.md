# 52: Declare opcode operand layouts and derive every decoder

## Outcome

Each opcode row declares what its `a`, `b`, `c`, and `imm` operands mean. The
encoder, residual validator, liveness, rewrite legality, disassembler, and
interpreter accessors are generated from that row. A decoder that disagrees
with the encoder can no longer be written.

## Current gap

`opcodes!` (`bytecode.rs`) declares only an opcode's name and effect. The
meaning of each operand is decoded again by hand in `bytecode/validate.rs`,
`compile/liveness.rs` (77 opcode arms), `compile/rewrite.rs`,
`bytecode/disassemble.rs`, and `vm/dispatch.rs`. The same bitfield expression
`(imm & 0x3fff_ffff) >> 16` appears in five places across four files, and the
flag bits (`SUPER_CONSTRUCT_BIT`, `SUPER_CONSTRUCT_ARRAY_BIT`, the eval bits of
`Call`) are known only to the sites that test them.

These copies have drifted. On 2026-09-23 the residual validator rejects
programs that the compiler emits and the interpreter would run:

- `validate.rs` checks `Op::Call | Op::CallKnown` in one arm and requires
  `register(b)`. For `CallKnown`, `b` is a function index, not a register.
  Any known call whose target index is at least the caller's register count
  fails with `function N call is invalid`. Twenty top-level functions and a
  call to the last from inside another function reproduce it. This error
  stops Richards, DeltaBlue, and Splay
  (`target/reviews/core-review-2026-09-23/README.md`).
- `validate.rs` limits `CallKnown` to 8 arguments (`call has too many
arguments`). The compiler does not honor that limit.
- `function N construct is invalid` accounts for 3,195 failing Test262 files
  in `target/test262-next-task08-parallel.json` (for example
  `built-ins/Array/S15.4.2.1_A2.2_T1.js`). Its root cause is not yet
  isolated; the standalone body passes, so the harness prefix changes the
  emitted `Construct` window.

## Scope and implementation sequence

1. Extend each `opcodes!` row with an operand layout. Operand roles are data:
   destination register (including the `RETURN_REGISTER`/`SET_THIS_REGISTER`
   bits), source register, tagged `Operand`, register window (base and count,
   with its bitfield), site-table index (field, method, object, name, closure,
   constant), function index, jump target, and named flag bits.
2. Generate typed accessors per role from the rows. Remove every hand-written
   bitfield decode from the compiler, rewrite engine, liveness, validator,
   disassembler, and interpreter.
3. Generate residual validation from the roles. Each role checks its own
   domain once: register bounds, window bounds, table lengths, function count,
   and code length. Keep only the cross-instruction invariants hand-written.
   Remove any limit (such as `CallKnown`'s 8 arguments) that the encoder does
   not also enforce from the same row.
4. Generate liveness uses and definitions and the disassembler text from the
   roles. `Wide` instructions and superinstruction rows decode through the
   same layouts.
5. Diagnose the `Construct` rejection from step 3's output, then remove the
   manual checks it replaces.

This is structural work that removes duplicate authorities. It is not tuning:
the `Instr` encoding, the opcode set, and the interpreter's hot paths stay as
they are.

## Definition of done

- Each opcode's operand meaning has one declaration.
- The encoder, validator, liveness, rewrite engine, disassembler, and
  interpreter read operands only through generated accessors.
- The validator accepts every program the compiler emits and rejects operands
  outside their declared domain.

## Implementation evidence

The opcode rows now declare the immediate layout for capture depth/slot pairs,
call argument windows (including direct-eval flag variants), constructor count
and flags, and register pairs. Named layout-owned masks and typed accessors are
shared by packed and wide instructions. The compiler, validator, liveness,
rewrite legality, and VM dispatch now consume those views rather than
re-decoding call windows, capture pairs, yield-star register pairs, or
constructor flags. `CallKnown` validation treats operand `b` as a function
index, validates its argument window, and no longer has an independent
eight-argument cap. `cargo check -p quench-runtime-next -p quench-test262`
passes. The ordered next-core Test262 prefix 0–2 passes 481/481 in batches no
larger than 100. Full opcode operand-role generation and the Construct failure
family diagnosis remain open; this is partial task evidence, not completion.
Operand tags are now represented by `OperandKind` and shared by residual
validation, liveness, VM resolution, and numeric dispatch rather than duplicated
tag-number branches. A fresh cumulative stages 0–9 rerun passed 1,157/1,157;
stage 10 remains at 10,891/11,101 with the same 210-case/190-family failure
aggregate (`target/test262-next-prefix-0-10-operand-kinds.log`).

Result-register flags now have an opcode-row-owned `ResultLayout`, covering
plain destinations, returnable results, `GetField`'s optional current-`this`
write, and numeric local targets. Packed and wide instruction views derive
result registers, return/`this`/local behavior, and flag validation from that
layout. Compiler rewriting, control-flow/liveness, profile dependencies,
numeric dispatch, ordinary dispatch, and validation consume these accessors.
Both Test262 runners build in the iteration profile. A fresh ordered 0–10 run
confirms stages 0–9 at 1,157/1,157 and stage 10 at 11,083/11,101 (18 failures
across 11 families), unchanged from the preceding Proxy-construction
checkpoint. Evidence: `target/test262-next-prefix-0-10-result-layout.log`;
all cases used the required 900,000 ms timeout and batches ≤100. This
structural slice adds no Test262 pass yet; remaining operand roles and the
Construct validator failure diagnosis are still open.

`CallKnown` now declares `a=ResultRegister`, `b=FunctionIndex`, and an unused
`c` in its opcode row; its validator and VM dispatch consume the generated
`known_function_index()` view instead of treating `b` as a register. `Construct`
declares its destination, constructor register, and tagged argument source,
and the shared decoder asserts that `c` has that role before deriving its
register window or argument-array operand. `cargo check -p quench-runtime-next
-p quench-test262` passes. The existing Test262 Array constructor fixture
`built-ins/Array/S15.4.2.1_A2.2_T1.js` passes through stage 31 with a positive
30,000 ms per-case timeout. This is a structural increment only: the remaining
opcode fields still lack row-owned roles, and task 52 remains in progress.
