# 52: Declare opcode operand layouts and derive every decoder

## Outcome

Each opcode row declares what its `a`, `b`, `c`, and `imm` operands mean. The
encoder, residual validator, liveness, rewrite legality, disassembler, and
interpreter accessors are generated from that row. A decoder that disagrees
with the encoder can no longer be written.

## Current gap

The row table now declares each opcode's three field roles, immediate role and
layout, result behavior, and control-flow layout. Packed and wide accessors,
validation, liveness, rewrite legality, disassembly, VM dispatch, and profile
dependency/region analysis consume those declarations. Semantic field/immediate
decoding is centralized in `bytecode`; remaining raw accesses in
`profile/instruction_words.rs` measure encoded word widths, and raw accesses in
compiler files are confined to existing test code.

The validator's field and immediate domain dispatch is exhaustive, so a new
role cannot silently inherit a wildcard accept. Compile-time row checks bind
numeric-local stores, constructor arguments, nested field lookup, and
wide-marker chunks to their required companion roles/layouts. The exact
historical Construct cohort has now been rerun: no case retains the old
`construct is invalid` / `call is invalid` failure family. The remaining
failures are semantic (primarily Intl/Temporal calendar handling), not
residual decoding. Latest full Stage 74 is 4,343/4,603 and ordered Stages 0–74
are 44,353/44,613; task 20 owns the still-incomplete Test262 ratchet. See the
completion evidence at the end of this file.

Historical diagnosis (2026-09-23): the residual validator once conflated
`CallKnown.b` with a register and imposed an independent eight-argument cap;
the table-driven validation now treats it as a function index and validates
its argument window. The representative old Array Construct case passes on
the current core; cohort results are recorded below.

## Scope and implementation sequence

1. Extend each `opcodes!` row with an operand layout. Operand roles are data:
   destination register (including the `RETURN_REGISTER`/`SET_THIS_REGISTER`
   bits), source register, tagged `Operand`, register window (base and count,
   with its bitfield), site-table index (field, method, object, name, closure,
   constant), function index, jump target, and named flag bits.
2. Generate typed accessors per role from the rows. Remove every hand-written
   bitfield decode from the compiler, rewrite engine, liveness, validator,
   disassembler, and interpreter.
3. Generate residual validation from the roles. Each role checks its own
   domain once: register bounds, window bounds, table lengths, function count,
   and code length. Keep only the cross-instruction invariants hand-written.
   Remove any limit (such as `CallKnown`'s 8 arguments) that the encoder does
   not also enforce from the same row.
4. Generate liveness uses and definitions and the disassembler text from the
   roles. `Wide` instructions and superinstruction rows decode through the
   same layouts.
5. Diagnose the `Construct` rejection from step 3's output, then remove the
   manual checks it replaces.

This is structural work that removes duplicate authorities. It is not tuning:
the `Instr` encoding, the opcode set, and the interpreter's hot paths stay as
they are.

## Definition of done

- Each opcode's operand meaning has one declaration.
- The encoder, validator, liveness, rewrite engine, disassembler, and
  interpreter read operands only through generated accessors.
- The validator accepts every program the compiler emits and rejects operands
  outside their declared domain.
