# 061: Investigate catastrophic DeltaBlue/Richards slowdown (v8-v7 suite)

- **Theme:** vm_completeness
- **Executor:** codex
- **Depends on:** 050
- **Priority: P0/P1, ahead of 053-060.** Found running the real v8-v7 suite
  after the 050 console fix landed: this is either a real correctness bug
  or a severe performance pathology, not a tuning question. Tuning survey
  work (053-060) is premature until this is understood.

## Context

Running `quench-bench/dist/run.js` (the bundled v8-v7 harness) against a
fresh build: `Richards: 4.65` (Node: 65182 — ~14,000x slower) then the
process makes no further progress — `DeltaBlue` alone, isolated
(`base.js` + `deltablue.js` + `BenchmarkSuite.RunSuites`), does not
complete in 30 seconds (Node: ~2 seconds, score 183815).

A `sample`-based profile during the hang shows execution spread across
ordinary paths — `finish_set_property`, `inherited_write_blocked`,
`get_property_with_receiver`, `set_with_receiver`, `construct_function`,
`intrinsic_overrides::read`, `resolve_global_owner` — not concentrated in
one function at a level that would indicate a tight infinite loop. This
looks like severe, broadly-distributed slowness in the property/construct/
method-dispatch path specifically, not a hang in one specific broken
opcode.

DeltaBlue creates many distinct constraint object shapes (`BinaryConstraint`,
`UnaryConstraint`, `StayConstraint`, `EqualityConstraint`,
`ScaleConstraint`, `OrderedCollection`, `Strength`, ...) accessed
polymorphically through a shared constraint-graph traversal — exactly the
megamorphic/shape-thrashing shape flagged as a structural risk earlier this
session. Richards' 14,000x (not infinite, but severe) slowdown on a
simpler, less polymorphic workload suggests the problem may be broader than
DeltaBlue specifically — possibly something recently changed in the
property/shape/construct path (tasks 040/044 landed Call/property/array
region bridges and generated admission wiring around when this would have
last been exercised, though v8-v7 itself was never actually run before the
050 fix, so this may be a pre-existing issue only now visible, not a
regression from that work — determine which).

## Scope
- Investigation first — do not guess the subsystem
- Likely: crates/quench-runtime/src/properties.rs, shape_cache.rs,
  construct.rs, methods.rs (per the profile's hot functions above)

## Deliverables
- Isolate a minimal reproduction smaller than full DeltaBlue: construct a
  synthetic workload creating many distinct object shapes (5-10 constructor
  functions, each instantiated many times) accessed through a shared
  polymorphic dispatch pattern (a loop calling a method that exists on all
  of them). Confirm whether this alone reproduces severe slowdown, isolated
  from DeltaBlue's full complexity.
- Determine: is this a genuine correctness bug (an accidental quadratic-or-
  worse algorithm somewhere in property/shape/construct handling — the
  exact class of bug already found and fixed twice this session, quadratic
  property writes and quadratic for-in scans), or a "working as designed
  but catastrophically slow" megamorphic dispatch cost?
- If quadratic-or-worse: this is the same bug class as the earlier for-in/
  property-write fixes — find and fix the root cause, add a regression test
  the same way those fixes did
- If genuinely megamorphic-dispatch-cost (not a bug, just slow): quantify
  exactly where the cost concentrates (shape lookup? property resolution?
  construct-time initialization? something else?) so tasks 040/041's
  existing coverage work — or a new, evidence-backed task — can target it
  specifically, rather than treating "DeltaBlue is slow" as an
  unaddressable fact

## Validation

1. A minimal reproduction case added as a regression test/benchmark,
   whatever the root cause turns out to be
2. If a bug: a differential test proving the fix, plus confirmation
   Richards' score and DeltaBlue's completion time both improve
   substantially (not just DeltaBlue — Richards' 14,000x gap suggests a
   shared root cause worth checking against both)
3. `cargo test -p quench-runtime --lib` and `--features execution-trace` —
   both pass
4. Full v8-v7 suite: DeltaBlue completes within a reasonable multiple of
   Node's time (this session's other benchmarks have run 1.2x-50x Node,
   not "doesn't finish in 30s, then 2 minutes") — record the actual number,
   don't just confirm it terminates
5. Re-run the full 38-case curriculum (`deegen-verify.mjs`) to confirm no
   regression from whatever fix is applied

**Fail condition**: reporting "DeltaBlue is just a slow benchmark, nothing
to fix" without the minimal-reproduction investigation above is not
acceptable — a 14,000x-plus gap (Richards) and a 15x-timeout gap
(DeltaBlue) are not normal variance, they are signals of a specific,
findable cause.
