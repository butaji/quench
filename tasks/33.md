# 33: Generalize opcode superinstruction fusion

## Outcome

Replace the single hand-written fusion in `superinstruction.rs` with a
macro-declared pattern table so new fused opcode sequences are added as data,
not as bespoke `execute_*` functions.

## Current gap

`superinstruction.rs` fuses exactly one four-opcode sequence
(`MakeConstArray` + `Binary` + `Binary` + `MakeObject2`) via a single
hand-written method. There is no general mechanism for discovering or
registering additional fusable sequences, so each new pattern would currently
require another bespoke function duplicating the same dispatch shape.

## Dependencies

See this task's `depends_on` in [index.json](index.json).

## Scope and implementation sequence

1. Profile representative corpora (existing benchmark suite plus a broader
   sample of supported syntax from task 10's test families) for frequently
   adjacent opcode sequences beyond the one already fused: candidates include
   property-chain load sequences, `for-of` step-plus-destructure, and
   template-literal concatenation chains.
2. Define fused sequences via the repository's existing macro-declared opcode
   vocabulary (per AGENTS.md: "Use Rust for implementation and Rust macros for
   code generation") so a new pattern is a table entry with its constituent
   opcodes and an execution closure, not a new hand-rolled function per
   pattern.
3. Keep semantics execution unified: a superinstruction may only fuse dispatch
   of an already-verified opcode sequence; it must not introduce behavior the
   unfused sequence would not produce, per task 10's residual-verification
   requirement.
4. Preserve the existing pattern (`superinstructions[site].code`) as the shared
   representation the table generates against, rather than introducing a second
   encoding for fused sequences.

## Verification

Differential tests against Node/Test262 for each newly fused sequence, plus a
control disabling fusion entirely and confirming byte-identical observable
behavior against the fused build (values, ordering, errors, exit status).

## Definition of done

- Adding a new fused sequence requires only a table entry, not a new dispatch
  function shape.
- Every fused sequence has a disable-fusion control proving behavioral
  equivalence to the unfused execution.
- No fusion selection depends on fixture identity or benchmark vocabulary.

## Performance evidence

Report per-pattern fusion frequency and dispatch-time delta on the existing
four-benchmark suite plus any corpus used for pattern discovery.
