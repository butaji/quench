# 33: Generalize opcode superinstruction fusion

## Outcome

Replace the single hand-written fusion in `superinstruction.rs` with a
macro-declared pattern table so new fused opcode sequences are added as data,
not as bespoke `execute_*` functions.

## Current gap

`superinstruction.rs` fuses exactly one four-opcode sequence
(`MakeConstArray` + `Binary` + `Binary` + `MakeObject2`) via a single
hand-written method, produced by a single hand-written `fuse_const_array_object2`
in `compile/rewrite.rs`'s `rewrite_super_window` loop. There is no general
mechanism for discovering or registering additional fusable sequences, so each
new pattern would currently require another bespoke function duplicating the
same dispatch shape.

`compile/rewrite.rs` already solves this exact problem one tier down: its
`fusion_recipes!` macro builds a table (`RULES: &[Rule]`, each a
`[Op; 2]` pattern plus a recipe closure) that fuses any adjacent
2-opcode sequence into one instruction — `ConstantLeft`, `ConstantRight`,
`StoreLoadLocal`, `ProducerMove`, `BinaryJumpFalse`, `ReturnResult`, and more,
all declared as data. That table is fixed at a 2-instruction window and
produces a single `Instr`, which is why the wider, multi-register
`Superinstruction` case (four instructions, stored in a side table because it
doesn't collapse into one instruction's operand slots) couldn't reuse it and
was hand-rolled instead. The fix is not a new macro system — it is extending
`fusion_recipes!` (or a sibling table with the same shape) to variable-width
windows that may emit a `Superinstruction` side-table entry instead of a
single `Instr`, so `fuse_const_array_object2` becomes one more table row.

## Scope and implementation sequence

1. Profile representative corpora (existing benchmark suite plus a broader
   sample of supported syntax from task 10's test families) for frequently
   adjacent opcode sequences beyond the one already fused: candidates include
   property-chain load sequences, `for-of` step-plus-destructure, and
   template-literal concatenation chains.
2. Extend `compile/rewrite.rs`'s existing `fusion_recipes!` table mechanism
   (per AGENTS.md: "Use Rust for implementation and Rust macros for code
   generation") to variable-width opcode windows and side-table
   (`Superinstruction`) output, rather than introducing a second, parallel
   table-driven mechanism alongside it. A new pattern becomes one table row
   with its constituent opcodes and a recipe closure, whether it collapses
   into a single `Instr` or a wider `Superinstruction` entry.
3. Keep semantics execution unified: a superinstruction may only fuse dispatch
   of an already-verified opcode sequence; it must not introduce behavior the
   unfused sequence would not produce, per task 10's residual-verification
   requirement.
4. Preserve the existing pattern (`superinstructions[site].code`) as the shared
   representation the table generates against, rather than introducing a second
   encoding for fused sequences.

## Verification

Differential tests against Node/Test262 for each newly fused sequence, plus a
control disabling fusion entirely and confirming byte-identical observable
behavior against the fused build (values, ordering, errors, exit status).

## Definition of done

- Adding a new fused sequence requires only a table entry, not a new dispatch
  function shape.
- Every fused sequence has a disable-fusion control proving behavioral
  equivalence to the unfused execution.
- No fusion selection depends on fixture identity or benchmark vocabulary.

## Performance evidence

Report per-pattern fusion frequency and dispatch-time delta on the existing
four-benchmark suite plus any corpus used for pattern discovery.

## Implementation evidence

`compile/rewrite.rs` now declares superinstruction patterns as data in a
variable-width `SUPER_RULES` table. The rewrite loop derives each window's
width, protected-boundary checks, relocation mapping, and handler dispatch from
that row; the existing four-opcode constant-array/object fusion is the first
entry and retains its exact semantic guard and execution path.
