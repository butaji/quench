# 058: Global shape hash-consing (structural deduplication)

- **Theme:** vm_completeness
- **Executor:** codex
- **Depends on:** none

## Context

Read directly from the local `../quickjs` checkout (`quickjs.c`):
`JSShape` isn't allocated fresh per object-per-transition — QuickJS
maintains a runtime-wide `rt->shape_hash` table (`resize_shape_hash`,
`find_hashed_shape`, `quickjs.c:5137-5210`) that deduplicates *structurally
identical* shapes: two unrelated objects that ended up with the same
property-add history share the exact same `JSShape` instance. This cuts
memory for any program that creates many same-shaped objects — exactly the
pattern of a web backend handling many structurally-identical request/
response/DTO objects over a long-running process, where shape count would
otherwise grow without bound as new instances are created (even though
their *shapes* are repeats).

## Scope
- crates/quench-runtime/src/shape_cache.rs (or wherever quench's current
  shape system lives — confirm exact location first, don't assume)

## Deliverables
- Audit first: does quench's current shape system already do structural
  deduplication (a global table keyed by structural shape identity), or
  does it allocate a new shape object per transition even when an
  identical one exists elsewhere? Check before assuming either way.
- If not deduplicated: add a runtime-wide hash table keyed by the shape's
  structural identity (property sequence + attributes + prototype, same
  key shape QuickJS uses), consulted on every shape transition — reuse the
  existing shape if a structural match exists, allocate only on genuine
  novelty
- Preserve existing shape-identity-based fast-path guards exactly (if any
  code currently compares shapes by pointer identity for IC purposes, that
  invariant must hold *more* strongly after dedup, never less — two
  objects with the same structure must now compare equal by pointer, which
  can only help existing monomorphic/polymorphic IC hit rates, never hurt
  them)

## Validation

1. Differential tests: object creation, property add/delete, prototype
   changes all produce identical observable behavior before/after
2. A specific test proving dedup actually happens: create two structurally
   identical objects via different code paths, confirm they share one
   shape instance (not just equal-by-value)
3. `cargo test -p quench-runtime --lib` — all pass
4. Memory measurement: a synthetic workload creating many same-shaped
   objects (simulating repeated request/response object creation) shows
   reduced shape-table memory growth after this change
5. Full neutral corpus + curriculum + v8-v7 (task 052) — no regression;
   this should be neutral-to-positive on wall time (existing ICs benefit
   from more shapes comparing pointer-equal) and positive on RSS for
   many-same-shaped-object workloads

**Fail condition**: any change to property enumeration order, descriptor
semantics, or shape-transition observable behavior — this is a physical
deduplication of an internal representation, never a semantic change.

## Non-goals
- Changing the shape transition algorithm itself (what counts as a
  transition, when a new shape is created at all) — only whether
  structurally-identical *results* of transitions get deduplicated
