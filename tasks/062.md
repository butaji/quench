# 062: Architecture invariant test suite (algorithmic-complexity regression tests)

- **Theme:** vm_completeness
- **Executor:** codex
- **Depends on:** none
- **Priority: do invariant #1 first, immediately — it's the fastest path to
  diagnosing task 061's DeltaBlue hang, not just a nice-to-have suite.**

## Context

This backlog has repeatedly found architecture-vs-implementation gaps only
after they showed up as a confusing benchmark symptom (the for-in quadratic
scan, the property-write quadratic bug, and now task 061's DeltaBlue hang —
all discovered live, none caught by an existing test). This task adds a
permanent, standing test module that pins down the VM's foundational
*complexity claims* directly, independent of absolute wall-clock speed —
so future regressions of this exact class are caught by `cargo test`, not
by a live benchmark hang.

The technique: don't assert a wall-clock threshold (noisy, hardware-
dependent). Assert **scaling behavior** — does the cost of one operation
stay flat as some dimension of the program grows, the way the architecture
claims it should. Use either (a) the `execution-trace` feature's existing
deterministic counters (dispatch/retired-instruction counts) as the metric,
which is unaffected by machine noise, or (b) a wall-clock **ratio** bound
(`time(N=large) / time(N=small) < K`) tolerant of noise but still catches
an O(n²)-or-worse blowup, which produces a wildly nonlinear ratio even
under noise. Prefer (a) where the existing counters support it; fall back
to (b) where they don't.

## Scope
- New: `crates/quench-runtime/src/architecture_invariants.rs` (or similar —
  a dedicated test module, not scattered into existing per-feature test
  files, so this suite's purpose stays visible as one thing)

## Deliverables — implement invariant 1 first, standalone, before the rest

1. **Property access cost is independent of the number of distinct shapes
   that have ever existed in the runtime.** Create K distinct object
   shapes (e.g. K=10 vs. K=1000 constructor functions, one instance each,
   each with a distinct property set), read one property from each,
   compare per-access cost between the K=10 and K=1000 runs. **Do this one
   first and report the result immediately** — it's the direct test for
   task 061's suspected megamorphic-shape-thrashing bug; if it fails, it
   hands task 061 the exact minimal repro it's currently hunting for by
   profiling a 30-second hang.
2. Shape-transition cost is independent of current property count (add the
   Nth property; cost shouldn't grow with N).
3. Call-dispatch cost is independent of the number of distinct callees ever
   observed (same shape as #1, for functions).
4. Enumeration (`for-in`) cost is independent of an object's mutation
   history, not just its current property count — makes the earlier
   quadratic-scan fix this session a permanent regression test instead of
   a one-off.
5. Dispatch overhead per bytecode is independent of total catalog size or
   program length.

For each: state the claimed complexity class in a doc comment, the metric
used (counter-based or ratio-based) and why, and the actual pass/fail
bound — this is a test suite whose value is in stating loud, checkable
performance-invariant claims, not just green checkmarks.

## Validation

1. Invariant #1 lands and reports its result (pass or a concrete measured
   failure) before anything else in this task proceeds — this directly
   feeds task 061
2. `cargo test -p quench-runtime --lib` and `--features execution-trace` —
   the whole new suite passes (or, if any invariant genuinely fails,
   that's a real finding to report to task 061/the relevant subsystem, not
   something to weaken the test to pass)
3. Each test's bound is tight enough to actually catch a real O(n)-vs-O(1)
   or O(n²)-vs-O(n) class regression, not so loose it would pass even with
   a real complexity bug present — sanity-check by temporarily introducing
   a deliberate O(n) regression in one subsystem and confirming the
   relevant test catches it, then revert

**Fail condition**: a test bound loose enough to pass regardless of the
actual complexity class defeats the entire purpose of this task — validate
each test actually fails against a deliberately-broken version before
trusting it passes against the real implementation.

## Non-goals
- Wall-clock performance benchmarking (that's `quench-bench/`'s job) — this
  suite only asserts scaling *shape*, never absolute speed
