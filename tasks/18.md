## Residual ownership for dynamic code

v2 executes one immutable residual. `eval`, `Function`, and dynamic `import`
compile new code during execution, so the residual store becomes append-only:
new function bodies receive fresh IDs and site ranges, and no existing body,
handler table, root map, or cache site is replaced in place. If a body must
ever be replaced, use v2's recorded versioned protocol (frames pin
`(function, version)` at entry; old versions live until their last frame
returns), as in [runtime re-specialization](../docs/v2/runtime-respecialization.md).

The next core currently passes one borrowed `ResidualProgram` through dispatch,
stores constants and closure identity in VM-global vectors, and identifies user
functions only by a program-local function index. Dynamic module execution
therefore needs an explicit program owner on closures and activations, plus
program-owned constant/cache tables; it must not reset or clone the heap/realm
to run a second VM. All program owners still dispatch through the same kernel
and interpreter. Static module metadata and runtime bindings should be views of
one module record, with the same OXC compiler and residual verifier used at
both initial and dynamic binding times. This follows the Ershov rule: no
second module evaluator or independent export-value simulator.

Stage-10 evidence makes this ownership boundary shared work rather than a
module-only concern: 45 dynamic-import cases require evaluated module bodies,
and the five-case `value is not a constructor` family includes tests that
construct classes through `realm.global.Function`. The old core's
`functions_dynamic.rs` uses OXC to
parse Function source and executes the result under an explicit realm; port
that pipeline to the next compiler/store boundary. Do not alias the main
`Function` intrinsic into new realms or extend `eval_source_simple` with a
class-source recognizer: both would preserve the missing program/realm
ownership semantics.

The compiler now accepts an existing atom prefix for unspecialized Script
and Module residuals and exposes `specialize_dynamic_function` for already
coerced Function parameter/body strings. These produce ordinary residuals
with canonical atom indices, but the VM does not yet own or execute
multiple program contexts; no Test262 pass increase is attributed to these
entry points. Next, use them from one append-only program store whose closures
and frames carry `ProgramId`, then implement realm-local Function intrinsics
and live module bindings on that same store.

The VM now has the first ownership slice: residuals are held immutably in a
`ProgramStore`; `FunctionKind`, closure identity keys, frames, and suspended
continuations carry `ProgramId`; and call/construct dispatch resolves the
program owner instead of assuming a function index is globally unique. Program
ID exhaustion returns no ID rather than panicking. This remains groundwork:
initialization currently installs only the main program, while constants,
site caches, module linking/evaluation, and dynamic Function execution are not
yet switched to program-owned contexts. It does not close dynamic import or
claim a conformance gain. The stage-10 dynamic-import sweep is still led by the
45-case evaluated-module family.
After this compiler change, the existing four-case stage-10
`class-name-ident-await` module-goal cohort passes 4/4; the complete stage-10
baseline remains 10,731/11,101, and no increase is claimed from the new
dynamic-compilation entry points.

The realm factory now exposes a realm-owned `Function` native and its
`Function("return this")` path retains that realm's global; dynamic class-base
lookup also consults that global. This fixes missing intrinsic ownership, but
not execution of returned dynamic bodies: `eval_source_simple` is still on
that path and must be replaced by execution from the append-only ProgramStore.
The 38-case private-class stage-10 subtree remains 0/38, with dynamic class
source unresolved; no conformance gain is attributed to the intrinsic change.

Static module import phases are now retained on both requests and local import
bindings. The VM supports `import defer * as ns`: it prepares a deferred
namespace without evaluating synchronous modules, preserves a distinct cached
deferred namespace alongside the eager module outcome, triggers deferred
evaluation on namespace access, and retains an already-observed module failure
for later deferred access. Deferred requests also evaluate transitive
top-level-await dependencies. Import attributes retain module type through
request deduplication, binary serialization, module caching, and static
resolution. JSON and text modules use the existing parser/namespace authority;
JSON numeric fractions/exponents consume all digits, malformed JSON throws a
SyntaxError, and JSON imports reject named bindings. Bytes modules preserve raw
host bytes and produce a Uint8Array over an immutable ArrayBuffer. The ordered
Test262 stage 16 (`language/import`) passes 127/127, and cumulative stages 0–16
pass 12,981/12,981. Async continuations now resume under their originating
program identity; deferred static modules wait for async dependencies, and
their deferred namespaces stay unmaterialized until evaluation settles. This
is a verified checkpoint, not task completion.

The ordered Test262 prefix now passes through stage 18: cumulative stages 0–18
pass 13,047/13,047, including `language/line-terminators` at 41/41. Global
direct Eval falls back to OXC Script compilation when the existing evaluator
reports its dynamic-expression parser diagnostic; single-expression completion
and caller-aware declaration semantics remain on their established paths. This
is an ordered conformance checkpoint only; dynamic Function/module/realm work
and later Test262 stages remain open.

### 2026-09-24 module-linking and source-phase checkpoint

The static linker carries active module export bindings through cycles.
Root-module export names and links are retained in residual metadata and
serialized; root and dependency modules share the linker, including exports of
imported bindings and identity-preserving namespace exports through stars. A
new per-export resolver tracks `(normalized module path, exportName)` with a
branch-local resolve set, follows named and star reexports, and detects
same-binding versus ambiguous star results. It closes
`instn-named-star-cycle.js`, `instn-iee-star-cycle.js`, and the unresolved-star
negative case on static graphs without local import bindings. Other graphs
retain the earlier linker until next-core local import cells are available to
this path. Module request metadata is retained independently of whether
the static linker can produce a link plan. Source-phase imports now bind to a
canonical `AbstractModuleSource` object cached by normalized module identity;
named/default source bindings and namespace reexports share that identity. The
pending root namespace,
including its valid empty-export case,
is available to dependencies during linking. Root self-imports use
main-program binding slots and cached
namespaces preserve binding metadata. The latest existing Test262 stage-20
module-code sweep passes 582/599; focused namespace internals pass 36/36,
namespace-unambiguity 3/3, ambiguous-export errors 4/4, default-class
self-import 5/5, cyclic star reexport 1/1, instantiation-binding initialization
6/6, and import attributes 13/13. The instantiation cohort is now 76/76;
the ambiguous-export cohort remains 9/10. The remaining 17 failures span 8
families, principally unresolved module imports and top-level-await scheduling.
The focused source-phase cohort passes 4/4. A follow-up TLA import-binding
slice resolves requests and drains completed jobs before reading the entry
module's imports, then refreshes retained namespace slots from the completed
module environment. This closes the three pending async import-resolution
cases and the rejection-type case; the latest stage-20 sweep is 587/599, with
12 failures across 6 families. This is not general live-binding support and
does not complete task 18: dynamic program ownership, general
instantiation/live bindings, async lifecycle, and realms remain open. The
Test262 harness was not changed; no new tests or unit tests were run.

The 2026-09-24 async-module follow-up routes dynamic JavaScript imports through

### 2026-09-24 module entry and import binding correction

The earlier 592/599 checkpoint overstated correctness: synchronous module
completion could hide a rejected root evaluation. Root modules now use async
function completion only when the OXC AST contains top-level `await`, so
synchronous abrupt completion propagates. Static named imports retain an
export `(ProgramId, slot)` target and load the live binding on each read; value
imports remain direct values. The two existing default-function self-import
fixtures pass 2/2. Direct namespace/value imports are initialized in the root
activation before its environment is promoted, while named-import reads keep
their exporter-slot lookup. The current complete stage-20 sweep is 573/599 (26
failures across 13 families), so the old 592 result is superseded and stage 20
remains the active gate. Namespace TDZ behavior and async cycle ordering
remain open.
The harness is untouched; no tests were added and no unit/project tests were
run. The runner used `TEST262_TEST_TIMEOUT_MS=900000` and six deterministic
batches capped at 100 cases each.

The follow-up linker path now establishes a named import from the namespace's
binding identity plus a non-observable fallback property value. It does not
invoke guest `[[Get]]` while linking. Captured reads now recover the owning
environment's `ProgramId` and route root import slots through that same live
binding authority; the existing `instn-iee-bndng` cohort passes 6/6. The latest
ordered stage-20 sweep is 579/599 (20 failures across 13 families), up from
573/599. The harness remains untouched and no tests or unit/project tests were
added or run.
