# 78: Build the dispatch engine from verified, threaded handlers

## Outcome

Each residual operation costs one indirect branch plus its own work. The
program counter, register base, and hot interpreter state stay in machine
registers across handlers. Handlers read operands without bounds checks,
because the residual validator has proved them. The layout is chosen by a
measured matrix, not by folklore, and it runs without executable memory.

## Current gap

Dispatch is one `match` per instruction that returns `Result<StepResult>`
and re-indexes the function, code, and frame at each step (the 2026-09-23
review). v2 kept its program counter and frame bases in native locals (v2
tasks 308, 317, 383), carried an accumulator (v2 327), tested handler-table
dispatch (v2 12, 220), and proposed guaranteed tail calls (v2 241) and
register-resident bases (v2 257). The CPython 3.14 tail-calling interpreter and
wasm3 show that threaded handlers with the interpreter state passed in
argument registers beat a central loop on modern compilers. Rohou et al.
("Branch prediction and the performance of interpreters: don't trust
folklore", 2015) show that the indirect-branch argument alone no longer
decides the question on modern predictors, so the choice must be measured.

## Scope and implementation sequence

1. Declare the interpreter state that every handler needs (pc, register
   base, constant base, accumulator, VM pointer) as one record. Its fields
   map to handler arguments, so the calling convention keeps them in
   registers.
2. Build three dispatch layouts from the same macro-generated handler bodies
   (v2 task 200 already generates shared semantics for two layouts):
   - the current central `match` loop, as the control;
   - tail-call threading, where each handler ends by calling the next one
     through a handler table, using guaranteed tail calls (`become`,
     `explicit_tail_calls`) and the `preserve_none`-style convention where
     rustc exposes it;
   - direct threading, where the residual loader rewrites each opcode into a
     handler address plus operands (wasm3's design, with no executable
     memory).
3. Remove checks the validator has proved: register and local indices are
   within the frame, constant indices are within the pool, and jump targets
   are instruction boundaries. Handlers use unchecked access behind a single
   validated-residual type, so an unvalidated residual cannot reach them.
4. Signal errors, exceptions, and interrupts through a state field that the
   next dispatch checks on the cold path. The hot path then carries no
   `Result`.
5. Evaluate decoding the next operation ahead (LuaJIT), in-place quickening
   versus the v2 sidecar decision (v2 tasks 78, 258), and operand-encoding
   density (v2 tasks 49, 50, 52, 333, 375) on the chosen layout.
6. Keep one layout. Delete the others, and record their numbers.

## Verification

Task 42's gate, the full conformance ratchet, and task 24's safety controls
(stack depth, interrupts, malformed residuals) under the retained layout.
Fuzz the residual validator (task 66) before relying on unchecked access.

## Definition of done

- One dispatch layout remains, chosen by the paired gate over all eight
  fixtures, with the rejected layouts recorded.
- No handler performs a check that the validator has already proved.
- Interpreter state stays in registers across handlers in the retained
  layout, confirmed by inspecting the generated assembly.

## Performance evidence

operation, and text size of the handler set (task 77's counters), plus the
