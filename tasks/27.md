# 27: Cut over to the single VM and delete the legacy runtime

## Outcome

Atomically make the next core the sole production `quench-runtime` and delete
the legacy runtime. This closes phase A (make it work). After this task the
repository runs JavaScript and Wasm on one VM through one engine, and every
host and runner uses it without flags. Cleaning the rest of the tree is the
first phase-B task (86); no phase-B task starts before this one is done.

## Current gap

The feature-complete engine still has a temporary package/name and production hosts still target the legacy package.

Legacy removal happens at the correctness gate (task 24), not after performance
parity. This keeps a second engine from being maintained while restructuring
(phase B) and efficiency work (phase C) proceed. Task 26 then reaches parity with the
pinned v2 binary on the single core, and task 61 leads the no-JIT reference
engines. Until then, production may be slower than the legacy runtime. That
difference is recorded at cutover as measurement only, and it does not block
the cutover.

Legacy material to delete (derive the final list from the tree at cutover time):

- `crates/quench-runtime` (evaluator, heap, value model, `builtin_meta/`, and
  the legacy copies of Temporal, Intl and Date; the next core already owns
  those authorities, and task 45 finishes extracting them in phase B)
- legacy runners: `run-stages`, `run-all`, `compare-runs`, `triage` (the `-next`
  runners are renamed to the canonical names)
- `quench-node`'s legacy host bindings and any adapter that exists only to feed
  both runtimes
- legacy implementations of the `AlgorithmBoundary` trait, if any exist at
  cutover
- the legacy Wasm execution path (`crate::hir`, `wasm/emit/*`) and any other
  executor of Wasm outside the shared VM

Every other stale or migration-only artifact (tools, vendored OXC, configs,
documents, tracked reports, task diaries, dead code) is task 86's, in phase B.
This task deletes only what must go for one engine to be the production
engine.

## Scope and implementation sequence

1. Freeze the green commit (task 24), move the next implementation into
   `crates/quench-runtime`, update all workspace dependencies and production
   binaries, and remove the legacy source tree and migration-only
   compatibility adapters. Rename next development targets to canonical
   production targets and remove backend selection plumbing.
2. Update the commands in `AGENTS.md`, `docs/`, and `tasks/README.md` that
   the rename changes, so every command they name still runs.

## Verification

From a clean build directory, run workspace check/test/clippy, CLI smoke/error/exit tests, complete Test262, tracked Node compatibility, complete Wasm, residual phase tests, and a recorded (not gating) eight-fixture V8-v7 Score/RSS measurement against legacy, v2, and the no-JIT reference engines when task 62 has landed. Search for legacy crate names, reducers, value models, runtime flags, JIT/stencil/native code, `-next` names, and sibling paths. Run the task-queue coherence check.

## Definition of done

- One `quench-runtime` package and one engine implementation remain; `quench-runtime-next` no longer exists as a name.
- All hosts and runners use it by default without flags.
- No legacy semantic fallback, guest JIT, executable-memory path, or sibling build dependency remains.

## Performance evidence

Record V8-v7 Score/RSS for the last legacy production binary and the first single-core binary, with matched provenance. This is the starting point for task 26. It is not a gate.
