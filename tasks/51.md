# 51: Evaluate interpreter mechanisms beyond v2 parity

## Outcome

After v2 parity, each of the remaining interpreter-architecture limits has
either a retained mechanism that wins the paired Score/RSS gate or a recorded
negative result. The final engine stays interpreter-only.

## Current gap

Task 26 targets parity with pinned v2, and v2 itself sits in the de-JITed
engine band ([performance-reference](../docs/v2/performance-reference.md)).
The 2026-09-23 review identified structural limits that parity does not
address:

| Limit             | Current representation                                                                                                            | Candidate mechanism                                                             |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Heap reference    | `Value` holds a `u32` slot index; a field read goes slab → `Option<Cell>` → `ValueVec` → shared arena, about four dependent loads | compressed 32-bit offsets into one reserved region, with inline object slots    |
| Allocation and GC | non-moving full mark-sweep over every slot, triggered by allocation count (floor 384), with per-object `malloc` for payloads      | bump nursery with copy-out promotion; a byte-based trigger                      |
| Array storage     | `Rc<Vec<Value>>` behind the cell, two extra hops                                                                                  | elements owned inline by the cell or the property arena                         |
| Dispatch          | one `match` per instruction returning `Result<StepResult>`; re-indexes the function, code, and frame each step                    | tail-call threaded handlers with pc and register base held in machine registers |
| Activation        | a pooled `Vec` for locals and registers per frame; one Rust recursion per JS call                                                 | one contiguous VM stack with register windows                                   |
| Constants         | `programs.constant(program, idx)` returns `Option` on every access                                                                | constant-pool base cached in the frame                                          |

## Dependencies

See this task's `depends_on` in [index.json](index.json). This task is a
non-blocking side lane: task 27's cutover does not depend on it.

## Scope and implementation sequence

1. Take one limit at a time as an isolated spike. Cite the governing
   `docs/v2/` decision where one exists (addressing domains, inline-cache
   layout, provable unboxing, runtime re-specialization) and beat its
   recorded measurement.
2. Keep every mechanism general, with an exact generic fallback and the
   benchmark-integrity rules. No guest JIT, executable memory, or stencils.
3. Retain a mechanism only if it wins the task-26 paired gate on Score
   without regressing maximum RSS, or on RSS without regressing Score.
   Otherwise remove it and record the negative result in `docs/v2/`-style
   decision notes.

## Verification

Task 24's safety controls and the full conformance ratchet after every
retained change. Task 42's optimized-versus-generic gate for each new fast
path.

## Definition of done

- Each row above has a retained mechanism with its paired report, or a
  recorded negative result.
- QuickJS and V8 interpreter-only
  (`--no-sparkplug --no-maglev --no-turbofan`) reference points are re-measured on the same host.

## Performance evidence

Paired Score/RSS reports under `target/` for each spike, with raw samples and
95% intervals, as in task 26.
