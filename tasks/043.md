# 043: Stencil-local tag register optimization

- **Theme:** deegen_full_jit
- **Executor:** codex
- **Depends on:** 040, 041

## Context

Paper §5.3: avoid repeatedly materializing large 64-bit boxing-scheme
constants by pinning one register to a base value and using small-offset
accesses instead. Task 030/031 concluded this was blocked — correctly, but
only for one specific place: pinning a register **across the Rust-level
interpreter dispatch loop** has no portable mechanism in stable Rust (no
GHCcc-equivalent fixed-register ABI). That conclusion doesn't extend to
where this technique actually matters most: `build.rs`'s stencil bytes
(tasks 039/042) are already hand-encoded machine code with fully-controlled,
explicit register arguments (e.g. `aarch64_fadd_d(rd, rn, rm)`,
`x86_sse2_binary(opcode, rd, rm)`). Within one stencil's byte sequence,
which register holds what was never blocked — it was simply not attempted,
because the original task scoped itself as depending on the (irrelevant)
dispatch-loop result.

This only pays off once regions are long enough to reuse a boxing constant
more than once — today's stencils are 1-5 instructions, hence the explicit
dependency on tasks 040/041 (loop-glue sequences, property chains, call
sequences) landing first.

## Scope
- crates/quench-runtime/src/tagged_value.rs (or wherever `TAG_PREFIX`/
  `TAG_SHIFT`/`TAG_MASK` now live)
- crates/quench-runtime/build.rs (stencil byte generation — new helper to
  materialize a boxing constant once into a scratch register at region
  entry, per ISA; const-fn encoder updates for any instruction that reads
  the constant to take a register-relative offset instead of an inline
  immediate)

## Deliverables
- Identify which of the regions landed by 040/041 actually reference a
  boxing-scheme constant more than once within their instruction span —
  this is the only case where pinning pays off; do not add scratch-register
  materialization to a region that only touches the constant once
- Add one `const fn` helper per ISA (AArch64, x86_64) that emits the
  instruction(s) to load the boxing constant into a designated scratch
  register at region entry, following task 039's encoder discipline (doc
  comment citing the ISA manual, no hand-typed hex, no assembler crate)
- Update the specific instructions inside multi-reference regions to use a
  register-relative offset from that scratch register instead of their own
  inline immediate
- Choose the scratch register carefully: it must not collide with any
  register the region's other instructions (or the calling convention at the
  region's entry/exit boundary) already use for live values — document the
  register choice and why it's safe per region

## Validation

1. A differential test per modified region: identical observable output
   (all NaN-boxing tag classes: number, object, function, undefined, null,
   boolean — whatever the full tag set is) before/after the constant is
   moved to a register-relative access
2. `cargo test -p quench-runtime --lib` and `--features execution-trace` —
   both pass
3. Before/after measurement on the specific curriculum case(s) whose region
   was modified — record the delta in `docs/architecture-evidence.md`; a
   region touching the constant only 2x may show a negligible/noisy delta,
   which is an acceptable and expected outcome to report honestly, not a
   reason to force a bigger claim
4. Confirm no register collision via the region's existing CFG/soundness
   test plus a targeted unit test asserting the scratch register's value is
   never read as a live operand by any other instruction in the span

**Fail condition**: any change to the boxing scheme's bit layout or tag
semantics — this is a constant-materialization optimization only, the value
computed must be bit-identical to before. A scratch-register collision that
corrupts a live value in the same region is a correctness bug, not a
performance regression — treat it as blocking regardless of benchmark
numbers.

## Non-goals
- Pinning any register across the Rust-level interpreter dispatch loop —
  still correctly out of reach, not reattempted here
- Widening which regions exist — that's tasks 040/041's job; this task only
  optimizes constant access within regions that already exist
