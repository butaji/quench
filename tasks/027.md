# 027: Profiling counters and tier-up policy

- **Theme:** deegen_full_jit
- **Executor:** codex
- **Depends on:** (none — first task in the new backlog)

## Context

The Deegen paper's VM promotes a function through interpreter → baseline JIT
→ optimizing JIT based on call-count/loop-count thresholds (§3). Quench's
copy-and-patch tier (021-026, closed) memoizes rendered stencils by
`RegionKey` but is explicitly not hotness-triggered — nothing in the runtime
currently counts invocations or loop iterations to decide *when* to promote
anything. This task adds that missing signal. It does not yet act on it beyond
the baseline JIT tier that already exists; tier-up into the optimizing JIT
(031) depends on this counter existing first.

## Scope
- crates/quench-runtime/src/quickening.rs (existing site/counter infrastructure)
- crates/quench-runtime/src/vm/vm_runtime.rs

## Deliverables
- Per-callable and per-loop-header counters, cheap enough to run unconditionally
  (bounded saturating counters, not allocations)
- A named threshold policy (e.g. call count N promotes interpreter -> baseline
  JIT eligibility; loop-header count M marks a loop as an OSR-entry candidate
  for 028) — thresholds are data, not scattered magic numbers
- Neutral microbenchmark corpus profiled before and after; counters must not
  regress interpreter dispatch cost measurably

## Acceptance
- Neutral corpus geomean does not regress
- Counters are Proven/Guarded facts consumed by later tasks (028+), not a new
  ad hoc state machine
- No behavior change yet — this task only produces the signal, not a new
  execution path

## Non-goals
- Any actual tier transition, OSR, or new codegen (028-031)
