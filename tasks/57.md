# 57: Derive value-kind facts as static binding times

## Outcome

The binding-time analysis knows what kind of value a register or local holds
at a program point, as well as whether that value is an exact constant. Each
fact comes from source evidence and has one transfer rule. The residual uses
proved facts in place of the dynamic check they discharge. Profiles,
observations and training runs never contribute to a proof.

## Current gap

`compile/binding_time.rs` tracks one flow-insensitive fact per root binding:
`BindingTime<StaticValue>`, where `StaticValue` is `Constant | Function`. It
has no abstraction between an exact constant and `Dynamic`. It cannot express
"Number, value unknown", and branch conditions never refine a binding.
Nothing records the static evidence a JavaScript program often carries:

```js
function f(x) {
  if (typeof x === "number") return x + 1; // x : Number on this edge
}
let n = a | 0;                              // n : Int32
```

The only numeric specialization is the bytecode-derived dispatch class in
`compile/numeric.rs`. It is selected by opcode, not by a proof about the
operands, so every execution still checks operand tags.
[Provable unboxing](../docs/v2/provable-unboxing.md) already specifies the
numeric part of the lattice this task needs. It recorded that the retained
workloads have no hot region the lattice would prove. That negative result
stands until this task's audit shows otherwise.

## Futamura and Ershov alignment

This task extends the static column of the
[binding-time table](README.md#v2-design-fidelity-and-binding-time). It adds
no new mechanism.

- **P1, a more precise static division.** The generating extension computes
  more of the program's static part. It does not become a type-feedback
  engine. A fact in this lattice is static only if it holds for every input
  `d` of `⟦residual(p)⟧(d)`.
- **Ershov's one definition.** Kind transfer comes from a declared
  *result-kind* column on each kernel primitive and statically evaluable
  library row: `ToNumber → Number`, `ToInt32 → Int32`, `typeof → String`,
  `=== → Boolean`. It describes the value on normal completion. The same
  definition runs at execution time. The analysis keeps no separate table of
  operator result types.
- **Congruence.** A fact is dynamic when it depends on a dynamic value, a
  binding that guest code can reassign, or heap state after a `reenters` or
  `throws` edge. A refinement of a local survives only where nothing can
  write the binding. The binding must be uncaptured, or captured with no
  writes, which is the rule `invalidate_captured` applies today.
- **Offline, not online.** The division is computed once per program, before
  execution. Runtime re-specialization stays a separate mechanism
  ([runtime re-specialization](../docs/v2/runtime-respecialization.md)).
- **P2/P3 in practice.** Transfer and refinement rules are rows that the task
  47 macros generate from the tables, next to fold eligibility and
  guard/fallback pairs. There is no hand-written matcher per expression shape.

## Lattice

There is one domain. `BindingTime<T>` stays the outer lattice. `StaticValue`
gains abstract members, ordered from most to least precise:

```text
Unknown (no reaching definition)
  ⊑ Constant(c) | Function(f)
  ⊑ Int32 ⊑ Number
  | fixed primitive kind (String, Boolean, Undefined, Null, BigInt, Symbol)
  | Object (non-nullish, not callable known)
  ⊑ Dynamic
```

The numeric chain and its widening rules are the ones in
[provable unboxing](../docs/v2/provable-unboxing.md): integer `+` and `*`
stay `Int32` only with a range proof, JavaScript `+` is numeric only when both
inputs are proved numeric, and loop headers join to a fixed point. The unions
this task needs are `Nullish`, `Primitive` and `NotNullish`. Represent them
as a kind bitset if a join needs them. Do not add a general union type. The
analysis becomes flow-sensitive: facts belong to program points, and each
conditional branch edge can carry a refinement.

## Evidence classification

Each source of evidence belongs to one binding-time class. Several common
"static type" claims about JavaScript do not hold for every input, so they
are dynamic here.

| Evidence | Class | Rule |
| --- | --- | --- |
| Literal `42`, `"x"`, `true`, `null`, `1n` | Static | exact `Constant` (exists today) |
| `const` or single-assignment uncaptured binding | Static | the kind of its one definition |
| `x \| 0`, `~x`, `x >> k` | Static | `Int32` on normal completion; `ToPrimitive` may reenter, which ends heap facts |
| `x >>> 0` | Static | `Number` (Uint32 range) |
| Unary `+x`, `x - y`, `x * y`, `x / y` | Static | `Number` if the operands are proved non-BigInt, otherwise `Number \| BigInt` |
| `typeof x`, `!x`, relational and equality operators, `in`, `instanceof` results | Static | the result kind (`String` or `Boolean`) |
| `typeof x === "number"` on a local | Static | refines `x` on the true edge (and excludes it on the false edge) while the congruence rule holds |
| `x === literal`, `x !== null`, `x != null` | Static | refines to the literal's kind, or to `NotNullish` |
| A successful `#x in o` or private access | Static | refines `o` to `Object` carrying brand `#x`; objects never lose private brands |
| Template literals, string concatenation where one operand is proved `String` | Static | `String` |
| Object, array, class and function literals | Static | `Object` or `Function(f)` for that allocation; shape facts stay dynamic |
| Intrinsic identity (`Math.sin`, `Float64Array`, `Array.prototype[@@iterator]`) | Dynamic | global bindings and intrinsic properties can be replaced; the result kind is known only behind a guarded `CallKnown` on the intrinsic |
| `new Foo()` result shape | Dynamic | `Foo` can return an object or change `prototype`; shapes belong to task 29 |
| `x instanceof C` refinement | Dynamic | `@@hasInstance` and prototype mutation make it unsound as a class fact |
| `"k" in o`, property existence, shape and monomorphism | Dynamic | proxies, deletion and accessors; handled by task 29's guarded caches |
| Typed-array element kind | Dynamic, with a static layer | the receiver kind needs a guard; once the guard passes, the element representation comes from the task 35 kind row |
| Profiles, counters, observed operand tags | Dynamic | never a static fact (task 30, README) |

## Scope and implementation sequence

1. Audit first. For each current consumer (numeric dispatch class, `typeof`
   lowering, TDZ checks from task 49's slot kinds, nullish checks in optional
   chaining, `ToPropertyKey` on computed keys), count the dynamic checks a
   kind proof would discharge on Test262, Node compatibility and V8-v7
   residuals. Record the counts in this file. Extend the unboxing audit table
   with the new numbers.
2. Add a result-kind column and a refinement column to the task 46 tables
   for kernel primitives and statically evaluable library rows. Leave the
   columns empty on rows that can observe guest-mutable state.
3. Extend `StaticValue` and `BindingTime::join` into the lattice above and
   make `binding_time::apply` flow-sensitive over the existing control-flow
   and liveness passes. Extend it to every function, not only the root, where
   capture analysis proves congruence. Keep one pass and one fact vector per
   program point.
4. Have task 47's macros generate transfer and refinement rules from the new
   columns. Remove any hand-written kind switch the audit found.
5. Add consumers only where step 1 counted a discharged check. Each consumer
   is a guard-free choice of an accelerated primitive under a `StaticValue`
   proof, with its reference definition as the fallback. Examples: fold
   `typeof`, select the numeric opcode from the proof, drop `ToNumeric` from
   proved-numeric `+`, and elide proved-unneeded TDZ or nullish checks.
6. Unboxed registers remain out of scope. Reopen them under
   [provable unboxing](../docs/v2/provable-unboxing.md) only when the audit
   finds a hot region whose inputs are all proved.

## Verification

- Task 47's Futamura check: the default kernel with kind folding matches the
  reference kernel without it, on the full Test262 run and the frozen Node set.
- Task 42's disable-specialization gate at every consumer.
- Differential cases from existing Test262 families exercise invalidation
  paths: `valueOf` reentry between a refinement and its use, a closure
  writing a refined binding, direct `eval` in scope, `with`, BigInt operands
  where `Number` was expected, and exception edges out of refined regions.

## Definition of done

- One lattice, `BindingTime<StaticValue>`, holds exact-constant, kind and
  refinement facts. It agrees with the provable-unboxing lattice.
- Every transfer and refinement rule comes from a table column. The analysis
  has no second copy of operator semantics.
- No fact in the lattice depends on observed values.
- Each retained consumer has an audit count and passes the task 42 and task
  47 gates.
