## Outcome

Every reference to a module binding, a script-level lexical binding, or a
global is classified as static, dependency-guarded, or dynamic before
execution. Static references compile to direct slots or constants.
Dependency-guarded references read a global property cell or a protector
instead of doing a global-object lookup.

## Current gap

Task 49 removes the name-based checks on function 0's immutable global
lexical bindings. Nothing else uses the static structure of modules and
globals:

- Module imports are resolved at link time, but reads still go through the
  namespace or binding lookup.
- `undefined`, `NaN`, and `Infinity` are non-writable and non-configurable
  properties of the global object. Reads of them are static in every scope
  that does not shadow them.
- Reads of replaceable globals such as `Math` and `Array`, and calls to
  intrinsic methods, pay a full lookup each time.

## Scope and implementation sequence

1. Classify each unresolved reference with the binding-time analysis's scope and closed-scope
   domains: module binding, script lexical binding, frozen global property,
   ordinary global property, or dynamic (open scope or `with`).
2. Module bindings: compile an import to a direct reference to the exporting
   module's binding slot, keeping live-binding semantics and the TDZ check. A
   `const` export whose initializer is statically constant folds after its
   TDZ point.
3. Frozen global properties: fold reads to their constant value where the
   binding is not shadowed.
4. Ordinary global properties: give each global data property a property cell
   owned by the global object. Its protector (an explicit validity guard) trips on
   write, reconfiguration, or deletion. A read site guards the cell, and on a trip it falls back to the
   generic global lookup. Intrinsic identity for `CallKnown` uses the same
   cell mechanism.
5. Script lexical bindings shared across scripts remain slots in the global
   declarative record, addressed by index.
