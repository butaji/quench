# 010: Inspector/debugger protocol + module compile-cache

- **Theme:** surface_gaps
- **Executor:** codex
- **Depends on:** (none)

## Context

Filename-prefix frequency (same reliability caveat as tasks 008/009):
`compile-cache` (19 hits), `debugger`/`cli-node` (3+6 hits). `inspector.rs`
exists. `compile-cache` refers to Node's `module.enableCompileCache()` /
`NODE_COMPILE_CACHE` V8 bytecode-cache-on-disk feature — for a Rust-native
engine (no V8 bytecode format) this may legitimately be a documented
non-goal rather than a real implementation gap; the task's first job is to
determine which.

## Scope
- `crates/quench-node/src/modules/inspector.rs`
- Whatever module implements (or should implement) `module.enableCompileCache`

## Deliverables
- `cargo run -q -p quench-node-test --bin run-parallel -- --all --filter compile-cache --timeout-secs 10 --results /tmp/task010-cc-baseline.json` — read a few of the actual fixtures first. If they only check that the API exists and doesn't throw (common for a no-op-on-this-engine feature), implement a spec-compliant no-op (function exists, returns the documented shape, doesn't error) rather than a real bytecode cache. If they assert actual cache-hit behavior that's observable from JS, implement that for real.
- `cargo run -q -p quench-node-test --bin run-parallel -- --all --filter debugger --timeout-secs 10 --results /tmp/task010-dbg-baseline.json` and `--filter cli-node`

## Validation

1. Baselines from Deliverables, recorded in this file along with which compile-cache behavior (no-op vs real) was chosen and why
2. Re-run both filters — after-counts strictly lower than baseline
3. `cargo test -p quench-node --lib` — no regressions

**Fail condition:** step 2 not improved, or a regression in step 3.

## Non-goals
- A real V8-bytecode-format on-disk cache — quench-node's Rust engine has
  no equivalent bytecode representation to serialize in that format; match
  the observable Node.js API contract, not the V8 implementation detail
