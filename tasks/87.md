# 87: Derive frame slot representation from static types

## Plan scope

Deferred outside the active two-stage plan. Stage B measures only V8-v7, and no
Wasm-speed requirement blocks either stage. Bring in a concrete part only for a
correctness need, a measured V8-v7 gap (step 5), or a later Wasm performance
goal. This task changes no conformance obligation.

## Outcome

JavaScript and Wasm keep one heap, root set, call ABI, opcode vocabulary and
dispatch loop. How a frame slot stores its value becomes a derived fact: the
validator's type for Wasm, or a proven specializer fact for JavaScript. Statically
typed 64-bit and 128-bit scalars no longer allocate heap cells.

## Current gap

`Value` is a NaN-boxed `u64` (`value.rs`). 32-bit Wasm scalars use immediate
slots, but every i64/f64 result allocates `Cell::WasmBits64` and every V128
result allocates `Cell::WasmV128` (`Vm::encode_wasm_value`, `vm/wasm.rs`).
Operands decode through a heap lookup (`wasm_i64_operand`, `wasm_f64_operand`).
Numeric Wasm therefore pays about one allocation per 64-bit instruction, plus GC
pressure. The validator already proves each slot's type, so this boxing guards
nothing. JavaScript doubles stay immediate, but each arithmetic operation still
re-checks tags that the specializer may already have proven.

## Dependencies

See this task's `depends_on` in [index.json](index.json). Task 40 fixes the
JS⇄Wasm adapter contract. That contract must keep scalar transport behind the
shared encode/decode operations so this task stays local to frames.

## Scope and implementation sequence

1. Measure first: allocations per iteration, GC share and dispatch cost for an
   i64/f64-heavy Wasm loop and a V128 loop. Record the boxed baseline.
2. Derive a slot class for each register from static facts: `Value`
   (tagged), `Raw64` and `Raw128`. Wasm locals and temporaries take the class
   their validated type implies. Reference-typed slots remain `Value`.
3. Derive GC root maps from slot classes, so only `Value` slots are traced.
   Raw slots need no roots and no cells.
4. Keep `Value` as the only boxed form at dynamic boundaries: host APIs,
   JS⇄Wasm adapters, globals, tables, exceptions and multi-result transport.
   They convert through one shared scalar encode/decode operation (`ScalarBits`).
5. Optionally extend the same classes to JavaScript slots where the
   specializer proves an int32 or number type, with a guarded exact fallback
   to `Value`. Admit this only with paired V8-v7 Score/RSS evidence.
6. Remove `Cell::WasmBits64`/`Cell::WasmV128` from frame-local traffic once
   no execution path produces them there. Keep them only where a boxed form is
   semantically required.

## Constraint note

The constraint "one Value representation" in [index.json](index.json) must
treat slot classes as storage projections of the same typed values, not a
second value model. If that reading is not accepted, amend the constraint
explicitly before implementation.

## Verification

Affected pinned Wasm scopes (i64, f64, conversions, SIMD, wide arithmetic,
exceptions, multi-results, globals) plus compare-runs, with no inventory change.
GC stress across calls that mix raw and tagged slots. Exact NaN payloads and
signed zero across the host and JS boundaries. For step 5, affected Test262
stages and the generic-path check of task 42.

## Definition of done

- Statically typed Wasm 64/128-bit scalars allocate no heap cells in frames.
- Slot class and root maps are derived from types, with no stored copy.
- One dispatch loop and executor. Boundaries use one scalar encode/decode
  authority.

## Performance evidence

Before/after allocation counts and time for the step 1 loops. Paired V8-v7
Score/RSS for any change touching JavaScript slots or shared dispatch size.
