# 045: Shared global megamorphic property/call cache (V8-style stub cache)

- **Theme:** deegen_full_jit
- **Executor:** codex
- **Depends on:** 041

## Context

External research check (2026-09): V8's actual answer to a megamorphic call
or property site isn't "give up and take the complete slow path forever" —
it's a **shared global cache keyed by `(shape/map, name, operation-kind) →
handler`**, populated across every call site in the program, not just one.
A site that individually exceeds its local IC bound still gets an amortized
O(1) lookup through this shared cache instead of repeating full property/
call resolution every time. Quench's `IcStubChain` (task 033) is per-site
only — once a site's bounded chain is exhausted, it falls back to the
complete ordinary path with no memory of what it already resolved, even if
another site (or the same site later) sees the exact same shape/name pair
again.

This is squarely non-speculative, build-time-provable-fallback work — no
deopt, no runtime type guessing — so it fits this project's standing
discipline exactly. It's queued as its own task rather than folded into
task 033 or the `IcStubChain` because it's a genuinely different
mechanism (global, cross-site memoization) from a per-site bounded chain.

## Scope
- crates/quench-runtime/src/quickening.rs (per-site IC state, degrade path)
- crates/quench-runtime/src/stencil_lifecycle.rs (`IcStubChain` — the
  fallback-on-exhaustion path is where this cache gets consulted)
- New: a global cache module (name/location TBD during implementation,
  likely a `HashMap`-backed structure keyed by `(ShapeId/CallableId, Name,
  OperationKind)`)

## Deliverables
- Profile first: on the neutral corpus and `quench-bench/deegen-curriculum`
  (especially case 014, the 400-distinct-shapes megamorphic case), measure
  how often a site degrading past its bounded chain later re-encounters a
  `(shape, name)` pair another site (or itself) already resolved. If this
  is rare in practice, the cache has no payoff — record that finding and
  stop, per this project's standing profile-before-implement discipline;
  do not build a cache with no measured hit rate.
- If justified: a single shared cache, populated on any site's *first*
  resolution of a given `(shape/callable, name, kind)` key (not only on
  chain exhaustion — populate it eagerly so even a monomorphic site's
  resolution benefits a later megamorphic site), consulted by any site once
  its own local bound is exhausted, before falling back to full resolution
- Bounded cache size (this project doesn't build unbounded caches) with a
  clear, documented eviction policy
- Complete fallback semantics unchanged: cache miss or any inconsistency
  routes to the exact same full-resolution path that exists today

## Validation

1. The profiling step above, recorded in `docs/architecture-evidence.md`
   with the actual measured re-encounter rate — a go/no-go decision, not a
   given
2. If proceeding: differential tests confirming identical observable output
   with the cache populated vs. disabled, for both a hit and a miss
3. `cargo test -p quench-runtime --lib` and `--features execution-trace` —
   both pass
4. Before/after measurement on curriculum case 014 (megamorphic property)
   and any megamorphic call-site case — record the delta
5. Cache size bound respected under an adversarial synthetic workload that
   tries to grow it unboundedly (many distinct shape/name pairs)

**Fail condition**: building the cache without step 1's measured
re-encounter rate, or an unbounded cache, blocks this task regardless of
benchmark numbers.

## Non-goals
- Any speculative optimization or deoptimization — this is a memoization
  structure, not a type-guessing mechanism
- Changing the per-site `IcStubChain`'s own bound or degrade policy (033) —
  this task adds a fallback layer beyond it, not a replacement
